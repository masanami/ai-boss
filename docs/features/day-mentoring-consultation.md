> **正はコードとテスト**であり、本ファイルは権威を持たない（`CLAUDE.md`「開発方針」）。実装と食い違う場合はコードが正。

## 概要

チャット画面ヘッダの「進め方を点検してもらう」（#411 / 親 #276 判断 6）で始めた**全日単位の随時メンタリング**を、タスク起点のメンタリング（#476 / S1b）と同じく web 側の「相談中」状態として保持し、継続中は入力欄からの 2 ターン目以降にも `mentoring: true` を送る。これにより `MENTORING_FLOW_INSTRUCTION`（「点検の結論を `record_mentoring` で 1 件以上記録すること」を含む）が、相談が続くあいだシステムプロンプトに積まれ続ける。**サーバ・DB・プロンプト文言は変更しない。**

## 背景・目的

### 何が欠けているか

ヘッダの導線は `mentoring: true` を**押したターンの 1 回だけ**送る。2 ターン目以降は入力欄からの通常送信（`options` 無し）になり、サーバ側の `mentoring` が偽になって点検の指示ごとプロンプトから消える。ボスが数往復してから結論に至る——メンタリングとしてはむしろ自然な——流れで、「記録せよ」という指示を受けていないまま対話が進む。

タスク起点側の同じ欠落は S1b（`4106645` / PR #498）で塞がれたが、S1b を小さく保つため全日単位側は意図的に範囲外とされた（`task-scoped-mentoring.md` 確証 (G)・「やらないこと」）。Issue #491 本文は「S1b の実装形が確定してから対応の方向を判断する」としており、その条件が満たされた。

## ユーザーストーリー

セルフマネジメント中のオーナーとして、チャット画面から今日の進め方の点検を頼み、数往復のやり取りのあとに出た結論も確実に記録してほしい。いま相談中であることが画面で分かり、終えたいときに自分で終えられるようにしたい。

## 機能要件

- [ ] ヘッダの「進め方を点検してもらう」を押すと、全日単位の相談中であることがチャット画面に**見える形**で表示される
- [ ] 全日単位の相談中のあいだは、入力欄から送った 2 ターン目以降の発言でもボスのシステムプロンプトにメンタリングの手順指示が積まれ続ける
- [ ] 全日単位の相談中の発言は、どのタスクにも紐づけて送られない
- [ ] 全日単位の相談中とタスク起点の相談中は同時に成立せず、後から始めたほうに置き換わる
- [ ] 全日単位の相談中は、利用者の明示操作・会の開始・会の終了のいずれでも解除できる
- [ ] 解除したあとの発言はメンタリングとして送られない

## クリティカル設計決定

> 意思決定者が 2026-09-13 に決定した方針であり、実装はこの決定に従う。

### 1. 状態の持ち方

- **採用案**: S1b の「相談中」状態を判別共用体へ一般化する（形の例: `{ kind: "task"; id; title } | { kind: "day" } | null`）。`useChat.send` の自動付加（`use-chat.ts:412-418`）を `kind` で分け、`task` は従来どおり `{ mentoring: true, mentoringTaskId }`、`day` は `{ mentoring: true }` を付加する。呼び出し側が `options` を明示した場合は従来どおりそのまま使い、相談中の文脈をマージしない
- **全日単位の開始は `useChat` 側の関数に置き、ヘッダはそれを呼ぶだけにする**（確証 (G)）。その関数は `startMentoring` と同じ規律に従う: `sendingRef` / `switchingRef` のガードで破棄される呼び出しでは**状態を設定せず送信もしない**。送信を試みて失敗した場合（セッション生成・ネットワーク）は**状態を残す**（`use-chat.ts:72-82` の `startMentoring` doc コメントと同じ）
- **理由**: 置き換え（排他）が「状態が 1 つ」であることから構造的に成り立ち、両方が立つ不正な状態を型で表現できない。付加は「すべての送信経路が通る 1 箇所」（S1b 決定 10 の構造上の理由）に残る。解除 3 箇所（`use-chat.ts:577` / `:762` / `:799`）は `null` 代入のままでよい
- **代替案**: (B) 全日単位専用の別フラグ（例: `dayMentoringActive: boolean`）を足し排他を手書きする — 却下（排他を開始 2 箇所・解除 3 箇所で手書きし、両方が真の状態が表現可能になる）。(C) 状態を持たず、一度ヘッダを押したら以後の `adhoc` 区間の全ターンで `mentoring: true` を送る — 却下（解除の概念が無くなり、確証 (E)(F) の害が常時化する）
- **明示的な仮定**: 型名・関数名は実装に任せる（受入基準は名前に依存しない）
- **影響範囲**: `use-chat.ts`（状態の型・自動付加・全日単位の開始関数）・`ChatView.tsx`（ヘッダの呼び出し先・帯の文面の出し分け）とテスト

### 2. 解除条件・置き換え・表示

- **採用案**: S1b 決定 11 と同じ 4 条件で解除・置き換えする。表示は S1b と同じ帯・同じ `相談を終える`、文面は `今日の進め方について相談中`
  1. 利用者の明示解除操作（`相談を終える`）
  2. 別のメンタリングの開始 — **タスク起点の相談中にヘッダを押すと全日単位の相談中へ置き換え**、**全日単位の相談中にタスクカードから開始するとタスク起点の相談中へ置き換え**
  3. 会（朝会・夕会）の開始（開始に失敗して `adhoc` に留まった場合は保持。S1b と同じ）
  4. 会の終了
- **出荷済み S1b の意味の変更（承認済み）**: S1b 決定 11 の 2 のうち「ヘッダ押下は対象タスク無しの状態へ解除」を「**全日単位の相談中へ置き換え**」に変える。上書きする受入基準と書き換える既存テストは「### S1b から上書きする受入基準と、意図して書き換える既存テスト」節に列挙した
- **理由**: 変更の向きは「タスク起点の相談中が全日単位の相談中に置き換わる」であり、S1b 決定 11 が防ごうとした害（古い対象タスクが全日単位の結論へ持ち越される）は、置き換え後の送信に `mentoringTaskId` が載らない限り同じく防がれる。したがって**置き換え後の全日単位の送信に `mentoringTaskId` が紛れ込まないこと**を受入基準（除外側）に必ず置く。解除条件と表示を S1b に揃えるのは、利用者から見て 2 つの導線の振る舞いが揃うため。文面は S1b の `「{タイトル}」について相談中` と対になり、`MENTORING_FLOW_INSTRUCTION` の「今日の仕事の進め方」と一致する
- **代替案**: 全日単位だけ別の解除条件・別の表示にする — 却下（2 導線の振る舞いが揃わない）。文面 `進め方を点検中` / `今日全体の進め方について相談中` — 不採用
- **影響範囲**: `use-chat.ts`・`ChatView.tsx` とテスト

### 3. 仕様の置き場

- **採用案**: 本ファイル（新規）に置く。`task-scoped-mentoring.md` への変更は、決定 11 と「やらないこと」の #491 の行へ本ファイルへの参照を 1 行ずつ足すことに限る（あわせて、同ファイルのスライス表の状態を「S1a・S1b 出荷済み」へ直す最小修正のみ行う）
- **理由**: 出荷済み S1b の決定・受入基準をその場で書き換えると、S1b が何を満たして出荷されたかの記録が失われる。書き換えずに同じファイルへ追補しても矛盾する記述が 2 箇所残る点は変わらない。主題を「全日単位の相談中の保持」に閉じれば、`/create-ticket` へ渡す対象スライスがファイル全体と一致する。先例として #477 は当初「同じ仕様ファイルの別の節で扱う」とされた（`task-scoped-mentoring.md:354`）が、実際には新規ファイル `chat-route-error-response-shape.md` で要件化された（`f8d6444`）
- **代替案**: (a) `task-scoped-mentoring.md` にスライス S1c として追補 — 却下（上記）。(b) `work-approach-mentoring.md` を改訂 — 却下（スライス表の後付けが要り、保持機構の根拠〔S1b 決定 10〜12〕は別ファイルにあるため結局ファイル間参照になる）

### 4. 解除忘れによる不要な記録への対応（残差）

- **採用案**: 本スライスは **R1**（明示解除＋画面表示のみ。`record_mentoring` の実行を観測しない）
- **理由**: 確証 (E) により、全日単位の解除忘れの害（決定ログの「タスクに紐づかない決定」へのノイズ）は、S1b が既に受容したタスク起点のそれ（無関係な記録の対象タスクへの紐づけ）より小さい
- **代替案**:
  - **R2**（`record_mentoring` の成功を観測して相談中の表示を変える／解除を促す。送る内容は変えない）— 本スライスでは採らず、後続スライス S2 の候補としてスライス表に置く（要件化しない）。確証 (D) により `onTool` で実現可能だが、ライブのみ・停止と競合したツール実行は観測できない・通知文面の区別も要る。両導線に同時に入れる UI である
  - **R3**（記録を観測したら自動解除）— 却下。S1b 決定 11 が「結論記録まで」を却下した理由は、タスク起点では「2 件目以降が対象タスクへ紐づかない」だった。全日単位では紐づけは無いが、**解除後のターンから点検の指示が消える＝ #491 の欠落そのものが 1 件目の記録後に再発する**（ユーザーが結論に異議を唱え、ボスが結論を改めても記録を求められない）
  - **R4**（プロンプト文言で重複・不要な記録を抑える）— オーナーの決定事項のため本仕様では決めない（下記「未決の論点」）

## 未決の論点（人間の決定待ち）

> **R4: 毎ターン積まれるメンタリングの指示による重複記録・不要な記録を、プロンプト文言で抑えるか。**
> プロンプト文言・指示の強度はオーナーの決定事項であり、**本仕様では決定しない。本スライス S1 の受入基準はこの論点に依存しない**（S1 はプロンプトを変えず、送信ボディと画面表示だけを基準にする）。

判断材料（実コード）:

- `MENTORING_FLOW_INSTRUCTION`（`persona-prompt.ts:569-577`）は「点検の結論を `record_mentoring` ツールで 1 件以上記録すること」（`:576`）とだけ書き、同じ会話で既に記録したかをボスに伝える経路は無い（確証 (F)）
- 同じ性質は出荷済み S1b（タスク起点・毎ターン `mentoring: true`）にも既にある。本スライスで新たに生じる論点ではなく、両導線に共通する
- 全日単位の記録は `task_id` が補完されず、日報・作業ログ・直近の決定・朝会ゲートに入らないため、害は決定ログのノイズに限られる（確証 (E)）
- LLM が実際に重複して記録するかは自動テストで固定できない（`work-approach-mentoring.md` 「技術的な制約・方針」）

選択肢:

- **(1) 変えない（現状維持）** — 実運用で重複・不要な記録が問題になるかを見てから判断する。コード変更ゼロ
- **(2) 指示に「この会話で既に記録した結論は、結論が変わらない限り再記録しない」旨を足す** — 重複は減りうるが、結論を改めたときの再記録を抑制しすぎないかは LLM 依存で検証できない
- **(3) 指示に「進め方の申告・点検と無関係な発言には記録しない」旨を足す** — 解除忘れ時の不要な記録を減らしうる。手順 1「申告を受けたら」（`:570`）で既に条件づけられているため、効果の上積みは不確か

提示されている推奨は無い（オーナーの決定事項）。
