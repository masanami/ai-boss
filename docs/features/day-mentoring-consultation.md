## 概要

チャット画面ヘッダの「進め方を点検してもらう」（#411 / 親 #276 判断 6）で始めた**全日単位の随時メンタリング**を、タスク起点のメンタリング（#476 / S1b）と同じく web 側の「相談中」状態として保持し、継続中は入力欄からの 2 ターン目以降にも `mentoring: true` を送る。これにより `MENTORING_FLOW_INSTRUCTION`（「点検の結論を `record_mentoring` で 1 件以上記録すること」を含む）が、相談が続くあいだシステムプロンプトに積まれ続ける。**サーバは変更しない。**

## 背景・目的

### 何が欠けているか

ヘッダの導線は `mentoring: true` を**押したターンの 1 回だけ**送る。2 ターン目以降は入力欄からの通常送信（`options` 無し）になり、サーバ側の `mentoring` が偽になって点検の指示ごとプロンプトから消える。ボスが数往復してから結論に至る——メンタリングとしてはむしろ自然な——流れで、「記録せよ」という指示を受けていないまま対話が進む。

タスク起点側の同じ欠落は S1b（`4106645` / PR #498）で塞がれたが、S1b を小さく保つため全日単位側は意図的に範囲外とされた（`task-scoped-mentoring.md` 確証 (G)・「やらないこと」）。Issue #491 本文は「S1b の実装形が確定してから対応の方向を判断する」としており、その条件が満たされた。

## ユーザーストーリー

セルフマネジメント中のオーナーとして、チャット画面から今日の進め方の点検を頼み、数往復のやり取りのあとに出た結論も確実に記録してほしい。いま相談中であることが画面で分かり、終えたいときに自分で終えられるようにしたい。

## 機能要件

> 推奨案（判断 1 (A)・判断 2 推奨）を仮に採った場合の草案。

- [ ] ヘッダの「進め方を点検してもらう」を押すと、全日単位の相談中であることがチャット画面に**見える形**で表示される
- [ ] 全日単位の相談中のあいだは、入力欄から送った 2 ターン目以降の発言でもボスのシステムプロンプトにメンタリングの手順指示が積まれ続ける
- [ ] 全日単位の相談中の発言は、どのタスクにも紐づけて送られない
- [ ] 全日単位の相談中とタスク起点の相談中は同時に成立せず、後から始めたほうに置き換わる
- [ ] 全日単位の相談中は、利用者の明示操作・会の開始・会の終了のいずれでも解除できる
- [ ] 解除したあとの発言はメンタリングとして送られない

## 技術的な制約・方針

- **変更対象（web のみ）**: `web/src/use-chat.ts` / `web/src/ChatView.tsx` とそれぞれのテスト、および (A) の期待値が変わる `web/src/AppLayout.test.tsx`。`AppLayout.tsx` は変更不要の見込み（タスク起点の起動は `chatState.startMentoring` のまま）
- **サーバは 1 行も変えない・マイグレーションもしない**（最大 version は 8 のまま。`migrate.ts:307`）。`chat-api.ts` も変更不要（`options` を body へ載せる形が既にある。`chat-api.ts:195-209`）
- **プロンプトの文言（`MENTORING_FLOW_INSTRUCTION` / `MENTORING_TARGET_TASK_INSTRUCTION`）は変えない**。ボスの人格・トーン・指示の強度はオーナーの決定事項である
- **朝会ゲート（`mentoring-gate.ts`）・判断 7（タスク起点のメンタリングが朝会ゲートを満たすか）には触れない**
- ヘッダボタンの表示条件（`adhoc` のみ）と送る定型文（`今の進め方を見てほしい`）は変えない
- 本件は日付境界に触らないため `npm run test:tz` は必須ゲートではない。時刻を固定する場合は `new Date(y, m, d, h)` 由来で導出する（ADR 0007 決定 5）
- **jsdom は HTML フォームの暗黙送信（input で Enter → submit）を実装しない**。入力欄からの送信は「送信」ボタンのクリック（`AppLayout.test.tsx:1215-1223` の `sendFromInput` と同じ形）か `send` の直接呼び出しで検証する

## 未決の論点（意思決定者の回答待ち）

> 以下は `/define-feature` のクリティカル設計に相当するが、**本ドラフトでは決定していない**。回答を得て「クリティカル設計決定」節へ書き直す。

### 判断 1: 状態の持ち方

- **(A) S1b の状態を判別共用体へ一般化する**（例: `{ kind: "task"; id; title } | { kind: "day" } | null`）。`send` の自動付加（`use-chat.ts:412-418`）を `kind` で分け、`task` は従来どおり `{ mentoring: true, mentoringTaskId }`、`day` は `{ mentoring: true }`。全日単位の開始は `startMentoring` と同じガードを持つ `useChat` の関数へ移す（確証 (G)）
  - 利点: 置き換え（排他）が「状態が 1 つ」であることから構造的に成り立ち、両方が立つ不正な状態を型で表現できない。付加は「すべての送信経路が通る 1 箇所」（S1b 決定 10 の構造上の理由）に残る。解除 3 箇所（`:577` / `:762` / `:799`）は `null` 代入のままで変更不要
  - 欠点: 公開型 `mentoringTarget` の形が変わり、S1b のテスト（`makeChatState` に渡す `mentoringTarget: { id, title }` や `result.current.mentoringTarget` の期待値）の書き換えが広がる
- **(B) 全日単位専用の別状態（例: `dayMentoringActive: boolean`）を足し、`mentoringTarget` と排他にする**
  - 利点: S1b の型・テストに触らない
  - 欠点: 排他を `startMentoring`・全日単位の開始の 2 箇所で手書きし、解除 3 箇所でも 2 状態を落とす必要がある。両方が真の状態が表現可能で、表示の優先規則も要る。変異の余地（片方だけ落とし忘れる）が増える
- **(C) 状態を持たず、一度ヘッダを押したら以後の `adhoc` 区間の全ターンで `mentoring: true` を送る** — 解除の概念が無くなり、雑談にも毎ターン点検指示が積まれる（確証 (E)(F) の害が常時化）。推奨しない
- **推奨: (A)**。根拠は上記利点。型名・関数名は受入基準に依存しないため実装裁量とする

### 判断 2: 解除条件・置き換え・表示

- **解除条件**: S1b 決定 11 と同じ 4 条件（明示解除・別メンタリングの開始・会の開始・会の終了）に揃えるか
  - 推奨: **揃える**。ただし「別メンタリングの開始」の意味が変わる——**ヘッダ押下は「対象タスク無しの状態へ解除」（S1b 決定 11 の 2）から「全日単位の相談中へ置き換え」へ**、**全日単位の相談中にタスクカードを押すと「タスク起点の相談中へ置き換え」**になる。これは出荷済み S1b の決定と受入基準の意味の変更であり（確証 (A)）、既存テスト `AppLayout.test.tsx:1514` の期待値が `{ content: "続き" }` → `{ content: "続き", mentoring: true }` に変わる
  - 会の開始に失敗して `adhoc` に留まる場合は保持する（S1b と同じ。`use-chat.ts:756-762`・テスト `use-chat.test.ts:3213`）
- **表示**: 同じ帯・同じ解除ボタンに出すか。文面をどうするか
  - 文面の候補: (i) `今日の進め方について相談中`（S1b の `「{タイトル}」について相談中` と対になり、`MENTORING_FLOW_INSTRUCTION` の「今日の仕事の進め方」と一致）／(ii) `進め方を点検中`（ボタン名「進め方を点検してもらう」と対応）／(iii) `今日全体の進め方について相談中`
  - 推奨: **同じ帯・同じ `相談を終える`・文面 (i)**
- **残差（不要な記録）への対応**: 下記 4 案。推奨は **(R1) を本スライスに、(R2) を後続スライス候補に**
  - **(R1) S1b と同じく明示解除＋可視表示のみ（記録を観測しない）** — 確証 (E) により、全日単位の解除忘れの害は S1b が既に受容したタスク起点のそれより小さい
  - **(R2) `record_mentoring` の成功を観測したら表示を変える／解除を促す（送る内容は変えない）** — 確証 (D) により `onTool` で実現可能。ただしライブのみ（リロードで消える＝決定 12 と同じく状態ごと失われるので整合はする）・停止と競合したツール実行は観測できない・通知文面の区別も要る。**送信内容を変えないので S1b 決定 11 の却下理由と矛盾しない**。両導線に同時に入れるべき UI なので、全日単位だけに先に入れない
  - **(R3) 記録を観測したら自動解除する** — 推奨しない。S1b 決定 11 が「結論記録まで」を却下した理由は、タスク起点では「2 件目以降が対象タスクへ紐づかない」だった。全日単位では紐づけは無いが、**解除後のターンから点検の指示が消える＝ #491 の欠落そのものが 1 件目の記録後に再発する**（ユーザーが結論に異議を唱え、ボスが結論を改めても記録を求められない）。理由の形は違うが結論は同じになる
  - **(R4) プロンプト文言で重複・不要な記録を抑える**（例:「この会話で既に記録した結論は再記録しない」）— プロンプト文言はオーナーの決定事項のため、本件では決めない。確証 (F) は S1b にも同じくあるため、両導線共通の論点として人間へ上げる

### 判断 3: 仕様の置き場

- **(a) `task-scoped-mentoring.md` にスライス（S1c）として追補し、決定 10〜12 を一般化する**
  - 利点: 保持機構の決定（10〜12）と同じファイルにある

## 受入基準

> 推奨案（判断 1 (A)・判断 2 推奨〔4 条件・同じ帯・文面 (i)・R1〕）を仮に採った草案。**リクエストボディに関する基準は `fetch` 境界で実際に送られた body で検証する**（S1b と同じ理由: #491 の欠陥は呼び出し側の渡し忘れであり、`send` の引数側で見る基準は欠陥を再現しても緑のままになりうる）。**包含側と除外側の両方を基準にする。**

### 全日単位の相談中の開始と可視化

- [ ] `adhoc` 区間でヘッダの「進め方を点検してもらう」を押すと、チャット画面に全日単位の相談中の状態表示が現れる
- [ ] その状態表示の文面は `今日の進め方について相談中` である
- [ ] その状態表示には解除の導線（`相談を終える` ボタン）が含まれる
- [ ] 全日単位の相談中の状態表示は、会話履歴（タイムライン）の中ではなくセッションヘッダ側の帯に描画される
- [ ] 送信中または切替中に全日単位の相談中の開始が呼ばれても、状態は設定されず送信も行われない（破棄された送信が相談中の表示だけを残さない）

### 継続中の送信内容（包含側）

- [ ] ヘッダ押下のターンのリクエストボディは `{ content: "今の進め方を見てほしい", mentoring: true }` と完全一致する
- [ ] 全日単位の相談中に入力欄から送った 2 ターン目のリクエストボディに `mentoring: true` が載る
- [ ] 3 ターン目も `mentoring: true` が載り続ける（2 ターン目だけの特別扱いになっていない）
- [ ] `options` を渡さない `send(content)` でも、全日単位の相談中なら `mentoring: true` が載る（付加は `useChat.send` 自身が行う）

### 継続中の送信内容（除外側）

- [ ] 全日単位の相談中に入力欄から送った 2 ターン目以降のリクエストボディは `mentoringTaskId` キーを持たない
- [ ] 全日単位の相談中でも、`options` を明示した `send` のリクエストボディには相談中の文脈がマージされない

### 置き換え

- [ ] タスク起点の相談中にヘッダボタンを押すと、状態表示が `今日の進め方について相談中` に置き換わり、タスクのタイトルを含む表示は消える
- [ ] タスク起点の相談中にヘッダボタンを押したあと入力欄から送ったリクエストボディは `{ content, mentoring: true }` と完全一致する（`mentoringTaskId` を持たない）
- [ ] 全日単位の相談中にタスクカードの「メンタリングする」を押すと、状態表示がそのタスクのタイトルを含む表示に置き換わる
- [ ] 全日単位の相談中にタスクカードから開始したあと入力欄から送ったリクエストボディの `mentoringTaskId` は、そのタスクの id と一致する

### 解除

- [ ] 全日単位の相談中に解除の導線を押すと、状態表示が消える
- [ ] 解除したあとに入力欄から送ったリクエストボディは `{ content }` と完全一致する（`mentoring` / `mentoringTaskId` を持たない）
- [ ] 全日単位の相談中に会（朝会・夕会）を開始すると、状態表示が消える
- [ ] 全日単位の相談中に朝会を開始したあと、会の中で入力欄から送ったリクエストボディは `{ content }` と完全一致する
- [ ] 全日単位の相談中に会の開始が失敗して `adhoc` に留まった場合、全日単位の相談中は保持される
- [ ] 全日単位の相談中に `endSession` が呼ばれると、相談中は解除される

### 受容する劣化

- [ ] リロードすると全日単位の相談中は失われ、状態表示も消える
- [ ] 状態が失われたあとに入力欄から送ったリクエストボディは `{ content }` と完全一致する

### 既存契約の保全（回帰確認）

- [ ] サーバ側のコードに差分が無い（`server/` に変更が無い）
- [ ] DB マイグレーションは追加されていない（`migrate.ts` の最大 version が 8 のまま）
- [ ] やりなおし経路（`rewrite`）のリクエストボディは、全日単位の相談中でも `mentoring` / `mentoringTaskId` を持たない
- [ ] 朝会・夕会の会中は、ヘッダの「進め方を点検してもらう」が表示されない
- [ ] タスク起点の相談中の 2 ターン目以降のリクエストボディには、従来どおり `mentoring: true` と開始したタスクの `mentoringTaskId` が載る
- [ ] メンタリングでない通常の送信のリクエストボディは `{ content }` と完全一致する

### 変異で証明する項目

次の各変異で、狙いの受入基準のテストが落ちることを確認する（緑のまま未担保にしない）。

- [ ] ヘッダ押下を「置き換え」ではなく従来の「解除」に戻すと、「ヘッダ押下のあとの入力欄送信が `{ content, mentoring: true }`」のテストが落ちる
- [ ] 明示解除・会の開始・`endSession` の各解除を 1 つずつ落とすと、それぞれに対応する解除のテストが落ちる
- [ ] 全日単位の相談中の開始でガードより前に状態を設定すると、「送信中・切替中は状態が設定されない」のテストが落ちる
