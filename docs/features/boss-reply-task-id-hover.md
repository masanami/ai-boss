# ボスの文面中のタスク ID（`#<id>`）にタスク名を添える

> **ドラフト（未確定）**: 判断 1〜4 と新論点 N1〜N3 は意思決定者の回答待ち。本文の「採用案」「受入基準」は**推奨案で仮置き**しており、回答に応じて書き換える。仕様クリティーク（3 レンズ批評）は論点確定後に実施する。

## 概要

ボスがチャット返信・決定ログで `#1`・`#2` のようにタスクを ID で呼んだとき、その `#<id>` にホバーすると該当タスクのタイトルが表示されるようにする。**web の表示だけを変える**（サーバ・プロンプト・DB は変えない）。

## 背景・目的

### 課題

ボスは `#<id>` でタスクを呼ぶことがあるが、UI のどこにもタスク ID が表示されないため、どのタスクの話か分からない（Issue #508。2026-09-13 のデモで、タスク 2 件のメンタリング時に返信・決定ログ本文へ `#1`・`#2` が繰り返し現れた）。

### 現状の確証（`62edbe4` 時点の実コード）

**(A) `#<id>` は chat 用プロンプトにだけ入り、文面へ漏れうる。**

- `server/src/boss/persona-prompt.ts:292-303` の `formatTaskLine` が `includeId` のとき `#${task.id} ` を前置する（半角 `#` ＋ 半角数字）。`:705` で `purpose === "chat"` のときだけ真
- 朝会・夕会の開始メッセージも `purpose` 未指定＝既定 `"chat"` で生成される（`server/src/sessions/meeting-opening.ts:132`）ため、会の冒頭の返信にも漏れうる
- メンタリングの「対象タスク」セクションは常に ID を含む（`persona-prompt.ts:598-601`）
- ダッシュボードのひとこと（`dashboard/boss-comment.ts:101`）・通知（`notifications/notification-body.ts:190`）は `purpose: "notification"`、日報は `"daily-report"`（`reports/extract-evening-summary.ts:143`）で ID を含まない

**(B) ボスの文面が描画される箇所。**

| 箇所 | 描画 | 書き手 |
|---|---|---|
| チャットの確定済みメッセージ | `web/src/ChatView.tsx:212` `{entry.content}`（ユーザー発言も同じ行を通り、`entry.role` で分かれる。`:207`） | ボス／ユーザー |
| チャットのストリーミング中 | `web/src/ChatView.tsx:632` `{streamingText}` | ボス |
| 決定ログ本文 | `web/src/DecisionLog.tsx:25` `{decision.content}` | ボス（`record_decision` / `record_mentoring` の `content`） |
| 決定ログ根拠 | `web/src/DecisionLog.tsx:27` `根拠: {decision.rationale}` | ボス（同 `rationale`） |
| タスクカードのボスコメント | `web/src/TaskCard.tsx:346` `ボスコメント: {task.boss_comment}` | ボス（`update_task` の `boss_comment`。chat 経路＝ID 入りプロンプト） |
| ツール通知 | `web/src/ChatView.tsx:40-60`（ツール結果の `title` を使う） | web 固定文言（ID を含まない） |

いずれも平文をテキストノードとして描画しており（`ChatView.css:80` は `white-space: pre-wrap`）、Markdown を解釈しない。Markdown 見出しは `#` の直後が空白であり、プロンプトも Markdown を禁じている（`persona-prompt.ts:645-646`）。

**(C) web のタスク一覧は全件だが、チャット・決定ログの描画には渡っていない。**

- `GET /api/tasks`（`server/src/tasks/tasks-routes.ts:40-42`）は `listTasks`（`tasks-repository.ts:28-33`、`WHERE` なし）＝**完了・中止を含む全件**。chat のプロンプトも同じ `listTasks` を使う（`sessions/chat-messages-route.ts:284`）ため、**プロンプトに載る ID の集合と web が取得する一覧は一致する**
- 一覧は `AppLayout` が 1 回だけ持つ（`web/src/AppLayout.tsx:58`）。`TaskBoard`・`CheckinPanel`・`TodaySummary` には渡っているが、`ChatView`（`:218`）・`DecisionLog`（`:232`）には渡っていない
- 決定ログは「自前でタスク一覧を持たない」設計で、見出しのタイトルはサーバの `LEFT JOIN`（`decisions-repository.ts:83-85`）が決定自身の `task_id` の分だけ解決する（`web/src/decision.ts` のコメント・#358 判断5）。本文中で**別のタスク**を `#id` で呼んだ場合の名前は持っていない

**(D) タスクは削除できない。** 本番コードに `DELETE FROM tasks` は無い（`migrate.ts:50` の `DROP TABLE tasks` は ID を保ったままのテーブル作り直し）。したがって「一覧に無い ID」が生じるのは、(1) web の一覧が古い、(2) モデルが存在しない ID を書いた、(3) DB リセット後の古い記録、に限られる。

**(E) web の一覧はチャットでのボスのタスク作成に追随しない。** `useTasks` の再取得はマウント時（`use-tasks.ts:51`）・タスクボードのマウント時（`TaskBoard.tsx:90`）・チェックイン後（`use-checkin-panel.ts:120`）だけで、ボスが chat で `create_task` しても再取得されない。朝会でボスが作ったタスクを同じ会話で `#3` と呼ぶと、一覧に `#3` が無い状態が起こる（→ 新論点 N1）。

**(F) 先例。** `web/src` に独自ツールチップ・`title` 属性の使用例は無い（`aria-label` のみ）。チャットの編集ボタンは「キーボードで到達でき、ホバー専用の実装は採らない」を明示的な仮定としている（`ChatView.tsx:218-221`）。

### 目的

ボスが `#<id>` でタスクを呼んだとき、ユーザーが画面上でその場でタスク名を確かめられるようにする。

## ユーザーストーリー

ai-boss のユーザーとして、ボスの返信や決定ログに出てくる `#1` にマウスを載せてタスク名を確かめ、どのタスクについての指示かを取り違えずに動きたい。

## 機能要件

- [ ] ボスのチャット返信（確定済み）中の `#<id>` を、web が保持するタスク一覧に引き当て、引き当たったものにタスクのタイトルを表示できるようにする（判断 1）
- [ ] 決定ログの本文中の `#<id>` を同じ規則で引き当てる（判断 1）
- [ ] 引き当ての規則は 1 つの純粋関数に置き、チャット・決定ログで共有する（判断 2）
- [ ] 一覧に引き当たらない `#<id>` は装飾せず原文のまま表示する（判断 2）
- [ ] ユーザー発言中の `#<id>` は引き当てない（判断 1）

## 画面・API設計

API は変えない。`AppLayout` が保持する `tasksState.tasks` を `ChatView`・`DecisionLog` へ渡す（推奨案。判断 2 の波及範囲を参照）。

## 機能全体の設計

### 引き当て規則（判断 2・推奨案で仮置き）

- 対象トークン: 半角 `#` の直後に半角数字が 1 文字以上続き、その次の文字が数字でないもの（正規表現で `#([0-9]+)(?![0-9])`。`#12` は `#1` と `2` に割らない）
- `#` の直前の文字は問わない（「タスク#1」「##1」の `#1` も対象）
- 数字列が一覧のいずれかのタスクの `id` を 10 進表記した文字列と**完全一致**するときだけ引き当てる（`#01` は `#1` に引き当てない）
- 全角 `＃`・全角数字は対象外（プロンプトが半角で渡すため。`persona-prompt.ts:300`）
- 一覧に無い ID・一覧が未取得（`loading` / `error`）のときは装飾しない
- 描画は React のテキストノードと要素の並びで行い、HTML 文字列を組み立てない（`dangerouslySetInnerHTML` を使わない）

### 表示形（判断 3・推奨案で仮置き）

引き当たった `#<id>` を要素で包み、`title` 属性にタスクのタイトルを持たせる（ホバー時の表示はブラウザのネイティブツールチップ）。フォーカス可能にはしない。

### 実装計画（チケット分解の見通し）

1 チケット（引き当ての純粋関数＋チャット・決定ログへの適用＋`AppLayout` からの受け渡し）。

## やらないこと

- プロンプトで「`#id` でなくタスク名で呼ぶ」よう指示する（理由: LLM 依存で受入基準にしにくい。サーバ変更を伴う。判断 4 (c)）
- タスクカードに ID を表示する（理由: ボスが ID で呼ぶこと自体を UI の語彙にしてしまう。タスクカードは #506 で別途変更中。判断 4 (d)）
- ストリーミング中の返信の装飾（理由: 途中の `#1` が `#12` に伸びうる。確定後の表示で装飾される。N2）
- 全角 `＃`・全角数字の引き当て（理由: 観測されておらず、プロンプトは半角で渡す）
- ダッシュボードのひとこと・通知・日報（理由: ID を含まない生成経路。(A)）
- チャットでのボスのタスク作成後に web のタスク一覧を再取得する（理由: 既存の追随漏れで、サイドパネルにも影響する別課題。N1 の回答次第で扱いを変える）

## 受入基準

> 推奨案で仮置き。jsdom は CSS を適用せずネイティブツールチップも出さないため、「表示される」は DOM 上の `title` 属性で検証する。

- [ ] ボスのチャット返信に一覧にある ID の `#1` が含まれるとき、その `#1` のテキストを持つ要素の `title` がタスク 1 のタイトルと一致する
- [ ] 決定ログの本文に一覧にある ID の `#2` が含まれるとき、その `#2` のテキストを持つ要素の `title` がタスク 2 のタイトルと一致する
- [ ] 一覧に無い ID（例: `#9999`）は `title` を持つ要素で包まれず、本文のテキストは原文と一致する
- [ ] ID の数字列は最長一致で引き当てる（一覧にタスク 1 と 12 があるとき `#12` はタスク 12 に引き当たり、一覧にタスク 1 だけがあるとき `#12` は装飾されない）
- [ ] ユーザー発言に一覧にある ID の `#1` が含まれても、`title` を持つ要素で包まれない
- [ ] 装飾の有無にかかわらず、描画された本文のテキスト（`textContent`）は元の文面と一致する
- [ ] 引き当ての規則を外す変異（引き当てを常に失敗させる／数字の境界条件を外す／役割の判定を外す）で、上記の対応するテストがそれぞれ落ちる
