# ボスの文面中のタスク ID（`#<id>`）にタスク名を添える

## 概要

ボスがチャット返信・決定ログ本文で `#1`・`#2` のようにタスクを ID で呼んだとき、その `#<id>` にホバーすると該当タスクのタイトルが表示されるようにする。**S1 は web の表示だけを変える**（サーバ・プロンプト・DB・API は変えない）。

## 背景・目的

### 課題

ボスは `#<id>` でタスクを呼ぶことがあるが、UI のどこにもタスク ID が表示されないため、どのタスクの話か分からない（Issue #508。2026-09-13 のデモで、タスク 2 件のメンタリング時に返信・決定ログ本文へ `#1`・`#2` が繰り返し現れた）。決定ログの見出しは**その決定自身の** `task_id` のタスク名であり（`web/src/group-decisions-by-task.ts:58-60`）、本文が別のタスクを `#<id>` で呼んだ場合は見出しからも辿れない。

### 現状の確証（`62edbe4` 時点の実コード）

**(A) `#<id>` は chat 用プロンプトにだけ入り、文面へ漏れうる。**

- `server/src/boss/persona-prompt.ts:292` の `formatTaskLine` が `includeId` のとき `#${task.id} ` を前置する（半角 `#` ＋ 半角数字、`:300`）。`:705` で `purpose === "chat"` のときだけ真
- 朝会・夕会の開始メッセージも `purpose` 未指定＝既定 `"chat"` で生成される（`server/src/sessions/meeting-opening.ts:132`）
- メンタリングの「対象タスク」セクションは常に ID を含む（`persona-prompt.ts:598-601`）
- ダッシュボードのひとこと（`server/src/dashboard/boss-comment.ts:101`）・通知（`server/src/notifications/notification-body.ts:190`）は `purpose: "notification"`、日報は `"daily-report"`（`server/src/reports/extract-evening-summary.ts:143`）で ID を含まない

**(B) ボスの文面が描画される箇所。**

| 箇所 | 描画 | 書き手 | 本仕様での扱い |
|---|---|---|---|
| チャットの確定済みメッセージ | `web/src/ChatView.tsx:212`（ユーザー発言も同じ行を通り、`entry.role` で分かれる。`:207`） | ボス／ユーザー | S1（ボスのみ） |
| チャットのストリーミング中 | `web/src/ChatView.tsx:632` | ボス | 装飾しない |
| 決定ログ本文 | `web/src/DecisionLog.tsx:25` | ボス（`record_decision` / `record_mentoring` の `content`） | S1 |
| 決定ログ根拠 | `web/src/DecisionLog.tsx:27` | ボス（同 `rationale`） | S3 |
| タスクカードのボスコメント | `web/src/TaskCard.tsx:346` | ボス（`update_task` の `boss_comment`） | S3 |
| ツール通知 | `web/src/ChatView.tsx:40-60`（ツール結果の `title` を使う） | web 固定文言 | 対象外（ID を含まない） |

いずれも平文をテキストノードとして描画し（`web/src/ChatView.css:80` は `white-space: pre-wrap`）、Markdown を解釈しない。Markdown 見出しは `#` の直後が空白であり、プロンプトも Markdown を禁じている（`persona-prompt.ts:644-646`）ため、下記の引き当て規則と衝突しない。

**(C) web のタスク一覧は全件だが、チャット・決定ログの描画には渡っていない。**

- `GET /api/tasks`（`server/src/tasks/tasks-routes.ts:40-42`）は `listTasks`（`server/src/tasks/tasks-repository.ts:28-33`、`WHERE` なし）＝**完了・中止を含む全件**。chat のプロンプトも同じ `listTasks` を使う（`server/src/sessions/chat-messages-route.ts:284`）ため、**プロンプトに載る ID の集合と web が取得する一覧は一致する**
- 一覧は `AppLayout` が 1 回だけ持つ（`web/src/AppLayout.tsx:58`）。`TaskBoard`・`CheckinPanel`・`TodaySummary` には渡っているが、`ChatView`（`:218`）・`DecisionLog`（`:232`）には渡っていない
- 決定ログは「自前でタスク一覧を持たない」設計で、見出しのタイトルはサーバの `LEFT JOIN`（`server/src/decisions/decisions-repository.ts:83-85`）が決定自身の `task_id` の分だけ解決する（`web/src/decision.ts` のコメント・#358 判断5）

**(D) タスクは削除できない。** 本番コードに `DELETE FROM tasks` は無い（`server/src/db/migrate.ts:50` の `DROP TABLE tasks` は ID を保ったままのテーブル作り直し）。したがって「一覧に無い ID」が生じるのは、(1) web の一覧が古い、(2) モデルが存在しない ID を書いた、(3) DB リセット後の古い記録、に限られる。

**(E) web の一覧はチャットでのボスのタスク作成に追随しない。** `useTasks` の再取得はマウント時（`web/src/use-tasks.ts:51`）・タスクボードのマウント時（`web/src/TaskBoard.tsx:90`）・チェックイン後（`web/src/use-checkin-panel.ts:120`）だけで、ボスが chat で `create_task` しても再取得されない。朝会でボスが作ったタスクを同じ会話で `#3` と呼ぶと、一覧に `#3` が無い状態が起こる（→ S2）。

**(F) 先例。** `web/src` に独自ツールチップ・`title` 属性の使用例は無い（`aria-label` のみ）。

### 目的

ボスが `#<id>` でタスクを呼んだとき、ユーザーが画面上でその場でタスク名を確かめられるようにする。

## ユーザーストーリー

ai-boss のユーザーとして、ボスの返信や決定ログに出てくる `#1` にマウスを載せてタスク名を確かめ、どのタスクについての指示かを取り違えずに動きたい。

## 機能要件

- [ ] ボスのチャット返信（確定済みメッセージ）中の `#<id>` を、web が保持するタスク一覧に引き当て、引き当たったものにタスクのタイトルをホバーで表示する
- [ ] 決定ログの本文中の `#<id>` を同じ規則で引き当て、タイトルをホバーで表示する
- [ ] 引き当ての規則は 1 つの純粋関数に置き、チャット・決定ログで共有する
- [ ] 一覧に引き当たらない `#<id>`、および一覧が未取得（`loading` / `error`）のときの `#<id>` は装飾せず原文のまま表示する
- [ ] ユーザー発言中の `#<id>` は引き当てない
- [ ] ストリーミング中の返信は装飾しない（確定後のメッセージで装飾される）

## 画面・API設計

API は変えない。`AppLayout` が保持する `tasksState` のタスク一覧（と読み込み状態）を `ChatView`・`DecisionLog` へ props で渡す。

## クリティカル設計決定

本機能はセキュリティ・機密データ・外部連携・DB スキーマのいずれにも触れない。以下は後続の実装が逸脱してはならない設計決定として記録する。

### 決定 1: 対象面

- **採用案**: チャットのボス返信の確定済みメッセージ（`ChatView.tsx:212` の `role === "boss"`）と決定ログ本文（`DecisionLog.tsx:25`）の 2 面。ストリーミング中（`:632`）・ユーザー発言は装飾しない
- **理由**: 両面で `#1` を実測した。ストリーミング中は途中の `#1` が `#12` に伸びうるため、確定後の表示に委ねる
- **代替案**: 決定ログ根拠・タスクカードのボスコメントも含める → 観測されておらず、タスクカードは #506 で変更中のため S3 に回した
- **影響範囲**: `ChatView`・`DecisionLog`・`AppLayout`

### 決定 2: #358 判断5（決定ログがタスク一覧を持たない）の見直しの範囲

- **採用案**: `DecisionLog` は**追加の取得をせず**、`AppLayout` が既に保持しているタスク一覧を props で受け取るだけとする。**見出しのグルーピングとタイトルは従来どおりサーバの `LEFT JOIN` 由来の `task_title` のまま**とし、受け取った一覧は本文中の `#<id>` の引き当てにだけ使う
- **理由**: 本文が別のタスクを呼ぶ場合の名前は `LEFT JOIN` では解決できない（決定自身の `task_id` の分しか持たない）。アプリは一覧を既に全件保持しており（(C)）、渡すだけなら新たな取得・状態は増えない
- **代替案**: サーバが本文中の `#<id>` を解決して返す → API とサーバの変更を伴い、チャットと別の経路で同じ規則を二重に持つことになる
- **影響範囲**: `DecisionLog` の props、`AppLayout` の受け渡し。`groupDecisionsByTask` は変えない

### 決定 3: 引き当て規則

- **採用案**:
  - 対象トークンは半角 `#` の直後の半角数字の最長の並び（正規表現で `#([0-9]+)(?![0-9])`。`#12` を `#1` と `2` に割らない）
  - `#` の直前の文字には条件を付けない（「タスク#1」「##1」の `#1` も対象）
  - 数字列が一覧のいずれかのタスクの `id` を 10 進表記した文字列と**完全一致**するときだけ引き当てる（`#01` は `#1` に引き当てない）
  - 全角 `＃`・全角数字は対象外
  - 一覧に無い ID、および一覧が `loading` / `error` のときは原文のまま表示する
  - 描画は React のテキストノードと要素の並びで行い、HTML 文字列を組み立てない（`dangerouslySetInnerHTML` を使わない）
- **理由**: プロンプトは半角 `#` ＋数字で ID を渡す（`persona-prompt.ts:300`）。日本語の文面では `#` の直前が文字であることが普通で、直前の条件を付けると取りこぼす。直前の条件で防げるのは `1#2` のような現実的でない並びだけである
- **代替案**: 直前が数字・英数字でないことを要件にする → 「タスク#1」を取りこぼしうる割に防げる誤引き当てが無い

### 決定 4: 表示形

- **採用案**: 引き当たった `#<id>` を要素で包み、`title` 属性にタスクのタイトルを持たせる（ホバー時の表示はブラウザのネイティブツールチップ）。フォーカス可能にはしない
- **理由**: 利用者の要望はマウスホバーである。ネイティブの `title` はキーボードフォーカスでは表示されないため、フォーカス可能にしてもタブ停止が増えるだけで表示は得られない
- **代替案**: ホバーとフォーカスの両方で出す独自ツールチップ（`tabIndex=0`・`role="tooltip"`・`aria-describedby`）→ CSS と状態が増える。「やらないこと」に置き、将来の拡張候補とする

## 機能全体の設計

### 実装計画（チケット分解の見通し）

S1 は 1 チケット（引き当ての純粋関数＋チャット・決定ログへの適用＋`AppLayout` からの受け渡し）。

## やらないこと

- クリックで該当タスクのカードへ移動する（理由: タスクボードは別ビューで、ビュー切替とスクロールを伴う。後続の別 Issue 候補）
- ホバーとフォーカスの両方で出す独自ツールチップ・キーボードでの到達（理由: 決定 4。将来この形で拡張しうる）
- プロンプトで「`#id` でなくタスク名で呼ぶ」よう指示する（理由: LLM 依存で受入基準にしにくく、サーバ変更を伴う）
- タスクカードに ID を表示する（理由: ボスが ID で呼ぶこと自体を UI の語彙にしてしまう。タスクカードは #506 で別途変更中）
- ストリーミング中の返信の装飾（理由: 決定 1）
- 全角 `＃`・全角数字の引き当て（理由: 観測されておらず、プロンプトは半角で渡す）
- ダッシュボードのひとこと・通知・日報（理由: ID を含まない生成経路。(A)）

## 受入基準

> jsdom は CSS を適用せずネイティブツールチップも出さないため、「ホバーで表示される」は DOM 上の `title` 属性で検証する。

- [ ] ボスのチャット返信（確定済み）に、一覧にある ID の `#1` が含まれるとき、テキストが `#1` の要素の `title` がタスク 1 のタイトルと一致する
- [ ] 決定ログの本文に、一覧にある ID の `#2` が含まれるとき、テキストが `#2` の要素の `title` がタスク 2 のタイトルと一致する
- [ ] 一覧に無い ID（例: `#9999`）は `title` を持つ要素で包まれない
- [ ] 一覧が `loading` または `error` のとき、`#<id>` は `title` を持つ要素で包まれない
- [ ] ID の数字列は最長一致で引き当てる（一覧にタスク 1 と 12 があるとき `#12` はタスク 12 のタイトルを持ち、一覧にタスク 1 だけがあるとき `#12` は包まれない）
- [ ] 数字列は ID の 10 進表記と完全一致するときだけ引き当てる（一覧にタスク 1 があるとき `#01` は包まれない）
- [ ] 全角 `＃1` は、一覧にタスク 1 があっても包まれない
- [ ] ユーザー発言に一覧にある ID の `#1` が含まれても、`title` を持つ要素で包まれない
- [ ] ストリーミング中の返信テキストに一覧にある ID の `#1` が含まれても、`title` を持つ要素で包まれない
- [ ] 装飾の有無にかかわらず、描画された本文の `textContent` は元の文面と一致する
- [ ] 引き当てを常に失敗させる変異で、チャットと決定ログの引き当てのテストがそれぞれ落ちる
- [ ] 数字の最長一致の境界（`(?![0-9])` 相当）を外す変異で、最長一致のテストが落ちる
- [ ] ユーザー発言を除外する役割の判定を外す変異で、ユーザー発言のテストが落ちる
