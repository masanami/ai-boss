# チャットルートのエラー応答の形（`mentoringTaskId` の 404）

## 概要

`POST /api/sessions/:id/messages` が `mentoringTaskId` の存在検証で返す 404 を、同ルートの他のユーザー到達型拒否と同じ形（日本語の `error` ＋ 安定した `code`）に揃える。あわせて、その 404 を検証しているテストが「404 の出どころ」を区別できていない緩さを締め、変異で担保されていることまで確認する。

**サーバの応答契約とそのテストだけを変える。** web は 1 行も変えない（`chat-api.ts` が既に `code` を透過するため、契約を足すだけで受け取れる）。

## 背景・目的

### 課題の性格（「ユーザーに英語が出る不具合」ではない）

Issue #477 本文は「削除済みタスクに対して『メンタリングする』が押され、英語のエラーがバナーに出うる」を動機としている。**この経路は現在のコードでは成立しない**（下記「現状の確証」(C)）。したがって本スライスが解くのは**利用者に見えている不具合ではなく、防御的エラー契約の不揃いと、それを守るテストの緩さ（潜在欠陥）**である。

この読み替えの帰結として、**受入基準に「画面に日本語が出る」を書かない**。通常操作では到達しないため検証不能な基準になるからである。基準はサーバの応答契約（ボディの形）と、テストが変異で落ちること（テストの締まり）で書く。

### 現状の確証（`bcb2780` 時点の実コード）

**(A) `chat-messages-route.ts` のエラー応答は 4 形に割れている。**

| 行 | 応答 | `error` の形 | `code` |
|---|---|---|---|
| 161 | 404 | `` `session ${rawId} not found` `` | なし（英語） |
| 167 | 400 | `validation.error`（`sessions-validation.ts` の全件が英語） | なし |
| 181 | 404 | `` `task ${mentoringTaskId} not found` `` | なし（英語） |
| 198-199 | 409 | 「終了したセッションの発言は編集できません」 | `session_already_ended` |
| 209-210 | 404 | `` `message ${id} not found in session ${id}` `` | `message_not_found`（英語＋`code`） |
| 218 | 400 | 「ボスの発言は編集できません」 | `message_not_editable` |
| 232 | 500 | クライアント初期化失敗のメッセージ（英語） | なし |

すなわち「日本語＋`code`」「英語＋`code`」「英語・`code` なし」が同居している。本スライスが直すのは **181 行だけ**である（範囲の根拠は決定 1）。

**(B) `code` は既に web まで透過している。** `web/src/chat-api.ts:30-41` の `toChatApiError` がボディの `code` を読み `ChatApiError` に載せ、`chat-api.ts:216-218` が `!response.ok` でそれを throw する。`ChatApiError` のドキュメントコメント（`chat-api.ts:11-19`）は「UI は日本語文言でなく安定した `code` で分岐すべき」と明記し、`mentoring_required`（ADR 0008 決定2）を先例として挙げている。**サーバが `code` を付けるだけで web 側は無改修で受け取れる。**

**(C) タスクもセッションも削除できないため、181 行・161 行のいずれも UI からは到達しない。** `server/src` の本番コードにある `DELETE FROM` は `task-evidences-repository.ts`（エビデンス）と `messages-repository.ts`（メッセージ）の 2 本のみで、`DELETE FROM tasks` はテスト（`collect-work-log-data.test.ts:293`）にしか存在しない。`tasks-routes.ts` が公開するのは `GET /` `POST /` `PATCH /:id` だけで削除エンドポイントは無く、`TaskCard.tsx:270` の「削除」ボタンはエビデンス削除である。セッションにも削除経路が無い。これは `docs/features/task-scoped-mentoring.md` の確証 (L) が既に記録している事実の独立再現である。

181 行に実際に到達しうるのは、DB を手で書き換えた場合・DB ファイルをリセットしたのにタブを開いたままの場合・API を直接叩いた場合に限られる。

**(D) 該当テストは 404 の出どころを区別できていない。** `server/src/sessions/chat-messages-route.test.ts:875-894`（AC-14/AC-15）は `expect(res.status).toBe(404)` と `expect(typeof body.error).toBe("string")` までしか照合しない。161 行のセッション 404 でも通るため、**実装が task 404 をセッション 404 に取り違えてもこのテストは緑のまま**である。同じ describe 内の 400 のテスト（`:839` `:870`）は `toContain("mentoringTaskId")` まで見ており、そこと非対称である。

### 目的

- 181 行の応答を、同ルートの「日本語＋`code`」形（198-199 行・218 行）へ寄せ、機械可読な `code` で他の 404 と区別できるようにする
- (D) の緩さを締め、**変異で落ちること**まで確認して「テストが 404 の出どころを守っている」状態にする

## ユーザーストーリー

**web の実装者**として、`mentoringTaskId` の 404 を安定した `code` で識別できる状態にして、将来「対象タスクが見つからない」を他の 404 と別扱いしたくなったときに、**サーバの応答契約を変えずに web 側だけで分岐を足せる**ようにしたい。

## 機能要件

- [ ] `mentoringTaskId` に存在しないタスク id を指定したリクエストの 404 応答が、安定した `code` を持つ
- [ ] 同応答の `error` が `"対象のタスクが見つかりません"` である
- [ ] 同 404 を検証するテストが、セッション 404 と取り違える実装では落ちる

## 画面・API設計

### API（`POST /api/sessions/:id/messages`）

`mentoringTaskId` が指し示すタスクが存在しない場合の応答を次の形に変える。ステータスコード `404` は変えない。

```jsonc
// 変更前（chat-messages-route.ts:181）
{ "error": "task 999 not found" }

// 変更後
{ "error": "対象のタスクが見つかりません", "code": "mentoring_task_not_found" }
```

同ルートの他の応答（161・167・198-199・209-210・218・232 行）は**変えない**。

## クリティカル設計決定

> 本節は意思決定者が確定済みの決定であり、実装者が独自判断で逸脱しない。

### 1. 揃える範囲は 181 行（task 404）のみ

- **採用案**: `chat-messages-route.ts:181` の task 404 だけを日本語＋`code` へ寄せる。同ルートのセッション 404（161 行）は**変えない**
- **理由**: セッション 404 を「ルート内の対称」のために 161 行だけ日本語化すると、**同一文言 `` `session ${id} not found` `` が `sessions-routes.ts:270`（`POST /:id/end`）と `:328`（`GET /:id/messages`）にも同形で存在する**ため、「同じセッション不在エラーが、叩いたエンドポイントによって日本語だったり英語だったりする」という**資源単位の新しい非対称**が生まれる。ルート内の対称を得る代わりに資源単位の対称を壊す取引であり、採らない。加えて確証 (C) のとおりセッション 404 は UI から到達しないため、「同じ経路に英語が残る」という懸念も通常経路では現れない
- **代替案**:
  - (B) task 404 ＋ 同ルートのセッション 404 の 2 件 — 却下（上記の資源単位の非対称を生むため）
  - (C) セッション不在 404 を `chat-messages-route.ts:161` / `sessions-routes.ts:270` / `:328` の 3 箇所で横断的に揃える — 本スライスでは却下（スコープ拡大。**別 Issue として起票し、そちらで扱う**）
  - (D) 209 行（`message_not_found`・英語＋`code`）の日本語化も同時に行う — 却下（どのメッセージ id がどのセッションに無いかを文面から落とすため、やりなおし経路のデバッグ性を損なう）
- **影響範囲**: `chat-messages-route.ts` の 1 行。他ルート・web への波及は無い

### 2. `code` の値は `mentoring_task_not_found`

- **採用案**: `code` を `"mentoring_task_not_found"` とする
- **理由**: 同ルートの既存 `code`（`session_already_ended` / `message_not_editable` / `message_not_found`）と `mentoring_required`（ADR 0008 決定2）はいずれも**操作・文脈スコープ**の粒度であり、資源スコープではない。本件は `mentoringTaskId` という**このルート固有のフィールド**に対する拒否なので、その粒度に揃う
- **代替案**: `task_not_found`（資源スコープ。`tasks-routes.ts:84` の task 404 と将来共用できる）— 却下（共用すると「どのフィールドが不正か」を web が区別できなくなる。既存 `code` の粒度とも合わない）
- **影響範囲**: `chat-messages-route.ts` の 1 行と、それを照合するテスト

### 3. `error` の文言は「対象のタスクが見つかりません」

- **採用案**: `"対象のタスクが見つかりません"`
- **理由**: 同ルートの既存の日本語文言（「終了したセッションの発言は編集できません」「ボスの発言は編集できません」）はいずれも回復示唆を含まない簡潔形であり、それと揃える一貫性を優先する
- **代替案**: 「対象のタスクが見つかりません（一覧が古い可能性があります）」等の回復示唆付き — 却下（既存文言と形が揃わない。かつ確証 (C) のとおり通常操作では表示されないため、示唆の価値が薄い）
- **影響範囲**: `chat-messages-route.ts` の 1 行と、それを照合するテスト

### 4. web は変更しない（`code` による分岐を今は入れない）

- **採用案**: サーバに `code` を足すだけで、web には `code` による UI 分岐も回復動作も入れない。バナー表示は現状のまま（`use-chat.ts:456-462` が `setError(err.message)`）
- **理由**: 確証 (B) のとおり `ChatApiError` が既に `code` を透過しており、**分岐が必要になった時点で web 側だけで足せる**（サーバの契約を後から変えずに済む）。確証 (C) のとおり到達性が限定的な現状で回復動作を書くのは YAGNI
- **代替案**: `code` で分岐しタスク一覧の再取得まで行う — 却下（上記）
- **影響範囲**: なし（web 無改修）

### 5. テストは `code` まで照合し、変異で担保を証明する

- **採用案**: `chat-messages-route.test.ts:875-894` の照合を `code`（および `error` の文言）まで締めたうえで、**実装に「task 404 をセッション 404 の文言・`code` で返す」変異を打ち、当該テストだけが落ちること**を確認する
- **理由**: 確証 (D) のとおり、現行の `expect(typeof body.error).toBe("string")` はセッション 404 でも通る。照合を足すだけでは「締まったつもり」になりうるため、**取り違えの変異で実際に落ちること**を確認して初めて担保が証明される（`MEMORY` の教訓「AC 担保は変異で証明する」と同じ規律）
- **代替案**: 照合を足すだけで変異確認はしない — 却下（恒真アサーションの混入を検出できない）
- **変異の手順**: 変異は本番コード（`chat-messages-route.ts:181`）へ一時的に加える。**適用後に `git diff` で変異が意図した 1 箇所に限られていることを確認し、確認が済んだら `git checkout -- server/src/sessions/chat-messages-route.ts` で確実に復元する**（復元漏れのまま次の変更へ進まない）。変異はコミットしない
- **変異結果の記録先**: 変異はコミットされないため、**何をどう変異させ、どのテストが落ち、どのテストが落ちなかったかを PR 本文に記載する**。これが「変異を加えたときに当該テストだけが落ちる」という受入基準の充足を、後からレビュアーが確認する唯一の証跡になる
- **影響範囲**: `chat-messages-route.test.ts` の当該テスト。変異は上記手順で復元する
