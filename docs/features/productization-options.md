### 0.2 推奨する組み合わせ（段階移行案）

| 段階 | 構成 | LLM | データ | 通知 | 移行コストの目安 |
|---|---|---|---|---|---|
| **Phase 1（先行販売）** | **A: デスクトップアプリ**（Electron 推奨・§2） | **BYOK**（`api` バックエンド・キーは OS キーチェーン） | ローカル SQLite のまま | 常駐＋OS ネイティブ通知 | 小〜中（server/web をほぼ流用。パッケージング・署名・公証・自動更新・キー保管が新規） |
| **Phase 2（需要次第）** | **C: A＋最小クラウド**（ライセンス／課金／LLM プロキシ） | **事業者キー（料金込み）プランを追加**。BYOK は残す | ローカルのまま（推論内容だけプロキシを通る） | Phase 1 と同じ | 中（プロキシ・課金・利用上限の新設。ADR 0001 を「業務データを保存しない中継」まで広げる改訂） |
| **Phase 3（任意）** | **B: SaaS** またはデータ同期の追加 | 事業者キー | サーバー保存（ADR 0001 撤回） | Web Push／メール＋（あれば）デスクトップ通知 | 大（マルチテナント化・認証・運用責任） |

**推奨の根拠**（詳細は各節）:

1. 現行コードは「単一プロセスの Node サーバーが DB・スケジューラ・通知・LLM 呼び出しをすべて抱える」形であり（§現行構成）、**そのままデスクトップアプリの中に入れられる**。B は同じコードでも前提（単一ライター・ユーザー ID 無し・ローカル通知）が全面的に崩れる。
2. 「サボると来る」催促はコア価値で、**アプリのウィンドウを閉じていても届く**必要がある。これを最も確実に満たすのは OS ネイティブ通知を出す常駐プロセス（A/C）。Web Push はブラウザや OS の設定・状態に到達性が左右される（§4、要検証）。
3. 業務内容を**事業者のサーバーに保存しない**ことは、ADR 0001 の背景どおり差別化要素になりうる。A/C はそれを維持したまま販売できる。
4. 規約上、**利用者の Claude サブスクリプション認証を第三者製品で使う経路は許されない方向の記述が一次情報にある**（§1。最終判断は要確認）。そのため現行の既定（`claude-code`）は製品版の前提にできず、BYOK か事業者キーのどちらかになる。BYOK は事業者の推論コストがゼロで先行販売のリスクが低いが、一般利用者には敷居が高い。そこで **Phase 1 は BYOK で需要を測り、Phase 2 で料金込みプランを足す**。

### 関連 ADR の要点

| ADR | 要点 | 製品化で効く点 |
|---|---|---|
| 0001 | 保存はローカル SQLite のみ。外部送信は Anthropic への推論のみ。テレメトリ・**自動更新確認**・分析は既定で無効化の対象。破る拡張は ADR 改訂が必要 | **ライセンス確認・自動更新・LLM プロキシ・クラウド保存はいずれも ADR 0001 の外側** |
| 0002 | `ANTHROPIC_API_KEY` は `server/.env` のみ。LLM 呼び出しは必ずサーバー側。OS キーチェーンは「単一ユーザーのローカルツールには過剰」として却下済み | 一般利用者に `.env` 編集は求められない。**BYOK ならキーチェーン保管へ改訂**が要る |
| 0003 | Claude Code を in-process で使い、能力を剥奪。API キーを子プロセスから除外してサブスク認証を強制。自動更新確認も無効（依存更新で取り込む方針） | サブスク認証経路を製品版で使えない場合、**0003 の前提（既定 `claude-code`）が製品版では成り立たない** |
| 0005 | SQLite 単一ファイル・単一ライター・排他制御は最小限。複数プロセス／端末からの同時書き込みは前提外 | B では置き換え（Postgres 等）、A/C ではそのまま |

## 1. LLM の課金モデル

### 選択肢

| 選択肢 | 概要 | 長所 | 短所 |
|---|---|---|---|
| (s) サブスク認証（現行既定 `claude-code`） | 利用者が自分の Claude（Pro/Max 等）でログイン | 利用者の追加負担なし・事業者コストゼロ | **一次情報に「第三者製品での claude.ai ログイン提供は許可しない」旨の記述がある**（下記）。要確認 |
| (b) BYOK | 利用者が Claude Console で API キーを発行し、アプリへ入力 | 事業者の推論コストゼロ・データ経路が「利用者 → Anthropic」のまま（ADR 0001 と整合） | 一般利用者には敷居が高い（Console 登録・支払い設定・キー入力）。利用者ごとに料金が変動する |
| (o) 事業者キー（料金込み） | 事業者のキーで推論し料金に含める | 導入の敷居が最も低い | 推論コストを事業者が負う（§8）。**キーをクライアントに配れないため、中継サーバー（C の LLM プロキシ）または SaaS（B）が必須**。利用上限・不正利用対策が要る |
| (b+o) 両対応 | BYOK と料金込みを選ばせる | 層を分けて取りこぼしを減らす | 経路が 2 本になり、検証・サポートが倍になる |

### 規約について取得できた一次情報（**最終判断は要確認**）

2026-09-26 に次のページを取得した。**本資料は規約を解釈・断定しない**。記述の抜粋を示し、判断は一次情報と必要に応じた Anthropic への確認に委ねる。

- Claude Agent SDK overview — <https://code.claude.com/docs/en/agent-sdk/overview>（取得日 2026-09-26）
  - 「Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK. Use the API key authentication methods …」
  - Agent SDK の利用は Commercial Terms of Service に従う旨（自社の顧客へ提供する製品を含む）
- Claude Code Legal and compliance — <https://code.claude.com/docs/en/legal-and-compliance>（取得日 2026-09-26）
  - 「Developers building products or services …, including those using the Agent SDK, should use API key authentication …. Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users.」
  - Claude Code を製品に組み込む場合の条件として「バイナリを改変しない・組み込みの認証方式を除去／無効化／制限しない」「利用者に代わって Claude の利用料を支払う・再販・仲介しない（各利用者が自分の資格情報で認証する）」
  - Pro/Max の利用上限は「ordinary, individual usage」を前提とする旨

**この記述から読み取れる、確認すべき論点**（いずれも要確認）:

1. 製品版で `claude-code` バックエンド（利用者のサブスク認証）を残せるか。上記の記述は許されない方向を示しているように読める。
2. 現行の `claude-code` バックエンドは子プロセス環境から `ANTHROPIC_API_KEY` を除外している（ADR 0003 決定 6）。これが「組み込みの認証方式を制限しない」という条件にどう関わるか。
3. 事業者キーで推論して料金に含める場合、`claude-code`（Claude Code を組み込む）経路では「再販・仲介しない」条件に触れうる。料金込みにするなら **`api` バックエンド（Messages API 直接）で行う前提**が安全側と考えられるが、これも要確認。

### 既存資産の流用度

- `api` バックエンドは既に完成しており（`server/src/llm/backends/api-backend.ts`、リトライ・エラー分類つき）、**BYOK も事業者キーもこの経路をそのまま使える**。変わるのはキーの供給元（`.env` → キーチェーン／プロキシ）だけ。
- `claude-code` バックエンド（871 行）と ADR 0003 の能力剥奪は、製品版でサブスク認証を使わないなら**製品版では使われない**（オーナー個人の利用には残せる）。Agent SDK は Claude Code 実行ファイルを同梱するため、製品版から外せば配布物も軽くなる（サイズは未計測）。

### 影響を受ける ADR

0002（キーの保管場所）・0003（既定バックエンドと能力剥奪の前提）。事業者キーなら 0001（プロキシ経由の送信）も。

### 推奨

**製品版は `api` バックエンドに一本化する前提で設計し、Phase 1 は BYOK、Phase 2 で事業者キー（料金込み）を追加（両対応）**。根拠: 上記一次情報がサブスク認証を第三者製品で提供しない方向を示している（要確認）／`api` 経路は既に完成している／BYOK は事業者コストゼロで ADR 0001 と整合し、先行販売の損失上限が小さい。

## 2. 配布形態（A／B／C／段階移行）

### 選択肢の比較

| 観点 | A デスクトップ | B SaaS | C ハイブリッド |
|---|---|---|---|
| インストール | 必要（署名・公証済みインストーラ） | 不要 | 必要（A と同じ） |
| 事業者のインフラ | ほぼ不要（ライセンス配布・更新配信のみ） | 常時運用（アプリ・DB・スケジューラ・監視・バックアップ） | 小（ライセンス・課金・LLM プロキシ） |
| 業務データの保存先 | 利用者の Mac | 事業者のサーバー | 利用者の Mac |
| 通知の到達性（§4） | 高（常駐＋OS 通知） | Web Push 依存（要検証） | 高（A と同じ） |
| 複数端末 | 不可（単一マシン） | 可 | 不可（同期を足さない限り） |
| 利用状況の把握 | できない（ADR 0001 によりテレメトリ無し） | できる | ライセンス・推論量のみ |
| 更新配信 | 自動更新の仕組みが必要 | 即時 | 自動更新の仕組みが必要 |
| セキュリティ・個人情報の責任 | 小（事業者は業務データを持たない） | 大（業務データを預かる） | 中（推論内容が中継を通る） |

### ラップ技術（A/C）の比較

| 観点 | Electron | Tauri |
|---|---|---|
| Node サーバーの扱い | **メインプロセスが Node そのもの**。`server/` をそのまま `import` して起動できる | Rust 製。Node サーバーは**サイドカー（別バイナリ）**として同梱する必要がある（Node ランタイムの単一バイナリ化など） |
| better-sqlite3（ネイティブ） | Electron の Node ABI 向けに再ビルド（`@electron/rebuild` 等）が要る | サイドカーの Node に合わせてビルド |
| 自動更新・署名・公証 | 定番の仕組みがある（要検証） | 公式の updater あり（要検証） |
| 配布サイズ | 大きい（Chromium 同梱） | 小さい（OS の WebView） |
| 通知 | Electron の `Notification` API（macOS・Windows 共通） | Tauri の通知プラグイン（サイドカーから呼ぶ経路の設計が要る） |

**流用度**: A/C は `server/`（Hono・検知エンジン・DB・LLM 呼び出し）と `web/`（React）を**ほぼそのまま**使える。書き換えが要るのは起動部（`server/src/index.ts`）・通知アダプタ（`notifier.ts`）・キーの取得元・待ち受けアドレス（`127.0.0.1` 固定、または IPC 化）程度。B は同じコードを出発点にできるが、DB 層（同期 API の better-sqlite3 → 非同期の Postgres クライアント）・全クエリへのテナント条件・認証・スケジューラの全ユーザー化・通知経路が全面的に変わる。

### 影響を受ける ADR

A: 0001（自動更新・ライセンス確認の通信）・0002・0003。B: 0001（撤回）・0002・0003・0005（置換）。C: A に加えて 0001（プロキシ）。

### 推奨

**段階移行（A で先行 → 料金込みプランを出すときに C へ拡張 → 複数端末の需要が確認できたら B を検討）**。ラップ技術は **Electron を推奨**。根拠: 現行サーバーは Node 前提で better-sqlite3（ネイティブ）と Agent SDK（実行ファイル起動）を抱えており、Node をそのまま内包できる Electron が最も書き換えが少ない。Tauri は配布サイズで有利だが、Node サイドカーの同梱・ネイティブモジュールのビルドという追加の手間がある。

## 3. データ境界（ADR 0001）を維持するか改訂するか

### 選択肢

| 選択肢 | 内容 | 必要になる構成 |
|---|---|---|
| (1) 完全維持 | 通信は Anthropic への推論のみ。ライセンスはオフライン検証（署名付きライセンスキー）、更新は手動ダウンロード | A＋BYOK |
| (2) 部分改訂 | **業務データは端末外へ保存しない**を不変制約として残し、「業務データを含まない通信」（ライセンス確認・更新確認）を列挙して許可する | A＋BYOK（自動更新あり） |
| (3) 中継まで拡張 | (2) に加え、**推論リクエストが事業者の中継（LLM プロキシ）を通ることを許す**。中継は本文を保存・記録しない、と定義する | C |
| (4) 撤回 | 業務データを事業者のサーバーに保存する | B |

### 判断材料

- **現行 ADR 0001 は自動更新確認そのものを「既定で無効化する対象」に挙げている**。販売するアプリで自動更新を持たないのは、セキュリティ修正の配布が遅れるという点で現実的でない。したがって**自動更新を持つなら A でも ADR 0001 の改訂は避けられない**（Issue 本文は「A はローカル完結を維持できる」としているが、厳密には (1) を選ばない限り部分改訂が要る）。
- ADR 0001 の「却下した代替案」は、匿名統計の送信を「境界が再交渉になる」として退けている。部分改訂ではこの教訓を引き継ぎ、**許す通信を列挙（許可リスト）する形**にし、利用状況の収集は含めないのが整合的。
- (3) の LLM プロキシは、推論内容（タスク名・会話）が事業者の設備を通過する。「保存しない」は運用とコードで担保するしかなく、利用者から検証できない。プライバシーを売りにするなら、**BYOK（プロキシを通らない）を残す**ことで「中継を信用しない利用者」の逃げ道を持てる。
- (4) は「業務内容という最も見せたくないデータ」（ADR 0001 背景）を事業者が預かる。差別化要素を失うだけでなく、漏えい時の責任・個人情報保護の義務が事業者に発生する（§9、要確認）。

### 影響を受ける ADR

0001（全選択肢）。(4) は 0005 も。

### 推奨

**Phase 1 は (2) 部分改訂、Phase 2 で (3) まで拡張**。根拠: 業務データのローカル保存という差別化要素を守りつつ、自動更新とライセンス確認という販売上必須の通信だけを許せる。(1) は理論上可能だが、手動更新は販売製品として弱い。

## 4. 通知・検知の実現方式

### 現状

検知は `server/` 内の node-cron が毎分 tick して純粋関数のルールエンジン（ADR 0004）を評価し、`osascript`／`terminal-notifier` で macOS 通知を出す。**「サーバープロセスが動いていれば、ブラウザを閉じていても通知が届く」**のが現行の性質（ブラウザは表示にしか関与しない）。

### 選択肢

| 方式 | 構成 | アプリ非表示中 | ブラウザ／アプリを閉じている間 | PC がスリープ中 | 備考 |
|---|---|---|---|---|---|
| OS ネイティブ通知＋常駐 | A/C。Electron メインプロセスで cron を動かし `Notification` で通知。メニューバー常駐＋ログイン時自動起動 | 届く | **ウィンドウを閉じても常駐していれば届く**。アプリを終了したら届かない | 届かない（復帰後の tick で判定） | 現行の性質をそのまま保てる。`terminal-notifier`（外部コマンド）への依存を解消できる |
| Web Push | B。サーバー側スケジューラ＋Service Worker | 届く | ブラウザや OS の実装・設定に依存（**要検証**） | 端末側の状態に依存 | 利用者の通知許可・ブラウザの設定で到達性が落ちうる |
| メール／チャット連携 | B/C の補助 | 届く | 届く | 届く（読むのは復帰後） | 「催促」としては即時性・圧力が弱い。ADR 0001 の外部送信に当たる |
| モバイル通知 | B（将来） | — | 届く | — | ネイティブアプリ開発が別途必要 |

### 既存資産の流用度

- 検知ロジック（`server/src/detection/*`・`scheduler-tick.ts`）は純粋関数と DI で書かれており、**どの方式でも流用できる**。差し替えるのは通知アダプタ（`notifier.ts` の `NotifierDeps.execFile`）だけ。
- B では tick を「全ユーザー × 各ユーザーのタイムゾーン・勤務時間」で回す必要がある。現行の検知は「ローカル暦日」（ADR 0007・0010）に強く依存しており、**サーバー側で利用者ごとのタイムゾーンを持つ設計変更**が要る。

### 影響を受ける ADR

0001（メール等を足す場合）。B では 0007・0010（暦日の基準がサーバーのローカル時刻でなくなる）。

### 推奨

**A/C の「常駐＋OS ネイティブ通知＋ログイン時自動起動」**。根拠: 催促がコア価値であり、ウィンドウを閉じても届く現行の性質を保てる唯一の方式。検知コードはそのまま流用できる。

## 5. 対象 OS

| 選択肢 | 長所 | 短所 |
|---|---|---|
| macOS のみ | 現行の実装・検証環境のまま。署名・公証の手順も 1 系統 | 市場が限られる |
| macOS＋Windows | 市場が広がる | 通知・自動起動・パス・キー保管（Windows 資格情報マネージャー）の差分、コード署名の別手続き、検証環境の追加 |

**判断材料**: 現行コードで macOS 専用なのは通知アダプタ（`osascript`／`terminal-notifier`）と、開発・検証の前提。Hono・React・better-sqlite3（Windows 用ビルドあり）・検知エンジンは OS 非依存。Electron を採れば通知・自動起動・キー保管は OS 共通の API で書ける。B なら OS は問われない（ブラウザ依存）。

**影響を受ける ADR**: なし（CLAUDE.md の「macOS ローカル実行のみ」は更新が要る）。

**推奨**: **macOS で先行し、Windows は需要が確認できてから**。根拠: 検証環境がオーナーの Mac のみで、先行販売での品質を優先する。ただし A を Electron で作り、OS 依存部を通知アダプタ・キー保管・自動起動の 3 箇所に閉じておけば、後から Windows を足すコストは中程度に抑えられる。

## 6. マルチユーザー化の要否

| 選択肢 | 必要な変更 | 影響 |
|---|---|---|
| 不要（1 インストール＝1 ユーザー） | なし | A/C の前提 |

## 7. 価格・課金基盤

### 課金モデル × LLM 課金の組み合わせ

| | BYOK | 事業者キー（料金込み） |
|---|---|---|
| 買い切り | 成立する（事業者の継続費用がほぼ無い） | **成立しにくい**（推論コストが継続的に発生する） |
| 年額・月額ライセンス | 成立する（更新・サポートの原資） | 成立する。**利用上限（1 日／1 か月の呼び出し数・トークン数）とモデル固定が必須** |

### 課金基盤の選択肢（すべて要確認）

| 種類 | 例 | 特徴 |
|---|---|---|
| Merchant of Record 型 | Paddle、Lemon Squeezy など | 販売者として税（消費税・各国 VAT）の計算・納付を代行する。ライセンスキー発行の仕組みを持つものもある。手数料は高め |
| 決済代行型 | Stripe など | 手数料は低め。税務・請求書・ライセンス管理は自前か別サービス |
| アプリストア | Mac App Store | 配布・課金・更新を一括で任せられるが、サンドボックス制約（常駐・子プロセス・ネイティブモジュール）の適合性が要検証 |

### 判断材料

- 現行コードにライセンス・課金の仕組みは無い（新規）。A でオフライン検証の署名付きライセンスキーにすれば ADR 0001 を大きく崩さない（§3 の (1)/(2)）。
- 料金込みでは、§8 の概算で**ヘビー利用者が標準の 2〜3 倍のコスト**になる。定額制にするなら上限設計（超過時の挙動＝停止か、テンプレート文面への縮退か）が価格と同じくらい重要。検知の通知文面・ダッシュボードコメントには既にテンプレートへのフォールバックがある（ADR 0003 決定 9）ため、**上限超過時にチャット以外をテンプレートへ縮退させる**設計は既存資産で実現しやすい。

### 影響を受ける ADR

0001（オンラインのライセンス確認・課金 API 通信）。

### 推奨

**Phase 1（BYOK）は年額ライセンス（または買い切り＋メジャー更新有償）、Phase 2（料金込み）は月額＋利用上限**。決済は、個人事業として税務負担を減らせる **Merchant of Record 型を第一候補として比較検討**（手数料・対応国・日本の消費税の扱いは要確認）。価格そのものは §8 のコストとオーナーの事業判断で決める。
