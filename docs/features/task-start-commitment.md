## 概要

ボスとの会話で決めた「このタスクは何時から着手する」を**着手の約束**としてタスクに保存し、約束の時刻を過ぎても着手していなければ、既存のサボり検知の枠内でボスが催促する。見るための表示は、約束を見せる手段として従属させる。

## 背景・目的

### 確定済みの方向（プロダクトオーナーが 2026-09-13 に確定・案 A）

当日スケジュールは「見える化」のためではなく、**着手の約束（時間枠）を保存し、約束の時刻を過ぎても未着手ならボスが催促する**ために持つ。見るだけのタイムライン（案 B）は主目的にしない。

### 何が欠けているか

ボスと「20 時から構成 30 分」と決めても、その時刻はどこにも構造化して保存されない。

- タスクが持つ時間の情報は `estimated_minutes`（所要時間）と `due_at`（締切の**暦日**）だけで、着手時刻を持つ列は無い（`server/src/tasks/task.ts:7-27`）。`due_at` は ADR 0010 で暦日に一本化されており、時刻を載せる器ではない（`docs/adr/0010-due-at-is-a-local-calendar-date.md` 帰結「個別の機能で時刻付きの値をこっそり保存しない」）
- ボスの決定は `record_decision` で `decisions.content`（自由文）に残るだけで、時刻を構造化して持つ列は無い（`server/src/boss/decision-tool.ts:14-27`・`server/src/decisions/decision.ts:10-19`）
- 未着手検知は**タスク作成時刻 `created_at` からの経過**でしか判定しない（`server/src/detection/unstarted.ts:19-34`）。「20 時と約束したのに 20 時を過ぎても手を付けていない」を起点にできず、逆に「20 時からと約束したタスクに 15 時の時点で未着手の催促が来る」ことも起きうる

### 観測（2026-09-13 のデモ・親エージェントが実ブラウザで観測。Issue #510 本文より・本仕様では未検証）

タスク 2 件でメンタリングしただけでも、ボスの返信・決定は時間配分に集中した（「構成30分＋本文執筆120分、9/14午前に本文」「経費精算は明日9/14夕方に15分」「現時点で19時台のため今日中の構成決定を確実に今夜こなす」）。

## 技術的な制約・方針

- **ローカル完結**（ADR 0001）。外部カレンダー連携はしない
- **検知は純粋関数のまま**（ADR 0004 決定 2・3）。約束の判定に LLM を使わない。LLM は通知の文面生成と、会話中に約束を提案・保存するツール呼び出しにだけ使う
- **`due_at` を使わない・変えない。** 着手の約束は締切とは別の概念であり、`due_at` に時刻を戻さない（ADR 0010 帰結）
- **書き手はボス（LLM）である**ことを前提に、ツールの説明文で保存形式を明示する。ADR 0010 の実測では、ツール説明文が曖昧だったため LLM が就業終わりの時刻を自分で補っていた（`server/src/boss/task-tools.ts:34-42`）。説明文は `claude-code-backend.ts` の Zod shape と二重に書き、一致テストを保つ（C11）
- **テストの固定時刻はローカル日時（`new Date(y, m, d, h, min)`）から導出し、TZ 非依存に組む**（ADR 0007 決定 5）。約束の時刻は暦日の区切りに触る可能性があるため `npm run test:tz` も通す（同 決定 6）
- テストでは Claude API・現在時刻・macOS 通知コマンドをモックし、SQLite はモックしない
- **マイグレーションの version 番号は予約しない。** `working-hours-intervals.md` は #432〜#434 が version 9 を使う前提を記しているが、いずれも未着手である。先にマージされた方が次の番号を取り、後続は番号を付け替える（ADR 0005 決定 4：既存 version を書き換えない）

## 未決の論点（A 群・プロダクトオーナーの決定待ち）

> **ここは本仕様では確定させない。** 実装エージェントも親エージェントも埋めてはならない。選択肢ごとに、オーナーの体験がどう変わるかを書いた。

### A1: 約束を誰が・いつ作るか

- **(a) 朝会でだけ、ボスが着手時刻を提案してオーナーが確認する** — 朝会の流れに「何時から何をやるか」を決める一歩が加わる。朝会の後に相談で決めた時刻（デモの「19 時台に今夜の構成」のような決め方）は保存されず、催促も来ない
- **(b) どの会話でも（朝会・随時の相談・夕会）、ボスが着手時刻を提案してオーナーが確認する** — 朝会でも相談でも、ボスと時刻を決めてオーナーが「それで」と言った時点で約束になる。所要時間の見積もりが既にこの形で全会話に効いている（C7）
- **(c) オーナーが画面で自分で時刻を入れる** — ボスと話さなくても約束を置ける。代わりにタスクカードに入力欄が増え、S1 で触る画面が増える
- **(d) 見積もりから自動で時間枠を並べる** — オーナーは何もしなくてよいが、自分で決めた時刻ではないので「約束を破った」という感覚になりにくい。しかも見積もりは現状、画面にもボスの文脈にも出ていない（C9・C10）

**推奨: (b)**。理由: Issue の観測では時刻の話はメンタリングの相談（19 時台）で出ており、(a) だと観測された使い方を取りこぼす。確認手順は見積もりと同形で、見積もりの確認指示が既に全会話に積まれている（`persona-prompt.ts:746-753`）ため、同じ場所に並べられる。(c) は S2 以降に足せる。

**親の叩き台（朝会で提案・相談中の変更はツールで更新）との差**: 叩き台は「作るのは朝会、変えるのは相談中」だが、推奨は「作るのも変えるのもどの会話でも」。

### A2: 約束を破ったときの強さ

- **(a) 既存の段階的な催促（穏やか → 念押し → 強い催促、以後 10 分ごと）に乗せる** — 約束の時刻を過ぎて手を付けていないと通知が来て、放置すると強まる。着手（チェックインの「着手」）するか、約束を変えるまで続く
- **(b) 通知はせず、夕会でボスが「約束を守ったか」に触れるだけ** — 日中は何も来ない。守れなかった事実はその日の振り返りで扱われる
- **(c) 中間: 約束の時刻に 1 回だけ通知し、それ以上は強めない** — 時刻を知らせてはくれるが、無視しても追いかけてこない

**推奨: (a)**。理由: 確定済みの方向が「約束を過ぎても未着手ならボスが催促する」であり、「サボると来る」を強化する目的に最も直接合う。(b) は方向（案 A）から外れる。

### A3: S1 の範囲（何件の約束を持つか・どこまで見せるか）

- **件数**
  - **(a) 最優先タスク 1 件の約束だけを見る** — 約束は他のタスクにも付けられるが、催促が来るのは「アプリが最優先とみなしたタスク」だけ。ボスと「17 時に経費精算」と決めても、経費精算が最優先でなければ催促は来ない。何が最優先かは優先度・締切・登録順で自動に決まり（C2）、会話や画面からは見えない
  - **(b) 約束を持つタスクはすべて見る（1 タスクにつき約束 1 件）** — ボスと決めた時刻はどのタスクでも催促の対象になる。締切超過が既にこの形で全タスクを見ている（C4）
- **表示**
  - **(i) 画面には出さず、ボスの会話の中だけで扱う** — 約束はボスに聞けば分かるが、画面では確認できない
  - **(ii) タスクカードに「着手の約束 20:00」を 1 行出す** — 締切の「ボス決定: 締切」行（C10）と並ぶ。一覧や時間軸はない
  - **(iii) 今日の約束を時刻順の一覧で出す** — 一日の並びが見える。見るための画面を主目的にしない方向とは緊張関係にあり、S1 が大きくなる
- **日付**
  - **(x) 今日の約束だけ保存できる** — 「明日 9/14 午前に本文」のような翌日の約束は保存されない
  - **(y) 翌日以降の約束も保存でき、その日時に催促される（翌日の予定一覧は出さない）** — デモのように前日の相談で決めた「明日の午前」も、翌朝その時刻に効く

**推奨: 件数 (b)・表示 (ii)・日付 (y)**。理由: (a) は「決めたのに催促が来ない」がオーナーから見えない条件（何が最優先か）で起き、約束の信頼を損なう。締切超過の全件ループという前例があり、(a) と (b) で作る量はほぼ変わらない。日付は時刻を「日時」として保存すれば (y) は追加の作り込み無しに成立し、(x) にするほうが「今日かどうか」の検査を足す分だけ手間が増える。

**親の叩き台（最優先タスク 1 件・表示は 1 行）への反証**: 件数については上記 (a) の問題があるため (b) を推す。表示は叩き台と同じ。

### A4: 勤務時間外の約束をどう扱うか（確証で見つかった論点）

勤務時間帯の外では、朝会・夕会以外の催促がすべて止まる（C6）。既定の勤務時間は 9:00〜18:00 で、デモで出た「20 時から構成」「19 時台に今夜の構成」は既定の勤務時間の外にある（オーナーの実際の設定値は未確認）。

- **(a) 勤務時間外の約束には催促しない（今の止め方に従う）** — 夜の約束をボスと決めても、通知は来ない。翌日の勤務開始から、約束を過ぎたタスクとして催促が始まる
- **(b) 自分で決めた約束だけは勤務時間外でも催促する** — 20 時の約束には 20 時に通知が来る。約束の無いタスクへの催促は従来どおり勤務時間内だけ。「催促は勤務時間内だけ」という既存の設計決定（ADR 0004 決定 6）の改訂になる
- **(c) 勤務時間外には約束を作れないようにする** — ボスが「その時間は勤務時間外だ」と返す。夜に作業する日は、先に勤務時間の設定を変える必要がある

**推奨: (b)**。理由: 約束はオーナーが時刻を明示して同意したもので、勤務時間の設定より具体的な意思表示である。副業・夜間作業（#440 の背景）の日にこそ約束が効いてほしい。ただし ADR 改訂を伴うため、**A4 が決まらない場合は S1 を (a) で出し、(b) を S2 に回す切り方ができる**（「スライス」節）。

### A5: 朝会の終了に「約束を決めたこと」を条件にするか（ADR 0009 との関係）

- **(a) 条件にしない** — 約束は決めたいときに決める。朝会は従来どおりメンタリングを終えれば閉じられる
- **(b) 条件にする（約束が 1 件も無いと朝会を終われない）** — 毎朝必ず時刻まで決めることになる。決めたくない日は設定で外す逃げ道が要る（ADR 0009 決定 4 と同型）

**推奨: (a)**。理由: 朝会の終了条件は ADR 0009 がメンタリングで既に 1 系統持っており、2 系統に増やすと「終われない理由」が追いにくくなる（ADR 0009 が日報のブロックを増やさなかった理由と同じ）。約束の定着を見てから判断できる。

### A6: 約束を何度でも後ろ倒しできてよいか

- **(a) 制限しない（変更は記録に残る）** — 「やっぱり 21 時で」と言えば催促は 21 時からになる。後ろ倒しした事実はタスクの更新記録と決定ログに残り、夕会・日報でボスが扱える
- **(b) 後ろ倒しを回数や幅で制限する、または後ろ倒し自体を催促の対象にする** — 逃げ道が狭くなり約束が重くなる。代わりに「どこまでなら許すか」の線引きを決める必要がある

**推奨: (a)**。理由: 変更の痕跡は既存の仕組み（C12 の更新記録・`record_decision`）で残せ、S1 を小さく保てる。後ろ倒しの常習が観測されてから (b) を検討できる。

## クリティカル設計の論点（B 群・未決）

> 親エージェントの決定待ち。A 群の回答に依存するものは条件付きで推奨を書いた。**確定するまで「クリティカル設計決定」として扱わない。**

### B1: 約束の保存先（DB スキーマ変更）

- **(a) `tasks` に列を 1 つ足す**（仮称 `committed_start_at TEXT NULL`。`ALTER TABLE ... ADD COLUMN` のみでテーブル再構築は不要）
  - pros: 1 タスク 1 約束（A3 (b)）にそのまま合う。`Task` 型・検証・`formatTaskLine`・タスクカードが既に通っている経路に 1 フィールド足すだけ。`updateTask` の共通層を通るので `task_update` イベントも自動で残る（C12）
  - cons: 変更履歴は列に残らない（B2 で補う）。1 タスクに複数の時間枠（「構成 30 分」と「本文 120 分」を別時刻に）を持てない
- **(b) 新テーブル `task_start_commitments`（`task_id`・約束日時・作成/取消時刻）を足す**
  - pros: 1 タスク複数枠・履歴を持てる
  - cons: 読み書き・検知入力（`DetectionInput`）・タスク一覧 API の組み立てが増える。現時点で複数枠・履歴を使う要件が無い（YAGNI）

**推奨: (a)**（A3 が (b) 件数・1 タスク 1 約束のとき）。A3 で「1 タスクに複数の時間枠」が求められた場合のみ (b)。

### B2: リスケ（約束の変更）と履歴

- **(a) 列を上書きし、変更前後を `task_update` イベントの `note` に残す**（エビデンス要否の前例 `tasks-repository.ts:164-181` と同形）。ボスは変更の裁定を `record_decision` で記録する（既存の応答規律）
- **(b) 履歴テーブルを持つ**（B1 (b) とセット）
- **(c) 上書きのみで痕跡を残さない**

**推奨: (a)**（A6 が (a) のとき）。A6 で後ろ倒しを制限・検知する (b) が採られた場合は、判定に回数が要るため B1 (b) を再検討する。

### B3: 約束の時刻の保存形式と日付・勤務時間との関係

- **形式**
  - **(a) オフセット付き ISO 8601 の日時で受け付け、瞬時として保存する**（`created_at` 等と同じく UTC ISO に正規化）。ボスは現在日時をオフセット付きで受け取っている（C14）
  - **(b) 当日の `HH:mm` だけを受け付け、日付は保存時のローカル暦日とする**（A3 (x) のとき）
  - **(c) オフセット無しのローカル日時 `YYYY-MM-DDTHH:mm`** — サーバ TZ で解釈する。ADR 0007 が避けてきた「解釈を各所に散らす」形になりやすい
- **日付をまたぐ約束**: 約束の時刻を過ぎた未着手タスクは、その日が終わっても**失効させない**（着手・約束の変更・完了・取り下げまで対象に残る）案を推奨する。失効させても翌日には作成時刻起点の未着手が同じタスクで成立する（C1）ため、失効の規則を足しても体験は変わらず、境界の規則とテストだけが増える
- **勤務時間外の約束**: A4 に従う

**推奨: 形式 (a)・失効なし**（A3 が (y) のとき。(x) なら形式 (b)）。形式不正・暦として解釈できない値は保存を拒否する（書き手が LLM でもツール失敗の文言でボスが言い直せる。`due_at` が「受理して暦日へ落とす」を選んだ理由〔ADR 0010 決定 4〕は旧形式の既存データがあったためで、新しい列には当たらない）。

### B4: 検知への組み込み（既存の未着手・回避・無音との関係と重複催促の防止）

- **(a) 未着手ルールの起点だけ差し替える** — 最優先タスクに約束があれば起点を `created_at` から約束時刻へ、無ければ従来どおり。`rule_key` は `unstarted:{id}` のまま
  - A3 (a)（最優先 1 件）のときの最小形。回避との排他（C3）もそのまま保たれる
  - cons: 最優先でないタスクの約束は見ない（A3 (a) の問題をそのまま持つ）。約束を変えても `rule_key` が変わらず、エスカレーションが前の約束の続きから始まりうる
- **(b) 新しいルール種別（仮称 `commitment_missed`）を足し、約束を持つ全タスクをループで評価する**（締切超過 C4 と同形）。`rule_key` に約束の時刻を含め（仮称 `commitment_missed:{taskId}:{約束時刻}`）、リスケで新しい段階の列として L1 から始まるようにする。重複防止の規則:
  1. `status === "todo"` かつ `now >= 約束時刻 + 猶予` のタスクで発火する（`paused` は対象外。未着手の定義 C1 と揃える）
  2. **最優先タスクが約束を持つ場合、`unstarted`/`avoidance` は評価しない**（約束前は催促しない＝機能要件、約束後は `commitment_missed` に一本化する）
  3. 最優先タスク以外の約束は、最優先タスクの `unstarted`/`avoidance` と独立に発火しうる（別事由として扱う。締切超過が未着手と並んで出るのと同じ整理）
  4. `silence`・`deadline_overdue`・`break_overrun` は変えない。休憩ゲートは約束にも効かせる
  - 追加が要るもの: `DETECTION_RULE_TYPES`・`RULE_TYPE_MAP`・通知文面の `RULE_TYPES`/ラベル/フォールバック定型文。通知文面生成へ約束の時刻を渡す（いまは時刻が渡らない。C13）。`notifications` のマイグレーションは不要（C13）
- **(c) 最優先タスクの決め方に約束を反映する**（約束時刻を過ぎたタスクを最優先へ繰り上げ、既存の未着手・回避をそのまま効かせる）
  - pros: 「約束の時刻に他のタスクをやっている」が回避として催促される
  - cons: 最優先の決め方が時刻で変わり、回避の判定対象も巻き込んで変わる。約束を過ぎたタスクが複数あると 1 件しか見ない

**推奨: A3 件数 (b) なら (b)、A3 件数 (a) なら (a)**。猶予は **0 分（約束時刻ちょうどで発火）** を推奨する（スケジューラは毎分評価で、約束は「その時刻から着手する」という意味のため。所要時間でスケールする既存の閾値〔C1〕は「着手までの許容時間」ではないので流用しない）。A2 が (c)（1 回だけ）なら、`resolveEscalation` を通さず「その `rule_key` の履歴が 1 件でもあれば発火しない」とする分岐が要る。A2 が (b)（夕会で触れるだけ）なら検知への組み込み自体が不要になり、B4 は夕会フロー指示と夕会の文脈へ約束を渡す設計に置き換わる。

**既存の挙動として留意（本機能では変えない）**: C5 のとおり、通知後に活動シグナル（チャット発言を含む）が 1 件でもあると L1 にリセットして**次の毎分評価で即再発火**する。約束を過ぎてボスに「今からやる」と話しかけただけで L1 がもう一度来る。これは未着手・回避と同じ既存挙動であり、本仕様で直すかは別 Issue とする。

### B5: ADR の追加・改訂

- **A4 が (b)（勤務時間外でも約束は催促）なら、ADR 0004 決定 6（勤務時間帯外ゲートの例外）の改訂が要る**（`/create-adr`）。例外が「朝会・夕会の定時催促」から「＋着手の約束の催促」に広がる
- A4 が (a)/(c) なら、ADR 0004 の枠内（純粋関数・`rule_key` 単位のエスカレーション・ゲート）に収まり、新規 ADR は不要。「着手の約束は `due_at` と別の列で持つ」は ADR 0010 帰結の範囲内（締切に時刻を戻さない）で、改訂は不要
- A5 が (b) なら ADR 0009 と同型の前提条件になり、新規 ADR が要る

**推奨**: A4・A5 の回答に従う（上記の条件のとおり）。

### B6: ボスへの露出（ツール・プロンプト）

- `create_task`/`update_task` の入力に約束の時刻を足す（`null` で取り消し）。説明文に保存形式を明示し、Zod shape と二重に書く（C11）
- 確認前に保存させない指示を、見積もりの確認指示（`TASK_ESTIMATE_CONFIRMATION_INSTRUCTION`）と同じ位置に積む（A1 (b) のとき）。A1 (a) のときは `MORNING_FLOW_INSTRUCTION` にだけ積む
- `formatTaskLine` に約束の時刻を足す。**あわせて `estimated_minutes` も足すか**（C9：ボスは保存済みの見積もりを見られない。時間配分を話すなら欲しい情報だが、本 Issue の範囲を広げる）
- **確認を担保するのはプロンプト指示だけ**になる（見積もりと同じ。C7）。ADR 0009 が「プロンプト指示だけでは強制にならない」とした領域とは違い、ここで担保したいのは「勝手に約束を作らない」ことであり、機械的なゲートは置かない案を推奨する

**推奨**: 上記のとおり。`estimated_minutes` の追加は **S1 に含めない**（範囲を広げない）が、親の判断で含めてもよい小さな変更である。

- **翌日以降の計画の一覧表示**（理由: 同上。A3 (y) で翌日の約束を保存・催促しても、一覧は出さない）

### 保存と検証【B1 (a)・B3 (a)】

- [ ] `PATCH /api/tasks/:id` はオフセット付き ISO 8601 の日時を着手の約束として保存し、`GET /api/tasks` の該当タスクにその瞬時が返る
- [ ] `PATCH /api/tasks/:id` は着手の約束に `null` を受け付け、約束を取り消す
- [ ] `PATCH /api/tasks/:id` は日時として解釈できない着手の約束（例: `"20:00"`・`"2026-09-13"`・`"not-a-date"`）を 400 で拒否する
- [ ] 着手の約束を拒否したとき、タスクのどのフィールドも更新されず `task_update` イベントも記録されない
- [ ] 着手の約束を変更したとき、`task_update` イベントの `note` に変更前と変更後の時刻が残る【B2 (a)】
- [ ] 既存のタスク行は、マイグレーション適用後に着手の約束を持たない（`null`）

### ボスのツールと文脈【A1 (b)・B6】

- [ ] `create_task` と `update_task` のツール定義が着手の約束の入力を持ち、その説明文が保存形式（オフセット付きの日時）を明示する
- [ ] `update_task` ツール経由の着手の約束の保存は、`PATCH /api/tasks/:id` と同じ検証を通る（不正値はツールのエラーとして返る）
- [ ] 通常チャットのシステムプロンプトに、着手の約束はユーザーの確認後にのみ保存するよう指示する文言が、会の種別（朝会・夕会・随時）を問わず含まれる
- [ ] ボスに渡すタスク一覧の行に、着手の約束を持つタスクではその時刻が含まれ、持たないタスクでは含まれない

- [ ] `evaluateRules` は、着手の約束を持つタスクが `in_progress`・`paused`・`done`・`dropped` のとき、約束の時刻を過ぎていても `commitment_missed` を発火しない
- [ ] `evaluateRules` は、最優先でないタスクの着手の約束についても `commitment_missed` を発火する
- [ ] `evaluateRules` は、最優先タスクが着手の約束を持ち約束の時刻より前であれば、作成時刻から閾値を超えていても `unstarted` を発火しない
- [ ] `evaluateRules` は、最優先タスクが着手の約束を持ち約束の時刻より前であれば、他タスクへの直近の活動があっても `avoidance` を発火しない
- [ ] `evaluateRules` は、最優先タスクが着手の約束を持ち約束の時刻を過ぎているとき、同じタスクに `unstarted` と `commitment_missed` を同時に発火しない
- [ ] `evaluateRules` は、着手の約束を持たない最優先タスクについて、従来どおり作成時刻を起点に `unstarted` を発火する（閾値ちょうどで発火し、1 分前は発火しない）
- [ ] `commitment_missed` の `rule_key` は約束の時刻を含み、約束の時刻を変更すると変更前の通知履歴を引き継がず L1 から発火する
- [ ] `commitment_missed` は同一 `rule_key` の既存のエスカレーション（L1 → L2 → L3・レベル別間隔）に従う
- [ ] 勤務時間帯外では `commitment_missed` を発火しない【A4 (a) の挙動で S1 を出す場合。(b) なら「発火する」に反転】
- [ ] 休憩申告中は `commitment_missed` を発火しない
- [ ] `commitment_missed` の通知文面の生成依頼に約束の時刻が含まれ、LLM 失敗時のフォールバック定型文が L1〜L3 のそれぞれに存在する
