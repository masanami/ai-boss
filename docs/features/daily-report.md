# 日報生成

## 概要

夕会セッションの完了を前提条件として、当日のタスク実績・チェックイン記録・夕会での報告とボスの評価から Markdown 日報（本仕様の「日報テンプレート」に従う固定構成）を自動生成し、アプリ内で表示・クリップボードコピー・保存（見返し）できるようにする。生成物はオーナーの記録リポジトリ work-record へそのまま貼り付けて利用できる。

## 背景・目的

- オーナーは現在、別リポジトリ work-record に日々のタスク一覧・実施記録・日報メモを手で書いている。ai-boss は日中の実態（タスクの完了/未完了、チェックイン・休憩、夕会での報告とボスの評価）を既に自動収集しており、日報を「手で書く」作業を「生成して確認し、work-record へ貼り付ける」作業に置き換えられる。
- 役割分担の方針（future-ideas.md「外部ツール連携によるタスク取り込み」で確立）: 計画・恒久記録の層は外部（work-record）、実行規律の層は ai-boss。日報生成はその間を埋める ai-boss → 外部への一方通行の出力である。
- **将来の toB 展開の布石（オーナー構想・2026-08-14）**: 生成した日報を実在の上司へ共有するサービス展開を見据える。その際「AI ボスとの壁打ち（夕会での報告・対話）を経ないと日報を生成できない」という製品制約によって、AI との振り返り対話を利用者に強制する。本機能は MVP からこの制約（夕会完了の前提条件）を体現する。

## ユーザーストーリー

自己管理が苦手な個人ワーカーとして、夕会でボスに一日の報告をするだけで日報 Markdown が自動生成される仕組みを使って、日報を手で書く作業を無くしつつ、記録リポジトリ（work-record）への蓄積を続けたい。

## 機能要件

- [ ] 夕会セッションを終了すると、当日（ローカル日付）の日報が自動生成され DB に保存される
- [ ] **夕会完了の前提条件（壁打ち強制）**: 「当日の夕会セッションが終了済みで、かつそのセッションにユーザーの発言メッセージ（role=user）が1件以上ある」場合のみ日報を生成できる。満たさない場合、生成 API はエラーを返し、UI は「夕会を完了すると日報を生成できます」という状態表示を行う（無言のままセッションを終了しても日報は生成されない — 対話を経ることを強制する製品制約・オーナー決定 2026-08-14）
- [ ] **夕会は1日1回**: 当日（ローカル日付）に夕会セッションが既に存在する場合、新たな夕会セッションは作成できない（セッション作成 API が 409 を返す。オーナー決定 2026-08-14）。夕会をやり直したい場合は既存の当日夕会セッションで会話を続け、日報を再生成する。朝会・随時セッションの挙動は変更しない
- [ ] **日付基準の統一**: 本機能で「当日」と言うときは常に**サーバーのローカルタイムゾーンでの暦日**（既存 `toDateKey` と同じ基準）を指し、判定の基準時刻は次で固定する。日付をまたぐ夕会（例: 23:50 開始 → 翌 00:30 終了）は**開始日の日報**になる
  - 夕会セッションの所属日 = その夕会の `started_at` のローカル日付
  - `daily_reports.date` = 対象夕会の `started_at` のローカル日付（1 夕会 : 1 日報）
  - タスク実績・activity_events の集計範囲 = 同じローカル日付の 00:00:00.000〜23:59:59.999
- [ ] 日報は下記「日報テンプレート」の固定セクション構成に従う（含める内容もテンプレートで定義する）
- [ ] 日報ビュー（画面）で当日の日報を表示し、クリップボードへコピーできる
- [ ] 過去の日報を一覧から選択して閲覧できる
- [ ] 手動の再生成ボタンを提供する。再生成は同日分を上書きする（前提条件は自動生成時と同じ）
- [ ] **Markdown の構造はレンダラーが決め、LLM には値だけを出させる**: LLM の役割は夕会の会話から「報告の要点」「ボスの講評」「翌日への持ち越し」の3つの**値**を返すことに限る（構造化された応答を要求する）。表題・セクション見出し・順序・チェックボックス記法・「決定事項」の省略は、すべてサーバー側の単一のレンダラーが決定する。**通常経路とフォールバック経路は同じレンダラーを共用する**（Markdown 構造をプロンプトで保証しようとしない）
- [ ] LLM 呼び出しが失敗した（またはタイムアウトした・応答が期待の形式でない）場合は、同じレンダラーに値なしの入力を渡してフォールバック日報を生成する。フォールバック時の「夕会サマリ」セクションは固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみとし、3項目（報告の要点・ボスの講評・翌日への持ち越し）は出力しない（夕会完了の前提条件はフォールバック時も維持する）

### 日報テンプレート

生成する日報は次の固定構成とする。work-record のメモ書きよりフォーマルな体裁とする（オーナー決定 2026-08-14）。「決定事項」はデータが無い日はセクションごと省略する。それ以外のセクション見出しと順序は固定。

```markdown
# 日報 2026-08-14（金）

## 本日のタスク

- [x] タスクA
- [ ] タスクB（進行中）


## 活動記録

- 着手: {当日最初の task_start の時刻}
- 休憩: {休憩回数}回（合計 {休憩合計時間}分）

## 夕会サマリ

- 報告の要点: {夕会での報告内容の要約}
- ボスの講評: {ボスの評価コメントの要約}
- 翌日への持ち越し: {持ち越し裁定の要約。無ければ「なし」}

## 決定事項

- {当日の決定ログの内容}
```

- 表題は `# 日報 YYYY-MM-DD（曜）`（曜日は漢字1文字）とする
- 「本日のタスク」に載せるのは次の2種のみとする（オーナー決定 2026-08-14）: **完了タスク** = `completed_at` が当日（ローカル日付）の done タスク。**進行中タスク** = 生成時点で status が in_progress、かつ当日の `activity_events`（type が `task_start` または `task_update` で `task_id` が当該タスク）が1件以上あるもの（当日に動きの無い長期継続タスクは載せない）。未着手（todo）・中止（dropped）のタスクは日報に含めない（中止の経緯が重要な日は夕会サマリ・決定事項に現れる。「中止」は既存 UI のステータス表示ラベルに合わせた表記）
- タスクは完了を `- [x] タスク名`、進行中を `- [ ] タスク名（進行中）` で表す（チェックボックスとタスク名の間に半角空白を1つ置く）。優先度マーク（⭐️ 相当）は付けない（⭐️ は実施前の優先度付けに使う記号であり、実績報告である日報には不要 — オーナー決定 2026-08-14）
- 「活動記録」の数値の定義: 着手は当日最初の `task_start` イベントの時刻、休憩回数は当日の `break_start` イベント件数、休憩合計時間は下記の対応付け規則で求めた各休憩の長さの合計（分単位・切り捨て）
- **休憩イベントの対応付け規則**（`activity_events` に相関 ID が無いため規則で決定的にする。`expected_minutes` は申告値であり実績の対応付けには使わない）:
  - **走査順**: イベントを `created_at ASC, id ASC` の順に走査する（同一 `created_at` でも順序が一意に定まるよう二次キーに `id` を使う）
  - **対応付け**: `break_start` を見たら**その後に現れる最初の未対応 `break_end` と対応付ける**（FIFO）
  - **休憩回数のカウント対象**: 当日（対象ローカル暦日）に属する `break_start` の件数。未対応の `break_end` は数えない
  - **`break_end` の探索範囲**: 当日の範囲に加え、**夕会セッションの `ended_at` までを探索する**（日付をまたぐ夕会で 23:55 開始・翌 00:05 終了の休憩が、翌日のイベントであっても実測 10 分として対応付くようにするため）
  - **打ち切り**: 上記の範囲で対応する `break_end` が見つからない `break_start`（未復帰のまま夕会が終わった場合）は**夕会セッションの `ended_at` までを休憩時間とする**
  - **孤立した `break_end`**: 対応する `break_start` の無い `break_end`（前日からの持ち越し等）は**無視する**
- 「活動記録」でイベントが無い項目は行全体を固定文字列にする: `task_start` が無い日は `- 着手: なし`、`break_start` が0件の日は `- 休憩: なし`（「0回（合計0分）」とは出力しない）
- 「決定事項」の対象は、当日（ローカル日付）に記録された全セッション（朝会・随時・夕会）由来の決定のうち `status = active` のもの。作成日時の昇順で、`content` のみを1件1行の箇条書きにする（`rationale` は含めない）
- **動的値のエスケープ・正規化**（固定構造を壊さないための契約）: レンダラーが Markdown に埋め込む動的値（タスク名・決定の `content`・LLM が返す3値）は、埋め込み前に次の処理を行う。テストには改行入り・Markdown 記号入りの入力を含める
  - 改行（CR/LF）を半角空白1つに置換して**1行へ正規化**する（連続する空白は1つに畳む）
  - 行頭に来ると構造を壊す記号（`#` `-` `*` `+` `>` `|` および `1.` 形式の番号）を、値の先頭に現れる場合はバックスラッシュでエスケープする
- LLM が抽出する項目（報告の要点・ボスの講評・翌日への持ち越し）の内容の正確性は、本仕様の受入基準・自動テストの対象外とする。自動テストで検証するのは構造（表題・セクション見出し・チェックボックス・固定文言・上記の正規化）のみ

## 非機能要件

- ローカルファースト（不変制約）: 日報の保存はローカル SQLite のみ。外部送信は生成時の Claude API への推論リクエストのみ。work-record への反映（貼り付け・コミット）はユーザーの手動操作とする
- 夕会終了の応答性: 日報の自動生成が失敗してもセッション終了自体は成功させる（best-effort。既存の「通知文生成失敗でも通知は送る」と同じ契約）
- 日付の扱いはローカル日付キーで統一し、テストはタイムゾーン非依存に書く（既存 `toDateKey` / `isSameLocalDay` のパターンに従う）

## 技術的な制約・方針

- 使用技術: 既存スタックのまま（Hono + better-sqlite3 / React）。新規依存の追加はクリップボードコピー（`navigator.clipboard`、依存追加なし）を含め不要
- 変更対象:
  - `server/src/db/migrate.ts`（マイグレーション version 3）
  - `server/src/reports/`（新設: リポジトリ・生成サービス・ルート）
  - `server/src/sessions/`（夕会終了時の自動生成フック、夕会セッション作成の1日1回制限）
  - `server/src/boss/persona-prompt.ts`（日報生成用の purpose 追加）
  - `web/src/`（日報ビュー・ナビ項目の追加）
- 既存コードとの関係:
  - 入力データは `tasks` / `activity_events` / `sessions`・`messages`（夕会の会話）/ `decisions` を読み取り専用で参照する
  - Issue #96（セッション要約）とは独立に実装可能: 日報生成は夕会セッションの会話メッセージを直接読む。#96 実装後に要約を再利用する最適化は任意
  - LLM 呼び出しは既存の `server/src/llm/claude-client.ts`（`api` / `claude-code` 両バックエンド対応）を使う。「報告の要点」「ボスの講評」「翌日への持ち越し」の3値を夕会セッションの会話メッセージから抽出させる（持ち越しを表す構造化データは持たない）。プロンプトは既存のボス人格プロンプト生成器の purpose 追加で組み立てる。**Markdown への組み立ては LLM ではなくレンダラーの責務**

## 画面・API設計

### API

| メソッド/パス | 動作 |
|---|---|
| `GET /api/reports` | 日報一覧（date と作成・更新日時のみ）を新しい順で全件返す（ページネーションなし・MVP スコープ） |
| `GET /api/reports/:date` | 指定ローカル日付の日報本文を返す。無ければ 404 |
| `POST /api/reports/generate` | 当日の日報を生成して保存し、本文を返す。「当日の夕会セッションが終了済みで、かつユーザー発言（role=user）が1件以上ある」を満たさなければ 409 を返す |

- 夕会終了時の自動生成はサーバー内部で `POST /api/reports/generate` と同じ生成サービスを呼ぶ（HTTP を経由しない）

#### レスポンススキーマ

日時は既存テーブルと同じ ISO 8601 文字列、`date` はローカル日付キー（`YYYY-MM-DD`）。

```jsonc
// GET /api/reports → 200
[
  { "date": "2026-08-14", "created_at": "2026-08-14T19:30:00.000Z", "updated_at": "2026-08-14T19:35:00.000Z" }
]

// GET /api/reports/:date → 200 ／ POST /api/reports/generate → 200
{
  "date": "2026-08-14",
  "content": "# 日報 2026-08-14（金）\n\n## 本日のタスク\n...",
  "evening_session_id": 12,
  "created_at": "2026-08-14T19:30:00.000Z",
  "updated_at": "2026-08-14T19:35:00.000Z"
}
```

#### エラー形式

既存 API と同じ `{ "error": "<メッセージ>" }` に、UI が分岐に使う**安定した `code`** を加える。

| 状況 | HTTP | `code` | 用途 |
|---|---|---|---|
| 当日の夕会が未終了、またはユーザー発言0件 | 409 | `evening_session_required` | 日報ビューが「夕会を完了すると日報を生成できます」を表示する分岐に使う |
| 指定日付の日報が無い | 404 | `report_not_found` | 一覧から消えた日付を開いた場合等 |
| 当日に夕会セッションが既に存在する状態での夕会作成 | 409 | `evening_session_already_exists` | セッション作成 API（既存）側 |

```jsonc
{ "error": "夕会を完了すると日報を生成できます", "code": "evening_session_required" }
```

### 画面

- ナビゲーションに「日報」を追加
- 日報ビュー: 当日の日報（未生成なら前提条件の状態表示）、Markdown 本文の表示、「コピー」ボタン、「再生成」ボタン、過去日報の一覧
- **コピー操作のフィードバック**: 成功時は「コピーしました」を一時表示する。`navigator.clipboard` が失敗した場合（権限拒否・非セキュアコンテキスト等）はエラーメッセージを表示し、**日報本文を全選択した状態のテキスト領域**を出して手動コピーへ退避できるようにする（再試行はコピーボタンの再押下）。成功・失敗の通知は `role="status"` / `role="alert"` を付け、キーボード操作でも結果が分かるようにする

## クリティカル設計決定

> セキュリティ・機密データ・外部連携・DBスキーマ等のクリティカル領域について、要件定義時に決定した方針を記録する。後続の `feature-implementer` はこの決定に従い、独自判断で逸脱しない。

### DB スキーマ（daily_reports テーブル新設）

- **採用案**: マイグレーション version 3 として以下を追加する。1日1行・再生成は同日行の UPSERT（上書き）

```sql
CREATE TABLE IF NOT EXISTS daily_reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL UNIQUE,           -- ローカル日付キー（toDateKey 形式）
  content TEXT NOT NULL,               -- 日報 Markdown 全文
  evening_session_id INTEGER NOT NULL REFERENCES sessions(id),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- **理由**: 過去日報の見返し（オーナー決定 2026-08-14）と、将来の toB 共有機能の土台になる。日付 UNIQUE ＋上書きは履歴管理を持たない最小構成（KISS）
- **代替案**:
  - 保存せず都度生成 — 見返し不可のため却下（オーナー決定）
  - 世代管理（append-only の versions テーブル）— 再生成履歴を参照するユースケースが現状無いため YAGNI で却下
- **影響範囲**: `server/src/db/migrate.ts`（`LATEST_VERSION` を 3 へ）、新設の `server/src/reports/`。既存テーブルの変更は無し

## 機能全体の設計

### アーキテクチャ決定

- 生成フローは「収集 → 値の抽出 → レンダリング → 保存」の4段とし、`server/src/reports/` の生成サービスに集約する:
  1. 収集: 当日のタスク・activity_events・夕会メッセージ・決定を SQLite から読む（純粋なデータ取得）
  2. 値の抽出: 夕会メッセージを LLM に渡し「報告の要点」「ボスの講評」「翌日への持ち越し」の3値を得る。失敗・タイムアウト・形式不正なら3値なしとして次段へ進む
  3. レンダリング: 収集データ＋（あれば）3値を**単一のレンダラー関数**に渡して「日報テンプレート」の Markdown を組み立てる（純粋関数。LLM を介さないため構造は決定的）。3値が無い場合はフォールバックの注記1行を出す
  4. 保存: `daily_reports` へ UPSERT
- レンダラーが純粋関数であることにより、構造に関する受入基準（表題・見出し順・チェックボックス記法・活動記録の算出）は LLM を介さずユニットテストできる
- 夕会終了フック: `POST /api/sessions/:id/end` が夕会セッションを終了した後に生成サービスを best-effort で呼ぶ（失敗してもセッション終了は成功。エラーはサーバーログのみ）
  - **初回終了時のみ実行する**: `endSession` は冪等で、終了済みセッションに再度呼んでも既存行を返し 200 になる。フックは `ended_at` が `NULL` から値に変わった**初回の遷移でのみ**発火させる（再終了の呼び出しで LLM 呼び出しと UPSERT が再実行されないようにする。初回終了と再終了を区別するテストを置く）
  - **実行境界**: フックはリクエスト内で**同期実行**するが、(a) セッション終了の DB 更新を先に確定させ、(b) 生成には終了 API 用の上限時間（既定 20 秒。LLM 呼び出しの上限とは別に終了 API の応答遅延を抑えるための値）を設ける。上限超過・失敗時はフォールバック日報を保存し、いずれの場合も終了 API は 200 を返す（非同期のバックグラウンド実行はローカル単一ユーザーでは複雑さに見合わないため採らない）
- 前提条件チェック（当日の夕会終了済みか＋ユーザー発言1件以上）は生成サービスの入口で行い、自動生成・手動再生成の両経路で共通化する
- **夕会の1日1回制限の原子性**: 「当日（ローカル日付）に type=evening が存在しないこと」の検査と INSERT を**単一の書き込みトランザクション**（better-sqlite3 の `db.transaction`）で行い、競合時は 409 を返す。`sessions` テーブルにローカル日付の一意制約カラムを追加する変更は行わない（検査と挿入をトランザクションで囲めば単一プロセス・単一ライターの SQLite では十分なため。DB スキーマ変更は `daily_reports` の追加のみに留める）
- 同時実行の排他制御は行わない（MVP スコープ外・オーナー決定 2026-08-14）: 自動生成と手動再生成が重なった場合は `daily_reports` の UPSERT の後勝ちで上書きされることを許容する

### 実装計画（チケット分解の見通し）

1. スキーマ + 収集・生成サービス + テンプレートフォールバック（server）
2. LLM 文章化 + 夕会終了フック + API ルート（server）
3. 日報ビュー + コピー/再生成 UI（web）

最終的な分解は `/create-ticket` で行う。

## 受入基準

- [ ] **ユーザー発言が1件以上ある**夕会セッションを終了すると、当日の日報が `daily_reports` に保存され、日報ビューで表示・クリップボードコピーができる
- [ ] 当日の夕会セッションが終了していない状態、またはユーザー発言が0件のまま終了した状態では、`POST /api/reports/generate` が 409（`code: evening_session_required`）を返し、日報ビューに「夕会を完了すると日報を生成できます」という状態表示が出る（日報は生成されない）
- [ ] 当日に夕会セッションが既に存在する状態で夕会セッションの作成を要求すると、セッション作成 API が 409（`code: evening_session_already_exists`）を返す（朝会・随時セッションの作成は従来どおり成功する）。検査と INSERT は単一トランザクションで行う
- [ ] クリップボードコピーが失敗した場合にエラーが表示され、日報本文を全選択したテキスト領域から手動コピーできる（成功時は「コピーしました」の一時表示）
- [ ] 生成された日報が「日報テンプレート」の固定構成に従う: 表題 `# 日報 YYYY-MM-DD（曜）`、セクション見出し「本日のタスク」「活動記録」「夕会サマリ」（および決定ログがある日は「決定事項」）が定義順に存在し、完了タスクが `- [x] タスク名`・進行中タスクが `- [ ] タスク名（進行中）` で記載され、未着手・中止タスクが含まれない（構造はレンダラー（純粋関数）のユニットテストで検証する）
- [ ] 23:50 開始・翌 00:30 終了の夕会で生成した日報の `date` と表題が**開始日**になり、集計対象のタスク・activity_events も開始日のローカル暦日の範囲で選ばれる（日付境界のテスト）
- [ ] 休憩イベントの対応付けが規則どおり決定的である: 複数の休憩、`break_end` の無い未復帰の休憩（夕会 `ended_at` まで計上）、対応する `break_start` の無い `break_end`（無視）、同一 `created_at` のイベント（`id` 昇順で順序が一意）、**日付をまたぐ休憩（23:55 開始・翌 00:05 終了・夕会は翌 00:30 終了 → 10 分として計上）**の各ケースで休憩回数・合計時間が期待値になる
- [ ] 動的値（タスク名・決定の `content`・LLM の3値）に改行や行頭の Markdown 記号が含まれても日報の固定構造が壊れない（1行へ正規化され、行頭記号がエスケープされる）
- [ ] 終了済みの夕会セッションに対して終了 API を再度呼んでも、日報の再生成（LLM 呼び出しと UPSERT）が走らない（初回の `ended_at` 遷移時のみフックが発火する）
- [ ] 再生成ボタンで同日分が上書きされ、`GET /api/reports` の一覧に同一日付が重複しない
- [ ] LLM 呼び出しを失敗させた場合でも、テンプレートフォールバックの日報が保存され、「夕会サマリ」セクションが固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみで構成される（報告の要点・ボスの講評・翌日への持ち越しの3項目は含まれない）
- [ ] 持ち越し事項の無い夕会の場合、「翌日への持ち越し」欄に「なし」と出力される（LLM をモックし「持ち越しなし」相当の応答を返させて、テンプレートへの反映のみを検証する。実 LLM の抽出精度は検証対象外）
- [ ] 「活動記録」の着手時刻・休憩回数・休憩合計時間が、`activity_events` から日報テンプレートの定義どおりに算出される（イベントが無い項目は「着手: なし」「休憩: なし」となる）
- [ ] 過去日付の日報を一覧から選択して閲覧できる
- [ ] 日報生成が失敗しても夕会セッションの終了 API は成功する
