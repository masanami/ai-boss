# 日報生成

## 概要

夕会セッションの完了を前提条件として、当日のタスク実績・チェックイン記録・夕会での報告とボスの評価から Markdown 日報（本仕様の「日報テンプレート」に従う固定構成）を自動生成し、アプリ内で表示・クリップボードコピー・保存（見返し）できるようにする。生成物はオーナーの記録リポジトリ work-record へそのまま貼り付けて利用できる。

## 背景・目的

- オーナーは現在、別リポジトリ work-record に日々のタスク一覧・実施記録・日報メモを手で書いている。ai-boss は日中の実態（タスクの完了/未完了、チェックイン・休憩、夕会での報告とボスの評価）を既に自動収集しており、日報を「手で書く」作業を「生成して確認し、work-record へ貼り付ける」作業に置き換えられる。
- 役割分担の方針（future-ideas.md「外部ツール連携によるタスク取り込み」で確立）: 計画・恒久記録の層は外部（work-record）、実行規律の層は ai-boss。日報生成はその間を埋める ai-boss → 外部への一方通行の出力である。
- **将来の toB 展開の布石（オーナー構想・2026-08-14）**: 生成した日報を実在の上司へ共有するサービス展開を見据える。その際「AI ボスとの壁打ち（夕会での報告・対話）を経ないと日報を生成できない」という製品制約によって、AI との振り返り対話を利用者に強制する。本機能は MVP からこの制約（夕会完了の前提条件）を体現する。

## ユーザーストーリー

自己管理が苦手な個人ワーカーとして、夕会でボスに一日の報告をするだけで日報 Markdown が自動生成される仕組みを使って、日報を手で書く作業を無くしつつ、記録リポジトリ（work-record）への蓄積を続けたい。

## 機能要件

- [ ] 夕会セッションを終了すると、当日（ローカル日付）の日報が自動生成され DB に保存される
- [ ] **夕会完了の前提条件（壁打ち強制）**: 「当日の夕会セッションが終了済みで、かつそのセッションにユーザーの発言メッセージ（role=user）が1件以上ある」場合のみ日報を生成できる。満たさない場合、生成 API はエラーを返し、UI は「夕会を完了すると日報を生成できます」という状態表示を行う（無言のままセッションを終了しても日報は生成されない — 対話を経ることを強制する製品制約・オーナー決定 2026-08-14）
- [ ] **夕会は1日1回**: 当日（ローカル日付）に夕会セッションが既に存在する場合、新たな夕会セッションは作成できない（セッション作成 API が 409 を返す。オーナー決定 2026-08-14）。夕会をやり直したい場合は既存の当日夕会セッションで会話を続け、日報を再生成する。朝会・随時セッションの挙動は変更しない
- [ ] 日報は下記「日報テンプレート」の固定セクション構成に従う（含める内容もテンプレートで定義する）
- [ ] 日報ビュー（画面）で当日の日報を表示し、クリップボードへコピーできる
- [ ] 過去の日報を一覧から選択して閲覧できる
- [ ] 手動の再生成ボタンを提供する。再生成は同日分を上書きする（前提条件は自動生成時と同じ）
- [ ] LLM 呼び出しが失敗した場合はタスク実績・チェックイン記録の機械整形によるテンプレートフォールバックで日報を生成する。フォールバック時の「夕会サマリ」セクションは固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみとし、3項目（報告の要点・ボスの講評・翌日への持ち越し）は出力しない（夕会完了の前提条件はフォールバック時も維持する）

### 日報テンプレート

生成する日報は次の固定構成とする。work-record のメモ書きよりフォーマルな体裁とする（オーナー決定 2026-08-14）。「決定事項」はデータが無い日はセクションごと省略する。それ以外のセクション見出しと順序は固定。

```markdown
# 日報 2026-08-14（金）

## 本日のタスク

- [x] タスクA
- [ ] タスクB（進行中）

## 活動記録

- 着手: {当日最初の task_start の時刻}
- 休憩: {休憩回数}回（合計 {休憩合計時間}分）

## 夕会サマリ

- 報告の要点: {夕会での報告内容の要約}
- ボスの講評: {ボスの評価コメントの要約}
- 翌日への持ち越し: {持ち越し裁定の要約。無ければ「なし」}

## 決定事項

- {当日の決定ログの内容}
```

- 表題は `# 日報 YYYY-MM-DD（曜）`（曜日は漢字1文字）とする
- 「本日のタスク」に載せるのは次の2種のみとする（オーナー決定 2026-08-14）: **完了タスク** = `completed_at` が当日（ローカル日付）の done タスク。**進行中タスク** = 生成時点で status が in_progress、かつ当日の `activity_events`（type が `task_start` または `task_update` で `task_id` が当該タスク）が1件以上あるもの（当日に動きの無い長期継続タスクは載せない）。未着手（todo）・中止（dropped）のタスクは日報に含めない（中止の経緯が重要な日は夕会サマリ・決定事項に現れる。「中止」は既存 UI のステータス表示ラベルに合わせた表記）
- タスクは完了を `- [x]`、進行中を `- [ ]（進行中）` で表す。優先度マーク（⭐️ 相当）は付けない（⭐️ は実施前の優先度付けに使う記号であり、実績報告である日報には不要 — オーナー決定 2026-08-14）
- 「活動記録」の数値の定義: 着手は当日最初の `task_start` イベントの時刻、休憩回数は当日の `break_start` イベント件数、休憩合計時間は各 `break_start` から対応する `break_end`（未復帰なら夕会終了時刻）までの差の合計（分単位・切り捨て）
- 「活動記録」でイベントが無い項目は行全体を固定文字列にする: `task_start` が無い日は `- 着手: なし`、`break_start` が0件の日は `- 休憩: なし`（「0回（合計0分）」とは出力しない）
- 「決定事項」の対象は、当日（ローカル日付）に記録された全セッション（朝会・随時・夕会）由来の決定のうち `status = active` のもの。作成日時の昇順で、`content` のみを1件1行の箇条書きにする（`rationale` は含めない）
- LLM が抽出する項目（報告の要点・ボスの講評・翌日への持ち越し）の内容の正確性は、本仕様の受入基準・自動テストの対象外とする。自動テストで検証するのは構造（表題・セクション見出し・チェックボックス・固定文言）のみ

## 非機能要件

- ローカルファースト（不変制約）: 日報の保存はローカル SQLite のみ。外部送信は生成時の Claude API への推論リクエストのみ。work-record への反映（貼り付け・コミット）はユーザーの手動操作とする
- 夕会終了の応答性: 日報の自動生成が失敗してもセッション終了自体は成功させる（best-effort。既存の「通知文生成失敗でも通知は送る」と同じ契約）
- 日付の扱いはローカル日付キーで統一し、テストはタイムゾーン非依存に書く（既存 `toDateKey` / `isSameLocalDay` のパターンに従う）

## 技術的な制約・方針

- 使用技術: 既存スタックのまま（Hono + better-sqlite3 / React）。新規依存の追加はクリップボードコピー（`navigator.clipboard`、依存追加なし）を含め不要
- 変更対象:
  - `server/src/db/migrate.ts`（マイグレーション version 3）
  - `server/src/reports/`（新設: リポジトリ・生成サービス・ルート）
  - `server/src/sessions/`（夕会終了時の自動生成フック、夕会セッション作成の1日1回制限）
  - `server/src/boss/persona-prompt.ts`（日報生成用の purpose 追加）
  - `web/src/`（日報ビュー・ナビ項目の追加）
- 既存コードとの関係:
  - 入力データは `tasks` / `activity_events` / `sessions`・`messages`（夕会の会話）/ `decisions` を読み取り専用で参照する
  - Issue #96（セッション要約）とは独立に実装可能: 日報生成は夕会セッションの会話メッセージを直接読む。#96 実装後に要約を再利用する最適化は任意
  - LLM 呼び出しは既存の `server/src/llm/claude-client.ts`（`api` / `claude-code` 両バックエンド対応）を使う。日報本文の文章化は LLM（既存のボス人格プロンプト生成器の purpose 追加）で行い、「報告の要点」「ボスの講評」「翌日への持ち越し」は夕会セッションの会話メッセージから LLM が抽出する（持ち越しを表す構造化データは持たない）

## 画面・API設計

### API

| メソッド/パス | 動作 |
|---|---|
| `GET /api/reports` | 日報一覧（date と作成・更新日時のみ）を新しい順で全件返す（ページネーションなし・MVP スコープ） |
| `GET /api/reports/:date` | 指定ローカル日付の日報本文を返す。無ければ 404 |
| `POST /api/reports/generate` | 当日の日報を生成して保存し、本文を返す。「当日の夕会セッションが終了済みで、かつユーザー発言（role=user）が1件以上ある」を満たさなければ 409 を返す |

- 夕会終了時の自動生成はサーバー内部で `POST /api/reports/generate` と同じ生成サービスを呼ぶ（HTTP を経由しない）

### 画面

- ナビゲーションに「日報」を追加
- 日報ビュー: 当日の日報（未生成なら前提条件の状態表示）、Markdown 本文の表示、「コピー」ボタン、「再生成」ボタン、過去日報の一覧

## クリティカル設計決定

> セキュリティ・機密データ・外部連携・DBスキーマ等のクリティカル領域について、要件定義時に決定した方針を記録する。後続の `feature-implementer` はこの決定に従い、独自判断で逸脱しない。

### DB スキーマ（daily_reports テーブル新設）

- **採用案**: マイグレーション version 3 として以下を追加する。1日1行・再生成は同日行の UPSERT（上書き）

```sql
CREATE TABLE IF NOT EXISTS daily_reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  date TEXT NOT NULL UNIQUE,           -- ローカル日付キー（toDateKey 形式）
  content TEXT NOT NULL,               -- 日報 Markdown 全文
  evening_session_id INTEGER NOT NULL REFERENCES sessions(id),
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
);
```

- **理由**: 過去日報の見返し（オーナー決定 2026-08-14）と、将来の toB 共有機能の土台になる。日付 UNIQUE ＋上書きは履歴管理を持たない最小構成（KISS）
- **代替案**:
  - 保存せず都度生成 — 見返し不可のため却下（オーナー決定）
  - 世代管理（append-only の versions テーブル）— 再生成履歴を参照するユースケースが現状無いため YAGNI で却下
- **影響範囲**: `server/src/db/migrate.ts`（`LATEST_VERSION` を 3 へ）、新設の `server/src/reports/`。既存テーブルの変更は無し

## 機能全体の設計

### アーキテクチャ決定

- 生成フローは「収集 → 文章化 → 保存」の3段とし、`server/src/reports/` の生成サービスに集約する:
  1. 収集: 当日のタスク・activity_events・夕会メッセージ・決定を SQLite から読む（純粋なデータ取得）
  2. 文章化: 収集データを LLM に渡し「日報テンプレート」に従う Markdown を生成。失敗時はテンプレートフォールバック（機械整形）
  3. 保存: `daily_reports` へ UPSERT
- 夕会終了フック: `POST /api/sessions/:id/end` が夕会セッションを終了した後に生成サービスを best-effort で呼ぶ（失敗してもセッション終了は成功。エラーはサーバーログのみ）
- 前提条件チェック（当日の夕会終了済みか）は生成サービスの入口で行い、自動生成・手動再生成の両経路で共通化する
- 同時実行の排他制御は行わない（MVP スコープ外・オーナー決定 2026-08-14）: 自動生成と手動再生成が重なった場合は `daily_reports` の UPSERT の後勝ちで上書きされることを許容する

### 実装計画（チケット分解の見通し）

1. スキーマ + 収集・生成サービス + テンプレートフォールバック（server）
2. LLM 文章化 + 夕会終了フック + API ルート（server）
3. 日報ビュー + コピー/再生成 UI（web）

最終的な分解は `/create-ticket` で行う。

## 受入基準

- [ ] 夕会セッションを終了すると、当日の日報が `daily_reports` に保存され、日報ビューで表示・クリップボードコピーができる
- [ ] 当日の夕会セッションが終了していない状態、またはユーザー発言が0件のまま終了した状態では、`POST /api/reports/generate` が 409 を返し、日報ビューに「夕会を完了すると日報を生成できます」という状態表示が出る（日報は生成されない）
- [ ] 当日に夕会セッションが既に存在する状態で夕会セッションの作成を要求すると、セッション作成 API が 409 を返す（朝会・随時セッションの作成は従来どおり成功する）
- [ ] 生成された日報が「日報テンプレート」の固定構成に従う: 表題 `# 日報 YYYY-MM-DD（曜）`、セクション見出し「本日のタスク」「活動記録」「夕会サマリ」（および決定ログがある日は「決定事項」）が定義順に存在し、完了タスクが `- [x]`・進行中タスクが `- [ ]（進行中）` で記載され、未着手・中止タスクが含まれない
- [ ] 再生成ボタンで同日分が上書きされ、`GET /api/reports` の一覧に同一日付が重複しない
- [ ] LLM 呼び出しを失敗させた場合でも、テンプレートフォールバックの日報が保存され、「夕会サマリ」セクションが固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみで構成される（報告の要点・ボスの講評・翌日への持ち越しの3項目は含まれない）
- [ ] 持ち越し事項の無い夕会の場合、「翌日への持ち越し」欄に「なし」と出力される（LLM をモックし「持ち越しなし」相当の応答を返させて、テンプレートへの反映のみを検証する。実 LLM の抽出精度は検証対象外）
- [ ] 「活動記録」の着手時刻・休憩回数・休憩合計時間が、`activity_events` から日報テンプレートの定義どおりに算出される（イベントが無い項目は「着手: なし」「休憩: なし」となる）
- [ ] 過去日付の日報を一覧から選択して閲覧できる
- [ ] 日報生成が失敗しても夕会セッションの終了 API は成功する
