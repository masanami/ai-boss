# ボスの返信を平文で出す（HTML タグの混入対策）

## 概要

ボスの応答に HTML タグや Markdown 記法が混ざり、`white-space: pre-wrap` ＋ JSX 補間の描画でそれらが**文字としてそのまま画面に出る**問題に対処する（#439）。対策は 2 層で、**(1) 通常チャット（`purpose="chat"`）のシステムプロンプトへ「HTML タグ・Markdown 装飾を使わず平文で書く」指示を積む**、**(2) server 側に HTML タグを落とす純粋関数を新設し、応答の送出／読み出し境界へ適用する**。**保存する `messages.content` は書き換えない**（LLM の生出力をそのまま残す）。

**HTML は (1)+(2) の 2 層で覆い、Markdown は (1) の 1 層のみで覆う**（Markdown を表示側で機械的に剥がすと正当な `**`・行頭 `- `・`1. ` を壊すため）。この非対称は意図的であり、下記「対策の層構成と LLM 依存範囲」に明記する。

**S1 は出荷済み**（PR #467・2026-09-10 マージ。子 Issue #459 / #460 / #461 / #462）。残るスライスは次の 2 本で、**2026-09-20 にコード読解にもとづいて要否を判定した**（初版が予定していた「S1 出荷後のデータの実測にもとづく判定」は実行不能と判明した。下記「S2 / S3 の要否判定（2026-09-20）」）。

- **S2**: 会話履歴をプロンプトへ写す `toClaudeMessages` で、ボスの過去発言を正規化する。**根拠は「表示と履歴の一致」であり、初版が置いていた few-shot 仮説ではない**（下記「保存 `content` がプロンプトへ戻る経路」）
- **S3**: `purpose="notification"` へ Markdown 装飾を使わない旨を追記する。**通知 purpose の Markdown は現状 0 層**である（下記「対策の層構成と LLM 依存範囲」）

## 背景・目的

> **本節は Issue #439 起票時点（S1 出荷前）の状態の記録である。** 行番号・「チャットには形式指示が無い」という記述は当時のもので、S1 出荷後の `main` には `CHAT_PLAIN_TEXT_INSTRUCTION`（`persona-prompt.ts:651-655` → `:772`）が入っている。**`purpose="notification"` が長さのみを指示している点は 2026-09-20 時点でも変わっておらず**（`persona-prompt.ts:736-739`）、それが S3 の対象である。

チャットのボス応答は `web/src/ChatView.tsx:213` が `<p className="chat-message-content">{entry.content}</p>` として描画する。JSX の文字列補間は React がエスケープするため **HTML として解釈されることはなく、タグが文字として画面に出る**（`dangerouslySetInnerHTML` は `web/src` 全体で 0 件）。CSS は `.chat-message-content { white-space: pre-wrap }`（`ChatView.css`）で改行と連続空白だけが保持される。

一方、**チャット応答の出力形式を制約する指示がシステムプロンプトに無い**。`buildPersonaPrompt`（`server/src/boss/persona-prompt.ts:612-670`）が形式に触れるのは次の 2 経路だけである。

- `purpose="notification"` → 「要点を絞り、短く簡潔な文章にすること」（**長さのみ**。形式の指定は無い）
- `purpose="daily-report"` → `DAILY_REPORT_INSTRUCTION`「各値は平文の簡潔な文章とし、Markdown の見出し・箇条書き記号・装飾は使わないこと」

`purpose="chat"` の分岐（`persona-prompt.ts:655-668`）が積むのは `MENTORING_FLOW_INSTRUCTION` / セッションフロー指示（朝会・夕会）/ `TASK_ESTIMATE_CONFIRMATION_INSTRUCTION` の 3 つで、**出力形式の指示は 1 つも無い**。同型の平文指示は夕会要約 `submit_evening_summary`（`server/src/reports/evening-summary-tool.ts:17`）にもあり、**日報・夕会要約では「平文で返せ」を明示しているのに通常のチャット応答だけ形式が野放し**という状態になっている。

Issue #439 の「HTML タグが生のまま表示される」という報告に対し、稼働中の実 DB を集計した。**本文は参照せず、件数と形式マーカーの出現数のみ**を取得している。

| `messages` のうち HTML タグらしき文字列（`*<*>*`）を含む行 | **0 件** |
| `decisions`（4 件）のうち HTML タグらしき文字列を含む行 | **0 件** |

**この実測から言えること**: 入手できたデータの範囲では**生の HTML タグは 1 件も観測されず、Markdown 記法は boss 発言の約 2/3 に出現している**。`white-space: pre-wrap` ＋ JSX 補間では `**強調**` はそのまま文字として見えるため、**現に観測できる症状は Markdown が生で出ていること**である。

**この実測の限界（重要）**: 集計対象 DB の**最終書き込みは 2026-09-05、Issue #439 の起票は 2026-09-10** である。**報告のきっかけになった応答そのものがこの DB に入っている保証はない。** したがって本仕様は「HTML は発生しない」とは述べない。正確な記述は「**入手できたデータの範囲では HTML は観測されなかった**」であり、HTML 対策（正規化層）は**症状が確認できていない事象への保険**として位置づける。この位置づけが、後述の判定方式（許可リスト）と処理内容（除去・改行置換）の選択理由になっている。

## クリティカル設計決定

### 判定方式: 許可リスト（既知の HTML タグ名にのみ一致）

- **採用案**: `<` ＋ 任意の `/` ＋ **許可リストに載った小文字のタグ名** ＋ 任意の属性 ＋ 任意の `/` ＋ `>` に一致したものだけを対象にする。許可リストは次の 2 群（この集合は仕様として固定し、追加は表への 1 行追加で足りる）。
  - **ブロック境界タグ**: `br` `p` `div` `li` `ul` `ol` `h1` `h2` `h3` `h4` `h5` `h6` `tr` `hr` `table` `blockquote` `pre`
  - **インラインタグ**: `strong` `em` `b` `i` `span` `code` `a` `td` `th`
- **理由**:
  1. 実測で HTML は 0 件であり、**この層は保険**である。保険のために正当な文章を壊すのは損失が勝つ
  2. **包含側・除外側をどちらも有限に列挙できる**ため、両方向を受入基準としてテストで固定できる。このリポジトリの規律は「担保はテストが持つ」であり、担保できない約束は受入基準に書けない
  3. LLM が出す HTML は既知タグにほぼ限られる
- **代替案**: 汎用正規表現 `<\/?[a-zA-Z][^>]*>` で「タグらしきもの」を全部対象にする案。未知タグも覆えるが、**ボス自身がプレースホルダ記法を使う場面（例: 「`<タスク名>` の形式で報告しろ」）を壊す**。除外側が「壊れないことを祈る」形にしかならず、テストで担保できないため却下した。未知タグを覆えない不利益は「タグが文字として見える」だけで安全性の問題ではなく、許容できる
- **タグ名の一致は小文字のみとする（大文字・混在は対象外）**: LLM が出す HTML は小文字であり、`<A>` `<B>` のような大文字のラベル表記を守れるため
- **残る誤爆の可能性（既知の限界）**: `a<b>c` のように、`<` ＋ 単文字タグ名（`a` `b` `i` `p` `u`）＋ `>` の形が正当な文章に現れると除去される。単文字タグを許可リストから外すと最頻出の `<p>` を取り逃すため、この形は**既知の限界として受け入れる**。Issue が名指しした 2 例（`x < 10`・`<タスク名>`）はいずれも保護される
- **影響範囲**: `server/src/lib/strip-html-tags.ts`（新規）のみに閉じる。既存モジュールは呼び出し 1 行が増えるだけ

### 一致したタグの処理: ブロック境界は改行 1 個へ、インラインは除去

- **採用案**: 上記のブロック境界タグ（開始・終了・自己終了形のいずれも）を**改行 1 個**へ置換し、インラインタグを**除去**する
- **理由**: `white-space: pre-wrap` が既に効いているため改行はそのまま反映され、「HTML が出ても壊れて見えない」という Issue の目的に直結する。**このコストは判定方式の決定に相乗りしており実質ゼロ**である——許可リスト方式を採る時点でタグ名の表は必ず持つので、各エントリに置換先を 1 つ足すだけで済む。したがって YAGNI が禁じる「使わないかもしれない一般化」には当たらない（後から読む人が KISS 違反と誤読しないよう、この理由をここに残す）
- **代替案**: 一律に除去する案（より単純）。ただし `<li>甲</li><li>乙</li>` が `甲乙` に潰れ、**壊れて見える状態が残る**ため Issue の目的を半分しか満たさない
- **置換・除去以外の加工は行わない**。とくに**結果のトリム（先頭・末尾の空白除去）や連続改行の畳み込みは行わない**。`<p>甲</p>` は `\n甲\n` になり、前後に空行が見えることを許容する。理由は 2 つ——(1) トリムは「応答全体でタグが 1 つでも見つかったか」という**大域的な条件**で発火するため、ストリーミングでは非単調になる（`   <br>本文` の場合、タグが届く前の delta では「一致 0 件＝トリムなし」として先頭の空白を送出済みにしてしまい、後から条件が成立しても撤回できない。後述「SSE 送出の制約」の前提と矛盾する）。(2) HTML は実測で観測されておらず、空行の見た目は「タグが文字として見える」に比べて実害が小さい
- **したがって正規化は位置ごとの局所変換のみで構成される**。これにより「入力の接頭辞に対する正規化結果は、入力全体に対する正規化結果の接頭辞になる」（末尾の未確定タグを除く）という単調性が成り立ち、ストリーミング送出と確定読み出しの一致（後述）が実現可能になる
- タグに一致する箇所が 1 つも無い入力は **1 文字も変更せずそのまま返す（恒等）**

### 保存 `content` の扱い: 書き換えず、送出／読み出し境界でのみ正規化する

- **採用案**: `messages.content` は LLM の生出力のまま保存し、**送出／読み出しの境界でのみ**正規化する
- **理由**: 生出力が残るため、後から「実際に何が出たのか」を調べられる（本仕様の実測がまさにその作業であり、この能力を失うと同種の調査が二度とできない）
- **代替案**: 保存時に正規化する案。プロンプト再投入も同時に解消できるが、LLM の生出力が失われるため却下した
- **Issue #439 本文が挙げた却下理由は誤りである**: 「保存を書き換えるとリライト機能（`select-rewrite-range.ts`）に影響する」とあるが、同ファイルは `content` を一切読まない（上記「現状の確証」#6）。採用理由は上記の再現性のほうである
- **影響範囲**: DB スキーマの変更なし。既存の `messages` 行に対する遡及的な書き換えも行わない

### 適用面: チャット 3 境界＋macOS 通知本文＋ダッシュボードのボスコメント（3 系統・5 箇所）

- **採用案**: 上表の「S1 で覆う」5 箇所へ適用する
- **理由**: Issue #439 の症状は「ボスの返信」＝チャットであり、macOS 通知とダッシュボードのボスコメントは同じ LLM 生テキストである。とりわけ **macOS 通知は React が介在しないため、web の表示層に正規化を置く案では覆えない**——正規化を server 側へ置く決定はこの事実が決め手になっている
- **代替案**: 決定ログ・作業ログも含める案。症状の報告が無く、実測でも `decisions` 4 件は HTML 0 件であるため S1 から外した。正規化は純粋関数なので後から面を足すのは安価である
- **正規化はボスの発言にのみ掛ける**: `GET /api/sessions/:id/messages` は `role: "user"` の行も返す。ユーザーの発言はオーナー自身が入力した文字列であり、正規化するとオーナーが書いた内容を勝手に書き換えることになるため対象外とする

### SSE 送出の制約: 累積文字列に掛け、未確定の末尾は保留する

- **前提**: `chat-messages-route.ts:317-323` の `onTextDelta` は**サーバ側も per-delta で送出**しており、`fullText += delta` の累積値が同じ関数内にある。送出済みの内容は撤回できない
- **採用案**: 正規化は**累積文字列に対して**行い、正規化結果のうちまだ送出していない部分を送る。ただし**タグの一部になりうる末尾（未閉じの `<` 以降）は送出を保留**し、タグが確定するか応答が終了した時点で確定させる
- **理由**: **per-delta 正規化は成立しない**。`<`／`p`／`>`／`甲` の順に届いた場合、per-delta では `<` と `p` を送出済みにしてしまい、`>` が届いてタグが確定しても撤回できない。保留を置かないと、ストリーミング中に見えたものと確定後に読み出したものが食い違う
- **代替案**: ストリーミング中は正規化せず確定時のみ正規化する案。ストリーム中にタグが見えて確定時に消える挙動になり、Issue の目的を満たさないため却下した。応答全体をバッファしてから一括送出する案は、ストリーミングの意味が失われるため却下した
- **保留の最悪ケースは応答終了時に解消する**（`<` が閉じないまま終わった場合、その末尾は終了時にそのまま送出される）。**フラッシュの経路を明示する**——LLM の生成が完了した時点で保留中のテキストが残っていれば、**追加の `text` イベントとして 1 回送出してから `done` を送る**（保留が無ければこの追加イベントは発生しない）。`done` の `content` に反映するだけでは、`text` イベントの断片を連結した結果が確定読み出しと食い違う
- **`done` イベントの `content` も正規化する**: `chat-messages-route.ts:394-397` は `insertMessage` の戻り値をそのまま `done` の payload として送っており、その `content` は**生の `fullText`** である。web 側（`use-chat.ts:398-400` の `onDone`）はこの payload をそのままタイムラインへ追加して `ChatView.tsx:213` で描画し続けるため、`text` イベントだけを正規化すると**応答完了の瞬間に未正規化の生テキストへ表示が差し替わる**。`done` の payload を組み立てる際に `content` を正規化した値へ差し替える（**DB へ挿入する行は生のまま**であり、「保存 `content` を書き換えない」決定と両立する）
- **中断・エラー時の SSE は対象外**: 中断パス（`chat-messages-route.ts:433-456`）は部分テキストを DB へ永続化するのみで、`content` を含む SSE イベントを送出しない（`error` イベントは定型文のみ）。したがって正規化の適用点にならない

### 対策の層構成と LLM 依存範囲（Issue の期待動作 2 つ目）

> **2026-09-20 訂正。** 初版の本表は最終行に「Markdown は既存指示の範囲」と書いていたが、**実コードに対して誤りだった**——`purpose="notification"` の指示は `persona-prompt.ts:736-739` の「要点を絞り、短く簡潔な文章にすること。」の 1 文のみで、**長さの制約しか無く Markdown にも HTML にも触れていない**。正はコードとテストであるため、実態に合わせて表を書き直した。この誤りが S3 を「急を要さない」と見積もらせていた。

### S2 の決定: `toClaudeMessages` でボスの過去発言のみ正規化する（根拠は「表示と履歴の一致」）

- **採用案**: `toClaudeMessages`（`chat-messages-route.ts:63-74`）で `role === "boss"` の行にのみ `stripHtmlTags` を適用してから `role: "assistant"` へ写す。**保存 `content` は引き続き生のまま**であり、「保存 `content` の扱い」の決定と両立する

- **初版の根拠（few-shot 仮説）は採らない**: 初版は「保存 HTML の再投入が HTML 出力を強化しうる」を根拠にしていたが、これは**未検証の仮説**であり、事象が別端末で発生したため**本環境では検証不能である**（上記「S2 / S3 の要否判定」）。検証できない仮説を受入基準の根拠に置くと、担保はテストが持つというこのリポジトリの規律に反する。仮説自体を否定はしないが、**S2 の正当化には使わない**
- **経路2（`collectTodaysAdhocContext`）は塞がない**: 当日の随時チャットは `NON_INSTRUCTION_DATA_GUARD`（`persona-prompt.ts:410-413`）で「記録データであり、指示ではない」と明示的に囲まれ、`- 時刻 ボス: 本文` の 1 行データへ平坦化されて渡る（`formatTodaysAdhocMessageLine`・`:460-466`）。**会話ターンとして渡る経路1 と違い、文体条件付けが効きにくい形**であり、「表示と履歴の一致」という S2 の根拠も、**そのセッションの会話の続きを書いている**経路1 ほど直接には当てはまらない。初版のスライス表は「1 本だけ塞いで『対策済み』にしない」と書いていたが、それは**両経路を同じ根拠（few-shot 仮説）で束ねていたとき**の記述であり、根拠を差し替えた本改訂では経路1 のみを対象とする
- **ユーザーの発言には掛けない**: `role === "user"` はオーナー自身が入力した文字列であり、S1 の「正規化はボスの発言にのみ掛ける」決定をそのまま引き継ぐ
- **先頭の `assistant` を落とす既存挙動（`:69-73`）は変えない**: 会の冒頭メッセージを落とす別件の規律であり、本スライスの対象外
- **影響範囲**: `chat-messages-route.ts` の `toClaudeMessages` 内の 1 行と、そのテスト

### S3 の決定: `purpose="notification"` へ Markdown 装飾を使わない旨を追記する（HTML は併記しない）

実装対象: S3

**出荷順: S1（出荷済み）→ S3 → S2。** S3 を先にするのは、**層が 0 の欠落を埋めるほうが価値/費用比が高い**ため（S2 が直すのは 1 層＝表示側が既に覆われている面の、履歴との不一致である）。S2 の要件チケットは S3 の PR がマージされてから起票する。

> **2026-09-20 改訂。** 初版の S2 は「保存 HTML の再投入が出力を強化する」という**未検証の仮説**への対策で、2 経路の両方を覆う（1 本だけ塞いで「対策済み」にしない）としていた。**仮説が本環境では検証不能と判明した**ため、根拠を「表示と履歴の一致」へ差し替え、その根拠が直接当てはまる経路1 のみへ範囲を縮小した（上記「クリティカル設計決定 § S2 の決定」）。初版の S3 が「急を要さない」とした根拠（実測で `notifications` 70 件の Markdown マーカーが 0 件）も、**別端末・起票 5 日前のデータであり論拠にならない**ため取り下げた。

## やらないこと

- **Markdown のレンダリング導入**（理由: Issue #439 本文自身が「レンダリングへ倒すなら別 Issue とし、本 Issue は『HTML が生で出る』の解消に閉じる」と切り分けを指定している）
- **Markdown 記法を表示側で機械的に剥がすこと**（理由: 正当な `**`・行頭 `- `・`1. ` を壊す。HTML と違い日常の文章と字面が区別できず、表示側で判別できる約束にならない）
- **既存 `messages` の遡及的な正規化**（理由: 保存値は LLM の生出力の記録であり、書き換えると「実際に何が出たのか」を後から調べられなくなる）
- **保存する `messages.content` の書き換え**（理由: 同上。Issue が挙げた却下理由〔リライト機能への影響〕は誤りだが、再現性という別の理由で保存は据え置く）
- **決定ログ（`record_decision`）・作業ログの表示への正規化の適用**（理由: 症状の報告が無く、実測でも `decisions` 4 件は HTML 0 件。純粋関数なので後から面を足すのは安価）
- **ボス人格・トーンの指示内容そのものの変更**（理由: 本件は出力形式の話であり、`TONE_DESCRIPTIONS` や応答の規律は対象外）
- **`web/` 配下への正規化の追加**（理由: macOS 通知を覆えないため server 側へ集約する決定を採った。両方に置くと同じ規則が二重管理になる）
- **DB スキーマの変更**（理由: 正規化は境界で行うため保存形式は変わらない）
- **当日の随時チャットの参考情報ブロック（`collectTodaysAdhocContext` 経路）の正規化**（理由: `NON_INSTRUCTION_DATA_GUARD` で囲まれた 1 行データへ平坦化されており、会話ターンとして渡る `toClaudeMessages` と違って文体条件付けが効きにくい。S2 の根拠である「表示と履歴の一致」も、そのセッションの会話の続きを書いている経路1 ほど直接には当てはまらない。上記「クリティカル設計決定 § S2 の決定」）
- **直近の決定（`formatDecisionSection`）・報告履歴（`formatSessionSummaryLine`）の正規化**（理由: 同種の経路だがスコープ拡大にあたるため本仕様では扱わない。とくに決定ログは S1 が意図的に非正規化面として固定済みで、そこへ正規化を入れると S1 の決定と衝突する。上記「未決の論点」論点1）
- **`purpose="notification"` への HTML 禁止指示の追記**（理由: 通知面の HTML は S1 の正規化で既に 1 層覆われており、S3 が埋めるのは 0 層の Markdown である。併記は S1 の機能要件の改訂にあたる。上記「未決の論点」論点2）

### S1: 正規化の純粋関数（出荷済み）

- [ ] 許可リストのブロック境界タグ（`br` `p` `div` `li` `ul` `ol` `h1`〜`h6` `tr` `hr` `table` `blockquote` `pre`）は、開始タグ・終了タグ・自己終了形のいずれも改行 1 個へ置換される
- [ ] 許可リストのインラインタグ（`strong` `em` `b` `i` `span` `code` `a` `td` `th`）は、開始タグ・終了タグ・自己終了形のいずれも除去される
- [ ] 許可リストのブロック境界タグは、属性を伴う形（例: `<p class="x">` `<div id="a">`）でも改行 1 個へ置換される
