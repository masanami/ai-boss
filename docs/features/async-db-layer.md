# DB 層を非同期 API へ移す（better-sqlite3 → plugin-sql・ADR 0005 改訂）

## 概要

リポジトリ層が受け取る DB を**非同期の DB ポート**に統一し、開発者用の版（Node・better-sqlite3）と製品版（Tauri 2・`@tauri-apps/plugin-sql`）の両方で同じ TS コードが動くようにする。接続プール越しでは同一接続が保証されないため、単一ライターの前提（ADR 0005 決定 5）を「**接続 1 本＋TS 側の直列化層**」で保ち直す。

## 背景・目的

- ADR 0011 決定 17（製品化）: DB は better-sqlite3（同期 API）から plugin-sql（非同期 API）へ移す。better-sqlite3 はネイティブ Node モジュールで WebView では動かないため、#579 S2（Tauri の器）はこの DB 層を前提にする（#579 の機能仕様 `docs/features/tauri-in-app-runtime.md` の「#580（DB 層）との境界」。本仕様の作成時点では PR #593〔ブランチ `docs/issue-579-tauri-in-app-runtime`〕にあり未マージ）。
- ADR 0011 決定 18（#590・PR #591）: 端末間の同期は一時中継＋暗号化で、衝突解決は端末側で行う。衝突解決の方式と同期向けのスキーマは、当初 #580 で扱う想定だったが、オーナーの決定で #595 へ移した（「オーナー・親の決定」）。
- 開発者用の版（オーナーが日常利用している Node 版）は移行中も移行後も better-sqlite3 のまま動き続ける。

## ユーザーストーリー

- 開発者として、製品版（Tauri）と開発者用の版（Node）で同じリポジトリ層・ルートのコードを使い、DB の実装だけを差し替えたい。
- オーナーとして、DB 層の作り替えの途中でも、開発者用の版を日常利用し続けたい。

## 機能要件（機能全体。スライスごとの範囲は「スライス」節）

- [ ] リポジトリ層・ルート・スケジューラ・マイグレーションは、非同期の DB ポートだけを通して DB を使う（S1）
- [ ] 開発者用の版は、非同期の DB ポートの better-sqlite3 実装で、現行どおり起動・動作する（S1。AC-15・AC-16）
- [ ] トランザクションはポートの `transaction` で張る（S1）
- [ ] トランザクションの中で例外が投げられると、その中の書き込みはロールバックされる（S1）
- [ ] トランザクションの実行中は、別の流れの DB 操作をトランザクションに混ぜない（S1）
- [ ] 製品版は、非同期の DB ポートの plugin-sql 実装で、同じリポジトリ層を動かす（S2）
- [ ] ADR 0005 の決定 1・5 と帰結の「複数端末からの同時書き込みは前提外」を、「クリティカル設計決定 6」の方向で書き換える（S2。文面は S2 の実装で具体が決まってから確定する）

## クリティカル設計決定

### 1. トランザクションの同一接続の保証（Q1・確定）

- **採用案（A）**: **接続を 1 本に固定し、TS 側の直列化層でトランザクションを張る**。
  - ドライバ（better-sqlite3 実装・plugin-sql 実装）の責務は「**1 本の接続の上で文を実行する**」ことだけにする。製品版は plugin-sql の Rust 側を fork し、プールの最大接続数を 1 にする（差分は `wrapper.rs` の `Pool::connect` を `PoolOptions::new().max_connections(1)` に替える程度。JS 側の API `@tauri-apps/plugin-sql` はそのまま使う）。
  - **fork は ADR 0011 決定 17 の範囲内とみなす**。理由: 決定 17 が決めたのは「非同期 API の `@tauri-apps/plugin-sql` へ移す」ことで、fork 後も JS 側は同じパッケージの API を使い、Rust 側の差分はプールの大きさの設定に限られるため。ADR 0011 は通知プラグインでも fork を手当てとして認めている（決定 14）。
  - **fork の成立性（ビルド・動作）は未検証**である。S2 の受入基準で確かめ、**成り立たなければ (C) 自前の Rust コマンドへ切り替える**（直列化層とポートの契約は変えない）。
  - 直列化層（TS・ドライバ非依存・両版で共有）が、非同期のロックで**DB 操作を 1 つずつ通す**。`transaction(fn)` はロックを取って `BEGIN IMMEDIATE`→`fn(tx)`→`COMMIT`（例外なら `ROLLBACK`）を行い、終わるまで他の流れの DB 操作を待たせる。入れ子の `tx.transaction(fn)` は `SAVEPOINT` で合成する（better-sqlite3 の現行の入れ子の意味を保つ）。
  - **`fn` の中では渡された `tx` だけを使う**。`fn` の中から外側のポートを呼ぶと、ロックを二重に取ろうとして待ち続ける（デッドロック）。移行でとくに間違えやすいのは、入れ子になる T2・T3（`checkins-routes` が `updateTask(db, …)` に外側の DB を渡している）である。`tx` の型をトップレベルのポートの型と区別できる形にするかどうかは実装で決める（軽微・可逆）。入れ子の箇所で `tx` を引き回していることは、コードレビューの確認項目にする。
  - **理由**: 9 箇所のトランザクションの中身（夕会 1 日 1 件の検査、変更の有無による `task_update` の記録。いずれも読み→判定→書き）を TS のまま両版で共有できる。1 本の接続でも await の間に別の流れの文が混ざることを実測で確かめたため、プールの大きさだけでなく直列化層が要る。直列化層はドライバに依存しないので、Node の vitest でトランザクションの意味を検証できる。`migrateToV4` の `PRAGMA foreign_keys` の切り替えも接続が 1 本なので成り立つ（プールのままだと別の接続にしか効かない）。
- **代替案**:
  - (B) トランザクションを Rust 側で実行する（9 箇所の本体を Rust コマンドへ移す。#576 README の提案）— 読み→判定→書きのロジックが Rust と TS（開発者用の版）に二重化する。#579 の決定「永続状態と DB 副作用は WebView 内の TS コアが受け持つ」とずれる。
  - (C) 自前の Rust コマンド（rusqlite か sqlx で接続 1 本を保持し、execute/select だけを出す）で plugin-sql を置き換える — fork の上流追従は要らないが、ADR 0011 決定 17 の字面から外れる。**fork が成り立たない場合の切り替え先**。
  - (D) 1 回の `execute` に `BEGIN; …; COMMIT;` を詰める — 条件分岐を含む T3・T5 が書けない。
  - (E) plugin-sql をそのまま使い、TS のロックだけで直列化する — 10 接続のプールでは `BEGIN` と後続の文が別の接続に乗りうる。スパイクで効いたのは偶然である。
- **影響範囲**: `server/src/db/`、トランザクションを張る 9 箇所、製品版の plugin-sql の fork（S2）。

### 2. 同期実行に頼っていた原子性の扱い（Q1 に付随・確定）

- **採用案**: 非同期化で割り込めるようになる「トランザクションの外で読み、その結果を根拠に中で書く」箇所は、**判定に使う読み出しもトランザクションの中へ入れる**。S1 の対象は T1〜T9 の周辺で実測した次の 5 箇所に固定する（新たな洗い出しはしない。トランザクションを張っていない読み→書きの箇所は S1 の対象外。「やらないこと」参照）。

  | 箇所 | トランザクションの前の読み出し | 非同期化で起きうること |
  |---|---|---|
  | T1 設定 | `resolveEffectiveWorkingHours`（保存済みの勤務時間の組） | `work_start` と `work_end` を別々の要求で並行に送ると、どちらも古い相方で検査され、開始が終了以後の組が保存される |
  | T2 `updateTask` | `findTaskById` の行に差分を重ねて行全体を UPDATE する | 同じタスクへ異なる項目の更新を並行に送ると、後に書いた側が古い行で上書きし、先の変更が消える |
  | T3 チェックイン | `findTaskById`・`isNewerThanLatestTransition` | 同じタスクへの `task_start` を並行に送ると、遷移が 2 回記録される |
  | T4 会議時刻 | `buildMeetingDefaults`（既定の時刻。削除か upsert かの判定と、遅延の上限〔`isAllowedMeetingTime`〕の判定に使う） | 既定の時刻の変更が判定と書き込みの間に入ると、古い既定の時刻で判定した上書きが書き込まれる |
  | T6 発言の書き直し | `findSessionById`（終了済みの検査）・`findMessageInSession` | 会の終了が判定と書き込みの間に入ると、終了済みの会へ書き直しが入る |

- **理由**: 現行の正しさは「await を挟まない」ことに依存しており（`checkins-routes.ts:158-163` のコメントが明記）、非同期化すると黙って壊れる。
- **代替案**: 何もしない — 単一利用者のため割り込みはまれだが、製品版では IPC を挟むため 1 操作ごとに割り込みの機会が生じる。

### 3. Node 版と Tauri 版の両立の形（Q2・確定）

- **採用案**: リポジトリ層を**非同期の DB ポートに統一**し、開発者用の版は better-sqlite3 を包む実装を使う（同期の結果を Promise で返す）。製品版は plugin-sql（fork）を包む実装を使う。ポートの口は `run`/`get`/`all`/`exec`/`transaction` の 5 つとし（「IF / API」）、better-sqlite3 固有の API（`prepare` の再利用・`pragma` の戻り値の形・`lastInsertRowid` の bigint）はポートに出さない。
- **移行中に Node 版を壊さない順番**: S1 は統合ブランチ（`feat/issue-<親Issue番号>`）で進め、`main` への昇格は S1 全体を 1 本で行う。非同期化は呼び出し元へ波及する（非同期の関数を呼ぶ関数も非同期になる）ため、統合ブランチ上でも子 PR ごとに開発者用の版の既存テストが合格する順（ポートと直列化層 → マイグレーション → 葉のリポジトリから呼び出し元へ）で分ける。
- **代替案**: 版ごとにリポジトリ層を持つ（同期版と非同期版）— DB を使う関数がすべて二重化し、DRY に反する。

### 4. マイグレーションの置き場所（ADR 0005 決定 4 を維持）

- **採用案**: 両版とも `migrate.ts`（`user_version`・版ごとのトランザクション）をポート経由で走らせる。plugin-sql のマイグレーション機能（`_sqlx_migrations`）は使わない。
- **理由**: 版の目印を 2 種類にしない。v4 のように `foreign_keys` をトランザクションの外で切り替える手順は、plugin-sql のマイグレーション機能では表せない。

### 5. 同期に向けたスキーマ（Q4 ★・オーナー決定）

- **採用案**: 本機能では**同期向けのスキーマ変更をしない**（オーナーの決定 (a)）。衝突解決の単位とスキーマの変更（端末をまたいで衝突しない ID・更新日時・墓標の要否と形）は #595 で決める。
- 本機能が守るのは、**ポートが ID を端末で生成する形を妨げないこと**だけである（`run` は挿入した行の ID を返せるが、呼び出し元が ID を指定して挿入することも妨げない）。
- **却下した案**: (ii) スキーマの準備だけ行う／(iii) 衝突解決まで行う — 衝突解決の単位が決まる前にスキーマを決めると手戻りになる。同期は #595 で要件から扱う。

### 6. ADR 0005 の改訂の方向（Q3・確定。改訂の本体は S2）

- **採用案**: ADR 0011 の帰結に従い、改訂の本体は S2（両版の実装がそろった時点）で行う。方向は次のとおり。
  - 決定 1: 「better-sqlite3 の同期 API・単一ライター」→「非同期の DB ポート越しに使い、ドライバは版ごと（開発者用: better-sqlite3／製品版: plugin-sql の fork。成り立たなければ自前の Rust コマンド）。**接続は 1 本**」
  - 決定 5: 「単一ライターの前提で、原子性は書き込みトランザクションで足りる」→「**単一ライターは接続 1 本＋TS の直列化層で保つ**。トランザクションはポートの `transaction` で張り、判定に使う読み出しもその中で行う」（決定 2 の規則を恒常的な設計決定へ昇格）
  - 帰結「複数プロセス・複数端末からの同時書き込みは前提外」→「端末内は単一ライターのまま。端末間の変更は同期の層（ADR 0011 決定 18・#595）が取り込む。衝突解決の方式は #595 の結論に従って書く」
- **代替案**: S1 で決定 1・5 を先に改訂する — S1 の時点では製品版のドライバが無く、ADR 0011 の帰結（実装で具体が決まってから改訂）に反する。

## 機能全体の設計

### アーキテクチャ決定

- `server/src/db/` に、非同期の DB ポート（型）・直列化層・better-sqlite3 実装を置く。製品版の plugin-sql 実装は S2 で足す（置き場所は #579 の「実行環境に依存しないコア」と「Node の周辺」の分け方に従う。better-sqlite3 実装は Node の周辺）。
- `createApp`・`startScheduler`・各ルートの工場関数は、ポートを受け取る。

### IF / API（ポートの契約・S1 で固定する）

- `run(sql, params)`: 書き込み文を実行し、`{ changes: number; lastInsertRowid: number }` を返す（名前は現行の better-sqlite3 の `.changes`・`.lastInsertRowid` を踏襲し、呼び出し元の差分を小さくする。`lastInsertRowid` は bigint ではなく number）。
- `get(sql, params)` / `all(sql, params)`: 行を読む（無ければ `undefined` / 空配列）。
- `exec(sql)`: パラメータの無い複数文を実行する（マイグレーション用）。`PRAGMA` の設定（`foreign_keys = ON/OFF`・`user_version = N`）も `exec` で行う。`PRAGMA` の値の読み出し（`user_version`・`foreign_key_check`）は `get` / `all` で行う。ポートに `pragma` 専用の口は設けない（plugin-sql には `pragma` の API が無く、両版で同じ形にするため）。
- `transaction(fn)`: 上記「クリティカル設計決定 1」の意味で `fn(tx)` を実行し、その戻り値を返す。`tx` はポートと同じ操作を持つ（入れ子の `transaction` を含む）。`fn` が投げた例外（拒否された Promise を含む）は、`ROLLBACK` とロックの解放を行った後、**同じ例外オブジェクトのまま**呼び出し元へ投げ直す（包み直さない・握りつぶさない）。
- パラメータは位置指定（`?`）に統一する（現行コードは名前付きを使っていない）。

### 実装計画（S1 のチケット分解の見通し）

1. ポート・直列化層・better-sqlite3 実装と、その契約テスト（ロールバック・例外の投げ直し・割り込み・入れ子）
2. マイグレーション（T8・T9）の非同期化
3. リポジトリ層とルートの非同期化（領域ごと。T2 と T3 は入れ子のため同じチケット）
4. 決定 2 の表の 5 箇所（T1・T2・T3・T4・T6）で、判定に使う読み出しをトランザクションの中へ移す（新たな洗い出しはしない。3 と同じチケットで行ってもよい）

## やらないこと

- 端末間の同期の実装（中継・暗号化・ペアリング・衝突解決）と、同期向けのスキーマ変更（端末をまたいで衝突しない ID・更新日時・墓標）（理由: オーナーの決定 (a)。#595 で扱う）
- 開発者用の版のスキーマ変更とデータ移行（理由: S1 はポートの差し替えだけを行い、オーナーの DB をそのまま開けることを保つ）

- 実行の仕組みの作り替え（Tauri の器・スケジューラ・通知）（理由: #579・#594 の範囲）
- Rust 通信層・BYOK・LLM プロバイダの抽象化・予約通知方式・バックアップと端末移行（理由: #581・#582・#585・#588 の範囲）
