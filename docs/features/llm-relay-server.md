# LLM 中継サーバー（プラン込み枠・利用量の計測と上限・既定モデルと推論原価）

> Issue #583。2026-09-28 に論点を確定した（★ はオーナーの決定、それ以外は親の決定。「決定」節）。

## 概要

製品版の既定の LLM の利用方式「料金プラン込み」で、アプリの推論要求を受けて事業者の API キーでプロバイダへ転送する **ai-boss の LLM 中継サーバー**を作る。中継はアカウントごとに利用量を計測し、上限で止める。推論内容は保存もログ出力もしない。既定のモデル（Haiku 系）の具体の ID は中継の設定で持ち、アプリのリリースなしに差し替えられるようにする（[ADR 0011](../adr/0011-productization-architecture.md) 決定 2・3・9、[ADR 0001](../adr/0001-local-only-data-boundary.md) 改訂の決定 3）。

## 背景・目的

- 事業者のキーは配布物に埋め込めない（抜き取られる）。プラン込み枠を提供するには中継が必須である（ADR 0011 決定 9・ADR 0002 改訂の決定 6）。
- 中継サーバーは推論内容（プロンプト・応答）を保存もログ出力もしない。中継が扱ってよいのは、推論をプロバイダへ転送することと、利用量の計測・制限に要る情報だけである（ADR 0001 改訂の決定 3）。
- クラウドが持つのはアカウント・ライセンス・利用量だけで、ライセンスと利用量は顧客ごとに分けて認可する（ADR 0011 決定 3）。アカウント・ライセンスの仕組みは #584 で作る。#584 は本機能の後に着手するため（#584「依存: 先行 #583」）、本機能は認証を仮の境界（認証のポート）で受ける。
- #582 の仕様（クリティカル設計決定 1）は「中継サーバーが同じ形式を話すなら、宛先を足すだけで同じ変換器を使える」としている。#581 の仕様（クリティカル設計決定 3）は「中継サーバーの宛先とライセンストークンの付与は、#583・#584 が宛先の表と保管のポートに 1 行ずつ足す」としている。本機能はこの 2 つの前提に乗る。
- 既定の低価格モデルの選定と、1 利用者あたりの推論原価の見積もりも本機能で行う（#575 の論点・#583 の本文）。

## ユーザーストーリー

- 製品版の利用者として、自分で API キーを用意しなくても、料金プランの範囲でボスとの対話・朝会・夕会を使いたい。
- 事業者として、利用者ごとの推論の利用量を計測し、プランの枠を超えた利用を止めたい（推論原価を料金プランの範囲に収めるため）。
- 事業者として、既定モデル（Haiku）の新版が出たときに、アプリを出し直さずに中継の設定変更だけで切り替えたい。
- 製品版の利用者として、自分の業務の内容（プロンプトと応答）が中継サーバーに保存されず、ログにも残らないでほしい。

### Anthropic の公式ドキュメントで確かめたこと（2026-09-28 に platform.claude.com を参照。実 API は呼んでいない）

- Haiku 4.5 の Claude API ID は `claude-haiku-4-5-20251001`、エイリアスは `claude-haiku-4-5`。
- **「最新の Haiku」を指す、バージョンをまたいで浮動するエイリアスは無い**。4.6 世代より前のモデルのエイリアスは同じ版の日付つき ID を指す便宜上のもの。4.6 世代以降は日付の無い ID がそれ自体で固定のスナップショットになる（Models overview の「Claude API alias」「Claude API ID」の注記）。このため本機能は、**中継の設定のモデル ID を差し替えて新版に追随する**設計にする（クリティカル設計決定 3）。
- Haiku 4.5 の退役は「2026-10-15 より前にはしない」。新版への切り替えを設定の差し替えで行えることが要る。
- Haiku 4.5 の thinking は Extended（`type: "enabled"` と `budget_tokens`）で、adaptive thinking と effort の指定には対応しない（effort は「Not supported」）。アプリのチャットは `thinking: { type: "adaptive" }` と `output_config.effort` を送るため、**中継がモデルの行に従って `thinking` と `output_config` を書き換える**（クリティカル設計決定 3）。
- 単価（1M トークンあたり）: Haiku 4.5 は入力 $1・出力 $5・キャッシュ読み出し $0.10。Sonnet 5 は入力 $2・出力 $10（Claude 4.7 以降の新しいトークナイザは同じ文で約 30% 多くのトークンになる。Haiku 4.5 は旧トークナイザ）。
- OpenAI（2026-09-28 に developers.openai.com の料金表を参照）: `gpt-6-luna` は入力 $0.10・出力 $0.50、`gpt-6-sol` は入力 $2・出力 $10。

## 推論原価の見積もり（前提つき）

### 1 日の呼び出し量（実コードからの推定）

日本語は 1 字 ≒ 1〜1.5 トークンとして換算した。文字数は実コードで数えたが、トークン数と「典型的な 1 日」の利用頻度は仮定である。

| 経路 | 契機（根拠） | 回数/日 | 入力トークン | 出力トークン |
|---|---|---|---|---|
| チャット | 1 メッセージごとに最低 1 回、ツールのループで最大 5 回。セッションの履歴を上限なしで毎回全部送る（`sessions/messages-repository.ts:57-65`）。ツール定義（約 3,300 字）を毎ラウンド送る | 11（朝会 3・夕会 3・随時 5 往復） | 約 59,000 | 約 3,300 |
| セッション要約 | 朝会・夕会の初回終了時だけ（`sessions/sessions-routes.ts:326-334`）。`maxTokens` 300 | 2 | 約 2,200 | 約 600 |
| 会議の開始文 | 朝会・夕会の作成時（`sessions/meeting-opening.ts:75-83`）。`maxTokens` 150 | 2 | 約 3,400 | 約 160 |
| ダッシュボードのひとこと | 暦日＋タスクの状態でキャッシュする（`dashboard/boss-comment-cache.ts`）。`maxTokens` 150 | 2 | 約 3,000 | 約 120 |
| 夕会の要約抽出 | 夕会の初回終了時（`sessions/sessions-routes.ts:349-351`）。ツール呼び出しを強制 | 1 | 約 2,650 | 約 300 |
| 通知文面 | 検知の発火ごと。ルールごとに 1 日 5 件まで（`detection/detection-types.ts:120`）。`maxTokens` 150 | 3（理論上の最大は約 30） | 約 3,780 | 約 180 |
| **合計（典型的な 1 日）** | | | **約 74,000** | **約 4,700** |

### 1 利用者あたりの月の推論原価（30 日換算・プロンプトキャッシュなし）

| モデル | 典型的な日 | 重い日（入出力とも 4 倍と仮定） |
|---|---|---|
| **`claude-haiku-4-5`（既定・決定 O1）** | **約 $0.098/日 → 約 $2.9/月** | 約 $0.40/日 → 約 $11.9/月 |
| `gpt-6-luna`（参考） | 約 $0.010/日 → 約 $0.3/月（reasoning のトークンは別途） | 約 $1.2/月 |
| `claude-sonnet-5`（参考） | 約 $0.195/日 → 約 $5.9/月（新しいトークナイザで +30% なら約 $7.6） | 約 $23.7/月 |
| `gpt-6-sol`（参考） | 約 $5.9/月 | 約 $23.7/月 |

- 原価の大半はチャットで、主な原因は「履歴を毎回全部送る」「ツール定義を毎ラウンド送る」「ツールのループが最大 5 ラウンド」の 3 つである。プロンプトキャッシュ（`cache_control`）は現行コードが使っておらず、見積もりにも含めていない。使えばチャットの入力の原価は大きく下がる見込みだが、本機能の範囲外とする（「やらないこと」）。
- この見積もりは、プランの上限値と価格帯を決める材料になる（決定 O2 は未決）。上限値は、重い日の原価を踏まえて設定の値で決める。

## 機能要件（機能全体。スライスごとの範囲は「スライス」節）

- [ ] 中継は、アプリの Anthropic Messages 形式の要求を、事業者のキーを付けてプロバイダへ転送する
- [ ] 中継は、アプリが指定したプラン込みの既定の依頼を、設定の既定モデルの ID に解決して転送する
- [ ] 設定の既定モデルを差し替えると、アプリの変更なしに転送先のモデルが変わる
- [ ] 中継は、許可リストに無いモデルへは転送しない
- [ ] 中継は、ストリーミングの応答を逐次アプリへ流す
- [ ] 中継は、アカウントごとに利用量を原価単位で記録する
- [ ] 中継は、1 日または 1 か月の上限に達したアカウントの要求を転送せずに拒否する
- [ ] 中継は、推論内容を保存もログ出力もしない
- [ ] 中継は、認証できない要求を転送しない
- [ ] アプリは、プラン込みの推論を中継経由で行う（S2）
- [ ] アプリは、中継の失敗（上限到達を含む）時に BYOK へ自動で切り替えない（S2。#582 の機能要件「別の課金経路へ自動で切り替えない」の検証はここで行う）
- [ ] 上限到達をアプリの画面で案内する（S2）
- [ ] 中継を実行基盤にデプロイし、利用量を永続化する（S3）
- [ ] 中継の認証を #584 のアカウント・ライセンスと結合する（S4）

## 非機能要件

- 機密データ: 中継はプロンプト・応答・ツールの入出力を保存しない・ログに出さない・エラーの応答や例外のメッセージにも含めない（ADR 0001 改訂の決定 3）。
- 秘密情報: 事業者のキーは中継の設定の秘密情報としてだけ持ち、応答・ログ・利用量の記録に出さない（ADR 0002 改訂の決定 6・7）。アプリの利用者のトークンもログに出さない。
- ストリーミング: 応答をまとめて溜めずに逐次流す（最初の差分がプロバイダから届いたら、応答の終わりを待たずにアプリへ流す）。
- 実行基盤の非依存: 中継のコアは Web 標準の API（`fetch`・`Request`・`Response`・`ReadableStream`）と Hono だけで書き、Node の組み込みを使わない（O4 の実行基盤を後から選べるようにする）。
- 外部送信: 中継の送信先はプロバイダ（設定の上流の URL）だけである（テレメトリ・分析のための送信を持たない）。

## クリティカル設計決定

### 1. アプリ → 中継の形式と要求の検査（Q1・親の決定）

- **採用案**: 中継は `POST /v1/messages` で **Anthropic Messages 形式**の要求を受ける。
  - 要求の JSON の最上位の項目は、許可リスト `model`・`max_tokens`・`system`・`messages`・`tools`・`tool_choice`・`thinking`・`output_config`・`stream` に限る。それ以外の項目（例: `mcp_servers`・`container`・`metadata`）があれば、転送せず 400 を返す。
  - `model` は、プラン込みの既定を表す固定の値（仮に `"ai-boss-plan-default"`。仮定 A2）だけを受ける。それ以外の値は転送せず 400 を返す（アプリはモデル ID を知らない。決定 O1）。
  - `max_tokens` は設定の上限（`maxTokensCap`）以下でなければならない。超えていれば、切り詰めずに転送せず 400 を返す。
  - `tools` の各要素は、アプリが定義する関数ツール（`type` が無いか `"custom"`）に限る。プロバイダ側で実行されるツール（`type` が `web_search_…` 等）が 1 つでもあれば、転送せず 400 を返す（追加課金のツールを枠の外で使わせないため・#582 のクリティカル設計決定 4 の旧決定 5 の読み替えと同じ考え方）。
  - 本文が JSON として解釈できないときも、転送せず 400 を返す。
  - 検査で拒否した要求は利用量を記録しない。
  - エラーの応答の本文は Anthropic の形（`{"type":"error","error":{"type":"…","message":"…"}}`）で返し、`message` は種類ごとの固定の文言にする（要求の中身を埋め込まない）。
- **理由**: #581 S2 の Anthropic の変換器がそのまま使え、中継に形式の変換を持たせずに済む（#582 のクリティカル設計決定 1 の想定どおり）。検査を許可リスト方式にすれば、プロバイダが項目を増やしても、中継が知らない項目は枠の外で使われない。
- **代替案**: 中継独自の中立な形式にして中継で変換する（変換器を二重に持つことになる）。項目を検査せず素通しにする（プロバイダ側で実行されるツールや巨大な `max_tokens` で枠が破られる）。`max_tokens` を上限へ切り詰める（アプリの意図と違う長さで黙って打ち切られる。拒否のほうが原因が見える）。
- **影響範囲**: `relay/` の要求の検査。S2 でアプリの `byok-anthropic` の変換器を中継の宛先でも使う。

### 2. 転送とストリーミング・中止の伝播（Q1・親の決定）

- **採用案**:
  - 上流（プロバイダ）への要求のヘッダは中継が一から組み立てる: `content-type: application/json`・`x-api-key`（事業者のキー）・`anthropic-version: 2023-06-01`（Rust の `ANTHROPIC_VERSION` と同じ値）。アプリから来たヘッダ（`authorization`・`x-api-key`・`anthropic-version`・`anthropic-beta` を含む）は上流へ渡さない。
  - 上流の応答は、ステータスと本文をそのままアプリへ返す（2xx 以外も、上流の本文を加工しない）。応答のヘッダは `content-type`・`retry-after`・`request-id` だけを通す。
  - ストリーミングの応答は、本文のバイト列を溜めずに逐次流しながら、並行して SSE を解釈し `usage` を読む（クリティカル設計決定 4）。
  - アプリが要求を中止した（接続を切った）ら、上流への要求を中止する（`AbortSignal` を伝える）。
  - 上流への接続が失敗したとき（応答が得られないとき）は 502 を返す。本文は固定の文言にする。
  - ストリーミングの本文を流し始めた後に上流との接続が切れたときは、ステータスを変えずにアプリへのストリームを終える（利用量はそれまでに届いた `usage` の値で記録する）。
  - 上流の URL・事業者のキーは設定で渡す。上流への送信は注入する `fetch` 相当の関数（上流のポート）で行い、テストはそれを模擬する。
- **理由**: 事業者のキーの付与を中継に閉じ、アプリ由来のヘッダでキーや API の版を差し替えられないようにする（#581 の `transport.rs` が呼び出し元の認証ヘッダを捨てるのと同じ規律）。上流のエラーの本文をそのまま返せば、アプリ側の既存のエラーの分類（`classifyByokAnthropicError`）がそのまま効く。
- **代替案**: 応答を全部受けてから返す（ストリーミングの体感が失われる）。上流のエラーを中継独自の形に作り替える（アプリ側に分類をもう 1 つ持つことになる）。
- **影響範囲**: `relay/` の転送部。

### 3. 既定モデルの解決とモデルの許可リスト（O1・★オーナーの決定）

- **採用案**: 中継の設定に**モデルの許可リスト**と**既定モデル**を持つ。
  - 許可リストの各行: モデル ID・原価単位の重み（入力・出力・キャッシュ読み出し・キャッシュ書き込みの 1M トークンあたり）・thinking の書き換え方・`output_config` の effort に対応するか。
  - 既定モデル（`defaultModel`）は許可リストのいずれかの行を指す。指さない設定では中継を組み立てられない（起動時に失敗する）。
  - 中継は、要求の `model`（プラン込みの既定の値）を設定の `defaultModel` のモデル ID に置き換えて転送する。
  - 中継は、転送前に、既定モデルの行に従って `thinking` と `output_config` を書き換える。Haiku 4.5 の行は adaptive thinking と effort に対応しないため、`thinking` を `{ "type": "disabled" }` にし、`output_config` の `effort` を取り除く（仮定 A4。`output_config` がほかの項目を持たなくなったら `output_config` ごと取り除く）。
  - Haiku の新版が出たら、中継の設定の許可リストに行を足し、`defaultModel` を差し替える。アプリのリリースは要らない。浮動するエイリアスは Anthropic に無いため使わない（「Anthropic の公式ドキュメントで確かめたこと」）。
  - 現時点の設定の値は `claude-haiku-4-5`（S3 で本番の設定に入れる。S1 はテストで値を渡す）。
- **理由**: オーナーの決定 O1（Haiku の版は頻繁に上がるので、最新を指定できるようにしたい）。モデル ID に依存する要求のパラメータ（thinking・effort の対応）も中継が持てば、アプリはモデルの差を知らずに済み、切り替えで 400 にならない。
- **代替案**: アプリにモデル ID を埋め込む（版を上げるたびにアプリの出し直しが要る）。中継が「最新の Haiku」をプロバイダのモデル一覧 API から自動で選ぶ（評価していない新版へ黙って切り替わり、原価の重みも付かない。外部への問い合わせも増える）。
- **影響範囲**: `relay/` の設定と要求の書き換え。

### 4. 利用量の計測と上限（Q2・親の決定）

- **採用案**:
  - **計測**: 上流の応答の `usage`（`input_tokens`・`output_tokens`・`cache_read_input_tokens`・`cache_creation_input_tokens`）を読む。ストリーミングは `message_start` の `message.usage` と、`message_delta` の `usage`（最後に届いた値）から、非ストリーミングは応答の JSON の `usage` から読む。
  - **原価単位**: `Σ（トークン数 × そのモデルの行の重み）÷ 1,000,000`。重みは設定で持つ（例: 重みを米ドルの単価に合わせれば、原価単位は米ドルになる）。
  - **記録**: 応答が終わった時点で、アカウント ID・その日の期間キー・その月の期間キーに原価単位とトークン数を加算する。上流が 2xx 以外を返した要求は記録しない。ストリーミングの途中でアプリが中止したときは、それまでに届いた `usage` の値で記録する。
  - **期間**: 注入する時計の現在時刻から、UTC の暦日（`YYYY-MM-DD`）と UTC の暦月（`YYYY-MM`）を期間キーにする（仮定 A5。#584 で課金周期に合わせて変える余地を残す）。
  - **上限の判定**: 送信前に、そのアカウントのその日の累計が 1 日の上限（`dailyLimit`）以上、またはその月の累計が 1 か月の上限（`monthlyLimit`）以上なら、転送せず 429 を返す。本文は `{"type":"error","error":{"type":"usage_limit_exceeded","limit":"daily"|"monthly","message":"…"}}`。`retry-after` は付けない。両方を超えているときは `"monthly"` にする（仮定 A6）。
  - **上限をまたぐ 1 件**: 送信前の判定を通った要求は、途中で上限を超えても最後まで流す。超過は 1 要求の `max_tokens`（`maxTokensCap` 以下）で抑えられる。同じアカウントの要求が同時に判定を通った場合の超過も同じく許容する（仮定 A7）。
- **理由**: 回数ではなくトークンに重みを掛けて数えれば、原価と連動し、既定モデルを差し替えても枠の意味が変わらない。送信前に判定すれば、ストリームを途中で切る必要が無い。
- **代替案**: 回数で数える（原価と連動しない。長い会話も 1 回）。重みなしのトークン合計で数える（モデルを変えると枠の意味が変わる）。上限をまたいだ時点でストリームを切る（応答が途中で途切れ、アプリ側の処理が複雑になる）。
- **影響範囲**: `relay/` の計測・利用量のポート。上限値（O2）と重みの実際の値は設定で渡す（S1 はテストで値を渡す）。

### 5. 認証の仮の境界（Q4・親の決定）

- **採用案**:
  - アプリは `authorization: Bearer <トークン>` で中継を呼ぶ（S2 で Rust の通信層に資格情報を 1 行足す）。
  - 中継は**認証のポート**（トークン → アカウント ID、または拒否）でトークンを検証する。ヘッダが無い・形が違う・ポートが拒否したときは、転送せず 401 を返す（本文は Anthropic の形の `authentication_error`）。
  - 利用量の記録と上限の判定は、ポートが返したアカウント ID ごとに分ける（ADR 0011 決定 3）。
  - S1 は認証のポートのテスト用の実装（トークンとアカウント ID の固定の対応表）だけを作る。トークンの形・発行・更新・失効は #584 で決め、S4 で結合する。
- **理由**: #584 が本機能の後に着手されるため、認証方式を推測で作らない（#581 のクリティカル設計決定 3 と同じ考え方）。ポートにしておけば、#584 の方式が決まっても中継のコアは変わらない。
- **代替案**: S1 で認証方式（JWT 等）まで決める（#584 の設計を先取りすることになる）。認証なしで作る（アカウントごとの計測が作れない）。
- **影響範囲**: `relay/` の認証部。

### 6. 推論内容を保存・ログ出力しないことの担保（Q5・親の決定）

- **採用案**:
  - 中継のログは注入する**ログのポート**だけに出し、渡してよい項目はアカウント ID・ステータス・モデル ID・トークン数・原価単位・所要時間・エラーの種類に限る。
  - **利用量の保存先の記録の型は、アカウント ID・期間キー・原価単位・トークン数（4 種）の項目だけを持つ**（構造で限定する）。
  - **自動テスト**: 要求（`system`・`messages`・ツールの入力）と模擬の上流の応答（本文の差分・ツールの入力）に目印の文字列を入れて中継を通し、ログのポートが受けたすべての記録・`console` の全メソッドへの出力・利用量の保存先のすべての記録・中継自身が作るエラーの応答の本文に、目印が現れないことを確かめる。
  - 本番の実行基盤の要求ログ・エラーの収集の検査手順は S3 で書く（O4 の実行基盤が決まってから）。
- **理由**: 「保存しない」は、保存先に中身を入れる場所が無いことを型で示せる。「ログに出さない」は、目印の文字列がどの出口にも現れないことをテストで固定できる。
- **代替案**: コードレビューだけで担保する（退行を機械で止められない）。
- **影響範囲**: `relay/` 全体。

## 機能全体の設計

### IF / API（S1 で固定する境界・名前は仮）

- **中継の HTTP**: `POST /v1/messages`（Anthropic Messages 形式・`stream` の真偽の両方）。
  - ステータス: 上流の応答のステータス（転送した場合）／400 `invalid_request_error`（検査で拒否）／401 `authentication_error`（認証で拒否）／429 `usage_limit_exceeded`（上限）／502（上流に接続できない）。
- **中継の組み立て**: `createRelayApp(deps)` が Hono のアプリを返す。`deps` は次を持つ。
  - `config`: `upstreamUrl`・`defaultModel`・`models`（許可リストの行）・`maxTokensCap`・`dailyLimit`・`monthlyLimit`
  - `operatorKey`: 事業者のキー（秘密情報）
  - `authenticate(token) → Promise<accountId | null>`（認証のポート）
  - `usageStore`: `get(accountId, dayKey, monthKey) → Promise<{ dayUnits, monthUnits }>`・`add(record) → Promise<void>`（利用量のポート。S3 で永続化する保存先へ差し替えるため非同期の契約にする。S1 はメモリ実装）
  - `upstreamFetch(request, signal) → Promise<Response>`（上流のポート）
  - `now() → Date`（時計）
  - `logger`（ログのポート）
- **利用量の記録の型**: `{ accountId, dayKey, monthKey, units, inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens }`（これ以外の項目を持たない）。
- **設定の検証**: `defaultModel` が許可リストに無い・上限や重みが負・`maxTokensCap` が正でない設定では、`createRelayApp` が例外を投げる。

### アプリ側の接続（S2 の見通し。S2 を実装対象にするときに詳細を書く）

- **Rust の通信層**（#581 の「1 行ずつ足す」）: 宛先 `relay-messages` → 中継の URL（S3 で決まる）、資格情報 `RelayBearer`（`authorization: Bearer <ライセンストークン>`）、保管の `Provider` にライセンストークンの行。`anthropic-version`・`x-api-key` は付けない（中継が付ける）。
- **TS のバックエンド**: 仮に `relay`。`byok-anthropic` の変換器を宛先の名前を引数に取る形にして使い回す（要求の `model` はプラン込みの既定の値）。能力の宣言は BYOK（Anthropic）と同じ。
- **エラーの分類**: 429 で `error.type` が `usage_limit_exceeded` の応答は再試行不可にする（プロバイダの 429 は従来どおり再試行可）。
- **自動で切り替えない**: 中継の失敗（上限到達を含む）で `byok-anthropic`・`byok-openai` の宛先へ送らない（ADR 0001 改訂の帰結・ADR 0003 決定 9・#582 の機能要件）。
- **課金経路の選択**（プラン込み ⇔ BYOK）は #582 の選択の解決関数（#582 のクリティカル設計決定 5）に「プラン込み」を足す形で入れる。選択の画面は #584 と合わせる。

### 実装計画（S1 のチケット分解の見通し）

## 受入基準（S1）

> テストはすべて模擬の上流のポート・テスト用の認証のポート・メモリの利用量のポート・固定時刻の時計で行い、実 API は呼ばない。期間キーの境界のテストは UTC の固定時刻（例: `2026-09-30T23:59:59Z` と `2026-10-01T00:00:00Z`）で行い、`npm run test:tz`（非 UTC のタイムゾーン）でも同じ結果になる。以下「既定のテスト設定」は、許可リストが `claude-haiku-4-5`（重み: 入力 1・出力 5・キャッシュ読み出し 0.1・キャッシュ書き込み 1.25）と `claude-haiku-9-9`（架空の新版・重みは同じ）の 2 行（どちらも adaptive thinking と effort に対応しない行。thinking の書き換えは `adaptive` → `{ "type": "disabled" }`）、`defaultModel` が `claude-haiku-4-5` の設定を指す。

**認証**

- [ ] `authorization` ヘッダの無い要求は 401 になり、上流のポートは呼ばれない
- [ ] 認証のポートが拒否するトークンの要求は 401 になり、上流のポートは呼ばれない
- [ ] 401 の応答の本文の `error.type` は `authentication_error` である
- [ ] 利用量は、認証のポートが返したアカウント ID ごとに分けて記録される（アカウント A の要求の後に、アカウント B の累計が 0 のままである）

**要求の検査**

- [ ] 最上位に許可リスト外の項目（例: `mcp_servers`）がある要求は 400 になり、上流のポートは呼ばれない
- [ ] `model` がプラン込みの既定の値でない要求（例: `claude-opus-5-5`）は 400 になり、上流のポートは呼ばれない
- [ ] `max_tokens` が `maxTokensCap` を超える要求は 400 になり、上流のポートは呼ばれない（`maxTokensCap` ちょうどの要求は転送される）
- [ ] `tools` にプロバイダ側で実行されるツール（例: `type: "web_search_20250305"`）を含む要求は 400 になり、上流のポートは呼ばれない
- [ ] `tools` が `type` の無い関数ツールだけの要求は転送される
- [ ] 本文が JSON として解釈できない要求は 400 になり、上流のポートは呼ばれない
- [ ] 400 の応答の本文の `error.type` は `invalid_request_error` である

**応答の転送**

**利用量の計測**

- [ ] ストリーミングの応答の `message_start` の `usage` の `input_tokens` が 1,000、最後の `message_delta` の `usage` の `output_tokens` が 200 のとき、記録の入力トークンは 1,000、出力トークンは 200 である

## 仮定（軽微・可逆）

- A1: 仕様ファイルの名前は `llm-relay-server.md`、workspace のディレクトリは `relay/`（決定 O3）。
- A2: プラン込みの既定を表す `model` の値は仮に `"ai-boss-plan-default"`。値は S1 の実装で決めてよい（S2 のアプリ側と同じ定数を使う）。
- A3: 中継の組み立て関数の名前（`createRelayApp`）・ポートの名前・設定の項目の名前は仮。実装で決めてよい。
- A4: Haiku 4.5 の行の thinking の書き換えは「`adaptive` → `disabled`・effort を取り除く」とする（Haiku 4.5 は adaptive と effort に対応しない。公式ドキュメントの Models overview）。`disabled` を送る要求はそのまま `disabled` で送る。書き換えの規則は許可リストの行の設定として持ち、S3 の実 API の確認で違っていたら設定を直す。
- A5: 利用量の期間は UTC の暦日と暦月とする。中継には利用者のタイムゾーンが無いため。#584 で課金周期（契約日起点等）に合わせる場合は、期間キーを求める関数を差し替える。

- A7: 同じアカウントの要求が同時に送信前の判定を通ったときの超過は許容する（1 要求の `max_tokens` が超過を抑える）。厳密な同時実行の制御は S3 の永続化する保存先で必要になったら決める。
- A8: 上流の URL は設定の値（本番は `https://api.anthropic.com/v1/messages`。S3 で入れる）。
- A9: 推論原価の見積もりの呼び出し量は、実コードの文字数からの概算（日本語 1 字 ≒ 1〜1.5 トークン）と、典型的な 1 日の利用頻度の仮定に拠る。実測は S3 の実 API の確認で行う。
