# LLM 中継サーバー（プラン込み枠・利用量の計測と上限・既定モデルと推論原価）

> Issue #583。2026-09-28 に論点を確定した（★ はオーナーの決定、それ以外は親の決定。「決定」節）。

## 概要

製品版の既定の LLM の利用方式「料金プラン込み」で、アプリの推論要求を受けて事業者の API キーでプロバイダへ転送する **ai-boss の LLM 中継サーバー**を作る。中継はアカウントごとに利用量を計測し、上限で止める。推論内容は保存もログ出力もしない。既定のモデル（Haiku 系）の具体の ID は中継の設定で持ち、アプリのリリースなしに差し替えられるようにする（[ADR 0011](../adr/0011-productization-architecture.md) 決定 2・3・9、[ADR 0001](../adr/0001-local-only-data-boundary.md) 改訂の決定 3）。

## 背景・目的

- 事業者のキーは配布物に埋め込めない（抜き取られる）。プラン込み枠を提供するには中継が必須である（ADR 0011 決定 9・ADR 0002 改訂の決定 6）。
- 中継サーバーは推論内容（プロンプト・応答）を保存もログ出力もしない。中継が扱ってよいのは、推論をプロバイダへ転送することと、利用量の計測・制限に要る情報だけである（ADR 0001 改訂の決定 3）。
- クラウドが持つのはアカウント・ライセンス・利用量だけで、ライセンスと利用量は顧客ごとに分けて認可する（ADR 0011 決定 3）。アカウント・ライセンスの仕組みは #584 で作る。#584 は本機能の後に着手するため（#584「依存: 先行 #583」）、本機能は認証を仮の境界（認証のポート）で受ける。
- #582 の仕様（クリティカル設計決定 1）は「中継サーバーが同じ形式を話すなら、宛先を足すだけで同じ変換器を使える」としている。#581 の仕様（クリティカル設計決定 3）は「中継サーバーの宛先とライセンストークンの付与は、#583・#584 が宛先の表と保管のポートに 1 行ずつ足す」としている。本機能はこの 2 つの前提に乗る。
- 既定の低価格モデルの選定と、1 利用者あたりの推論原価の見積もりも本機能で行う（#575 の論点・#583 の本文）。

## ユーザーストーリー

- 製品版の利用者として、自分で API キーを用意しなくても、料金プランの範囲でボスとの対話・朝会・夕会を使いたい。
- 事業者として、利用者ごとの推論の利用量を計測し、プランの枠を超えた利用を止めたい（推論原価を料金プランの範囲に収めるため）。
- 事業者として、既定モデル（Haiku）の新版が出たときに、アプリを出し直さずに中継の設定変更だけで切り替えたい。
- 製品版の利用者として、自分の業務の内容（プロンプトと応答）が中継サーバーに保存されず、ログにも残らないでほしい。

## 決定（2026-09-28）

| 論点 | 決定 | 決めた人 |
|---|---|---|
| Q1 アプリ → 中継の形式 | 中継は既定モデルのプロバイダの形式（**Anthropic Messages**）の要求を受け、要求の JSON を検査し、事業者のキーを付けてプロバイダへ転送する。応答はバイト列のまま逐次流し、途中で `usage` を読む。アプリの中止をプロバイダへの要求に伝える（クリティカル設計決定 1・2） | 親 |
| O1 既定モデル | 既定のモデルファミリーは **Haiku**。**具体のモデル ID はアプリに埋め込まず、中継の設定で持つ**。アプリは「プラン込みの既定」を依頼し、中継が設定の ID へ解決する。Haiku の新版が出たら中継の設定変更だけで切り替わり、アプリのリリースは要らない。現時点の値は `claude-haiku-4-5`。モデルごとの重み（原価単位）は設定の許可リストに持ち、許可リストに無いモデルへは転送しない（クリティカル設計決定 3） | ★オーナー（親が解釈を確定） |
| Q2 利用量の単位と上限 | プロバイダの応答の `usage` を記録し、モデルごとの重みを掛けた**原価単位**で数える。上限は **1 日と 1 か月の二段**。判定は送信前で、超えていれば転送せず 429（`usage_limit_exceeded`）を返す。重みと上限値は設定で持つ（クリティカル設計決定 4） | 親 |
| PR #634 の Codex の指摘 P1（同時要求で上限を超える） | 送信前にその要求の**最大原価を原子的に予約**し、予約後の合計が上限を超えるなら 429。応答の終了時に実際の `usage` で**精算**し、`usage` が得られなければ予約額をそのまま計上する。**アカウントごとの同時要求数の上限**も設定で持つ。「上限をまたぐ 1 件は最後まで流す」は「予約が通った要求は最後まで流す」へ読み替える。当初の仮定 A7（同時要求の超過を許容）は撤回した（クリティカル設計決定 4） | 親 |
| PR #634 の Codex の指摘 P2（入力の課金が抑えられていない） | **要求 1 件あたりの入力量の上限**（本文のバイト数・設定値）を要求の検査に加え、超えたら転送せず 413（再試行不可）。入力の見積もりは予約額にも使う（クリティカル設計決定 1・4） | 親 |
| #635 のオーナーの決定 1（PR #634 の 4 巡目の Codex の指摘 P1・外部の内容の取り込み） | URL・ファイル参照などで**外部の内容を取り込むブロックは、入力量の見積もりの前に拒否する**（400・上流を呼ばない・予約しない）。拒否の対象は内容のブロックの `type` の許可リストで決め、入れ子も同じ規則で検査する（クリティカル設計決定 1。S1 の実装で経路を全数監査し、本文に埋め込まれた base64 の画像・文書も拒否に倒した） | ★オーナー（拒否を採ったのは親・範囲は子） |
| #635 のオーナーの決定 2（PR #634 の 4 巡目の Codex の指摘 P1・精算の冪等性） | 精算と期限切れの回収を「未精算 → 精算済み」の **1 回だけの原子的な遷移**として利用量のポートの契約に書き、同じ予約 ID の 2 回目以降の精算は何も起きない（冪等）。回収と通常の精算が競合しても二重に記録しない。S1 のメモリ実装のテストで固定する（クリティカル設計決定 4） | ★オーナー |

### Anthropic の公式ドキュメントで確かめたこと（2026-09-28 に platform.claude.com を参照。実 API は呼んでいない）

- Haiku 4.5 の Claude API ID は `claude-haiku-4-5-20251001`、エイリアスは `claude-haiku-4-5`。
- **「最新の Haiku」を指す、バージョンをまたいで浮動するエイリアスは無い**。4.6 世代より前のモデルのエイリアスは同じ版の日付つき ID を指す便宜上のもの。4.6 世代以降は日付の無い ID がそれ自体で固定のスナップショットになる（Models overview の「Claude API alias」「Claude API ID」の注記）。このため本機能は、**中継の設定のモデル ID を差し替えて新版に追随する**設計にする（クリティカル設計決定 3）。
- Haiku 4.5 の退役は「2026-10-15 より前にはしない」。新版への切り替えを設定の差し替えで行えることが要る。
- Haiku 4.5 の thinking は Extended（`type: "enabled"` と `budget_tokens`）で、adaptive thinking と effort の指定には対応しない（effort は「Not supported」）。アプリのチャットは `thinking: { type: "adaptive" }` と `output_config.effort` を送るため、**中継がモデルの行に従って `thinking` と `output_config` を書き換える**（クリティカル設計決定 3）。
- 単価（1M トークンあたり）: Haiku 4.5 は入力 $1・出力 $5・キャッシュ読み出し $0.10。Sonnet 5 は入力 $2・出力 $10（Claude 4.7 以降の新しいトークナイザは同じ文で約 30% 多くのトークンになる。Haiku 4.5 は旧トークナイザ）。
- OpenAI（2026-09-28 に developers.openai.com の料金表を参照）: `gpt-6-luna` は入力 $0.10・出力 $0.50、`gpt-6-sol` は入力 $2・出力 $10。

## 推論原価の見積もり（前提つき）

### 1 日の呼び出し量（実コードからの推定）

日本語は 1 字 ≒ 1〜1.5 トークンとして換算した。文字数は実コードで数えたが、トークン数と「典型的な 1 日」の利用頻度は仮定である。

| 経路 | 契機（根拠） | 回数/日 | 入力トークン | 出力トークン |
|---|---|---|---|---|
| チャット | 1 メッセージごとに最低 1 回、ツールのループで最大 5 回。セッションの履歴を上限なしで毎回全部送る（`sessions/messages-repository.ts:57-65`）。ツール定義（約 3,300 字）を毎ラウンド送る | 11（朝会 3・夕会 3・随時 5 往復） | 約 59,000 | 約 3,300 |
| セッション要約 | 朝会・夕会の初回終了時だけ（`sessions/sessions-routes.ts:326-334`）。`maxTokens` 300 | 2 | 約 2,200 | 約 600 |
| 会議の開始文 | 朝会・夕会の作成時（`sessions/meeting-opening.ts:75-83`）。`maxTokens` 150 | 2 | 約 3,400 | 約 160 |
| ダッシュボードのひとこと | 暦日＋タスクの状態でキャッシュする（`dashboard/boss-comment-cache.ts`）。`maxTokens` 150 | 2 | 約 3,000 | 約 120 |
| 夕会の要約抽出 | 夕会の初回終了時（`sessions/sessions-routes.ts:349-351`）。ツール呼び出しを強制 | 1 | 約 2,650 | 約 300 |
| 通知文面 | 検知の発火ごと。ルールごとに 1 日 5 件まで（`detection/detection-types.ts:120`）。`maxTokens` 150 | 3（理論上の最大は約 30） | 約 3,780 | 約 180 |
| **合計（典型的な 1 日）** | | | **約 74,000** | **約 4,700** |

### 1 利用者あたりの月の推論原価（30 日換算・プロンプトキャッシュなし）

| モデル | 典型的な日 | 重い日（入出力とも 4 倍と仮定） |
|---|---|---|
| **`claude-haiku-4-5`（既定・決定 O1）** | **約 $0.098/日 → 約 $2.9/月** | 約 $0.40/日 → 約 $11.9/月 |
| `gpt-6-luna`（参考） | 約 $0.010/日 → 約 $0.3/月（reasoning のトークンは別途） | 約 $1.2/月 |
| `claude-sonnet-5`（参考） | 約 $0.195/日 → 約 $5.9/月（新しいトークナイザで +30% なら約 $7.6） | 約 $23.7/月 |
| `gpt-6-sol`（参考） | 約 $5.9/月 | 約 $23.7/月 |

- 原価の大半はチャットで、主な原因は「履歴を毎回全部送る」「ツール定義を毎ラウンド送る」「ツールのループが最大 5 ラウンド」の 3 つである。プロンプトキャッシュ（`cache_control`）は現行コードが使っておらず、見積もりにも含めていない。使えばチャットの入力の原価は大きく下がる見込みだが、本機能の範囲外とする（「やらないこと」）。
- この見積もりは、プランの上限値と価格帯を決める材料になる（決定 O2 は未決）。上限値は、重い日の原価を踏まえて設定の値で決める。

## 機能要件（機能全体。スライスごとの範囲は「スライス」節）

- [ ] 中継は、アプリの Anthropic Messages 形式の要求を、事業者のキーを付けてプロバイダへ転送する
- [ ] 中継は、アプリが指定したプラン込みの既定の依頼を、設定の既定モデルの ID に解決して転送する
- [ ] 設定の既定モデルを差し替えると、アプリの変更なしに転送先のモデルが変わる
- [ ] 中継は、許可リストに無いモデルへは転送しない
- [ ] 中継は、ストリーミングの応答を逐次アプリへ流す
- [ ] 中継は、アカウントごとに利用量を原価単位で記録する
- [ ] 中継は、1 日または 1 か月の上限に達したアカウントの要求を転送せずに拒否する
- [ ] 中継は、要求本文の入力量が設定の上限を超える要求を転送せずに拒否する
- [ ] 中継は、アカウントごとの同時要求数が設定の上限に達した要求を転送せずに拒否する
- [ ] 中継は、推論内容を保存もログ出力もしない
- [ ] 中継は、認証できない要求を転送しない
- [ ] アプリは、プラン込みの推論を中継経由で行う（S2）
- [ ] アプリは、中継の失敗（上限到達を含む）時に BYOK へ自動で切り替えない（S2。#582 の機能要件「別の課金経路へ自動で切り替えない」の検証はここで行う）
- [ ] 上限到達をアプリの画面で案内する（S2）
- [ ] 中継を実行基盤にデプロイし、利用量を永続化する（S3）
- [ ] 中継の認証を #584 のアカウント・ライセンスと結合する（S4）

## 非機能要件

- 機密データ: 中継はプロンプト・応答・ツールの入出力を保存しない・ログに出さない・エラーの応答や例外のメッセージにも含めない（ADR 0001 改訂の決定 3）。
- 秘密情報: 事業者のキーは中継の設定の秘密情報としてだけ持ち、応答・ログ・利用量の記録に出さない（ADR 0002 改訂の決定 6・7）。アプリの利用者のトークンもログに出さない。
- ストリーミング: 応答をまとめて溜めずに逐次流す（最初の差分がプロバイダから届いたら、応答の終わりを待たずにアプリへ流す）。
- 実行基盤の非依存: 中継のコアは Web 標準の API（`fetch`・`Request`・`Response`・`ReadableStream`）と Hono だけで書き、Node の組み込みを使わない（O4 の実行基盤を後から選べるようにする）。
- 外部送信: 中継の送信先はプロバイダ（設定の上流の URL）だけである（テレメトリ・分析のための送信を持たない）。

## 技術的な制約・方針

- 使用技術: TypeScript・Hono（`relay/` の新しい workspace）。テストは Vitest。
- 変更対象（S1）: 新規の `relay/`（`package.json`・`tsconfig.json`・`vitest.config.ts`・ソースとテスト）、ルートの `package.json` の `workspaces` に `relay` を足す。`eslint.config.js` に `files: ["relay/**/*.ts"]` のブロックを足し、既存の `server/**/*.ts` と同じ `globals: globals.node` を割り当てる（無いと `relay/` の lint が no-undef で落ちる）。`server/`・`web/`・`native/` は変えない。
- 既存コードとの関係: S1 はアプリのコードを変えない。中継が受ける要求の形は、#581 S2 の BYOK（Anthropic）の変換器が作る本文（最上位の 9 項目）に合わせる。S2 でアプリ側に中継の宛先・資格情報・バックエンドを足す。
- 品質ゲート: 新しい workspace もルートの `npm run lint`・`npm run typecheck`・`npm test`・`npm run test:tz` の対象に入る。

## クリティカル設計決定

### 1. アプリ → 中継の形式と要求の検査（Q1・親の決定）

- **採用案**: 中継は `POST /v1/messages` で **Anthropic Messages 形式**の要求を受ける。
  - 要求の JSON の最上位の項目は、許可リスト `model`・`max_tokens`・`system`・`messages`・`tools`・`tool_choice`・`thinking`・`output_config`・`stream` に限る。それ以外の項目（例: `mcp_servers`・`container`・`metadata`）があれば、転送せず 400 を返す。
  - `model` は、プラン込みの既定を表す固定の値（仮に `"ai-boss-plan-default"`。仮定 A2）だけを受ける。それ以外の値は転送せず 400 を返す（アプリはモデル ID を知らない。決定 O1）。
  - `max_tokens` は必須で、**正の整数**かつ設定の上限（`maxTokensCap`）以下でなければならない（PR #634 の Codex の 2 巡目の指摘）。無いとき・正の整数でないとき（0・負の数・小数・文字列）・超えるときは、予約せず、切り詰めずに転送せず 400 を返す（送信前の予約に `max_tokens` を使うため。クリティカル設計決定 4）。
  - **入力量の上限**（PR #634 の Codex の指摘 P2 を受けて追加）: 要求本文の UTF-8 のバイト数が設定の `maxRequestBytes` を超えるときは、転送せず 413 を返す（本文は Anthropic の既存の形の `request_too_large`。再試行不可）。この検査は JSON の解釈より前に行う。`max_tokens` が出力だけを抑えるのに対し、これが 1 要求の入力の課金を抑える。上限は**受け取った本文**に効く（上流へ送る本文は組み立て直すため、数値の表記の展開等でこれより大きくなりうる。その分は予約額の見積もりが大きいほうのバイト数で覆う。クリティカル設計決定 4）。
  - `tools` の各要素は、アプリが定義する関数ツール（`type` が無いか `"custom"`）に限る。プロバイダ側で実行されるツール（`type` が `web_search_…` 等）が 1 つでもあれば、転送せず 400 を返す（追加課金のツールを枠の外で使わせないため・#582 のクリティカル設計決定 4 の旧決定 5 の読み替えと同じ考え方）。
  - 本文が JSON として解釈できないときも、転送せず 400 を返す。
  - **外部の内容を取り込むブロックの拒否**（#635 のオーナーの決定 1）: `messages[].content` の配列に置いてよいブロックの `type` は `text`・`tool_use`・`tool_result`・`thinking`・`redacted_thinking` に限り（いずれも入力になる内容が本文にそのまま書かれている）、`tool_result` の `content` と `system` の配列は文字列か `text` のブロックだけにする（入れ子も同じ規則で再帰的に検査する）。それ以外（`image`・`document`・`search_result`・`container_upload`・`tool_reference`・サーバーツールや MCP の結果・`type` の無いブロック等）は、`source` が URL・ファイル参照でも**本文に埋め込まれた base64 でも**転送せず 400 を返す。この検査は予約より前（入力量の見積もりの前）に行う。
    - **base64 も拒否する理由**: 本文のバイト数から求める予約額（仮定 A10）は、入力のトークン数が本文のバイト数で抑えられることを前提にしている。PDF はページごとに画像としても課金され、可逆圧縮の画像は小さなバイト数で最大の画素数になりうるため、埋め込みのメディアはこの前提を満たさない。アプリ（#581 S2 の変換器）はこれらのブロックを送らない。必要になったら、メディアの最大のトークン数を見積もりに足す形で許可リストを広げる。
    - 最上位の項目の許可リスト（上記）は、`mcp_servers`・`container`（外部の内容の取り込み・実行）と、`service_tier`・`speed`・`inference_geo`・`context_management`（単価の割り増し等）も転送させない。アプリの `anthropic-beta` を上流へ渡さないこと（クリティカル設計決定 2）は、Files API 等のベータ機能の経路も塞ぐ。
  - **`cache_control` の `ttl` は `5m`（既定）に限る**（`system`・内容のブロック・`tools` のいずれも）。1 時間のキャッシュの書き込みは 5 分のキャッシュより高い単価で課金され、設定の `cacheWrite` の重みでは原価を下回って数えるため、転送せず 400 を返す。
  - 検査で拒否した要求は利用量を記録しない。
  - エラーの応答の本文は Anthropic の形（`{"type":"error","error":{"type":"…","message":"…"}}`）で返し、`message` は種類ごとの固定の文言にする（要求の中身を埋め込まない）。
- **理由**: #581 S2 の Anthropic の変換器がそのまま使え、中継に形式の変換を持たせずに済む（#582 のクリティカル設計決定 1 の想定どおり）。検査を許可リスト方式にすれば、プロバイダが項目を増やしても、中継が知らない項目は枠の外で使われない。
- **代替案**: 中継独自の中立な形式にして中継で変換する（変換器を二重に持つことになる）。項目を検査せず素通しにする（プロバイダ側で実行されるツールや巨大な `max_tokens` で枠が破られる）。`max_tokens` を上限へ切り詰める（アプリの意図と違う長さで黙って打ち切られる。拒否のほうが原因が見える）。
- **影響範囲**: `relay/` の要求の検査。S2 でアプリの `byok-anthropic` の変換器を中継の宛先でも使う。

### 2. 転送とストリーミング・中止の伝播（Q1・親の決定）

- **採用案**:
  - 上流（プロバイダ）への要求のヘッダは中継が一から組み立てる: `content-type: application/json`・`x-api-key`（事業者のキー）・`anthropic-version: 2023-06-01`（Rust の `ANTHROPIC_VERSION` と同じ値）。アプリから来たヘッダ（`authorization`・`x-api-key`・`anthropic-version`・`anthropic-beta` を含む）は上流へ渡さない。
  - 上流の応答は、ステータスと本文をそのままアプリへ返す（2xx 以外も、上流の本文を加工しない）。応答のヘッダは `content-type`・`retry-after`・`request-id` だけを通す。
  - ストリーミングの応答は、本文のバイト列を溜めずに逐次流しながら、並行して SSE を解釈し `usage` を読む（クリティカル設計決定 4）。中継は上流を、アプリの読み取りを待たずに最後まで読む（精算を上流の終わりに合わせ、読み取りの遅いアプリが精算を遅らせないようにする。S1 の実装で確定）。アプリが読むより速く届いた断片は中継の内部の待ち行列に残る。待ち行列のバイト数が設定の `maxBufferedResponseBytes`（省略時 1 MiB）を超えたら（読まないアプリ。非ストリーミングの応答も同じ待ち行列を通るため同じく中止する）、アプリの中止と同じ扱いで上流を止め、アプリへのストリームを固定の文言で異常終了させる。精算はアプリの中止と同じく、終端の `usage` を受け取っていなければ予約額で確定する（#641）。断片を積むと上限を超えるかは積む前に判定する（上限より大きい断片 1 つでも待ち行列は上限を超えない。ただしその断片 1 つで、読み続けているアプリも中止される）。非ストリーミングの計測器は本文が、ストリーミングの計測器は区切りを待つ行と組み立て中のイベントの `data` の合計が、同じ上限を超えたら持つのをやめ、予約額で確定する（アプリへの本文の中継は止めない。#641。この値を下げると、非ストリーミングの応答を実額で精算できる本文の大きさも狭まる）。待ち行列はバイト数、ストリーミングの計測器は UTF-16 の単位数（行ごとに区切りの 1 を足す）で数える。日本語などでは V8 の内部で 1 単位 2 バイトになるため、1 要求の定常の保持量は上限の約 3 倍のバイト数まで（待ち行列が 1 倍、ストリーミングの計測器が約 2 倍。イベントを閉じるときの一時的な複製などの山は含まない目安）。
  - 応答を終える（非ストリーミング・2xx 以外・502 の応答を返す、ストリームを閉じる）のは、利用量のポートの精算が終わってからにする（S1 の実装で追加。書き込みの前に応答が終わると、実行基盤によっては書き込みが打ち切られ、直後の要求が未精算の予約で拒否されうる）。
  - アプリが要求を中止した（接続を切った）ら、上流への要求を中止する（`AbortSignal` を伝える）。
  - 上流の失敗は、課金の有無が確定するかで 2 つに分ける（PR #634 の Codex の 2 巡目の指摘）。いずれもアプリへは 502 を返し、本文は固定の文言にする（アプリが中止した場合は応答を返さない）。
    - **送る前の失敗**（要求を送る前に失敗したことが確定している。例: 名前解決・接続の確立・TLS の確立の失敗）: プロバイダは要求を受けていないため課金されない。予約を解放し、記録しない。
    - **送った後の失敗で課金の有無が確定しない**（例: 送信後のタイムアウト・接続のリセット・応答ヘッダの前にアプリが中止）: プロバイダが処理して課金した可能性があるため、**予約額で確定して記録する**（安全側）。
    - どちらに当たるかは上流のポートが返す失敗の区分で決める。区分の無い失敗（未知の例外）は「送った後の失敗」として扱う（仮定 A12）。
  - ストリーミングの本文を流し始めた後に上流との接続が切れたときは、ステータスを変えずに、精算の後でアプリへのストリームを**異常終了させる**（正常な終わりに見せない。PR #638 のレビューで「終える」から改めた。終端の `usage` を受け取っていないため、途中までの `usage` では精算せず、予約額で確定して記録する。クリティカル設計決定 4）。
  - 上流の URL・事業者のキーは設定で渡す。上流への送信は注入する `fetch` 相当の関数（上流のポート）で行い、テストはそれを模擬する。
- **理由**: 事業者のキーの付与を中継に閉じ、アプリ由来のヘッダでキーや API の版を差し替えられないようにする（#581 の `transport.rs` が呼び出し元の認証ヘッダを捨てるのと同じ規律）。上流のエラーの本文をそのまま返せば、アプリ側の既存のエラーの分類（`classifyByokAnthropicError`）がそのまま効く。
- **代替案**: 応答を全部受けてから返す（ストリーミングの体感が失われる）。上流のエラーを中継独自の形に作り替える（アプリ側に分類をもう 1 つ持つことになる）。
- **影響範囲**: `relay/` の転送部。

### 3. 既定モデルの解決とモデルの許可リスト（O1・★オーナーの決定）

- **採用案**: 中継の設定に**モデルの許可リスト**と**既定モデル**を持つ。
  - 許可リストの各行: モデル ID・原価単位の重み（入力・出力・キャッシュ読み出し・キャッシュ書き込みの 1M トークンあたり）・thinking の書き換え方・`output_config` の effort に対応するか。
  - 既定モデル（`defaultModel`）は許可リストのいずれかの行を指す。指さない設定では中継を組み立てられない（起動時に失敗する）。
  - 中継は、要求の `model`（プラン込みの既定の値）を設定の `defaultModel` のモデル ID に置き換えて転送する。
  - 中継は、転送前に、既定モデルの行に従って `thinking` と `output_config` を書き換える。Haiku 4.5 の行は adaptive thinking と effort に対応しないため、`thinking` を `{ "type": "disabled" }` にし、`output_config` の `effort` を取り除く（仮定 A4。`output_config` がほかの項目を持たなくなったら `output_config` ごと取り除く）。
  - Haiku の新版が出たら、中継の設定の許可リストに行を足し、`defaultModel` を差し替える。アプリのリリースは要らない。浮動するエイリアスは Anthropic に無いため使わない（「Anthropic の公式ドキュメントで確かめたこと」）。
  - 現時点の設定の値は `claude-haiku-4-5`（S3 で本番の設定に入れる。S1 はテストで値を渡す）。
- **理由**: オーナーの決定 O1（Haiku の版は頻繁に上がるので、最新を指定できるようにしたい）。モデル ID に依存する要求のパラメータ（thinking・effort の対応）も中継が持てば、アプリはモデルの差を知らずに済み、切り替えで 400 にならない。
- **代替案**: アプリにモデル ID を埋め込む（版を上げるたびにアプリの出し直しが要る）。中継が「最新の Haiku」をプロバイダのモデル一覧 API から自動で選ぶ（評価していない新版へ黙って切り替わり、原価の重みも付かない。外部への問い合わせも増える）。
- **影響範囲**: `relay/` の設定と要求の書き換え。

### 4. 利用量の計測と上限（Q2・親の決定）

- **採用案**:
  - **計測**: 上流の応答の `usage`（`input_tokens`・`output_tokens`・`cache_read_input_tokens`・`cache_creation_input_tokens`）を読む。ストリーミングは `message_start` の `message.usage` と、`message_delta` の `usage`（最後に届いた値）から、非ストリーミングは応答の JSON の `usage` から読む。ストリーミングで実額の精算に使うのは、**終端（`message_stop`）まで受け取ったときの最後の `message_delta` の `usage`（終端の `usage`）だけ**とする（PR #634 の Codex の 3 巡目の指摘）。
  - **原価単位**: `Σ（トークン数 × そのモデルの行の重み）÷ 1,000,000`。重みは設定で持つ（例: 重みを米ドルの単価に合わせれば、原価単位は米ドルになる）。
    - **整数で数える**（PR #638 のレビューで追加）: 浮動小数で足すと「合計がちょうど上限に等しいときは成功する」が崩れる（`0.1 + 0.2 > 0.3`）ため、予約・精算・上限の判定は**原価単位 × 10^10 を 1 とする整数**で行う。重みは 10^-4 刻みに限り（`トークン数 × 重み × 10^4` がそのまま整数の原価単位になる）、上限値は整数表現が正確に数えられる範囲（約 90 万原価単位まで）に限る。利用量のポートの `units`（予約・記録・`get`）とログの `units` はこの整数表現である。
  - **期間**: 注入する時計の**予約の直前の**現在時刻（要求の受け付けの時刻ではない。境界の前に要求を開き、境界の後に本文を送り終えて、旧期間の枠で新期間を消費させないため。PR #638 の Codex の指摘）から、UTC の暦日（`YYYY-MM-DD`）と UTC の暦月（`YYYY-MM`）を期間キーにする（仮定 A5。#584 で課金周期に合わせて変える余地を残す）。予約（下記）の時点の期間キーを、その要求の精算にもそのまま使う（精算が日付をまたいでも予約した期間に計上する）。
  - **送信前の予約**（PR #634 の Codex の指摘 P1・P2 を受けて改めた）: 送信前に、その要求の**最大原価**を求め、利用量のポートで**原子的に予約**する。
    - 最大原価 ＝ `（入力の見積もりトークン数 × 入力側の重み ＋ max_tokens × 出力の重み）÷ 1,000,000`。入力側の重みは、そのモデルの行の入力・キャッシュ読み出し・キャッシュ書き込みの重みのうち最大のもの（入力がキャッシュに書き込まれて課金されても予約を下回らないため）。
    - 入力の見積もりトークン数 ＝ `ceil（要求本文の UTF-8 のバイト数 × 設定の inputTokensPerByte）`（仮定 A10）。ここでの要求本文のバイト数は、入力量の上限の検査（クリティカル設計決定 1）と同じ**アプリから受けた元の本文**のバイト数と、**上流へ送るために組み立て直した本文**（検査した値を `JSON.stringify` し直し、既定モデルの解決で書き換えたもの）のバイト数の**大きいほう**とする（S1 の実装で追加。数値の表記〔`1e20` 等〕は組み立て直すと長くなるため、元の本文だけで見積もると送る本文を下回りうる）。上流へは元の本文ではなく組み立て直した本文を送る（重複した項目等で、検査した値と送る値が食い違わないようにする）。
    - 予約は、そのアカウントの「その日の確定額＋未精算の予約額の合計＋この要求の最大原価」が `dailyLimit` を超える、または同じく月の合計が `monthlyLimit` を超えるなら失敗する（合計がちょうど上限に等しいときは成功する）。判定と予約の追加は、同じアカウントの他の予約と競合しない 1 つの操作で行う（原子的）。S1 のメモリ実装は、確定額・予約額・予約の件数の読み取りから予約の追加までを `await` を挟まない同期の処理で行う（JS の単一スレッドの実行を排他の根拠にする）。S3 の永続化する保存先では、その保存先のトランザクション等で同じ原子性を担保する。
    - 予約が失敗したら転送せず 429 を返す。本文は `{"type":"error","error":{"type":"usage_limit_exceeded","limit":"daily"|"monthly","message":"…"}}`。`retry-after` は付けない。日と月の両方で超えるときは `"monthly"` にする（仮定 A6）。
  - **同時要求数の上限**: 設定の `maxConcurrentRequests`（アカウントごと）を、未精算の予約の件数で数える。予約の時点でそのアカウントの未精算の予約が `maxConcurrentRequests` 件あれば、予約は失敗し、転送せず 429 を返す。本文は Anthropic の既存の形の `{"type":"error","error":{"type":"rate_limit_error","message":"…"}}` で、`retry-after: 1` を付ける（一時的な混雑であり、アプリの既存の分類で再試行可になる。仮定 A11）。同時要求数と金額の両方で失敗するときは、金額の上限（`usage_limit_exceeded`）を返す。
  - **精算**: 応答が終わった時点（正常終了・アプリの中止・上流の切断のいずれも）で、予約を取り除き、実額を記録する。
    - 実額は、上流の `usage` から求めた原価単位とトークン数。ストリーミングで終端の `usage` を受け取らずに終わったとき（アプリの中止・上流の切断のいずれも）は、途中までの `usage` では精算せず、**予約額をそのまま実額として記録する**（トークン数は 0。安全側。途中までの `usage` はその後に生成・課金された分を含まないため）。
    - 上流が 2xx を返したのに `usage` が 1 つも得られないまま終わったときは、予約額をそのまま実額として記録する（トークン数は 0。安全側）。
    - `usage` の項目があるのに値が壊れている（負の数・小数・文字列・入力と出力のトークン数の `null`。`usage` 自体がオブジェクトでない）ときも、予約額をそのまま実額として記録する（トークン数は 0。前のイベントの値を残したまま確定しない。PR #638 の Codex の指摘）。キャッシュの項目の `null` と、`usage` の無い `message_delta` は壊れた値とみなさない。
    - 必須の項目が欠けた `usage`（`message_start` と非ストリーミングの `usage` で `input_tokens` か `output_tokens` が無い、`usage` のある `message_delta` で `output_tokens` が無い）と、イベントの順序の崩れ（`message_start` が 2 度届く、`usage` のある `message_delta` が `message_start` より先に届く）も壊れた値と同じに扱い、予約額をそのまま実額として記録する（トークン数は 0。欠けた項目を前のイベントの値で埋めて過少に精算しない。PR #638 の Codex の 3 巡目の指摘）。
    - ストリーミングで JSON として解釈できない（またはオブジェクトでない）イベントが 1 つでも届いたときも、終端まで受け取ったかにかかわらず予約額をそのまま実額として記録する（トークン数は 0。そのイベントが `usage` を運んでいた可能性があるため。PR #638 の Codex の 2 巡目の指摘）。
    - 上流が応答を返した 2xx 以外の要求（確定的に課金されない）と、上流への「送る前の失敗」（クリティカル設計決定 2）の要求は、予約を取り除くだけで記録しない。
    - 上流への「送った後の失敗で課金の有無が確定しない」要求（クリティカル設計決定 2）は、予約額をそのまま実額として記録する（トークン数は 0。安全側）。
  - **精算の冪等性**（#635 のオーナーの決定 2）: 予約は「未精算 → 精算済み」へ **1 回だけ**原子的に遷移する。遷移の時点で予約を取り除き、結果（実額・予約額・記録しない）に応じて記録する。**すでに精算済み（または存在しない）の予約 ID への精算は何もしない**（書き込みの確定後にタイムアウトして再試行しても、二重に記録されない）。期限切れの回収（S3）も同じ遷移を「予約額で確定」として行うため、回収と通常の精算が競合したときは先に遷移したほうだけが記録され、後の呼び出しは何もしない。この契約は利用量のポートに書き、S1 のメモリ実装のテストで固定する（永続化する保存先では S3 で同じ契約を満たす）。
  - **予約の期限**（PR #634 の Codex の 2 巡目の指摘）: 予約は期限（有効期限の時刻 ＝ 予約の時刻 ＋ 設定の `reservationTtlMs`）を持つ。期限を過ぎても精算されない予約（中継の異常終了・`settle` の失敗で孤立した予約）は、**予約額で確定する**（安全側。解放はしない）。S1 のメモリ実装は予約に期限の項目を持つだけで、期限切れの予約を回収して確定する処理と、`settle` の失敗時の再試行は S3（永続化する保存先）で作る（メモリ実装の予約はプロセスと寿命を共にするため孤立しない）。
  - **予約が通った要求は最後まで流す**: 精算で実額が予約額を上回っても、ストリームを途中で切らず、実額で記録する（入力の見積もりが下回った場合に限られる。仮定 A10）。
  - **予約の後の想定外の例外**（PR #638 のレビューで追加）: 予約の後、転送や応答の組み立てで想定外の例外が起きたときは、上流を呼ぶ前なら予約を解放し、呼んだ後なら予約額で確定してから 500（`api_error`）を返す（予約を残さない）。
- **理由**: 回数ではなくトークンに重みを掛けて数えれば、原価と連動し、既定モデルを差し替えても枠の意味が変わらない。最大原価を送信前に原子的に予約すれば、同じアカウントの要求を同時に大量に送っても、確定額と予約額の合計が上限を超えない（判定だけで予約しないと、応答が終わる前の要求はすべて同じ累計を見て通ってしまう）。入力の量も予約に入れるため、巨大な履歴の 1 件でも上限を大きく超えない。ストリームを途中で切る必要も無い。
- **代替案**: 回数で数える（原価と連動しない。長い会話も 1 回）。重みなしのトークン合計で数える（モデルを変えると枠の意味が変わる）。上限をまたいだ時点でストリームを切る（応答が途中で途切れ、アプリ側の処理が複雑になる）。送信前に累計を読むだけで予約しない（当初案。同時要求で上限を任意の倍数まで超えうる。PR #634 の Codex の指摘 P1）。同時要求数の上限だけで抑える（1 件あたりの最大原価 × 同時数までは超えうる）。
- **影響範囲**: `relay/` の計測・利用量のポート。上限値（O2）と重みの実際の値は設定で渡す（S1 はテストで値を渡す）。

### 5. 認証の仮の境界（Q4・親の決定）

- **採用案**:
  - アプリは `authorization: Bearer <トークン>` で中継を呼ぶ（S2 で Rust の通信層に資格情報を 1 行足す）。
  - 中継は**認証のポート**（トークン → アカウント ID、または拒否）でトークンを検証する。ヘッダが無い・形が違う・ポートが拒否したときは、転送せず 401 を返す（本文は Anthropic の形の `authentication_error`）。
  - 利用量の記録と上限の判定は、ポートが返したアカウント ID ごとに分ける（ADR 0011 決定 3）。
  - S1 は認証のポートのテスト用の実装（トークンとアカウント ID の固定の対応表）だけを作る。トークンの形・発行・更新・失効は #584 で決め、S4 で結合する。
- **理由**: #584 が本機能の後に着手されるため、認証方式を推測で作らない（#581 のクリティカル設計決定 3 と同じ考え方）。ポートにしておけば、#584 の方式が決まっても中継のコアは変わらない。
- **代替案**: S1 で認証方式（JWT 等）まで決める（#584 の設計を先取りすることになる）。認証なしで作る（アカウントごとの計測が作れない）。
- **影響範囲**: `relay/` の認証部。

### 6. 推論内容を保存・ログ出力しないことの担保（Q5・親の決定）

- **採用案**:
  - 中継のログは注入する**ログのポート**だけに出し、渡してよい項目はアカウント ID・ステータス・モデル ID・トークン数・原価単位・所要時間・エラーの種類と、固定の語彙のイベントの種類（拒否・完了・精算の失敗・内部エラー・応答の待ち行列の上限の超過〔#641〕）・精算の結果の種類（実額・予約額・記録しない）に限る（後の 2 つは S1 の実装で追加）。ログのポートが例外を投げても、転送と精算は止めない。
  - **利用量の保存先の記録の型は、アカウント ID・期間キー・原価単位・トークン数（4 種）の項目だけを持つ**（構造で限定する）。**予約の型は、予約 ID・アカウント ID・期間キー・原価単位・期限の項目だけを持つ**。
  - **自動テスト**: 要求（`system`・`messages`・ツールの入力）と模擬の上流の応答（本文の差分・ツールの入力）に目印の文字列を入れて中継を通し、ログのポートが受けたすべての記録・`console` の全メソッドへの出力・利用量の保存先のすべての記録・中継自身が作るエラーの応答の本文に、目印が現れないことを確かめる。
  - 本番の実行基盤の要求ログ・エラーの収集の検査手順は S3 で書く（O4 の実行基盤が決まってから）。
- **理由**: 「保存しない」は、保存先に中身を入れる場所が無いことを型で示せる。「ログに出さない」は、目印の文字列がどの出口にも現れないことをテストで固定できる。
- **代替案**: コードレビューだけで担保する（退行を機械で止められない）。
- **影響範囲**: `relay/` 全体。

## 機能全体の設計

### IF / API（S1 で固定する境界・名前は仮）

- **中継の HTTP**: `POST /v1/messages`（Anthropic Messages 形式・`stream` の真偽の両方）。
  - ステータス: 上流の応答のステータス（転送した場合）／400 `invalid_request_error`（検査で拒否）／401 `authentication_error`（認証で拒否）／413 `request_too_large`（入力量の上限）／429 `usage_limit_exceeded`（金額の上限）／429 `rate_limit_error`（同時要求数の上限）／502（上流の失敗。送る前の失敗と送った後の失敗の両方）。
- **処理の順序**: (1) 認証 (2) 入力量の上限（本文のバイト数） (3) JSON の解釈と項目の検査 (4) 既定モデルの解決と書き換え (5) 送信前の予約 (6) 上流への転送 (7) 精算。最初に失敗した段階の応答を返す（例: 認証に失敗し本文も大きすぎる要求は 401）。
- **中継の組み立て**: `createRelayApp(deps)` が Hono のアプリを返す。`deps` は次を持つ。
  - `config`: `upstreamUrl`・`defaultModel`・`models`（許可リストの行）・`maxTokensCap`・`maxRequestBytes`・`inputTokensPerByte`・`dailyLimit`・`monthlyLimit`・`maxConcurrentRequests`・`reservationTtlMs`・`maxBufferedResponseBytes`（省略可。#641）
  - `operatorKey`: 事業者のキー（秘密情報）
  - `authenticate(token) → Promise<accountId | null>`（認証のポート）
  - `usageStore`: `reserve(accountId, dayKey, monthKey, units, limits, expiresAt) → Promise<{ ok: true, reservationId } | { ok: false, reason: "daily" | "monthly" | "concurrency" }>`（確定額・未精算の予約額・同時要求数の判定と予約の追加を原子的に行う。`expiresAt` は予約の期限の時刻で、予約の項目として保持する）・`settle(reservationId, outcome) → Promise<void>`（予約を取り除き、`outcome` に応じて予約が保持するアカウント ID・期間キーで記録する。呼び出し側は期間キーを渡さない。`outcome` は `{ type: "actual", units, inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens }`〔実額〕・`{ type: "reserved" }`〔予約が保持する予約額で確定し、トークン数は 0〕・`{ type: "release" }`〔記録しない〕のいずれか。S1 の実装で、仕様の当初の `actual | null` に「予約額で確定」を足した〔期限切れの回収が同じ遷移を使えるようにし、予約額を呼び出し側が持ち回らずに済むようにするため〕。**精算済み・存在しない予約 ID への `settle` は何もしない〔冪等〕**。クリティカル設計決定 4 の「精算の冪等性」）・`get(accountId, dayKey, monthKey) → Promise<{ dayUnits, monthUnits, reservedDayUnits, reservedMonthUnits, openReservations }>`（テストと S3 の観測用）。利用量のポートは、S3 で永続化する保存先へ差し替えるため非同期の契約にする。S1 はメモリ実装
  - `upstreamFetch(request, signal) → Promise<Response>`（上流のポート）
  - `now() → Date`（時計）
  - `logger`（ログのポート）
- **利用量の記録の型**: `{ accountId, dayKey, monthKey, units, inputTokens, outputTokens, cacheReadInputTokens, cacheCreationInputTokens }`（これ以外の項目を持たない）。
- **予約の型**: `{ reservationId, accountId, dayKey, monthKey, units, expiresAt }`（これ以外の項目を持たない）。期限を過ぎて精算されない予約は予約額で確定する（回収の実装は S3）。
- **設定の検証**: `upstreamUrl` が `https` の URL でない（事業者のキーを平文で送らない。S1 の実装で追加）・`upstreamUrl` がユーザー名・パスワードを含む（fetch の `Request` が拒否し、予約の後で失敗するため。PR #638 の Codex の 2 巡目の指摘）・事業者のキーがヘッダの値に使えない文字を含む（要求のたびに予約の後で失敗するため。PR #638 のレビューで追加）・重みが 10^-4 刻みでない・上限値が整数表現で数えられる範囲を超える（原価単位を整数で数えるため。同）・`defaultModel` が許可リストに無い・上限や重みが負・`maxTokensCap`・`maxRequestBytes`・`inputTokensPerByte`・`maxConcurrentRequests`・`reservationTtlMs` が正でない設定、`maxBufferedResponseBytes` を指定して正の整数でない設定（#641）では、`createRelayApp` が例外を投げる。

### アプリ側の接続（S2 の見通し。S2 を実装対象にするときに詳細を書く）

- **Rust の通信層**（#581 の「1 行ずつ足す」）: 宛先 `relay-messages` → 中継の URL（S3 で決まる）、資格情報 `RelayBearer`（`authorization: Bearer <ライセンストークン>`）、保管の `Provider` にライセンストークンの行。`anthropic-version`・`x-api-key` は付けない（中継が付ける）。
- **TS のバックエンド**: 仮に `relay`。`byok-anthropic` の変換器を宛先の名前を引数に取る形にして使い回す（要求の `model` はプラン込みの既定の値）。能力の宣言は BYOK（Anthropic）と同じ。
- **エラーの分類**: 429 で `error.type` が `usage_limit_exceeded` の応答は再試行不可にする（プロバイダの 429 と、中継の同時要求数の上限の 429〔`rate_limit_error`〕は従来どおり再試行可）。413（`request_too_large`）は既存の規則どおり再試行不可。
- **自動で切り替えない**: 中継の失敗（上限到達を含む）で `byok-anthropic`・`byok-openai` の宛先へ送らない（ADR 0001 改訂の帰結・ADR 0003 決定 9・#582 の機能要件）。
- **課金経路の選択**（プラン込み ⇔ BYOK）は #582 の選択の解決関数（#582 のクリティカル設計決定 5）に「プラン込み」を足す形で入れる。選択の画面は #584 と合わせる。

## 受入基準（S1）

> テストはすべて模擬の上流のポート・テスト用の認証のポート・メモリの利用量のポート・固定時刻の時計で行い、実 API は呼ばない。期間キーの境界のテストは UTC の固定時刻（例: `2026-09-30T23:59:59Z` と `2026-10-01T00:00:00Z`）で行い、`npm run test:tz`（非 UTC のタイムゾーン）でも同じ結果になる。以下「既定のテスト設定」は、許可リストが `claude-haiku-4-5`（重み: 入力 1・出力 5・キャッシュ読み出し 0.1・キャッシュ書き込み 1.25）と `claude-haiku-9-9`（架空の新版・重みは同じ）の 2 行（どちらも adaptive thinking と effort に対応しない行。thinking の書き換えは `adaptive` → `{ "type": "disabled" }`）、`defaultModel` が `claude-haiku-4-5`、`inputTokensPerByte` が 1 の設定を指す（`maxTokensCap`・`maxRequestBytes`・`dailyLimit`・`monthlyLimit`・`maxConcurrentRequests` は、各基準の検査に影響しない十分大きな値を既定とし、基準ごとに必要な値へ変える）。

**認証**

- [ ] `authorization` ヘッダの無い要求は 401 になり、上流のポートは呼ばれない
- [ ] 認証のポートが拒否するトークンの要求は 401 になり、上流のポートは呼ばれない
- [ ] 401 の応答の本文の `error.type` は `authentication_error` である
- [ ] 利用量は、認証のポートが返したアカウント ID ごとに分けて記録される（アカウント A の要求の後に、アカウント B の累計が 0 のままである）

**要求の検査**

- [ ] 最上位に許可リスト外の項目（例: `mcp_servers`）がある要求は 400 になり、上流のポートは呼ばれない
- [ ] `model` がプラン込みの既定の値でない要求（例: `claude-opus-5-5`）は 400 になり、上流のポートは呼ばれない

- [ ] `tools` にプロバイダ側で実行されるツール（例: `type: "web_search_20250305"`）を含む要求は 400 になり、上流のポートは呼ばれない
- [ ] `tools` が `type` の無い関数ツールだけの要求は転送される
- [ ] `max_tokens` の無い要求は 400 になり、上流のポートは呼ばれない
- [ ] `max_tokens` が正の整数でない要求（例: `0`・`-100000`・`1.5`・`"100"`）は 400 になり、上流のポートは呼ばれない（`1` と `maxTokensCap` ちょうどの要求は転送される）
- [ ] 本文が JSON として解釈できない要求は 400 になり、上流のポートは呼ばれない
- [ ] 400 の応答の本文の `error.type` は `invalid_request_error` である
- [ ] 本文の UTF-8 のバイト数が `maxRequestBytes` を超える要求は 413 になり、上流のポートは呼ばれない（`maxRequestBytes` ちょうどの要求は転送される）
- [ ] 413 の応答の本文の `error.type` は `request_too_large` である
- [ ] 検査で拒否した要求（400）は、利用量を記録しない
- [ ] 入力量の上限で拒否した要求（413）は、利用量を記録しない
- [ ] 検査で拒否した要求（400）の後、そのアカウントの未精算の予約は 0 件である（予約より前に検査すること、または拒否時に予約を取り除くことを確かめる）
- [ ] `messages` の内容に URL で参照する画像・文書（`source.type` が `url`）、ファイル参照の画像・文書（`source.type` が `file`）を含む要求は 400 になり、上流のポートは呼ばれず、予約も記録もされない（#635 のオーナーの決定 1）
- [ ] 同じく、`tool_result` の `content` の中（入れ子）に URL・ファイル参照の画像・文書・検索結果を含む要求と、`system` の配列に `text` 以外のブロックを含む要求は 400 になり、上流のポートは呼ばれず、予約も記録もされない
- [ ] 本文に埋め込まれた base64 の画像・PDF を含む要求も 400 になり、上流のポートは呼ばれず、予約も記録もされない（クリティカル設計決定 1 の「base64 も拒否する理由」）
- [ ] `search_result`・`container_upload`・サーバーツールや MCP の結果・`type` の無いブロックを含む要求は 400 になる
- [ ] `cache_control` の `ttl` が `1h` のブロック・ツールを含む要求は 400 になる
- [ ] アプリのチャットの形（`text`・`tool_use`・文字列または `text` のブロックの `tool_result`・`thinking`・`redacted_thinking`・`ttl` の無いか `5m` の `cache_control`）の要求は転送される
- [ ] 入力量の上限で拒否した要求（413）の後、そのアカウントの未精算の予約は 0 件である

- [ ] 同じ要求を、`defaultModel` だけを `claude-haiku-9-9` に差し替えた設定の中継へ送ると、転送される要求の本文の `model` は `claude-haiku-9-9` になる（アプリの要求は同じまま）

**転送のヘッダ**

- [ ] 上流の要求の `x-api-key` は、設定の事業者のキーである
- [ ] 上流の要求の `anthropic-version` は `2023-06-01` である

**応答の転送**

- [ ] 上流の非ストリーミングの 200 の応答の本文は、変わらずにアプリへ返る
- [ ] 上流の 529 の応答は、ステータスと本文が変わらずにアプリへ返る
- [ ] 上流の 429 の応答の `retry-after` は、アプリへの応答に同じ値で付く
- [ ] 上流の応答の `content-type`・`retry-after`・`request-id` 以外のヘッダ（例: `set-cookie`）は、アプリへの応答に付かない
- [ ] 上流のポートが例外を投げると、アプリへの応答は 502 になる
- [ ] 上流が 3xx を返すと、アプリへの応答は 502 で `location` が付かず、利用量を記録せず、未精算の予約も残らない
- [ ] 上流を呼んだ後に想定外の例外が起きた要求（例: 上流の応答の本文が読めない）は 500 になり、その要求の予約額が原価単位として記録され、未精算の予約は残らない

- [ ] ストリーミングの応答でアプリが受け取るバイト列の連結は、上流が返したバイト列の連結と一致する
- [ ] アプリがストリーミングの応答の途中で中止すると、上流のポートに渡した `AbortSignal` が中止の状態になる

**利用量の計測**

- [ ] 非ストリーミングの応答の `usage` の値が記録される

- [ ] 上流のポートが「送る前の失敗」の区分の例外を投げた要求（502）の後、そのアカウントの未精算の予約は 0 件である
- [ ] 上流のポートが「送った後の失敗」の区分の例外を投げた要求（502）は、その要求の予約額が原価単位として記録される

- [ ] 上流の応答ヘッダが届く前にアプリが中止した要求は、その要求の予約額が原価単位として記録される
- [ ] 上流のポートが「送った後の失敗」の区分の例外を投げた要求の後、そのアカウントの未精算の予約は 0 件である

## 仮定（軽微・可逆）

- A1: 仕様ファイルの名前は `llm-relay-server.md`、workspace のディレクトリは `relay/`（決定 O3）。
- A2: プラン込みの既定を表す `model` の値は仮に `"ai-boss-plan-default"`。値は S1 の実装で決めてよい（S2 のアプリ側と同じ定数を使う）。
- A3: 中継の組み立て関数の名前（`createRelayApp`）・ポートの名前・設定の項目の名前は仮。実装で決めてよい。
- A4: Haiku 4.5 の行の thinking の書き換えは「`adaptive` → `disabled`・effort を取り除く」とする（Haiku 4.5 は adaptive と effort に対応しない。公式ドキュメントの Models overview）。`disabled` を送る要求はそのまま `disabled` で送る。書き換えの規則は許可リストの行の設定として持ち、S3 の実 API の確認で違っていたら設定を直す。
- A5: 利用量の期間は UTC の暦日と暦月とする。中継には利用者のタイムゾーンが無いため。#584 で課金周期（契約日起点等）に合わせる場合は、期間キーを求める関数を差し替える。
- A6: 1 日と 1 か月の両方の上限を超えているときの `error.limit` は `"monthly"`（解除までが長いほうを知らせる）。
- A7: （撤回・2026-09-28）同時要求の超過を許容するとしていたが、PR #634 の Codex の指摘 P1 を受けて、送信前の原子的な予約と同時要求数の上限に改めた（クリティカル設計決定 4）。
- A8: 上流の URL は設定の値（本番は `https://api.anthropic.com/v1/messages`。S3 で入れる）。
- A9: 推論原価の見積もりの呼び出し量は、実コードの文字数からの概算（日本語 1 字 ≒ 1〜1.5 トークン）と、典型的な 1 日の利用頻度の仮定に拠る。実測は S3 の実 API の確認で行う。
- A10: 入力の見積もりトークン数は `ceil（要求本文の UTF-8 のバイト数 × inputTokensPerByte）` とする（上流の count_tokens 相当の API は呼ばない。送信の前に外部へもう 1 回送ることになり、遅延と中継の外部送信が増えるため）。`inputTokensPerByte` は設定値で、1 にすれば 1 バイト 1 トークン以下という安全側の上限になる（UTF-8 の日本語は 1 字 3 バイトで、1 字 ≒ 1〜1.5 トークン）。本番の値は S3 の実 API の確認で実測に合わせて決める。値を下げて見積もりが実際の入力を下回った場合、その 1 件は予約額を超えて記録される（クリティカル設計決定 4 の「予約が通った要求は最後まで流す」）。ツール使用時にプロバイダが足すシステムプロンプト（Haiku 4.5 で約 500 トークン）は本文に無いため、`inputTokensPerByte` の余裕で吸収する前提に立つ。
- A11: 同時要求数の上限の 429 は、Anthropic の既存のエラーの形の `rate_limit_error` と `retry-after: 1` にする（アプリの既存のエラーの分類で再試行可になり、S2 で新しい分類を足さずに済む）。金額の上限（`usage_limit_exceeded`）とは再試行の可否が逆である。
- A12: 上流のポート（`upstreamFetch`）は、失敗を区分つきの例外（仮に `UpstreamFailure`、項目 `phase: "before-send" | "after-send"`）で投げる。`"before-send"` は要求のバイトを 1 つも送っていないことが確定している失敗（名前解決・接続の確立・TLS の確立の失敗）に限り、それ以外（送信後のタイムアウト・接続のリセット等）は `"after-send"` とする。区分の無い例外（未知の例外）は `"after-send"` として扱う（安全側）。応答ヘッダが届く前のアプリの中止は、中継が自分で「送った後」と判定する（上流へ要求を渡した後の中止のため）。区分の名前・判定の実装（実行基盤の `fetch` の例外から区分を作る方法）は S3 の実行基盤に合わせて実装で決めてよい。S1 の受入基準は模擬の上流のポートが区分つきの例外を投げて固定する。
- A13: 上流のポートを Web 標準の `fetch` から作る関数（`createFetchUpstream`）は、リダイレクトに従わない（`redirect: "manual"`。PR #638 のレビューで `"error"` から改めた。どの実行基盤でも受け付けられる値にするため）。上流が 3xx（または `opaqueredirect`）を返したときは、`location` を通さずに 502（`api_error`）を返し、要求は処理されていないため予約を解放して記録しない。従うと、`fetch` はオリジンをまたいでも独自のヘッダ（`x-api-key`）を付けたまま転送先へ送るため、事業者のキーが上流の URL 以外へ漏れうる（S1 の実装で追加）。
