# 稼働時間の表現力（中抜け・副業への対応）

## 概要

稼働時間（`work_start` / `work_end`）を、中抜けや副業のある働き方でも壊れずに使えるようにする。**本仕様の実装対象スライス S1 は、現在すでに存在する欠陥——`work_start >= work_end` となる設定が保存でき、保存すると朝会・夕会以外の検知が無言で全停止する——を塞ぐことに限る。** 稼働時間の表現力そのものの拡張（複数区間・曜日別・当日上書き）は、何を可変にするかがまだ決まっていないため後続スライスとし、本仕様では「未決の論点」として記録するに留める。

## 背景・目的

### 稼働時間の設定は既にある。足りないのは表現力で、しかも壊れ方がある

稼働時間は `settings` テーブルの `work_start` / `work_end`（既定 `09:00` / `18:00`。`server/src/detection/detection-types.ts` の `DEFAULT_DETECTION_SETTINGS`）として保存され、`loadDetectionSettings`（`server/src/scheduler/detection-settings.ts`）が読み、`isWithinWorkingHours`（`server/src/detection/time-utils.ts`）が `nowMinutes >= start && nowMinutes < end` ＝ `[start, end)` で判定する。保持できるのは**連続した 1 区間だけ**である。

この構造から 3 つの制約が出る。中抜け（例 9-12 / 15-19）を表現できない、曜日別を表現できない、そして——**日をまたぐ区間が壊れる**。

### 問題A: `work_start >= work_end` は保存でき、保存すると検知が無言で全停止する（実証済み）

本仕様の作成時（2026-09-10）に、`main`（`c390487`）でスクラッチテストを書いて実測した。

`isWithinWorkingHours` に `{ start: "22:00", end: "02:00" }` を与え、ローカル暦日基準（`new Date(2026, 8, 10, h, m)`）で 24 時間を 30 分刻み・48 点走査したところ、**真になる時刻は 0 件**だった。`start=1320 / end=120` となり `nowMinutes >= 1320 && nowMinutes < 120` が成立しないためである。

さらに `evaluateRules`（`server/src/detection/rule-engine.ts`）に同一のタスク・活動・通知履歴・時刻（23:30）を与え、稼働時間の設定だけを変えて比較した:

| 稼働時間の設定 | 発火したルール |
|---|---|
| `22:00`-`02:00`（日またぎ） | `morning_meeting`, `evening_meeting` のみ |
| `22:00`-`23:59`（同日内） | `unstarted`, `deadline_overdue`, `morning_meeting`, `evening_meeting` |

**同一入力・同一時刻で、`work_end` が日をまたぐかどうかだけの違いにより、稼働時間ゲート下の 5 ルールが全滅する。** 残ったのは朝会・夕会だけで、これはゲートの対象外だからである（`rule-engine.ts` の `isWithinWorkingHours` 呼び出しは 1 箇所で、そこが `unstarted` / `avoidance` / `break_overrun` / `silence` / `deadline_overdue` の 5 ルールを一括ゲートする。朝会・夕会の定時ルールだけがゲートの外にある）。

**日またぎに限らない。** `09:00`-`09:00` のような同時刻の設定も同じく常時偽になる。したがって欠陥の条件は「日をまたぐこと」ではなく **`work_start >= work_end`** である。

### なぜ「無言で」なのか — 既存の安全網がこの経路だけ素通りする（発見①）

`isWithinWorkingHours` には、不正な設定値で検知が静かに停止しないための安全網がある。`timeStringToMinutes` が `null` を返したとき、警告ログを出して既定の勤務時間帯へフォールバックする実装で、コメントにも「不正な設定値で検知全体が静かに停止（常に false）しないよう」と明記されている。

しかしこの安全網が効くのは `timeStringToMinutes` が `null` を返すとき——すなわち `HH:mm` として**形式が壊れている**ときだけである。`22:00` も `02:00` も形式としては完全に正当なので `null` にならず、**フォールバックも警告ログも発生しないまま常時偽になる**。実測でも、`{ start: "xx", end: "yy" }` では 13:00 が勤務時間内（既定 09:00-18:00 へフォールバック）と判定される一方、`{ start: "22:00", end: "02:00" }` では 13:00 が勤務時間外のままだった。

**既存の安全網の設計意図が、この経路だけ果たされていない。** 後述の読み出し側ガード（決定 1）は新しい発明ではなく、この意図の回復である。

### 書き込み側だけを直しても既に壊れている DB は救えない（発見②）

読み出し側の `resolveTimeSetting`（`server/src/scheduler/detection-settings.ts`）も、`TIME_PATTERN` を**キー単位**で検査するだけで、`work_start` と `work_end` の相関を見ていない。したがって、既に `work_start=22:00 / work_end=02:00` が保存されている DB は、バリデータを直しても**検知が止まったままになる**。

書き込み側の拒否と読み出し側のガードは、片方だけでは「直った」と言えない。この repo には同型の前例がある（#442「`due_at` を暦日へ一本化し、**不正値を読み出し側でガードする**」）。

### 利用者から見た症状

サボり検知は本アプリの中核価値である（[ADR 0004](../adr/0004-deterministic-detection-engine.md)）。副業のつもりで `22:00`-`02:00` と設定した利用者には、次のことが起きる。

1. 設定画面で保存でき、エラーも警告も出ない
2. 以後、未着手・回避・無音・休憩延伸・締切超過のどれ一つとして通知が飛ばない
3. 通知が飛ばないので `notifications` に行が入らず、「今日は催促されなかった良い日」と見分けがつかない

**利用者が自分で自分の検知を、気付く手がかりの無いまま無効化できてしまう。** これを塞ぐことが S1 の目的である。

## ユーザーストーリー

中抜けや副業のある働き方をするオーナーとして、稼働時間に設定できない値を設定しようとしたときはその場で分かり、**気付かないうちに検知が止まっていることが無い**ようにしたい。

## 機能要件

> 実装対象スライス S1 の範囲。稼働時間の表現力そのものの拡張は「未決の論点」およびスライス表を参照。

- [ ] `work_start` と `work_end` が `work_start >= work_end` となる組み合わせは保存できない
- [ ] 保存が拒否されたとき、その理由が API 応答として返る（画面表示は既存のエラー表示経路が担う。決定 5 のとおり S1 では `web/` を変更しないため、本仕様の受入基準はサーバ側で完結する）
- [ ] `09:00`-`18:00` のような正当な稼働時間はこれまでどおり保存できる
- [ ] 既に `work_start >= work_end` が保存されている DB でも、検知は既定の稼働時間（`09:00`-`18:00`）で動作する
- [ ] 読み出し側のガードが作動したとき、警告ログでそれと分かる
- [ ] 不正な稼働時間設定が保存済みの状態でも、稼働時間ゲート下の 5 ルールが評価される（検知が全停止しない）

## 技術的な制約・方針

- **変更対象（サーバ）**: `server/src/settings/settings-validation.ts`（相関チェックの追加）、`server/src/settings/settings-routes.ts`（相関チェックへ現在の保存値を渡す）、`server/src/scheduler/detection-settings.ts`（読み出し側ガード）
- **送られなかった側が一度も設定されていない場合（`getSettingValue` が `undefined`）は、既定値（`09:00` / `18:00`）を相手として比較する**。`settings` テーブルは空で作られ `work_start` / `work_end` を seed しない（`server/src/db/migrate.ts`）ため、新規インストールでは両キーとも未設定であり、この経路は実在する。**未設定と「不正な値が保存されている」を区別する**のがこの規則の要点である——未設定のとき既定値は*実際に効く値*なので、既定値と突き合わせることは「保存後に実際に効く稼働時間」を評価していることになる。一方、不正な値が保存されているときの既定値は*ガードによる上書き*であり、それを基準にすると不正な書き込みを見逃す（下記）。したがって、例えば `work_start` 未設定の DB へ `{ work_end: "02:00" }` だけを送る更新は、実際に効く稼働時間が `09:00`-`02:00` となって壊れるため拒否する
- **相関チェックは「保存後に DB に入る生の値の組」を対象とする**。`PUT /api/settings` は部分更新（`SettingsPatch`）を受け付けるため、`work_start` / `work_end` の一方だけが送られた場合は、**送られなかった側の現在の保存値**（`getSettingValue` 相当の生値）と突き合わせる。**`loadDetectionSettings` / `readEffectiveSettings` が返すフォールバック適用後の値を基準にしてはならない**——既に `work_start=22:00` / `work_end=02:00` が保存された DB へ `{ work_start: "10:00" }` だけを送ると、フォールバック後の `work_end`（既定 `18:00`）と比較して通過し、生値としては `10:00` / `02:00` という依然として不正な組が書き込まれてしまうため（決定 1 の「保存できない」という趣旨に反する）
- **変更しない**: `server/src/detection/time-utils.ts` の `isWithinWorkingHours`（判定式そのものは S1 では変えない。決定 1 の代替案 C を参照）、`server/src/detection/rule-engine.ts`、`server/src/detection/detection-types.ts` の `DetectionSettings` / `WorkingHours`（表現を変えないため）、`server/src/db/migrate.ts`（S1 はスキーマ変更を伴わない）、休憩まわり（`break-overrun.ts` / `derive-break-status.ts` / `activity-record.ts`）
- **時刻の書式検証は既存の `TIME_PATTERN`（`detection-types.ts`）を再利用する**。新しい正規表現を作らない。S1 が足すのは書式検証ではなく**相関チェック**である
- **エラー応答は既存の `{ error }` 形式に揃える**（`settings-routes.ts` の `c.json({ error: result.error }, 400)`）。設定 API は `code` を持たない（`code` を持つのは reports 系のルータであり、設定 API の既存の作法に合わせる）
- **日付境界に触る変更であるため `npm run test:tz`（非 UTC タイムゾーンでの追加実行）も通す**（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 6）。新規テストの固定時刻は `new Date(y, m, d, h, m)` 由来のローカル日時から導出し、UTC 文字列リテラルで固定しない（同 決定 5）
- **`npm run test:tz` は `main` のベースラインと突き合わせて判定する**。本リポジトリには UTC-11 / UTC+14 でのみ露見する既存欠陥があり、S1 の変更に起因しない失敗をここで新規欠陥と誤認しないため
- **テストでは Claude API・現在時刻・macOS 通知コマンドをモックする**。SQLite はモックしない（一時ファイルまたは `:memory:` で実 DB を使う）

### 並行して走るチケットとの関係（発見③）

`docs/features/today-meeting-time-override.md`（#258）を実装する **#432 / #433 / #434 は 3 件とも未着手（OPEN）** であり、`server/src/meeting-schedule/` はコード上に存在しない。存在するのは仕様のみである。

**S1 と #432-434 はファイル衝突なしに並行出荷できる。** S1 が触る `settings-validation.ts` / `detection-settings.ts` / `SettingsView.tsx` は、#432-434 の仕様が「変更しない」として明示的に挙げている範囲であり、逆に #432-434 が予約している `migrate.ts` の version 9 を S1 は使わない（S1 はスキーマ変更を伴わない）。

## クリティカル設計決定

### 決定 1: 書き込みで弾き、読み出しでガードする（二層）

- **採用案**: `PUT /api/settings` が `work_start >= work_end` を 400 で拒否する。**加えて** `loadDetectionSettings` の読み出し時にも相関を検査し、不正なら既定の `09:00`-`18:00` へフォールバックして警告ログを出す。
- **理由**:
  1. 書き込み側だけでは、**既に不正値が保存されている DB を救えない**（発見②）。バリデータを直しても検知は止まったままで、「直った」と言えない。
  2. 読み出し側ガードは新しい発明ではなく、**既存の安全網の設計意図の回復**である（発見①。形式不正には既にフォールバック＋警告ログがあり、`start >= end` だけがその網を素通りしている）。
  3. repo に同型の前例がある（#442「不正値を読み出し側でガードする」）。
- **代替案**:
  - **B: 書き込みで弾くだけ** — 却下。既存の壊れた DB が救われない（上記 1）。
  - **C: 日またぎを正しく判定する**（`start > end` なら `now >= start || now < end`） — **S1 では却下**。日またぎを表現として認めることになり、**未決の論点 1（何を可変にするか）と暦日境界（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 3・4）との整合を先に決める必要**が生じる。S1 が人間の決定待ちに引きずられ、独立に出荷できるという S1 の存在理由そのものが失われる。
- **将来 C を採る道は閉じていない。** 本決定は「日またぎを永久に禁じる」ものではない。未決の論点 1 で日またぎ稼働を表現として採ると決まった場合、**書き込み側の拒否条件を緩めるだけでよく、読み出し側ガード（不正な組み合わせを既定へ倒して警告する仕組み）はそのまま残って有効に働く。**
- **影響範囲**: `server/src/settings/settings-validation.ts`、`server/src/settings/settings-routes.ts`（相関チェックへ現在の保存値を渡すため）、`server/src/scheduler/detection-settings.ts`。`isWithinWorkingHours` の判定式は変更しない。

### 決定 2: 拒否条件は `work_start >= work_end`（`>` ではない）

- **採用案**: 等号を含む `>=` を拒否条件とする。
- **理由**: 実測により **`09:00`-`09:00`（同時刻）も常時偽**であることを確認した。欠陥は日またぎに固有ではなく「区間が空になること」であり、`>` では同時刻の穴が残る。
- **影響範囲**: 受入基準は日またぎ（`22:00`-`02:00`）と同時刻（`09:00`-`09:00`）の**両方**を拒否される例として含む。

### 決定 3: 予定の中抜けと、その場の休憩は分ける

- **採用案**: 既存の休憩機能（`break_start` / `break_end` の活動イベントと `detection_break_fallback_minutes`）は「その場で始める一時的な状態」として現状のまま残し、稼働区間は設定側で表現する。未決の論点 1 で (a) 複数稼働区間 が採られた場合も、休憩機能と統合しない。
- **理由**:
  1. 休憩は `deriveIsOnBreak`（`web/src/derive-break-status.ts`）が示すとおり、活動イベントの畳み込みで導出される**その場の状態**であり、予定の概念を持たない。あらかじめ決まった中抜けとは意味論が異なる。
  2. [ADR 0007](../adr/0007-local-calendar-day-basis.md) の帰結が、休憩の解釈を `server/src/reports/activity-record.ts`（`pairBreaks`）・`server/src/detection/break-overrun.ts`（`getActiveBreak`）・`web/src/derive-break-status.ts`（`deriveIsOnBreak`）の **3 箇所へ意図的に重複実装**していると明記している（server / web は実行環境が異なり共有できないため）。**この重複は解消すべき負債ではなく意図された設計である。** 中抜けを休憩へ統合すると、この 3 箇所すべてに波及する。
- **影響範囲**: S1 では休憩まわりを一切変更しない。本決定は未決の論点 1 で (a) を採る場合の設計制約として効く。

### 決定 4: 朝会・夕会と稼働時間の非結合を維持する（既決事項の踏襲）

- **採用案**: 稼働時間の外に朝会・夕会の時刻が置かれても、警告も追随もしない。現状の非結合を維持する。
- **理由**: **これは本仕様が新たに決めた方針ではなく、既決事項の踏襲である。** `docs/features/today-meeting-time-override.md`（#258）が機能要件として「当日の時刻を変更しても、勤務時間帯ゲート（`work_start` / `work_end`）は変わらない」を掲げ、「変更しない」対象に `isWithinWorkingHours` を明示している。実装上も、朝会・夕会の定時ルールは稼働時間ゲートの外にあり（`rule-engine.ts`）、20:00-23:00 稼働＋夕会 18:00 という設定でも夕会は通常どおり発火する。
- **影響範囲**: S1 では何も変更しない。整合を促す警告 UI は未決の論点 1 の決定後に別スライスとして検討する。

### 決定 5: S1 ではクライアント側検証を入れず、既存のエラー表示経路に載せる

- **採用案**: 拒否はサーバ（`PUT /api/settings` の 400）のみで行い、`web/` にクライアント側検証を追加しない。表示は既存経路に委ねる。
- **理由**: 実コードで経路の存在を確認した。`settings-routes.ts` が `{ error }` を 400 で返す → `web/src/settings-api.ts` の `toErrorMessage` が `body.error` を読んで `Error` に載せる → `web/src/use-settings.ts` が catch して `saveError` に格納する → `web/src/SettingsView.tsx` が `{saveError !== null && <p role="alert">{saveError}</p>}` で描画する、という経路が**端から端まで既に通っている**。サーバのバリデーションメッセージはそのまま `role="alert"` で画面に出る。したがって S1 で UI へ投資する必要がない。未決の論点 1 の決定後に入力 UI ごと作り直す可能性があるため、いま UI へ投資しない。
- **影響範囲**: `web/` は変更対象外。受入基準はサーバ側で完結させる。

### 決定 6: 未設定キーは既定値を相手として相関チェックする（明示的な仮定）

- **採用案**: `work_start` / `work_end` の一方が未設定のまま他方だけが更新される場合、未設定側は既定値（`09:00` / `18:00`）を相手として相関チェックを行う。
- **理由**: 未設定のとき既定値は**実際に効く値**である（`resolveTimeSetting` が `undefined` に対して既定値を返す）ため、既定値と突き合わせることは「保存後に実際に効く稼働時間」を評価していることになる。決定 1 が禁じている「フォールバック後の値を基準にする」ことと矛盾しない——禁じているのは**不正な保存値をガードが上書きした結果**を基準にすることであり、そちらは不正な書き込みを見逃すのに対し、未設定に対する既定値は上書きではないため。
- **代替案**: **未設定側があるときは相関チェックをスキップする** — 却下。書き込みが素通りし、利用者は保存できたのに効かない設定を持つことになる（読み出し側ガードが作動して既定へ倒れるため検知は止まらないが、利用者から見た「保存できたのに効かない」は本仕様が塞ごうとしている症状に近い）。
- **これは仕様策定時に置いた明示的な仮定であり、オーナーの決定を経ていない。** 拒否範囲を広げる方向の選択であり、読み出し側ガードがどちらの選択でも安全性を担保するため、方針変更は容易（相関チェックの入力を変えるだけで、決定 1・2 の構造は影響を受けない）。

## 未決の論点（人間の決定待ち）

> **この 2 件は本仕様では確定させない。** 実装エージェントも親エージェントもここを埋めてはならない。決定は製品方針・体験の根幹に属し、オーナーの判断を要する。**S1 はこの 2 件のどちらにも依存しない**（背景・目的のとおり、問題A は表現力拡張の可否と独立に塞げる）。

### 論点 1: 何を可変にするのか

(a) 1 日の中の複数稼働区間（中抜け対応） / (b) 曜日別の稼働時間（副業・週末対応） / (c) 当日限りの上書き。**どれを採るか・どう組み合わせるかで設計が別物になる。**

判断材料:

- **(a) 複数区間**: `settings` は値が文字列の平坦な key-value テーブル（`settings-repository.ts` の `getSettingValue` / `setSettingValue`）である。複数区間を JSON 文字列として 1 キーに持つか、専用テーブルを作るかの選択が要る。採る場合は決定 3（休憩と分ける）が設計制約として効く。
- **(b) 曜日別**: 曜日軸は既存のどのデータにも無く、新規の軸になる。
- **(c) 当日限りの上書き**: #432-434 が**会の時刻について**同型の器を設計済みである（`docs/features/today-meeting-time-override.md`: 日付キーの新テーブル、`PUT /api/meeting-schedule/:date`、翌日は行が無い＝既定へ戻る、遅延上限）。ただし**その器はまだコード上に存在せず（3 件とも OPEN）、かつその仕様は稼働時間との非結合を明示的に決定している**（決定 4）。したがって (c) は「既存の器を流用する」のではなく「**同型の別の器を作る**」ことになる。

**後続スライス（S2 以降）は、本論点が決まってから切る。**

### 論点 2: 稼働時間外・中抜け区間で何を止めるのか、中抜け明けの再開を促す通知を出すのか

現状は稼働時間外で 5 ルールを一律停止し、朝会・夕会だけが動く。中抜け区間でも同じでよいか、それとも中抜け明けに再開を促す通知が要るか。

判断材料: 再開を促す通知を出すなら**新しい通知の性質（催促の強度）**に踏み込むことになり、これは本アプリの体験の根幹に当たる。現在の通知はすべて「サボりの検知」に紐づいており、「予定の再開時刻が来た」という時刻起点の通知は存在しない（朝会・夕会が唯一の時刻起点だが、これらはセッション開始を促すものである）。

## スライス（出荷の単位）

| スライス | 内容 | 触るファイル数（概算） | 出荷条件 |
|---|---|---|---|
| S1（最小） | `work_start >= work_end` を保存時に拒否し、読み出し時に既定へフォールバック＋警告する（問題A を塞ぐ） | 4-7 | これだけで価値が出る（利用者が気付かないまま検知を全停止させられる状態が無くなる） |
| S2 以降 | 稼働時間の表現力の拡張（複数区間 / 曜日別 / 当日上書き） | 未定 | **未決の論点 1 が決まってから切る**（何を可変にするかが未定のため、現時点ではスライスに分解できない） |

実装対象: S1

## やらないこと

- **稼働時間の表現力の拡張そのもの**（複数区間・曜日別・当日上書き）（理由: 未決の論点 1 が人間の決定待ちであり、決まるまで設計が定まらない。S1 はこの決定に依存せず独立に出荷できる）
- **日またぎ稼働時間を「正しく判定する」実装**（決定 1 の代替案 C）（理由: 日またぎを表現として認めることは未決の論点 1 と暦日境界の整合を先に決めることになり、S1 の独立性が失われる。将来採る道は閉じていない）
- **朝会・夕会の時刻設定そのものの変更**（理由: #258 / #432-434 の担当範囲であり、決定 4 のとおり稼働時間とは意図的に非結合）
- **休憩機能の作り替え**（理由: 決定 3 のとおり、予定の中抜けとその場の休憩は分ける）
- **通知チャネル・検知ルールの新設**（中抜け明けの再開催促を含む）（理由: 未決の論点 2 が人間の決定待ち）
- **クライアント側（`web/`）の入力検証の追加**（理由: 決定 5 のとおり、サーバのエラーが画面に出る経路が既に通っており、未決の論点 1 の決定後に入力 UI ごと作り直す可能性がある）
- **`isWithinWorkingHours` の判定式の変更**（理由: 決定 1 のとおり、S1 は判定式ではなく設定値の入口と出口を塞ぐ）

## 受入基準

> 実装対象スライス S1 の範囲。

- [ ] `PUT /api/settings` は、保存後に DB へ書き込まれる生の値の組（フォールバック適用前）が `work_start >= work_end` となる更新を 400 で拒否する（日またぎ `22:00`-`02:00`、同時刻 `09:00`-`09:00` のいずれも拒否される）
- [ ] 拒否時の応答ボディが既存の `{ error }` 形式であり、`work_start` / `work_end` の関係が不正であると分かるメッセージを含む
- [ ] `PUT /api/settings` は、`work_start` / `work_end` の一方だけを送る部分更新でも、送られなかった側の現在の保存値との組み合わせが `work_start >= work_end` になる場合は 400 で拒否する
- [ ] `PUT /api/settings` は、送られなかった側が未設定の場合、既定値（`09:00` / `18:00`）を相手として相関チェックを行う（`work_start` 未設定の DB への `{ work_end: "02:00" }` のみの更新は拒否される）
- [ ] `PUT /api/settings` は `work_start`=`09:00` / `work_end`=`18:00` の更新を拒否しない（正当な稼働時間の退行防止）
- [ ] `PUT /api/settings` が `work_start >= work_end` を拒否したとき、`work_start` と `work_end` のどちらの値も DB に書き込まれない（既存の all-or-nothing の作法を維持する）
- [ ] `loadDetectionSettings` は、DB の `work_start` / `work_end` が `work_start >= work_end` のとき `workingHours` として既定値（`09:00`-`18:00`）を返す
- [ ] `loadDetectionSettings` が上記のフォールバックを行うとき、`work_start` / `work_end` の関係が不正である旨の警告ログを出力する
- [ ] `loadDetectionSettings` は、DB の `work_start` / `work_end` が `work_start < work_end` のとき、その値をそのまま `workingHours` として返す（フォールバックしない）
- [ ] DB に `work_start`=`22:00` / `work_end`=`02:00` が保存されている状態でも、`evaluateRules` が稼働時間ゲート下の 5 ルール（`unstarted` / `avoidance` / `break_overrun` / `silence` / `deadline_overdue`）を評価する（検知が全停止しない）
- [ ] 上記の検知に関するテストの固定時刻が `new Date(y, m, d, h, m)` 由来のローカル日時から導出されている（UTC 文字列リテラルで固定しない。[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 5）
