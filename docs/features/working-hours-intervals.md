# 稼働時間の表現力（中抜け・副業への対応）

## 概要

稼働時間（`work_start` / `work_end`）を、中抜けや副業のある働き方でも壊れずに使えるようにする。

**S1 は出荷済み**（PR #488 / commit `f2672c7`。実装チケットは #480〔全量更新の拒否〕/ #481〔部分更新の相関チェック〕/ #482〔読み出し側ガード〕に分解された）。内容は、すでに存在した欠陥——`work_start >= work_end` となる設定が保存でき、保存すると朝会・夕会以外の検知が無言で全停止する——を塞ぐことだった。

**本改訂（2026-09-20 / 2026-09-21）は、S1 の時点で「未決の論点」として保留していたオーナー判断が出そろったことを受け、実装対象スライス S2 を切る。** 決定の逐語は「オーナーの決定（逐語）」節に保存してある。S2 の内容は**帯の外側でのふるまい**に限り、稼働時間の表現そのものは変えない（判断 1 が単一の広い帯を選んだため、表現の拡張が不要になった。決定 7）。

**2026-09-21 の追記**: 最後まで未決だった朝会・夕会の可変化（旧「問④」）に判断 6 で **(4-A)** の回答が出て決着した（決定 12）。(4-A) は**会の恒常設定を現状のまま使う**決定であり、コードを一切変更しない。**したがって朝会・夕会に関する未決の論点はここで閉じ、S2 の範囲は本改訂の前後で変わらない。**

## 背景・目的

### 稼働時間の設定は既にある。足りないのは表現力で、しかも壊れ方がある

稼働時間は `settings` テーブルの `work_start` / `work_end`（既定 `09:00` / `18:00`。`server/src/detection/detection-types.ts` の `DEFAULT_DETECTION_SETTINGS`）として保存され、`loadDetectionSettings`（`server/src/scheduler/detection-settings.ts`）が読み、`isWithinWorkingHours`（`server/src/detection/time-utils.ts`）が `nowMinutes >= start && nowMinutes < end` ＝ `[start, end)` で判定する。保持できるのは**連続した 1 区間だけ**である。

この構造から 3 つの制約が出る。中抜け（例 9-12 / 15-19）を表現できない、曜日別を表現できない、そして——**日をまたぐ区間が壊れる**。

### 問題A: `work_start >= work_end` は保存でき、保存すると検知が無言で全停止する（実証済み）

本仕様の作成時（2026-09-10）に、`main`（`c390487`）でスクラッチテストを書いて実測した。

`isWithinWorkingHours` に `{ start: "22:00", end: "02:00" }` を与え、ローカル暦日基準（`new Date(2026, 8, 10, h, m)`）で 24 時間を 30 分刻み・48 点走査したところ、**真になる時刻は 0 件**だった。`start=1320 / end=120` となり `nowMinutes >= 1320 && nowMinutes < 120` が成立しないためである。

さらに `evaluateRules`（`server/src/detection/rule-engine.ts`）に同一のタスク・活動・通知履歴・時刻（23:30）を与え、稼働時間の設定だけを変えて比較した:

| 稼働時間の設定 | 発火したルール |
|---|---|
| `22:00`-`02:00`（日またぎ） | `morning_meeting`, `evening_meeting` のみ |
| `22:00`-`23:59`（同日内） | `unstarted`, `deadline_overdue`, `morning_meeting`, `evening_meeting` |

**同一入力・同一時刻で、`work_end` が日をまたぐかどうかだけの違いにより、稼働時間ゲート下の 5 ルールが全滅する。** 残ったのは朝会・夕会で、これはゲートの対象外だからである（`rule-engine.ts` の `isWithinWorkingHours` 呼び出しは 1 箇所で、そこが `unstarted` / `avoidance` / `break_overrun` / `silence` / `deadline_overdue` の 5 ルールを一括ゲートする）。

> **訂正（2026-09-20・本改訂で実コードから確認）**: 上の計測当時（2026-09-10）は「ゲートの外にあるのは朝会・夕会の定時ルールだけ」だったが、**現在はもう真ではない**。`commitment_missed`（着手の約束）も 2026-09-13 の ADR 0004 改訂でゲートの外へ移っており（`rule-engine.ts` の `findMissedCommitmentTasks` ループ）、しかも**勤務時間帯の外では「その `rule_key` の通知履歴が 1 件も無いときだけ L1 で 1 回だけ発火する（段階を上げない・活動シグナルでリセットしない）」**という振る舞いを持つ。これは S2 が採る方式（決定 9）と同型の前例であり、S2 は新しい機構を発明しない。

**日またぎに限らない。** `09:00`-`09:00` のような同時刻の設定も同じく常時偽になる。したがって欠陥の条件は「日をまたぐこと」ではなく **`work_start >= work_end`** である。

### なぜ「無言で」なのか — 既存の安全網がこの経路だけ素通りする（発見①）

`isWithinWorkingHours` には、不正な設定値で検知が静かに停止しないための安全網がある。`timeStringToMinutes` が `null` を返したとき、警告ログを出して既定の勤務時間帯へフォールバックする実装で、コメントにも「不正な設定値で検知全体が静かに停止（常に false）しないよう」と明記されている。

しかしこの安全網が効くのは `timeStringToMinutes` が `null` を返すとき——すなわち `HH:mm` として**形式が壊れている**ときだけである。`22:00` も `02:00` も形式としては完全に正当なので `null` にならず、**フォールバックも警告ログも発生しないまま常時偽になる**。実測でも、`{ start: "xx", end: "yy" }` では 13:00 が勤務時間内（既定 09:00-18:00 へフォールバック）と判定される一方、`{ start: "22:00", end: "02:00" }` では 13:00 が勤務時間外のままだった。

**既存の安全網の設計意図が、この経路だけ果たされていない。** 後述の読み出し側ガード（決定 1）は新しい発明ではなく、この意図の回復である。

### 書き込み側だけを直しても既に壊れている DB は救えない（発見②）

読み出し側の `resolveTimeSetting`（`server/src/scheduler/detection-settings.ts`）も、`TIME_PATTERN` を**キー単位**で検査するだけで、`work_start` と `work_end` の相関を見ていない。したがって、既に `work_start=22:00 / work_end=02:00` が保存されている DB は、バリデータを直しても**検知が止まったままになる**。

書き込み側の拒否と読み出し側のガードは、片方だけでは「直った」と言えない。この repo には同型の前例がある（#442「`due_at` を暦日へ一本化し、**不正値を読み出し側でガードする**」）。

### 利用者から見た症状

サボり検知は本アプリの中核価値である（[ADR 0004](../adr/0004-deterministic-detection-engine.md)）。副業のつもりで `22:00`-`02:00` と設定した利用者には、次のことが起きる。

1. 設定画面で保存でき、エラーも警告も出ない
2. 以後、未着手・回避・無音・休憩延伸・締切超過のどれ一つとして通知が飛ばない
3. 通知が飛ばないので `notifications` に行が入らず、「今日は催促されなかった良い日」と見分けがつかない

**利用者が自分で自分の検知を、気付く手がかりの無いまま無効化できてしまう。** これを塞ぐことが S1 の目的である。

## ユーザーストーリー

**S1**: 中抜けや副業のある働き方をするオーナーとして、稼働時間に設定できない値を設定しようとしたときはその場で分かり、**気付かないうちに検知が止まっていることが無い**ようにしたい。

**S2**: フレックスで働くオーナーとして、稼働時間帯を広く取ったうえで、**その帯の外に出たあともボスに完全に黙られたくない**。帯の外で未着手・無音・締切超過・休憩延伸が起きていれば知らせてほしい。ただし**夜通し鳴り続けるのは困る**ので、帯の外では 1 件につき 1 回だけでよい。

## 機能要件

> 実装対象スライス S1 の範囲。S2 の要件は「機能要件（S2）」節を参照。

- [ ] `work_start` と `work_end` が `work_start >= work_end` となる組み合わせは保存できない
- [ ] 保存が拒否されたとき、その理由が API 応答として返る（画面表示は既存のエラー表示経路が担う。決定 5 のとおり S1 では `web/` を変更しないため、本仕様の受入基準はサーバ側で完結する）
- [ ] `09:00`-`18:00` のような正当な稼働時間はこれまでどおり保存できる
- [ ] 既に `work_start >= work_end` が保存されている DB でも、検知は既定の稼働時間（`09:00`-`18:00`）で動作する
- [ ] 読み出し側のガードが作動したとき、警告ログでそれと分かる
- [ ] 不正な稼働時間設定が保存済みの状態でも、稼働時間ゲート下の 5 ルールが評価される（検知が全停止しない）

## 機能要件（S2）

> 実装対象スライス **S2** の範囲。決定 7 により「帯を設定できるようにする」部分は**既に実装済み**（`work_start` / `work_end` を広く取るだけ）なので、S2 が足すのは帯の外側でのふるまいだけである。

- [ ] 勤務時間帯の外でも、稼働時間帯ゲート下の 5 ルール（`break_overrun` / `unstarted` / `avoidance` / `silence` / `deadline_overdue`）が評価され、条件が成立していれば通知が発火する
- [ ] 勤務時間帯の外での発火は、同じ `rule_key` について**その日 1 回だけ**である（段階を上げない・活動シグナルでリセットしない）
- [ ] 勤務時間帯の**中**でのふるまいは従来と変わらない（L1→L2→L3 のエスカレーションと、活動シグナルによる L1 リセットが維持される）
- [ ] 日付が変わると、勤務時間帯の外での「1 回だけ」の枠がリセットされる（前日に鳴ったルールが翌日も鳴りうる）
- [ ] 勤務時間帯の外に出ただけでは通知は発火しない（各ルールの発火条件そのものが成立していることが必要）

## 技術的な制約・方針

- **変更対象（サーバ）**: `server/src/settings/settings-validation.ts`（相関チェックの追加）、`server/src/settings/settings-routes.ts`（相関チェックへ現在の保存値を渡す）、`server/src/scheduler/detection-settings.ts`（読み出し側ガード）
- **送られなかった側が一度も設定されていない場合（`getSettingValue` が `undefined`）は、既定値（`09:00` / `18:00`）を相手として比較する**。`settings` テーブルは空で作られ `work_start` / `work_end` を seed しない（`server/src/db/migrate.ts`）ため、新規インストールでは両キーとも未設定であり、この経路は実在する。**未設定と「不正な値が保存されている」を区別する**のがこの規則の要点である——未設定のとき既定値は*実際に効く値*なので、既定値と突き合わせることは「保存後に実際に効く稼働時間」を評価していることになる。一方、不正な値が保存されているときの既定値は*ガードによる上書き*であり、それを基準にすると不正な書き込みを見逃す（下記）。したがって、例えば `work_start` 未設定の DB へ `{ work_end: "02:00" }` だけを送る更新は、実際に効く稼働時間が `09:00`-`02:00` となって壊れるため拒否する
- **相関チェックは「保存後に DB に入る生の値の組」を対象とする**。`PUT /api/settings` は部分更新（`SettingsPatch`）を受け付けるため、`work_start` / `work_end` の一方だけが送られた場合は、**送られなかった側の現在の保存値**（`getSettingValue` 相当の生値）と突き合わせる。**`loadDetectionSettings` / `readEffectiveSettings` が返すフォールバック適用後の値を基準にしてはならない**——既に `work_start=22:00` / `work_end=02:00` が保存された DB へ `{ work_start: "10:00" }` だけを送ると、フォールバック後の `work_end`（既定 `18:00`）と比較して通過し、生値としては `10:00` / `02:00` という依然として不正な組が書き込まれてしまうため（決定 1 の「保存できない」という趣旨に反する）
- **変更しない**: `server/src/detection/time-utils.ts` の `isWithinWorkingHours`（判定式そのものは S1 では変えない。決定 1 の代替案 C を参照）、`server/src/detection/rule-engine.ts`、`server/src/detection/detection-types.ts` の `DetectionSettings` / `WorkingHours`（表現を変えないため）、`server/src/db/migrate.ts`（S1 はスキーマ変更を伴わない）、休憩まわり（`break-overrun.ts` / `derive-break-status.ts` / `activity-record.ts`）
- **時刻の書式検証は既存の `TIME_PATTERN`（`detection-types.ts`）を再利用する**。新しい正規表現を作らない。S1 が足すのは書式検証ではなく**相関チェック**である
- **エラー応答は既存の `{ error }` 形式に揃える**（`settings-routes.ts` の `c.json({ error: result.error }, 400)`）。設定 API は `code` を持たない（`code` を持つのは reports 系のルータであり、設定 API の既存の作法に合わせる）
  - > **注記（#507）**: 「設定 API は `code` を持たない」は、[`settings-validation-error-response-shape.md`](settings-validation-error-response-shape.md) が意図的に上書きした（勤務時間の前後関係の 400 は日本語の `error` と `code` `invalid_working_hours` を返す）
- **日付境界に触る変更であるため `npm run test:tz`（非 UTC タイムゾーンでの追加実行）も通す**（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 6）。新規テストの固定時刻は `new Date(y, m, d, h, m)` 由来のローカル日時から導出し、UTC 文字列リテラルで固定しない（同 決定 5）
- **`npm run test:tz` は `main` のベースラインと突き合わせて判定する**。本リポジトリには UTC-11 / UTC+14 でのみ露見する既存欠陥があり、S1 の変更に起因しない失敗をここで新規欠陥と誤認しないため
- **テストでは Claude API・現在時刻・macOS 通知コマンドをモックする**。SQLite はモックしない（一時ファイルまたは `:memory:` で実 DB を使う）

- **固定時刻は `new Date(y, m, d, h, m)` 由来のローカル日時から導出する**（ADR 0007 決定 5）。18:00→翌 09:00 の毎分走査を書く受入基準があるため、起点・終点ともローカル暦日から導出すること

### 並行して走るチケットとの関係（発見③）

## クリティカル設計決定

### 決定 1: 書き込みで弾き、読み出しでガードする（二層）

- **採用案**: `PUT /api/settings` が `work_start >= work_end` を 400 で拒否する。**加えて** `loadDetectionSettings` の読み出し時にも相関を検査し、不正なら既定の `09:00`-`18:00` へフォールバックして警告ログを出す。
- **理由**:
  1. 書き込み側だけでは、**既に不正値が保存されている DB を救えない**（発見②）。バリデータを直しても検知は止まったままで、「直った」と言えない。
  2. 読み出し側ガードは新しい発明ではなく、**既存の安全網の設計意図の回復**である（発見①。形式不正には既にフォールバック＋警告ログがあり、`start >= end` だけがその網を素通りしている）。
  3. repo に同型の前例がある（#442「不正値を読み出し側でガードする」）。
- **代替案**:
  - **B: 書き込みで弾くだけ** — 却下。既存の壊れた DB が救われない（上記 1）。
  - **C: 日またぎを正しく判定する**（`start > end` なら `now >= start || now < end`） — **S1 では却下**。日またぎを表現として認めることになり、**未決の論点 1（何を可変にするか）と暦日境界（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 3・4）との整合を先に決める必要**が生じる。S1 が人間の決定待ちに引きずられ、独立に出荷できるという S1 の存在理由そのものが失われる。
- **将来 C を採る道は閉じていない。** 本決定は「日またぎを永久に禁じる」ものではない。未決の論点 1 で日またぎ稼働を表現として採ると決まった場合、**書き込み側の拒否条件を緩めるだけでよく、読み出し側ガード（不正な組み合わせを既定へ倒して警告する仕組み）はそのまま残って有効に働く。**
- **影響範囲**: `server/src/settings/settings-validation.ts`、`server/src/settings/settings-routes.ts`（相関チェックへ現在の保存値を渡すため）、`server/src/scheduler/detection-settings.ts`。`isWithinWorkingHours` の判定式は変更しない。

### 決定 2: 拒否条件は `work_start >= work_end`（`>` ではない）

- **採用案**: 等号を含む `>=` を拒否条件とする。
- **理由**: 実測により **`09:00`-`09:00`（同時刻）も常時偽**であることを確認した。欠陥は日またぎに固有ではなく「区間が空になること」であり、`>` では同時刻の穴が残る。
- **影響範囲**: 受入基準は日またぎ（`22:00`-`02:00`）と同時刻（`09:00`-`09:00`）の**両方**を拒否される例として含む。

### 決定 3: 予定の中抜けと、その場の休憩は分ける

- **採用案**: 既存の休憩機能（`break_start` / `break_end` の活動イベントと `detection_break_fallback_minutes`）は「その場で始める一時的な状態」として現状のまま残し、稼働区間は設定側で表現する。未決の論点 1 で (a) 複数稼働区間 が採られた場合も、休憩機能と統合しない。
- **理由**:
  1. 休憩は `deriveIsOnBreak`（`web/src/derive-break-status.ts`）が示すとおり、活動イベントの畳み込みで導出される**その場の状態**であり、予定の概念を持たない。あらかじめ決まった中抜けとは意味論が異なる。
  2. [ADR 0007](../adr/0007-local-calendar-day-basis.md) の帰結が、休憩の解釈を `server/src/reports/activity-record.ts`（`pairBreaks`）・`server/src/detection/break-overrun.ts`（`getActiveBreak`）・`web/src/derive-break-status.ts`（`deriveIsOnBreak`）の **3 箇所へ意図的に重複実装**していると明記している（server / web は実行環境が異なり共有できないため）。**この重複は解消すべき負債ではなく意図された設計である。** 中抜けを休憩へ統合すると、この 3 箇所すべてに波及する。
- **影響範囲**: S1 では休憩まわりを一切変更しない。本決定は未決の論点 1 で (a) を採る場合の設計制約として効く。

### 決定 4: 朝会・夕会と稼働時間の非結合を維持する（~~既決事項の踏襲~~ ← 下記の訂正を参照）

- **採用案**: 稼働時間の外に朝会・夕会の時刻が置かれても、警告も追随もしない。現状の非結合を維持する。
- **理由**: **これは本仕様が新たに決めた方針ではなく、既決事項の踏襲である。** `docs/features/today-meeting-time-override.md`（#258）が機能要件として「当日の時刻を変更しても、勤務時間帯ゲート（`work_start` / `work_end`）は変わらない」を掲げ、「変更しない」対象に `isWithinWorkingHours` を明示している。実装上も、朝会・夕会の定時ルールは稼働時間ゲートの外にあり（`rule-engine.ts`）、20:00-23:00 稼働＋夕会 18:00 という設定でも夕会は通常どおり発火する。
- **影響範囲**: S1 では何も変更しない。整合を促す警告 UI は未決の論点 1 の決定後に別スライスとして検討する。

> **訂正（2026-09-20・本改訂で実コードと `today-meeting-time-override.md` の全文から確認）**: 上の「**既決事項の踏襲である**」は**言い過ぎだった**。`today-meeting-time-override.md` には「非結合」も「追随」も**一語も出てこない**。同仕様が決めているのは一方向だけである——**「会の時刻を変更しても勤務時間帯ゲートを動かさない」**（機能要件「当日の時刻を変更しても、勤務時間帯ゲート（`work_start` / `work_end`）は変わらない」、および決定 3「朝会・夕会の定時催促の時刻だけを動かす。`work_start` / `work_end` は当日変更の対象にしない」）。

### 決定 5: S1 ではクライアント側検証を入れず、既存のエラー表示経路に載せる

- **採用案**: 拒否はサーバ（`PUT /api/settings` の 400）のみで行い、`web/` にクライアント側検証を追加しない。表示は既存経路に委ねる。
- **理由**: 実コードで経路の存在を確認した。`settings-routes.ts` が `{ error }` を 400 で返す → `web/src/settings-api.ts` の `toErrorMessage` が `body.error` を読んで `Error` に載せる → `web/src/use-settings.ts` が catch して `saveError` に格納する → `web/src/SettingsView.tsx` が `{saveError !== null && <p role="alert">{saveError}</p>}` で描画する、という経路が**端から端まで既に通っている**。サーバのバリデーションメッセージはそのまま `role="alert"` で画面に出る。したがって S1 で UI へ投資する必要がない。未決の論点 1 の決定後に入力 UI ごと作り直す可能性があるため、いま UI へ投資しない。
- **影響範囲**: `web/` は変更対象外。受入基準はサーバ側で完結させる。

### 決定 6: 未設定キーは既定値を相手として相関チェックする（明示的な仮定）

- **採用案**: `work_start` / `work_end` の一方が未設定のまま他方だけが更新される場合、未設定側は既定値（`09:00` / `18:00`）を相手として相関チェックを行う。
- **理由**: 未設定のとき既定値は**実際に効く値**である（`resolveTimeSetting` が `undefined` に対して既定値を返す）ため、既定値と突き合わせることは「保存後に実際に効く稼働時間」を評価していることになる。決定 1 が禁じている「フォールバック後の値を基準にする」ことと矛盾しない——禁じているのは**不正な保存値をガードが上書きした結果**を基準にすることであり、そちらは不正な書き込みを見逃すのに対し、未設定に対する既定値は上書きではないため。
- **代替案**: **未設定側があるときは相関チェックをスキップする** — 却下。書き込みが素通りし、利用者は保存できたのに効かない設定を持つことになる（読み出し側ガードが作動して既定へ倒れるため検知は止まらないが、利用者から見た「保存できたのに効かない」は本仕様が塞ごうとしている症状に近い）。
- **これは仕様策定時に置いた明示的な仮定であり、オーナーの決定を経ていない。** 拒否範囲を広げる方向の選択であり、読み出し側ガードがどちらの選択でも安全性を担保するため、方針変更は容易（相関チェックの入力を変えるだけで、決定 1・2 の構造は影響を受けない）。

### 決定 7: 帯は「単一の広い帯」＝既存の `work_start` / `work_end` をそのまま使う

- **採用案**: フレックスの「帯」は、始業可能帯と終業可能帯を別に持つのではなく、**1 本の広い帯**として表現する。すなわち**既存の `work_start` / `work_end` の値を広く取るだけ**で表現し、新しい設定キー・新しい型・新しいスキーマを**一切追加しない**（例: `07:00`-`22:00`）。
- **理由**: オーナーの回答（逐語は「オーナーの決定（逐語）」節・判断 2）が「単一の広い帯」を選んだ。実コード上、この表現は**すでに完全に実装されている**——`isWithinWorkingHours`（`detection/time-utils.ts`）は `[start, end)` の素直な包含判定であり、`work_start` / `work_end` に広い値を保存すれば「その帯の中で自由に働く」はそのまま成立する。
- **代替案**: **始業可能帯と終業可能帯を別々に 2 本持つ**（コアタイム付きフレックス、設定キー 4 本） — 却下。`SETTINGS_KEYS`（閉じた許可リスト）・`WorkingHours` 型・`isWithinWorkingHours`・`GET /api/settings` の平坦なキー名ビュー（`readEffectiveSettings`）・設定 UI がすべて動く一方、**その 4 値を消費するルールが 1 つも存在しない**（既存 5 ルールはどれも「帯の内側か外側か」しか見ていない）。器だけ作って使い道が後続になるため YAGNI に反する。
- **帰結（重要）**: **「帯を設定できるようにする」というスライスは、中身が空になる。** 判断 2 が (i-A) を選んだことで、#440 に残る実質的な未実装は**帯の外側でのふるまい**（決定 9）だけになった。S2 の内容がそこに絞られるのはこのためである。
- **影響範囲**: 変更なし（`work_start` / `work_end` の値の取り方が変わるだけで、コードは無改変）。

### 決定 8: 所定労働時間（「8 時間」）は設定値として持たない

- **採用案**: オーナーの発言に出てくる「8 時間」を、**検知・催促の対象となる設定値としては持たない**。
- **理由**: オーナーの回答（逐語・判断 2）が「催促させたい数字ではなく、タスクの調整をする際に参考にする稼働時間」と明示した。加えて実コード上、**「実働時間の積算」を検知エンジンへ渡す経路が存在しない**——最も近い `computeActivityRecord`（`server/src/reports/activity-record.ts`）が返すのは `firstTaskStartAt` / `breakCount` / `breakTotalMinutes` の 3 つだけで**実働合計分は無く**、しかもこれは日報の収集層であって `DetectionInput`（`detection/detection-types.ts`）には流れ込んでいない。設定値として持つには「新しい集計 ＋ 新しい入力経路 ＋ 新しいルール」の 3 点セットが要り、S2 より大きな機能になる。
- **保留（問④ に従属）→ 2026-09-21 に解消**: この決定には「問④ で **(4-C)〔稼働時間帯から会の時刻を導出する〕が採られた場合に限り、所定労働時間は『出勤可能帯の終端』を算出するための入力として必要になる**（催促の対象ではないが、導出の入力にはなる）」という保留が付いていた。**判断 6 が (4-A) を選び (4-C) を採らなかったため、この保留は発動しない**（決定 12）。所定労働時間は設定値として持たない、で確定である。
- **影響範囲**: 変更なし。

### 決定 9: 勤務時間帯ゲートは残し、帯の外では「1 回だけ発火」する

- **採用案**: 勤務時間帯ゲートを廃止も拡張もしない。**帯の中は現行どおり**（`resolveEscalation` による L1→L2→L3・活動シグナルでの L1 リセット）とし、**帯の外では `resolveEscalation` を通さず、その `rule_key` の通知履歴が 1 件も無いときだけ L1 で 1 回だけ発火**させる。対象は稼働時間帯ゲート下の 5 ルール（`break_overrun` / `unstarted` / `avoidance` / `silence` / `deadline_overdue`）。
- **理由**:
  1. オーナーの回答（逐語・判断 3）が「通知は止める必要はありません」と決めた一方、**ゲートを単純に外すと通知量が破滅的になる**。本改訂時にスクラッチ検証で実測したところ（ローカル暦日基準 `new Date(2026, 8, 20, h, m)` 由来の固定時刻で 18:00→翌 09:00 を毎分 tick）、**`unstarted` 90 件 ＋ `silence` 90 件 ＝ 一晩 180 件**が発火した。しかもこれは締切超過タスク 0 件・休憩申告なしという**最小構成**での数字で、実利用では `deadline_overdue` が超過タスク数ぶん上乗せされる。
  2. **同型の前例が既にコード上にある。** `commitment_missed` が勤務時間帯外でまったく同じ方式（履歴が無いときだけ L1 で 1 回・段階を上げない・活動シグナルでリセットしない）で動いており（`rule-engine.ts`、ADR 0004 改訂 2026-09-13）、S2 は新しい機構を発明しない。
  3. **通知上限の設計を待たずに出荷できる。** 1 回しか鳴らないため、上限が無くても一晩 3〜数件に収まる（後述の未決の論点「通知上限の細目」を S2 のブロッカーにしない）。
- **代替案**:
  - **(a) ゲートを廃止して 24 時間ずっと通常評価** — 却下。上記の実測 180 件/一晩。とくに `silence` は**就寝中が定義上ずっと無音**であるため最も激しく鳴り、`break_overrun` は `break_end` を押さずに就寝すると朝まで鳴り続ける。採るなら通知上限の新設が**同時に必須**になり、S2 が上限の設計待ちでブロックされる。
  - **(b) 帯の外側まで広げる（帯そのものを新しいゲートにする）** — 却下。鳴り方は (a) と同型で帯の幅に比例するうえ、**帯の外では通知が止まる**ため判断 3「通知は止めない」を字義どおりには満たさない。加えて `[start, end)` は半開区間なので**24 時間の帯は表現できない**（`00:00`-`23:59` でも 23:59〜00:00 の 1 分が穴として残り、`00:00`-`00:00` は決定 2 の 6-A が正しく拒否する）。
- **影響範囲**: `server/src/detection/rule-engine.ts`（帯外の分岐追加）と決定 10（`rule_key` の日次化）、およびそのテスト。**`isWithinWorkingHours` の判定式・`isValidWorkingHoursRange`・書き込み側の相関チェック・読み出し側ガードはいずれも無改変**であり、S1 で入った 6-A は無傷のまま働き続ける。

### 決定 10: 帯の外で使う `rule_key` は日次でリセットする

- **採用案**: 決定 9 の「履歴が 1 件も無いときだけ発火」方式を適用するにあたり、**日付を含まない固定 `rule_key` を持つルールには日付を埋める**（`silence` → `silence:2026-09-20` の形。`break_overrun` も同様）。
- **理由**: `silence` と `break_overrun` の `rule_key` は日付を含まない固定文字列であり（`rule-engine.ts` の `tryFire("silence", "silence", null)` / `tryFire("break_overrun", "break_overrun", null)`）、「履歴が無いときだけ」をそのまま適用すると**一度鳴ったら二度と鳴らなくなる**。日次リセットの先例は `buildMeetingRuleKey`（`detection/meeting.ts`。`morning_meeting:2026-09-20@09:00`）にある。
- **これは受入基準を変えない内部構造の選択であり、実装エージェントが置いた明示的な仮定である**（オーナー・親の決定を経ていない）。`rule_key` を解析している消費者は無く（等値比較とログ出力のみ。`today-meeting-time-override.md` 決定 6 が同じ確認を済ませている）、形式変更の影響は「移行当日に 1 回だけ余分に鳴りうる」側に倒れる。
- **影響範囲**: `rule-engine.ts` の該当 `tryFire` 呼び出しと、`rule_key` を期待値に持つ既存テスト。

### 決定 11: 日またぎ稼働は引き続き扱わない（6-A を維持する）

- **採用案**: S1 で入った 6-A（`work_start >= work_end` を保存時に拒否し、読み出し時に既定へフォールバックして警告する）を**そのまま維持**する。日またぎ稼働（`22:00`-`02:00` 等）は引き続き保存できない。
- **理由**: オーナーの回答（逐語・判断 4）が「外す」と決めた。判断 2 の逐語はフレックスタイムのみに触れており、日またぎを要求していない。
- **決定 7 との整合（重要）**: 単一の広い帯は**帯そのものが `work_start` / `work_end` である**ため、**相関チェックの判定基準は一切変わらない**。`isValidWorkingHoursRange`（`settings/settings-validation.ts`）も、書き込み側の 2 箇所（`validatePutSettingsInput` / `settings-routes.ts` の部分更新チェック）も、読み出し側ガード（`scheduler/detection-settings.ts` の `resolveWorkingHours`）も**無改変で正しく働き続ける**。
- **帰結**: Issue #440 のタイトルと本文が動機に挙げていた**副業（日またぎ）のケースは、本仕様の範囲では解決しない**。決定 1 の「将来 C を採る道は閉じていない」はそのまま有効で、採る場合は ADR 0007（ローカル暦日基準）との整合を先に決める必要がある。
- **影響範囲**: 変更なし。

### 決定 12: 朝会・夕会は「会に独立した恒常設定を持たせる」(4-A)。稼働時間帯から導出しない

- **採用案**: 朝会・夕会の時刻は、これまでどおり**会それぞれの恒常設定**（`morning_meeting_time` / `evening_meeting_time`）で持つ。稼働時間帯（`work_start` / `work_end`）から**導出しない**。決定 4（会の時刻は稼働時間に追随しない）を**維持する**。
- **理由**: オーナーの回答（逐語・判断 6）が (4-A) を選んだ。判断材料は下記のとおり。
- **(4-A) の実体は「現状維持 ＋ 運用の説明」である。** これは本決定のいちばん重要な帰結なので明記する——**新たに作るものは無い。**
  - 会の催促は「帯」ではなく**点**である。`isMeetingDue`（`detection/meeting.ts`）は `nowMinutes >= meetingMinutes` かつ当日その種別のセッションが未開始のときに真を返し、真である限り `resolveEscalation` を通って L1→L2→L3 と段階を上げながら鳴り続ける。
  - したがって「**08:30〜10:00 の間に朝会をすればよい**」という運用は、**`morning_meeting_time = 10:00` と設定すれば今この瞬間に成立する**。10:00 までに朝会を始めていれば `todaysSessionTypes` に `morning` が入って催促は出ず、始めていなければ 10:00 から催促が出る。**帯の始端が会の催促に対して担う仕事は無い**（始端より前に朝会をしても誰も止めないし、止めたい利用者もいない）。
  - **オーナーの「毎回入力が必要になるのはだるいです」への回答は、「#258 の当日上書きを使わず、恒常設定を一度決めればよい」である。** 当日上書き（`/api/meeting-schedule/:date`・ダッシュボードの「今日の会」）は*その日だけ*ずらしたいときの道具であって、常用するものではない。恒常設定はもともと一度決めれば以後の入力が要らない。
- **「夕会も退勤時に固定で良いと思います」は実現しない。** 退勤を検知する経路がコードに存在しないためである（実コードで確認）。
  - `ACTIVITY_EVENT_TYPES`（`server/src/activity/activity-event.ts`）は `task_start` / `break_start` / `break_end` / `checkin` / `chat_message` / `task_update` / `task_pause` の 7 種で、**出勤・退勤に相当する種別が無い**。
  - `sessions.ended_at` は存在するが、`endSession`（`server/src/sessions/sessions-repository.ts`）の docstring が「**`ended_at` is a UI-only marker, not consulted by the detection engine**」と明記しており、検知エンジンから参照されない。
  - 代理候補の評価: **(i) 帯の終端 `work_end`** — 唯一リアルタイムに確定する。実質これしかない。**(ii) 最終アクティビティ** — 「最後だった」は後からしか分からず**原理的にリアルタイム判定不能**。**(iii) 夕会セッションの `ended_at`** — 夕会の時刻を退勤から導くのに退勤を夕会で定義することになり**循環**。**(iv) `clock_out` イベント種別の新設** — 「毎回入力が必要になるのはだるい」に真っ向から反し、かつ検知ルール・イベント種別の新設は本仕様のスコープ外。
  - したがって「夕会 = 退勤時」は実装上「**夕会 = `work_end`**」と読み替えるしかなく、それは `evening_meeting_time` に `work_end` と同じ値を入れるのと**区別がつかない**。(4-A) のもとでは、そうしたい利用者はそう設定すればよい。
- **代替案（いずれも却下）**:
  - **(4-C1) 会の時刻 = 帯の両端**（朝会 = `work_start` / 夕会 = `work_end`） — 却下。**帯を広げるほど朝会が早く鳴りすぎる。** 帯 `07:00`-`22:00` で 10:00 始業のつもりでも、07:00 から段階を上げながら約 3 時間（既定間隔で約 15 件）催促が続く。
  - **(4-C2) 会の時刻 = 帯と所定労働時間から導出**（朝会 = `work_end` − 所定労働時間） — 却下。**帯を広げるほど朝会が遅く鳴りすぎる。** 帯 `07:00`-`22:00`・8 時間なら催促は 14:00 からで、朝会を忘れたまま半日働ける。加えて既定 `09:00`-`18:00`・8 時間でも朝会が **09:00 → 10:00** へ動き、帯を変えていない既存利用者の挙動まで変わる。さらに決定 8 の保留が発動して所定労働時間の設定キー新設を伴う。
  - **(4-C) 共通の却下理由**: 会の時刻は「点」、帯は「幅」であり、**点を帯のどちらの端に結び付けても帯の幅がそのまま催促時刻の誤差になる**。帯を広く取るほど（＝フレックスの自由度を上げるほど）会の催促が実態からずれるため、オーナーの動機と失敗モードが同じ方向を向いてしまう。
- **決定 8 との関係**: (4-C) を採らないため、決定 8 に置いた保留（「(4-C) が採られた場合に限り所定労働時間が導出の入力として必要になる」）は**発動しない**。所定労働時間は設定値として持たない、で確定した。
- **影響範囲**: **変更なし。** サーバ・web ともコードを一切変更しない。S2（決定 9・10）の範囲にも影響しない。

### (4-D) 会の時刻と稼働時間帯の整合を保存時に警告するか（後続スライス候補・今回は採らない）

決定 12 で (4-A) を採ったことにより、**「稼働時間帯と会の時刻がずれても、利用者がそれに気付く手がかりが無い」という穴は残ったままになる**（帯を `20:00`-`23:00` にしても夕会 `18:00` は動かず、警告も出ない。決定 4 のとおりこれは意図された非結合である）。

その受け皿として、**(4-D)「稼働時間帯を保存したとき、朝会・夕会の時刻が帯の外なら警告を出す」**を後続スライスの候補として記録する。決定 4 が「整合を促す警告 UI は……別スライスとして検討する」と書いていたものと同じ対象である。

**(4-D) は今回採らない**（オーナーの決定を経ていないため）。**ここで決めてはならない。**

判断材料:

- **(4-C) の失敗モードを持たない。** 会の時刻を動かさず、ずれていることを知らせるだけなので、帯の幅が催促時刻の誤差になる問題が起きない。
- **既存の経路に載る。** 保存時の拒否・警告は `PUT /api/settings` にあり（`settings/settings-validation.ts` の相関チェックと `settings-routes.ts`）、画面表示は `SettingsView.tsx` の `role="alert"` まで既に通っている（決定 5 で確認済みの経路）。
- **決めることが要る軸**: (1) **拒否か警告か** — 帯の外の会の時刻は正当な設定（決定 4）なので `work_start >= work_end` のような 400 での拒否は適切でない。「保存はできるが警告を出す」形が要り、**これは設定 API に現在存在しない応答の種類**である（現在は `{ error }` / `{ error, code }` の 400 か、成功かの二択）。(2) **どちらを保存したときに警告するか** — 稼働時間帯を変えたとき／会の時刻を変えたとき／両方。(3) **警告の消し方** — 一度閉じたら出さないのか、毎回出すのか。

### 通知上限の細目（S2 の範囲外・後続スライス）

オーナーは「通知は止める必要はありません（が、**通知上限は言ったように設定する**）」と述べたが、上限の細目は指定していない。**決定 9 を採ることで S2 は上限なしでも成立する**（一晩 3〜数件）ため、上限の設計は後続スライスへ送る。

**実コードで確証した前提（本改訂時）**: **「通知上限」は既存設定では表現できず、新設が必要である。** エスカレーション設定 3 本（`escalation_l2_after_minutes` / `escalation_l3_after_minutes` / `escalation_repeat_minutes`）が制御するのは**間隔だけ**であり、`intervalForLevel`（`detection/escalation.ts`）は L3 以降ずっと `level3RepeatMinutes` を返し、`resolveEscalation` は**間隔さえ経過すれば必ず発火を返す**。件数を数える経路も日次でリセットする経路も、`server/src/notifications/` と `server/src/detection/` のどこにも存在しない（走査して 0 件）。実測 90 件/ルール/一晩がその帰結である。

決めることが要る軸:

1. **上限の単位** — (a) 1 日あたりの通知総数 / (b) ルール種別ごと / (c) `rule_key` ごと
2. **リセット境界** — (a) ローカル暦日 00:00（ADR 0007 の既定の暦日境界と揃う） / (b) 朝会の時刻（「1 営業日」の体感と揃う）
3. **上限到達時の挙動** — (a) その日は黙る / (b) まとめて 1 件にする（「未対応が N 件あります」）

判断材料: `notifications` テーブルは `sent_at` を持つため、日次カウントの集計自体は SQL で取れる（新テーブルは不要）。一方、(3)(b) を採ると**通知文面の生成規則**（`notifications/notification-body.ts`）に踏み込むことになり、本アプリの体験の根幹に当たる。

### 中抜け明けの再開を促す通知（従来の論点 2・引き続き未決）

現在の通知はすべて「サボりの検知」に紐づいており、「予定の再開時刻が来た」という時刻起点の通知は存在しない（朝会・夕会が唯一の時刻起点だが、これらはセッション開始を促すものである）。**判断 2 が単一の広い帯を選んだことで「中抜け区間」という概念自体が本仕様の範囲から消えた**ため、本論点は当面発動しない。複数稼働区間を将来扱う場合に再燃する。
