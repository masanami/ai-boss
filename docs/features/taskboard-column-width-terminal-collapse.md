# TaskBoard の列幅を確保し、「完了」「中止」列を既定で畳む

> **ドラフト（2026-09-13）**: 判断 1〜5 は**未確定**（意思決定者の回答待ち）。本文の機能要件・受入基準は**各判断の推奨案で仮に起草**してあり、回答に合わせて書き換える。仕様クリティーク（`/define-feature` Step 6.5）も判断の確定後に行う。

## 概要

タスクボード（`web/src/TaskBoard.tsx`）の「完了」「中止」列を**既定で畳み**、空いた幅を「未着手」「進行中」「一時停止」の 3 列に回す。あわせて列に最小幅を与え、足りないときは横スクロールにしてカードが潰れないようにする。畳んだ列を展開したときに出すのは、従来どおり直近 7 日のタスクだけである（#509）。

## 背景・目的

`.task-board-columns` は `grid-template-columns: repeat(5, 1fr)`（`web/src/TaskBoard.css:50-54`）で、5 列がメイン領域の幅を等分する。メイン領域は `.app-body` の `minmax(0, 1fr)`（`web/src/AppLayout.css:23-32`）なので、左ナビ 200px（`web/src/index.css:19`）・スプリッター 6px・右サイドパネル（既定 280px・最大 420px。`web/src/side-panel-width.ts:8-13`）の分だけ狭くなる。

CSS から算出した 1 列の幅（`.app-main` の左右 padding 1.5rem・列間 gap 1rem を差し引いた外寸）:

| ウィンドウ幅 | サイドパネル | 現状 5 列等分の 1 列 |
|---|---|---|
| 1570px | 280px（既定） | 約 194px |
| 1570px | 420px（最大） | 約 166px |

一方、カード下部の操作行（`.task-card-actions`、`TaskBoard.css:108-112`。`flex` で折り返し指定なし）を 1 行に収めるには、列の外寸で**約 254px** が要る（「メンタリングする」8 字 × 0.85rem ＋ 左右 padding 0.9rem、「編集」2 字 ＋ padding、gap 0.5rem、カードと列それぞれの padding 0.75rem ×2・border 1px ×2 の合計 ≈ 253.6px。`TaskBoard.css:38-48`・`:56-62`・`:86-95`）。現状はこれを 60px 前後下回るため、ボタンが縮みタイトルも折り返す。

オーナーの要望は (1) 列の最小幅を広げる (2) 完了・中止列は基本は見えなくてよい、の 2 つで、どちらも**列幅の配分**に効く。終端 2 列を畳めば残り 3 列に幅が回るため、1 つの仕様で扱う。

### 既存仕様との関係

`taskboard-terminal-columns-recent-window.md`（#428）の決定 1 は「折りたたむ」案を「本件で畳む対象は**アプリの使用期間に比例して増える集合**であり、展開したときの描画件数が単調増加する問題が残る」として却下した（同仕様 :72）。本仕様は**直近 7 日の窓を残したまま畳む**ので、展開時の描画件数は 7 日分に抑えられ、この却下理由には当たらない（窓で絞る決定 1 はそのまま生きる）。

同仕様の決定 6 は「他 N 件は非表示」等の件数表示を「到達手段を作らない（決定 7）のに件数だけ出すと『押せば見られる』という誤った期待を与える」として却下した（同仕様 :115）。本仕様で見出しに出す件数は**窓内の件数＝展開すれば実際に見える件数**であり、押せば見られるという期待は正しい。したがって却下の理由には当たらない（判断 2）。ただし既存テストはこの却下を根拠に見出しを完全一致で固定しているため（`web/src/TaskBoard.test.tsx:934-939`）、テストの改訂が要る。

## ユーザーストーリー

タスクボードで今やる仕事を扱うオーナーとして、**普段は「未着手」「進行中」「一時停止」の 3 列を広い幅で見たい**。終えた仕事（完了・中止）は必要なときだけ開いて直近 7 日分を確かめられればよく、カードを完了・中止へ移す操作は畳んだままでもできてほしい。

## 機能要件

> 判断 1〜4 の推奨案で仮に起草（未確定）。

- [ ] 「完了」「中止」列は、ボードを開いた時点で畳まれている
- [ ] 畳んだ列は、見出しの開閉トグルだけを表示し、カードを表示しない
- [ ] 開閉トグルを押すと、その列が展開されてカードを表示する。もう一度押すと畳まれる
- [ ] 「完了」と「中止」は独立に開閉する
- [ ] 展開した「完了」「中止」列に表示するタスクは、従来どおり直近 7 日に入るものだけである（#428 の絞り込みを変えない）
- [ ] 「完了」「中止」の見出しは、窓の日数と窓内の件数を示す（例: `完了（直近 7 日・3 件）`）。文言は開閉で変わらない
- [ ] 「未着手」「進行中」「一時停止」列は開閉できず、常にカードを表示する
- [ ] 畳んだ「完了」「中止」列にもカードをドラッグして落とせ、そのステータスへ移る。落としても展開はしない
- [ ] 開閉状態は保存しない。タスクボードを開き直すと畳んだ状態に戻る
- [ ] 各列は最小幅を持ち、メイン領域に収まらないときは列グリッドを横スクロールで見る

### 判断 1: 最小列幅と、足りないときの挙動（未確定）

- **選択肢**:
  - **1A**: 展開している列に `minmax(<最小幅>, 1fr)`、畳んだ列は内容幅。足りない分は横スクロール
  - 1B: 最小幅を設けず、畳むだけ（3 列が `1fr` で伸縮）。1570px では足りるが、ウィンドウを狭める・サイドパネルを広げると再び潰れる
  - 1C: 最小幅 ＋ 列の折り返し（`auto-fill` で 2 段組み）。スクロールは出ないが、ステータスの左→右の並びが崩れる
  - 1D: 最小幅だけで畳まない。1570px・既定サイドパネルで常に横スクロールになる
- **最小幅の値**:
  - 16rem（256px）: 操作行の必要幅 約 253.6px に対して余裕 約 2px
  - **18rem（288px）**: 余裕 約 34px。フォント差・ボタン文言の変化に耐える
- **横スクロールの持ち主**:
  - **列グリッド（`.task-board-columns`）に閉じる**: タスク追加フォーム・エラー表示は横に動かない
  - `.app-main` 任せ（何も足さない）: フォームごと横に流れる（確証 #8）
- **推奨**: **1A ＋ 18rem ＋ 列グリッドに閉じた横スクロール**
- **根拠（算出。畳んだ列の幅を 40px と置く）**:

  | 状態 | 必要なメイン内寸（16rem / 18rem） | 横スクロールなしで収まるウィンドウ幅（サイドパネル 280px。16rem / 18rem） | 1570px・280px での 3 列の幅 |
  |---|---|---|---|
  | 既定（3 列展開・2 列畳み） | 912px / 1008px | 1446px〜 / 1542px〜 | 約 297px（どちらでも） |
  | 片方だけ展開（4 列） | 1128px / 1256px | 1662px〜 / 1790px〜 | 横スクロール |
  | 両方展開（5 列） | 1344px / 1504px | 1878px〜 / 2038px〜 | 横スクロール |

  サイドパネルを 420px にすると、表の各ウィンドウ幅に 140px を足す。
  既定の状態では、どちらの値でも 1570px に収まる。18rem のほうが展開したときに横スクロールが早く出るが、展開は利用者が明示的に選ぶ操作なので許容できる
- **波及範囲**: `TaskBoard.css` の `.task-board-columns`（と、畳んだ列のクラス）。見た目のみで、テストからは検証できない（実ブラウザ確認）

### 判断 2: 畳んだ状態の見せ方（未確定）

- **選択肢**:
  - **2A**: 各列を**グリッドの元の位置に細い帯として残す**。`section` と `aria-label` はそのままで、`h2` の中に開閉トグルを置き、カード一覧だけを描画しない。見出し文言は `完了（直近 7 日・N 件）`（N は窓内件数）
  - 2B: 2 列を 1 本のトグル（「完了・中止を表示」）にまとめる。ドロップ先が 1 つになり、完了と中止のどちらへ落としたかを区別できない（判断 4 と両立しない）。`aria-label` 5 列の固定テスト（`TaskBoard.test.tsx:148-157`・`:962-978`）も書き換わる
  - 2C: 畳んだ見出しをグリッドの外（タスク追加フォームの横に置くツールバー）へ出す。3 列が全幅を使えるが、展開すると列が差し込まれて位置が動く
  - 2D: 畳んでも通常の列幅のまま見出しだけ残す。幅が空かないので要望 (1) に効かない
- **推奨**: **2A**。見出しに出す件数は**窓内の件数**に限る
- **根拠**:
  - ドロップの受け口が `section` 全体にあるため（`TaskBoard.tsx:180-191`）、`section` を残せば判断 4 の推奨がコードの追加なしで成り立つ
  - 帯の高さは行の高さ（最低 200px。`TaskBoard.css:61`）まで伸びるので、縦書きの見出し（14 字 × 約 13.6px ≈ 190px）が収まり、細くても狙いやすいドロップ先になる
  - 件数を出すのは、畳んだまま「空かどうか」が分からないと、確かめるために毎回開くことになるため。**N を窓内件数に限れば #428 決定 6 の却下理由（範囲外の件数は押しても見られない）に当たらない**（「既存仕様との関係」）
  - 文言を開閉で変えないのは、押すたびに見出しの長さが変わって帯の幅や行の高さが揺れないようにするため
- **波及範囲**: `TaskBoard.tsx` の見出し描画（`:47-51`・`:193`）と開閉 state。既存テストの見出し固定 2 件（`TaskBoard.test.tsx:930-949`。件数表示の後付けを防ぐ意図のコメントつき）を新しい文言へ改訂する

### 判断 3: 展開状態を覚えるか（未確定）

- **選択肢**:
  - **3A**: 覚えない。`TaskBoard` 内の state。**リロードに加え、タブ切替でも畳んだ状態に戻る**（確証 #7）
  - 3B: 覚えない。state を `AppLayout` へ持ち上げる。タブ切替では保たれ、リロードで戻る。`AppLayout.tsx` と `TaskBoard` の props が増える
  - 3C: `localStorage` に保存する。前例は `resizable-side-panel.md`（キー `ai-boss:side-panel-width`、`side-panel-width.ts:16`・`:106-146`）。読み取りの例外・不正値の扱いまでテストが要る
  - 3D: 設定 API に保存する。`settings` の読み書き経路（サーバ含む）まで波及する
- **推奨**: **3A**
- **根拠**: オーナーの要望は「基本は非表示でよい」で、開くのは例外的な操作である。開き直すたびに既定（畳み）へ戻るのはこの要望に沿う。YAGNI。#245 の仕様も「展開状態は永続化せず、再マウント時は既定に戻る」を採っている（`today-tasks-completed-collapse.md:30`。ただし未実装）。頻繁に開くことが分かったら 3B/3C を別 Issue で扱う
- **波及範囲**: 3A は `TaskBoard.tsx` のみ。3B は `AppLayout.tsx`（本仕様の「変更しない」を外す）、3C は新規モジュールとそのテスト

### 判断 4: 畳んだ列へのドラッグ＆ドロップ（未確定）

- **選択肢**:
  - **4A**: 畳んだ列（帯）もドロップ先として残す。ハイライト（`.task-column-drag-over`）も付く。**落としても展開しない**（件数の増加がフィードバック）

  - 4B: 展開しないと落とせない。畳んだ `section` からハンドラを外す分岐が増え、今は `region "完了"` へ落とすテスト（`TaskBoard.test.tsx:302-354`・`:818-854`）が展開の手順を要するようになる

## 明示的な仮定

1. **畳んだ列の帯の幅を 40px と置いて算出した**（判断 1 の表）。実際の幅は見出しの組み方（縦書きにするか）で決まり、実ブラウザで確認する。帯が広がると、各ウィンドウ幅の閾値が同じ分だけ上がる
