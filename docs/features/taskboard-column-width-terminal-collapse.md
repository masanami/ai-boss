# TaskBoard の列幅を確保し、「完了」「中止」列を既定で畳む

## 概要

タスクボード（`web/src/TaskBoard.tsx`）の「完了」「中止」列を**既定で畳み**、空いた幅を「未着手」「進行中」「一時停止」の 3 列に回す。あわせて列に最小幅（18rem）を与え、足りないときは列グリッドの中だけを横スクロールにしてカードが潰れないようにする。畳んだ列を展開したときに出すのは、従来どおり直近 7 日のタスクだけである（#509）。

## 背景・目的

`.task-board-columns` は `grid-template-columns: repeat(5, 1fr)`（`web/src/TaskBoard.css` の 50〜54 行目）で、5 列がメイン領域の幅を等しく分け合う。メイン領域は `.app-body` の `minmax(0, 1fr)`（`web/src/AppLayout.css` の 23〜32 行目）なので、左ナビ 200px（`web/src/index.css` の 19 行目）・スプリッター 6px・右サイドパネル（既定 280px・最大 420px。`web/src/side-panel-width.ts` の 8〜13 行目）の分だけ狭くなる。

CSS から算出した 1 列の幅（`.app-main` の左右 padding 1.5rem・列間 gap 1rem を差し引いた外寸。実ブラウザでは未計測）:

| ウィンドウ幅 | サイドパネル | 現状（5 列が同じ幅）の 1 列 |
|---|---|---|
| 1570px | 280px（既定） | 約 194px |
| 1570px | 420px（最大） | 約 166px |

一方、カード下部の操作行（`.task-card-actions`。`TaskBoard.css` の 108〜112 行目。`flex` で折り返し指定なし）を 1 行に収めるには、列の外寸で**約 254px** が要る（「メンタリングする」8 字 × 0.85rem ＋ 左右 padding 0.9rem、「編集」2 字 ＋ padding、gap 0.5rem、カードと列それぞれの padding 0.75rem ×2・border 1px ×2 の合計 ≈ 253.6px。`TaskBoard.css` の 38〜48・56〜62・86〜95 行目から算出）。現状はこれを 60px 前後下回るため、ボタンが縮みタイトルも折り返す。

オーナーの要望は (1) 列の最小幅を広げる (2) 完了・中止列は基本は見えなくてよい、の 2 つで、どちらも**列幅の配分**に効く。終端 2 列を畳めば残り 3 列に幅が回るため、1 つの仕様で扱う。

### 既存仕様との関係

`taskboard-terminal-columns-recent-window.md`（#428）の決定 1 は「折りたたむ」案を「本件で畳む対象は**アプリの使用期間に比例して増える集合**であり、展開したときの描画件数が単調増加する問題が残る」として却下した。本仕様は**直近 7 日の窓を残したまま畳む**ので、展開時の描画件数は 7 日分に抑えられ、この却下理由には当たらない（窓で絞る決定 1 はそのまま生きる）。

同仕様の決定 6 は「他 N 件は非表示」のような件数表示を「到達手段を作らない（決定 7）のに件数だけ出すと『押せば見られる』という誤った期待を与える」として却下した。本仕様は見出しに**窓内の件数**を出すため、決定 6 のうち「件数を出さない」部分を改訂する（決定 2）。

## ユーザーストーリー

タスクボードで今やる仕事を扱うオーナーとして、**普段は「未着手」「進行中」「一時停止」の 3 列を広い幅で見たい**。終えた仕事（完了・中止）は必要なときだけ開いて直近 7 日分を確かめられればよく、カードを完了・中止へ移す操作は畳んだままでもできてほしい。

## 機能要件

- [ ] 「完了」「中止」列は、タスクボードを表示した時点で畳まれている
- [ ] 畳んだ列は、見出しの開閉トグルだけを表示し、カードを表示しない
- [ ] 開閉トグルを押すと、その列が展開されてカードを表示する
- [ ] 展開した列でもう一度トグルを押すと畳まれる
- [ ] 「完了」と「中止」は独立に開閉する
- [ ] 展開した「完了」「中止」列に表示するタスクは、従来どおり直近 7 日に入るものだけである（#428 の絞り込みを変えない）
- [ ] 「完了」「中止」の見出しは、窓の日数と窓内の件数を示す（`完了（直近 7 日・N 件）` / `中止（直近 7 日・N 件）`）
- [ ] 見出しの文言は開閉で変わらない
- [ ] 「未着手」「進行中」「一時停止」列は開閉できず、常にカードを表示する
- [ ] 畳んだ「完了」「中止」列にカードをドロップすると、そのステータスへ移る
- [ ] ドロップしても列は展開しない
- [ ] リロードすると畳んだ状態に戻る（開閉状態を保存しない）
- [ ] タブ切替でタスクボードを開き直すと畳んだ状態に戻る
- [ ] 展開している列は最小幅 18rem を持つ
- [ ] メイン領域に収まらないときは列グリッドの中だけが横スクロールする
- [ ] タスク追加フォームは横に動かない

## 設計決定

> #509 の論点に対する決定（2026-09-13 確定）。後続の実装はこの決定に従い、独自判断で逸脱しない。

### 1. 最小列幅と、足りないときの挙動

- **採用案**: 展開している列は `minmax(18rem, 1fr)`、畳んだ列は内容の幅に詰める。メイン領域に収まらないときは、**列グリッド（`.task-board-columns`）の中だけ**を横スクロールにする（列グリッド自身をスクロール領域にし、`.app-main` を横スクロールさせない）。開閉状態を DOM（列の `section` または列グリッドのクラス／属性）に反映し、それを CSS が参照して展開列と畳んだ列の幅を切り替える。反映の具体的な手段（クラス名・grid か flex か・`:has()` か）は実装者が決める
- **理由**:
  - 18rem（288px）は操作行の必要幅（約 253.6px）に約 34px の余裕を持つ。16rem（256px）では余裕が約 2px しかなく、フォント差やボタン文言の変化で折り返す
  - `.app-main` は `overflow-y: auto` のため、何も指定しないとタスク追加フォームやエラー表示まで横に流れる（確証 #8）。列グリッドに閉じればフォームは動かない
  - 既定（2 列を畳んだ状態）はウィンドウ 1542px 以上（サイドパネル 280px）で横スクロールが出ない。展開したときに横スクロールが出るのは、利用者が明示的に開いた結果として許容する
- **幅の算出**（仮定: 畳んだ帯の幅 40px・ルートの文字サイズ 16px・サイドパネル 280px。実ブラウザで確認する）:

  | 状態 | 必要なメイン内寸 | 横スクロールが出ないウィンドウ幅 | 1570px での展開列の幅 |
  |---|---|---|---|
  | 既定（3 列展開・2 列畳み） | 1008px | 1542px 以上 | 約 297px |
  | 片方だけ展開（4 列） | 1256px | 1790px 以上 | 横スクロール |
  | 両方展開（5 列） | 1504px | 2038px 以上 | 横スクロール |

  サイドパネルを 420px にすると、各ウィンドウ幅に 140px を足す
- **代替案**:
  - 最小幅 16rem — 却下（操作行の余裕が約 2px）
  - 最小幅を設けず畳むだけ — 却下。ウィンドウを狭める・サイドパネルを広げると再び潰れる
  - 最小幅 ＋ 列を 2 段に折り返す（`auto-fill`） — 却下。ステータスの左から右への並びが崩れる
  - 最小幅だけで畳まない — 却下。1570px・既定サイドパネルで常に横スクロールになる
  - `.app-main` の横スクロールに任せる — 却下（フォームごと横に流れる）
- **影響範囲**: `TaskBoard.css` の列グリッド側の規則と、開閉状態を DOM に反映する `TaskBoard.tsx` の変更。見た目の要件なので自動テストでは担保せず、実ブラウザで確認する

### 2. 畳んだ状態の見せ方（#428 決定 6 の改訂を含む）

- **採用案**: 各終端列を**グリッドの元の位置に細い帯として残す**。`section` と `aria-label` はそのままで、見出し（`h2`）の中に開閉トグル（`button`）を置き、畳んだときはカード一覧だけを描画しない。トグルの文言は開閉で変えず `完了（直近 7 日・N 件）` / `中止（直近 7 日・N 件）` とし、**N は窓内の件数**（展開したときに描画されるカードの数）とする。日数は `RECENT_TERMINAL_WINDOW_DAYS` から導出する
- **理由**:
  - ドロップの受け口が `section` 全体にあるため（`TaskBoard.tsx` の 180〜191 行目）、`section` を残せば決定 4 がハンドラの追加なしで成り立つ
  - 帯の高さは行の高さ（最低 200px。`TaskBoard.css` の 61 行目）まで伸びるので、縦書きの見出しが収まり、細くても狙いやすいドロップ先になる
  - 件数を出すのは、畳んだまま「空かどうか」が分からないと、確かめるために毎回開くことになるため
  - 文言を開閉で変えないのは、押すたびに見出しの長さが変わって帯の幅や行の高さが揺れないようにするため
- **#428 決定 6 の改訂**:
  - **改訂の範囲**: 決定 6 の代替案「件数表示を出す — 却下」のうち、**窓内の件数**を見出しに出すことを許す。範囲外の件数（「他 N 件は非表示」）を出さないことは変えない。あわせて、件数を後から足すのを防ぐ意図で見出しを完全一致で固定している既存テスト（`TaskBoard.test.tsx` の 930〜949 行目）を、新しい文言の完全一致へ改訂する
  - **改訂の理由**: 決定 6 の却下理由は「到達手段の無い範囲外の件数を出すと、押せば見られるという誤った期待を与える」ことである。窓内の件数はトグルを押せば全件見られる（到達手段がある）ため、この却下理由に当たらない
- **代替案**:
  - 2 列を 1 本のトグルにまとめる — 却下。ドロップ先が 1 つになり完了と中止を区別できない（決定 4 と両立しない）。`aria-label` 5 列の固定テストも書き換わる
  - 畳んだ見出しをグリッドの外（タスク追加フォームの横に置くツールバー）へ出す — 却下。展開すると列が差し込まれて位置が動く
  - 畳んでも通常の列幅のまま見出しだけ残す — 却下。幅が空かず要望 (1) に効かない
  - 件数を出さない — 却下（上記の理由）
- **影響範囲**: `TaskBoard.tsx` の見出し描画（47〜51 行目の `columnHeading`・193 行目の `h2`）と開閉 state。既存テストの見出し固定 2 件の改訂。#428 の仕様の決定 6 に本仕様を参照する注記を足す

### 3. 展開状態を覚えるか

- **採用案**: **覚えない**。開閉 state は `TaskBoard` の中に置く。したがって**リロードに加え、タブ切替（`TaskBoard` のアンマウント）でも畳んだ状態に戻る**
- **理由**: オーナーの要望は「基本は非表示でよい」で、開くのは例外的な操作である。開き直すたびに既定（畳み）へ戻るのはこの要望に沿う。YAGNI。#245 の仕様も「展開状態は永続化せず、再マウント時は既定に戻る」を採っている（`today-tasks-completed-collapse.md`。ただし未実装）
- **代替案**:
  - state を `AppLayout` へ持ち上げる（タブ切替では保ち、リロードで戻る） — 却下。`AppLayout.tsx` と `TaskBoard` の props が増える割に、要望は「基本は非表示」
  - `localStorage` に保存する（前例: `resizable-side-panel.md`、`side-panel-width.ts` のキー `ai-boss:side-panel-width`） — 却下。読み取りの例外・不正値の扱いまで要る。頻繁に開くと分かったら別 Issue で扱う
  - 設定 API に保存する — 却下。サーバの設定の読み書き経路まで波及する
- **影響範囲**: `TaskBoard.tsx` のみ

### 4. 畳んだ列へのドラッグ＆ドロップ

- **採用案**: 畳んだ列（帯）も**ドロップ先として残す**。ハイライト（`.task-column-drag-over`）も今と同じ条件で付く。**落としても展開しない**（件数の増加がフィードバック）
- **理由**: ドロップの受け口が `section` 全体にあるので、`section` を残す決定 2 と組めば既存のハンドラがそのまま使える。ドラッグ以外の手段（キーボード操作）は、カードの「ステータス」`select`（`TaskCard.tsx` の 347〜360 行目）が列の開閉と無関係に使えるため成り立つ（確証 #6）。エビデンス必須タスクを落としたときの拒否表示も今と同じ経路で出る
- **代替案**:
  - 落としたら展開する — 却下。展開で横スクロールが出る・レイアウトが動く
  - 展開しないと落とせない — 却下。畳んだ `section` からハンドラを外す分岐が増え、操作も増える
  - ドラッグ中に帯へ重ねたら自動で展開する — 却下。ドラッグ中に列幅が変わりドロップ位置がずれる
- **影響範囲**: なし（既存のハンドラを使う）。受入基準で「畳んだ列にも落とせる」ことを固定する

### 5. 仕様の置き場所

- **採用案**: 新規ファイル（本ファイル）とし、#428 の仕様（`taskboard-terminal-columns-recent-window.md`）の決定 1・決定 6 に本仕様を参照する注記を 1 行ずつ足す
- **理由**: #428 の仕様の受入基準・変異確認は実装済みのテスト（`TaskBoard.test.tsx` の 580〜979 行目）と対応しており、改訂すると 2 つの課題の受入基準が 1 文書に混ざる。一方、何も足さないと「折りたたみは却下」「件数表示は却下」を読んだ後続が本仕様を誤りと読む
- **代替案**: #428 の仕様を改訂する — 却下（上記）。新規ファイルのみで注記しない — 却下（上記）
- **影響範囲**: `docs/features` の 2 ファイル

## 機能全体の設計

### 実装計画（チケット分解の見通し）

## 明示的な仮定

1. **畳んだ列の帯の幅を 40px と置いて算出した**（決定 1 の表）。実際の幅は見出しの組み方（縦書きにするか）で決まり、実ブラウザ確認のときに 1 列の幅と帯の幅を実測して、算出表と食い違えば表を直す。帯が広がると、各ウィンドウ幅の閾値が同じ分だけ上がる
2. **ルートの文字サイズは 16px**（`web/src/index.css` に `html` の `font-size` 指定が無い）として rem を px に換算した
3. **「メンタリングする」ボタンは朝会・夕会の最中は描画されない**（`TaskCard.tsx` の `onStartMentoring` が `null`）。操作行の必要幅（約 254px）はボタンが出ている状態（adhoc 区間）で算出した
4. **`docs/` は非権威**（CLAUDE.md「開発方針」）。本仕様は実装を駆動する作業文書であり、正本はコードとテストである
