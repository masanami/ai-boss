# 仕事の進め方のメンタリング（朝会での必須メンタリング＋随時メンタリング）

> **正はコードとテスト**であり、本ファイルは権威を持たない（`CLAUDE.md`「開発方針」）。実装と食い違う場合はコードが正。本ファイルは実装を駆動するための作業文書である。
>
> 対象 Issue: #276
>
> **前提 Issue: #358（進言の削除と決定ログのタスク軸再構成）。** 本機能の記録先である `decisions.kind` 列と、参照面であるタスク軸の決定ログは #358 が作る（機能仕様は `docs/features/decision-log-task-axis.md`。本ブランチには未マージ）。**本機能は #358 のマージ後に着手する。**

## 概要

朝会に「今日の仕事の進め方が適切か」を点検するメンタリングのフェーズを差し込み、既定では**それを終えないと朝会を終了できない**ようにする。あわせて、朝会以外でも随時メンタリングを開始できる導線を用意する。点検の結論は `decisions`（`kind = 'mentoring'`）へ記録し、#358 のタスク軸ログから後から参照できるようにする。

## 背景・目的

### 何が足りていないか

朝会のフロー指示（`server/src/boss/persona-prompt.ts` の `MORNING_FLOW_INSTRUCTION`）は既に「今日の予定の報告を受けたら**優先順位とノルマを決定の形で提示**し、`create_task` / `update_task` でタスクへ反映し、その決定を `record_decision` で記録する」まで含んでいる。つまり**優先度を「決める」ことは既にある**。

無いのは、**その進め方自体が妥当かを問い直す**視点である。優先順位を決めても、着手前に決めるべきことを決めていない・関係者に伝えるべきことを伝えていない・そもそも見積もりの前提が崩れている、といった不備は素通りする。オーナーはこうした不備によって手戻りや時間のロスを繰り返しており、**朝会でまず「仕事の進め方に問題がないか」を点検する時間を取りたい**、問題が起きたら**随時も点検したい**、という要望である。

### 本質は「仕事の進め方が適切かのチェック」であり、特定の観点の点検ではない

**Issue に挙げられている 3 例（優先度付け／事前に決めるべき仕様の考慮漏れ／関連部署への連絡）は一例にすぎない。この 3 つを固定のチェック項目として実装すると要望を取り違える。** 実現したいのは「仕事の進め方が適切かどうかをチェックすること」そのものであり、何を見るべきかはその日の仕事の中身によって変わる。

本仕様では、**固定するのは「点検の骨組み（手順）」であって「観点（チェック項目）」ではない**という線引きを判断 4 で確定させている。3 例はプロンプトへ**例示として**渡すが、限定列挙ではないことを併記する。

### 「自分から始める」形にすると成立しない

任意の機能にするとサボられ、結果として失敗や時間のロスにつながる、というのがオーナーの出発点である。したがって**強制する設定を持ち、既定でオンにする**。

「強制」には直接の前例がある — [ADR 0008](../adr/0008-evening-dialogue-prerequisite.md)「日報の生成には夕会での対話完了を前提条件として課す」である。ADR 0008 は、この種の前提条件が**技術的な制限ではなく製品設計上の意図**であり、その区別が記録されていないと「不便だから外す」という一見妥当な改善として削除されうる、と明記している。**本件の強制はこれと同じ型**であり、実装形（409 ＋ 安定した `code`）も判定条件の組み方も流用する。

### 進言（#358 で削除）との関係

念のため記録しておく。#358 で削除する進言は「ユーザー → ボスへの異議申し立て」であり、本機能のメンタリングは「ボス → ユーザーへの指導」で**向きが逆である**。進言を削除する根拠はチャットによる代替であって、本機能ではない。**本機能に異議申し立ての経路を作る必要は無い**（メンタリングの内容に異議があればチャットで伝えればよく、それは進言と同じ理由で専用経路を要しない）。

## ユーザーストーリー

セルフマネジメント中のユーザーとして、朝会でその日の仕事の進め方をボスに点検してもらい、進め方の不備を着手前に潰したい。自分の意志に頼らず必ず点検が入るようにしたい。

## 機能要件

- [ ] 朝会のチャット送信時に組み立てられるシステムプロンプトへ、進め方を点検させる指示が積まれる（**検証範囲は指示の挿入までとし、ボスが実際に何を指摘したかの妥当性はテストしない**。判断 4）
- [ ] メンタリングの点検観点が固定のチェックリストではなく、その日の文脈から選ばれる（指示文が限定列挙を課さない）
- [ ] メンタリングを強制するかどうかを設定で切り替えられる
- [ ] メンタリングの強制は、設定が未設定のときオンとして扱われる
- [ ] 強制がオンのとき、メンタリングを終えていない朝会は終了できない
- [ ] 終了がブロックされたことを、UI が安定した `code` で判別できる
- [ ] 強制がオフのとき、朝会は従来どおりの流れで進み終了できる
- [ ] 朝会以外でもメンタリングを開始できる導線がある
- [ ] メンタリングで扱った観点と結論が、会話ログとは別に構造化された記録として残る
- [ ] 夕会の終了が本機能によってブロックされない
- [ ] 夕会終了時のセッション要約生成が従来どおり動作する
- [ ] 夕会終了時の日報生成フックが従来どおり動作する
- [ ] 既存の朝会フロー指示（優先順位・ノルマの決定 → タスク反映 → `record_decision`）が失われない

## 非機能要件

- ローカル完結を崩さない（[ADR 0001](../adr/0001-local-only-data-boundary.md)）。外部への送信は Anthropic への推論リクエストのみで、メンタリングは新たな外部送信を発生させない。
- メンタリングの完了判定は DB の状態だけで決まる決定的な判定とし、LLM の応答文の解釈に依存させない。

- **`sessions` テーブルのスキーマは変更しない**（判断 1）。本機能でマイグレーションが要るのは #358 の `decisions.kind` だけであり、それは #358 側で完了している。

## 画面・API設計

### 朝会の終了ブロック（`POST /api/sessions/:id/end`）

```jsonc
// POST /api/sessions/12/end  （type = "morning"、メンタリング未完了、強制オン）
// → 409
{
  "error": "仕事の進め方のメンタリングを終えると朝会を終了できます（設定でオフにもできます）",
  "code": "mentoring_required"
}
```

- 判定は**初回の終了遷移（`ended_at` が NULL）のときだけ**行う。既に終了済みのセッションへの再終了は、現行どおり冪等に 200 を返す。
- `type` が `evening` / `adhoc` のセッションでは判定しない。
- 強制設定がオフのときは判定しない。

### 設定（`GET` / `PUT /api/settings`）

```jsonc
{
  "morning_mentoring_required": true   // 追加。boolean で入出力し、DB には "true" / "false" の TEXT で保存
}
```

- キー未設定のときは `true`（＝オン）を返す。
- `PUT` は boolean のみ受理する。文字列 `"true"` も `null` も 400 とする（`boss_strictness` と同じ扱い。`null` を「未設定へ戻す」として受理する `boss_custom_instructions` の規約は、`GET` が `null` を返すキーの往復のためにあるもので、常に `true` / `false` に解決される本キーには当てはまらない。オンへ戻したければ `true` を送ればよい）。

### チャット（`POST /api/sessions/:id/messages`）

```jsonc
{ "content": "今の進め方を見てほしい", "mentoring": true }  // mentoring は任意・既定 false
```

- `mentoring: true` のとき、そのターンのシステムプロンプトへ `MENTORING_FLOW_INSTRUCTION` を積む。
- 朝会（`type = "morning"`）かつ強制設定がオンのときは、`mentoring` の指定にかかわらず同指示を積む。
- **サーバーは `mentoring: true` をセッション種別で拒否しない。** 「随時メンタリングは `adhoc` で行う」（判断 1・6）は**導線の置き方**の決定であって API の制約ではない。種別ごとの許可・不許可という分岐をサーバーに増やしても守るものが無く（単一ユーザーのローカルアプリで、悪意ある呼び出し元を想定しない）、`adhoc` 限定は UI 側のボタン表示条件で表現する。

### 画面

- **チャット画面（`web/src/ChatView.tsx`）**
  - 随時メンタリングの導線として「進め方を点検してもらう」ボタンを置く。押すと `mentoring: true` を付けた定型のユーザー発言を送る。
  - 朝会の終了が `mentoring_required` でブロックされたときは、エラー文言をそのまま出すのではなく `code` で分岐して「メンタリングを終えると朝会を終了できます」という状態表示を出す（[ADR 0008](../adr/0008-evening-dialogue-prerequisite.md) 決定 2 と同じ作法）。**その表示には、設定でオフにできることを併記する**（これを欠くと、ボスがメンタリングの記録を残さなかった場合にユーザーが朝会から抜ける手段を画面上から見つけられなくなる）。
- **設定画面（`web/src/SettingsView.tsx`）**: 「朝会でメンタリングを必須にする」のチェックボックスを追加する。
- **決定ログ画面**: #358 が作ったタスク軸のログをそのまま参照面として使う。**本機能では決定ログ画面を変更しない**（`kind = 'mentoring'` の表示・種別ラベル・タスク軸のグルーピングはすべて #358 の受入基準が担保済み）。したがって本機能の受入基準に決定ログ画面の表示は含めない。
- **随時メンタリングのボタンの表示条件**: **`adhoc`（会でない区間）のチャットのときだけ表示する。** 朝会・夕会の会中は、その会のフロー指示が会話を主導しており（朝会は強制オンなら同じ指示が既に積まれている）、そこへ別経路の点検ボタンを重ねると、どちらの流れにいるのかが画面から読めなくなる。会中に点検を受けたければ会を終えてから押す。

## クリティカル設計決定

### 判断 1: メンタリングは朝会の 1 フェーズとする（判断ポイント 1）

- **採用案**: **朝会セッションの中の 1 フェーズとして実装する。** `sessions.type` に 4 種目を追加しない。随時メンタリングは既存の `adhoc` セッション上で行う。
- **理由**:
  - `sessions.type` は CHECK 制約（`morning` / `evening` / `adhoc`）を持つため、種別追加はテーブル再構築を伴うマイグレーションになる。得られるのは「メンタリングだけを型で切り出せる」ことだけで、割に合わない。
  - メンタリングは「今日の進め方」を扱うため、朝会の予定報告と同じ文脈の中で行うのが自然。別セッションにすると当日のタスク・報告の文脈を再度組み立てる必要が出る。
  - 随時メンタリングも、既に「会でない区間」として存在する `adhoc` の上で成立する。新しい区間の概念を増やさない。**これは導線（ボタンを出す場所）の決定であって、API がセッション種別で `mentoring` フラグを拒否するという意味ではない**（「画面・API設計」参照）。
- **代替案**:
  - **独立したセッション種別 `mentoring` を追加する** — 却下。上記のマイグレーションコストに見合わない。加えて `selectRestoreSessions` / タイムライン境界表示（`BOUNDARY_LABELS`）など、種別を前提にした既存ロジックの改修が広範に発生する。
- **影響範囲**: マイグレーション不要。`persona-prompt.ts` と `chat-messages-route.ts` のプロンプト組み立てのみ。

### 判断 2: 強制は ADR 0008 型の前提条件ゲートとし、対象は朝会の終了操作とする（判断ポイント 2・7）

- **採用案**: **`POST /api/sessions/:id/end` が、`type = 'morning'` かつ強制設定がオンかつメンタリング未完了のとき 409 と `code: "mentoring_required"` を返す。** ブロックはここだけとし、日報生成・夕会・随時チャットはブロックしない。通知（催促）も追加しない。
- **理由**:
  - **プロンプト指示だけでは「強制」にならない。** LLM の裁量で飛ばされうるため、サボらせない仕組みとして機能しない。機械的なゲートが要る。
  - **朝会で機械的に観測できる「前進」は、会の終了しかない。** 「ノルマ確定」は LLM が `update_task` / `record_decision` を呼ぶことで進むもので、独立した確定操作が存在しない。したがってゲートを掛けられる点は終了操作である。ここを塞げば「メンタリングを終えずに朝会の成果へ進めない」が成立する（会を終えられない限り、その日の朝会は完了しない）。
  - **日報（夕会）まで巻き込まないのは、線引きを ADR 0008 と衝突させないため。** 日報は既に「夕会の対話完了」という前提条件を持っており、そこへ朝会のメンタリング未了という別条件を重ねると、日報が出せない理由が 2 系統になって原因を追いにくくなる。ローカル完結の単一ユーザーアプリとして、ブロックは 1 箇所で足りる。
  - **逃げ道は設定のオフ**とする。ボスがメンタリングの記録を残さなかった場合でも、設定をオフにすれば朝会を終了できる。この逃げ道が画面から辿れることを UI の要件に含める（「画面・API設計」参照）。
- **代替案**:
  - **プロンプト指示のみ（ゲート無し）** — 却下。上記のとおり強制にならない。
  - **日報生成もブロックする** — 却下。上記のとおり原因が二重化する。過剰な作り込みでもある。
  - **ブロックせず macOS 通知で催促する** — 却下。催促は無視できるため、オーナーの「自分の意志に頼らない」という要求を満たさない。
  - **朝会の開始をブロックする（メンタリングを終えるまで他の話題に進めない）** — 却下。メンタリングは会話の中で行うため、開始をブロックすると会話そのものが始められず自己矛盾する。
- **影響範囲**: `server/src/sessions/sessions-routes.ts` の `POST /:id/end`。ゲートは `endSession` を呼ぶ**前**に評価し、`type = 'evening'` の経路（要約生成・日報生成フック）には一切触れない。再終了（`ended_at` が既に非 NULL）では評価しない。**判定に使う `type` と「初回の終了遷移か」は、既に `endSession` の前で取得している `before`（`findSessionById` の戻り値）から読む**（`endSession` 後の戻り値を使うと「初回か」を判別できない。現行コードが `isFirstEnding` を `before` から求めているのと同じ理由）。
- **オーナー確定（2026-09-06）**: この案でよい、と口頭で確定。ブロックを朝会の終了 1 箇所に限る点、逃げ道を設定オフのみとする点を含めて承認済み。
- **ADR 化**: この前提条件は技術的制限ではなく製品設計上の意図であるため、実装フェーズで **ADR として記録する**（`/create-adr`）。ADR 0008 と同じ理由——記録が無いと「不便だから外す」という一見妥当な改善として削除されうる。

### 判断 3: メンタリング完了の機械判定（判断ポイント 3）

- **採用案**: **「その朝会セッションに `kind = 'mentoring'` の `decisions` 行が 1 件以上あり、かつそのセッションに `role = 'user'` のメッセージが 1 件以上ある」** の両方を満たすときに完了とする。判定は DB から読んだ 2 つの件数を受け取る純粋関数に切り出す。
- **理由**:
  - **記録の存在だけでは足りない。** ボスの開始ひとこと（`meeting-opening.ts`）や、ユーザーが一言も話さないうちのツール呼び出しで条件を満たせてしまうと、対話の強制にならない。ADR 0008 が「夕会の存在のみを条件にし発言の有無を問わない」案を却下したのと同じ理由である。
  - **ユーザー発言 1 件以上は ADR 0008 と同じ強度の条件**であり、機械的に判定できる。
  - **LLM の応答文を解釈しない。** 「観点をすべて通過したか」を文面から判定する形は非決定的で、テストで固定できない。
- **代替案**:
  - **`kind = 'mentoring'` の記録が 1 件以上あること（発言数を問わない）** — 却下。上記のとおり対話を経ずに満たせる。
  - **ユーザー発言が N 件（N ≥ 2）以上あること** — 却下。会話の往復数は点検の質と相関せず、閾値の根拠が無い。
  - **観点を固定し、すべて通過したかで判定する** — 却下。判断 4 で観点を固定しない方針を採るため成立しない。
- **影響範囲**: `server/src/sessions/mentoring-gate.ts`（新規・純粋関数）。DB 読み取り（該当セッションのメンタリング記録件数・ユーザー発言件数）は呼び出し側の責務とし、[ADR 0004](../adr/0004-deterministic-detection-engine.md) 決定 2 と同じ「純粋関数に DB を触らせない」作法に揃える。

### 判断 4: 「適切な仕事の進め方」の拠り所（判断ポイント 4・本 Issue の中心）

- **採用案**: **(c) ハイブリッド。固定するのは「点検の骨組み（手順）」だけで、「観点（何を見るか）」は固定しない。**

  固定する骨組みは次の 3 ステップ。

  1. ユーザーから、今日の仕事の**進め方**（何を・どの順で・どう進めるつもりか）の申告を受ける。
  2. ボスがその進め方について、**危ういと判断した点を具体的に指摘する**。指摘が無ければ「問題なし」と明示的に断定する。**どの観点で見るかは、その日のタスク・活動記録・直近の決定からボスが選ぶ**。
  3. 点検の**結論**（進め方をどう変えるか／変えないか）を `record_mentoring` で 1 件以上記録する。**このとき `content` に結論を、`rationale` に「どの点をどう危ういと判断したか」＝扱った観点を書く**（完了条件「扱った観点と結論が後から参照できる」を、会話ログを遡らずに満たすため。#358 の決定ログは `rationale` を「根拠」として表示する）。

- **理由**:
  - **観点を固定すると要望を取り違える。** Issue が明記しているとおり、実現したいのは特定の観点の点検ではなく「進め方が適切かのチェック」そのものである。固定チェックリストは、仕事の性質に合わないときに形骸化して「儀式」になる。
  - **一方、完全に LLM 任せ（(b)）では「完了した」を機械判定できず、判断 2 のゲートが成立しない。** 強制を機械的なゲートとして立てる以上、完了を判定できる固定部分がどこかに要る。
  - **骨組みだけを固定すれば、両方を満たせる。** 「結論を 1 件記録する」という手順の完了はツール呼び出しの有無で機械判定でき（判断 3）、その中身（どの観点で何を指摘したか）は毎回自由でよい。**固定しているのは「点検したことの証跡の形」であって「点検の中身」ではない。**
  - **Issue の 3 例（優先度付け／事前に決めるべき仕様の考慮漏れ／関連部署への連絡）は、プロンプトへ例示として渡す。** ただし**限定列挙ではないこと・これだけを点検するのではないことを指示文に明記する**。例示を一切渡さないと、ボスの指摘がその日の報告内容の言い換えに寄りやすいためである。
- **代替案**:
  - **(a) 既存フレームワークを固定する（作業分解・関係者洗い出し・着手前提の明確化・リスク先出し等を固定の観点として課す）** — 却下。再現性と機械判定のしやすさは (c) でも骨組みで確保でき、観点まで固定する追加の利得が無い一方、形骸化のリスクだけが増える。どのフレームワークを採るかという、根拠の無い選択も抱え込む。
  - **(b) LLM が完全にケースバイケースで判断する（骨組みも持たない）** — 却下。完了の機械判定ができず、判断 2 の強制ゲートと噛み合わない。
- **影響範囲**: `server/src/boss/persona-prompt.ts` の `MENTORING_FLOW_INSTRUCTION`。**テストが固定するのは「その指示がプロンプトに含まれる条件」までとし、ボスが実際に選んだ観点の妥当性はテストしない。**

### 判断 5: メンタリングの記録先と記録手段（判断ポイント 5・オーナー決定済み）

- **採用案（記録先はオーナー決定・2026-09-06）**: **`decisions` テーブルを流用し、`kind = 'mentoring'` の行として記録する。** 専用テーブルは作らない。書き込み手段としては、`record_decision` とは**別のツール `record_mentoring` を追加する**。
- **理由**:
  - 専用テーブルは JOIN とビューが増える（オーナー決定）。`decisions` は既に `session_id` / `task_id` / `content` / `rationale` を持ち、メンタリングの結論を表すのに過不足が無い。
  - **`kind` 列は #358 が追加済み**（`ALTER TABLE decisions ADD COLUMN kind ... CHECK (kind IN ('decision','mentoring'))`）。本機能でマイグレーションは発生しない。
  - **`record_decision` に `kind` 引数を足す形ではなく別ツールにする。** 同一ツールに種別引数を持たせると、ボスが通常の裁定を `mentoring` として記録する（またはその逆の）取り違えが起きうる。ツールを分ければ、プロンプト側の指示（骨組みのステップ 3）と呼ぶべきツールが 1 対 1 に対応する。判定（判断 3）が `kind` の正しさに依存するため、ここは曖昧にしない。
  - 実行本体は `insertDecision` に `kind` を任意引数として足して共有する（DRY）。既定値は `'decision'` とし、既存の呼び出しは変更しない。
- **代替案**:
  - **専用テーブル `mentorings` を新設する** — 却下（オーナー決定）。
  - **`record_decision` に `kind` 引数を足す** — 却下。上記の取り違えリスク。
  - **`messages` に残すだけ（構造化して保存しない）** — 却下。完了条件「扱った観点と結論が後から参照できる」を満たすには、会話ログを読み返す以外の手段が要る。判断 3 の完了判定も成立しなくなる。
- **観点の格納先**: **`content` = 結論、`rationale` = 扱った観点**（判断 4 のステップ 3）。ボスの指摘そのものは会話（`messages`）にも残るが、それだけでは会話ログを遡らないと参照できず、完了条件を満たさない。構造化して残すのは「観点」と「結論」の 2 つで足り、やり取りの逐語は `messages` に任せる。
- **`task_id` の扱い**: `record_mentoring` の `task_id` は `record_decision` と同じく任意とする。**対象タスクが特定できる結論には `task_id` を付けるようプロンプトで指示する**（付ければ #358 のタスク軸ログでそのタスクの下に並ぶ）。その日の進め方全体に関わる結論は `task_id` なしとなり、#358 の「タスクに紐づかない決定」セクションに入る。**どちらに落ちるかは LLM の判断であるため、受入基準にはしない。**
- **影響範囲**: `server/src/boss/mentoring-tool.ts`（新規）・`boss-tools.ts`（`BOSS_TOOLS` に常時追加）・`decisions-repository.ts`。

### 判断 6: 随時メンタリングは明示の導線のみとし、検知エンジンには足さない（判断ポイント 6）

- **採用案**: **ユーザーが明示的に開始する導線のみを用意する。** チャット画面の「進め方を点検してもらう」ボタンが、`mentoring: true` を付けた定型のユーザー発言を送る。**検知エンジンに新しいルールは追加しない。**
- **理由**:
  - Issue の完了条件は「朝会以外でも、**必要になったタイミングでメンタリングを開始できる導線がある**」であり、明示の導線で満たせる。
  - 「問題が発生したら」を機械的に定義できない。[ADR 0004](../adr/0004-deterministic-detection-engine.md) の検知ルールは「未着手」「無音」「休憩延伸」のように**経過時間で決まる**事象を対象にしており、「進め方が危うい」はこの形に落ちない。無理に閾値を作れば誤発火し、催促は誤発火が信頼を直接損なう領域である（ADR 0004 背景）。
  - フラグを付けたチャット送信にするのは、**随時でも朝会と同じ骨組み（指摘 → 結論の記録）を通すため**。単なる定型文の送信では `record_mentoring` を呼ぶ動機がプロンプトに無く、随時メンタリングだけ記録が残らないことになる。
- **代替案**:
  - **検知エンジンに「進め方の点検が必要」ルールを足す** — 見送り。上記のとおり機械的な定義が立たない。必要になったら別 Issue で、まず「何をもって問題発生とするか」の定義から始める。
- **オーナー確定（2026-09-06）**: 自動起動は**不要**。「こちらから申請したときのみ」と口頭で確定した。将来 Issue としても起こさない。
  - **ボタンが定型文を送るだけ（プロンプトへの指示追加なし）** — 却下。上記のとおり記録が残らない。
  - **随時メンタリング専用の API エンドポイントを新設する** — 却下。チャットと同じ経路（メッセージ送信 → ストリーミング応答 → ツール実行）を通るため、既存ルートにオプションを 1 つ足すほうが単純。
- **影響範囲**: `server/src/sessions/chat-messages-route.ts`・`sessions-validation.ts`（`mentoring` の検証）・`web/src/ChatView.tsx`・`use-chat.ts`・`chat-api.ts`。

### 判断 7: 設定キーの型と既定値（判断ポイント 8）

- **採用案**: **キー名 `morning_mentoring_required`。DB には既存の全 TEXT の慣習どおり `"true"` / `"false"` で保存する。API は boolean で入出力する。未設定はオン（`true`）として解決する。初期投入（マイグレーションでの INSERT）は行わない。**
- **理由**:
  - **`settings` は全 TEXT の KV**（`key TEXT PRIMARY KEY, value TEXT`）であり、boolean の設定キーは本件が第 1 号になる。保存形式を TEXT に合わせるのは既存構造との整合。
  - **API を boolean にするのは既存の作法と揃うため。** `boss_strictness` は API では number で受け取り `String(value)` で保存しており（`settings-validation.ts`）、「API は素の型・保存は TEXT」という形が既にある。文字列 `"true"` を API で受け付けると、型の揺れ（`"True"` / `"1"` など）を検証する分岐が増える。
  - **「未設定＝オン」で表現するのは、既定値の解決が読み手側にある既存構造にそのまま乗るため**（`resolveBossSettings` / `loadDetectionSettings` はいずれも「未設定または不正なら既定値」で解決する）。マイグレーションで初期値を INSERT すると、既定値の在り処が DB とコードの 2 箇所に分かれる。
  - **不正な値（例: `"yes"`）は既定値（オン）へフォールバックする。** 「読めない値なら既定値」は既存リーダーの一貫した作法であり、**フォールバック先をオンにするのは、壊れた値で強制が黙って無効化されるのを防ぐため**（安全側に倒す）。
- **代替案**:
  - **API も文字列 `"true"` / `"false"` で受ける** — 却下。上記の揺れの検証が増える。
  - **マイグレーションで `("morning_mentoring_required", "true")` を初期投入する** — 却下。既定値が 2 箇所になる。既存 DB への遡及も要る。
  - **キー名を `mentoring_required` にする** — 却下。強制の対象は朝会に限る（随時メンタリングは常に任意）ため、名前で範囲を示す。
- **影響範囲**: `server/src/settings/settings-validation.ts`（`SETTINGS_KEYS` と `VALIDATORS` への追加・boolean 用バリデータの新設）・`settings-routes.ts` の `readEffectiveSettings`・設定を読む側・`web/src/settings.ts` の `Settings` 型・`SettingsView.tsx`。

### 判断 8: 既存の朝会フローとの順序（判断ポイント 9）

- **採用案**: **予定の報告 → メンタリング（進め方の点検） → 優先順位・ノルマの決定 → タスクへの反映 → `record_decision`。** `MORNING_FLOW_INSTRUCTION` の既存の手順の**前段**にメンタリングを差し込む。
- **理由**:
  - 点検の結果は優先順位・ノルマに反映されるべきものである（「その仕様を先に決めないと着手できない」と分かれば、その日の順番自体が変わる）。決定の後に点検すると、決めたことをすぐ覆すか、点検が形だけになる。
  - 既存の手順そのものは変更しない（削らない・順序を入れ替えない）。前に 1 段足すだけなので、既存の朝会の振る舞いへの影響が最小になる。
- **代替案**:
  - **優先順位・ノルマを決めてから、その妥当性を点検する** — 却下。上記のとおり手戻りか形骸化になる。
  - **朝会の終了直前に点検する** — 却下。同上。加えてゲート（判断 2）が終了操作に掛かるため、「終了しようとしたら点検が始まる」という体験になり不自然。
- **影響範囲**: `server/src/boss/persona-prompt.ts`。強制設定がオフのときは `MENTORING_FLOW_INSTRUCTION` を積まず、`MORNING_FLOW_INSTRUCTION` は従来のまま出す。

### 判断 9: 「関連部署への連絡」は洗い出しと促しまで（判断ポイント 10）

- **採用案**: **本アプリの範囲は「連絡すべき相手と内容を洗い出し、ユーザーに促す」までとする。** 実際の連絡（メール・チャット送信）は行わない。
- **理由**: 全データはローカル SQLite のみ、外部送信は Anthropic への推論リクエストだけ、というのが不変制約である（[ADR 0001](../adr/0001-local-only-data-boundary.md)）。連絡の実行は外部送信そのものであり、この制約の再設計を伴う。
- **影響範囲**: `MENTORING_FLOW_INSTRUCTION` の文面（実行できないことを約束させない）。この線引きは判断 4 の「観点を固定しない」と両立する——「関連部署への連絡」は固定の観点ではなく例示の 1 つだが、**それが指摘として出たときにアプリが何をするか**の線引きは固定する。

## 機能全体の設計

### 処理の流れ

```text
[朝会]
POST /api/sessions        → 朝会セッション作成（既存・開始ひとこと生成も既存のまま）
POST /api/sessions/:id/messages
  └ sessionType = morning かつ 強制オン
      → system prompt = ... + MENTORING_FLOW_INSTRUCTION + MORNING_FLOW_INSTRUCTION
      → ボスが進め方を点検し、結論を record_mentoring で記録（kind='mentoring'）
POST /api/sessions/:id/end
  └ 初回終了 かつ type=morning かつ 強制オン
      └ isMentoringComplete(mentoringCount, userMessageCount) が false
          → 409 { code: "mentoring_required" }   ← ここで止まる（endSession を呼ばない）
      └ true → 既存どおり終了（要約生成は morning でも従来どおり動く）

[随時]
POST /api/sessions/:id/messages { mentoring: true }
  → system prompt に MENTORING_FLOW_INSTRUCTION を足す（強制設定に関わらず）
  → 記録は朝会と同じ（kind='mentoring'）

[参照]
GET /api/decisions → #358 のタスク軸ログが kind ごとのラベル付きで表示
```

### 実装計画（チケット分解の見通し・案）

`/create-ticket` で最終決定する前提の案。**すべて #358 のマージ後に着手する。**

1. **サーバー: 設定キー `morning_mentoring_required`** — `SETTINGS_KEYS` / boolean バリデータ / 実効設定への追加 / 読み手（未設定・不正値はオン）。
2. **サーバー: `record_mentoring` ツールと `insertDecision` の `kind` 対応** — ツール定義・実行関数・`BOSS_TOOLS` への追加・ディスパッチ。

6. **web: 設定画面の項目追加**。
7. **ADR: 朝会メンタリングの前提条件ゲート**（`/create-adr`。判断 2 の ADR 化）。

- [ ] 強制設定がオフのとき、朝会セッションのチャット送信で組み立てられるシステムプロンプトにメンタリングの指示が含まれない

- [ ] 強制設定がオフのとき、朝会セッションのシステムプロンプトに既存の朝会フロー指示が含まれる

### 朝会終了のゲート

- [ ] 強制オン・メンタリング記録なしの朝会を終了しようとすると 409 が返る
- [ ] そのときの応答の `code` が `mentoring_required` である
- [ ] 強制オン・メンタリング記録ありだがユーザー発言が 0 件の朝会を終了しようとすると 409 が返る
- [ ] 強制オン・メンタリング記録ありかつユーザー発言が 1 件以上ある朝会は終了できる（200）
- [ ] 強制オフの朝会は、メンタリング記録が無くても終了できる（200）
- [ ] ブロックされた朝会セッションの `ended_at` が NULL のままである
- [ ] 既に終了済みの朝会への再終了は、メンタリング記録の有無にかかわらず 200 を返す
- [ ] 夕会セッションの終了は、メンタリング記録の有無にかかわらず 409 にならない
- [ ] 夕会終了時のセッション要約生成が従来どおり実行される
- [ ] 夕会終了時の日報生成フックが従来どおり実行される

### 随時メンタリング

- [ ] `mentoring: true` を付けたチャット送信で、システムプロンプトにメンタリングの指示が含まれる
- [ ] `mentoring` を省略した随時チャットの送信では、システムプロンプトにメンタリングの指示が含まれない
- [ ] `mentoring` に boolean 以外を渡すと 400 が返る
- [ ] 随時チャット（`adhoc`）のチャット画面に、随時メンタリングを開始するボタンが表示される
- [ ] 朝会・夕会の会中のチャット画面に、随時メンタリングを開始するボタンが表示されない

### 設定

- [ ] `GET /api/settings` の応答に `morning_mentoring_required` が含まれる
- [ ] キーが未設定のとき `GET /api/settings` が `morning_mentoring_required: true` を返す
- [ ] `PUT /api/settings` で `morning_mentoring_required: false` を保存できる
- [ ] `PUT /api/settings` に `morning_mentoring_required` として文字列 `"true"` を渡すと 400 が返る
- [ ] `PUT /api/settings` に `morning_mentoring_required` として `null` を渡すと 400 が返る
- [ ] 保存された値が `settings` テーブルに `"true"` / `"false"` の文字列として入る
- [ ] キーの値が `"true"` / `"false"` 以外の文字列のとき、強制はオンとして解決される
- [ ] 設定画面にメンタリングの必須設定を切り替えるコントロールが表示される

### UI の分岐

- [ ] 朝会の終了が `mentoring_required` でブロックされたとき、UI がエラーメッセージの文言ではなく `code` で分岐する
- [ ] ブロック時の表示に、設定でメンタリングの強制をオフにできる旨が含まれる
