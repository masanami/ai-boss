# サイドパネルの幅を可変にする（ドラッグ可変スプリッター）

> **正はコードとテスト**であり、本ファイルは権威を持たない（`CLAUDE.md`「開発方針」）。実装と食い違う場合はコードが正。実装を駆動するための作業文書。

## 概要

右サイドパネル（`.app-side-panel`）と中央（`.app-main`）の境界にスプリッターを置き、ドラッグとキーボード操作で右サイドパネルの幅を変えられるようにする。変えた幅は `localStorage` に保存し、リロードをまたいで復元する。左ナビ（`--nav-width: 200px`）は対象外。

## 背景・目的

現状のレイアウトは `.app-body` の 3 カラムグリッド `var(--nav-width) 1fr var(--side-panel-width)` で、両脇が固定 px・中央だけが `1fr` で伸縮する。サイドパネルは `--side-panel-width: 280px` 固定、`padding: 1rem` ＋左ボーダー 1px を差し引いた実効内容幅は 247px しかない。ウィンドウをどれだけ広げてもこの 247px は変わらないため、サイドパネル内の情報量に対して幅が足りない場面（Issue #252 の折り返し問題の一因）でもユーザーに逃げ道がない。

幅の最適値は表示内容とディスプレイに依存し、開発側が単一の固定値で決め切れない。ユーザー自身が境界を掴んで決められるようにする。

## ユーザーストーリー

セルフマネジメント中のユーザーとして、右サイドパネルと中央ビューの境界をドラッグ（またはキーボード操作）して、その時の作業に合った幅配分に調整し、次回の起動でもその幅で使い始めたい。

## 機能要件

- [ ] 中央ビューと右サイドパネルの境界にスプリッターが表示される
- [ ] スプリッターをポインタでドラッグすると右サイドパネルの幅が追従して変わる（**自動テストで担保せず `/demo` の目視で完了とする**。下記「テストで担保する範囲／しない範囲」）
- [ ] スプリッターにキーボードフォーカスを当て、左右矢印キーで幅を増減できる
- [ ] 右サイドパネルの幅は下限 280px・上限 420px の範囲に制限される
- [ ] 中央ビューの幅は最小 480px を下回らない（ウィンドウ幅が足りる限り）
- [ ] 変更した幅がリロードをまたいで復元される
- [ ] ウィンドウを縮小して保存値が現在のウィンドウ幅に収まらなくなった場合、幅が自動的に再クランプされる
- [ ] 保存値の読み取りに失敗した場合・保存値が不正な場合、既定幅 280px で起動する
- [ ] 左ナビの幅は変更できない（200px 固定のまま）

## 非機能要件

- アクセシビリティ: スプリッターは WAI-ARIA の window splitter パターン（`role="separator"` ＋ `aria-orientation` ＋ `aria-valuenow` / `aria-valuemin` / `aria-valuemax`）に従い、**ポインタを使わずキーボードだけで操作できる**。マウス専用のスプリッターにしない
- ローカル完結: 幅の保存先はブラウザの `localStorage` のみ。サーバへ送信しない（[ADR 0001](../adr/0001-local-only-data-boundary.md) の不変制約に影響を与えない）

## 技術的な制約・方針

- 使用技術: 既存スタックのまま（Vite + React + TypeScript）。ドラッグ用のライブラリを追加しない
- 変更対象:
  - `web/src/index.css`（`--side-panel-width` は 280px のまま据え置き＝フォールバックとして維持。`--splitter-width` は追加しない——後述のとおり TypeScript 定数から注入する）
  - `web/src/AppLayout.css`（`.app-body` のグリッド定義・`.app-splitter` のスタイル）
  - `web/src/AppLayout.tsx`（スプリッター要素の追加・幅の適用）。スプリッターは既存の 7 通りの条件付き `<main>` ブロックの外側・`<aside class="app-side-panel">` の直前に **1 つだけ** 置く（`activeView` に依存しない）
  - `web/src/side-panel-width.ts`（新規・純粋関数と `localStorage` アクセス）
  - `web/src/use-side-panel-width.ts`（新規・状態と `resize` 購読）
- 既存コードとの関係:
  - `web/src/use-chat.ts` の「チャット下書きは `localStorage` を使わない（YAGNI）」というコメントは**下書き状態についての判断**であり、UI レイアウト状態には及ばない。本機能での `localStorage` 導入はこの判断と矛盾しない
  - サーバの settings API（`server/src/settings/settings-validation.ts`）には新しいキーを追加しない。同ファイルは "No new keys are invented here" と明記しており、画面の見た目の状態はドメイン設定ではない
  - 既存の `web/src/AppLayout.test.tsx` はロール／アクセシブル名で問い合わせており、グリッドのトラック数を増やしても壊れない。契約を壊さないこと
- テスト方針:
  - クランプ計算・保存値の読み書き・ポインタ座標からの幅算出は**純粋関数として切り出し**、DOM を介さずユニットテストする
  - jsdom は PointerEvent とポインタキャプチャを実装していないため、**実ドラッグの追従は自動テストで担保しない**（下記「テストで担保する範囲／しない範囲」）

## 画面・API設計

サーバ API の追加・変更は無い。

### レイアウト

`.app-body` のグリッドを 4 トラックにし、中央と右サイドパネルの間にスプリッターのトラックを挟む。

```css
.app-body {
  grid-template-columns:
    var(--nav-width)
    minmax(0, 1fr)
    var(--splitter-width)
    var(--side-panel-width);
}
```

中央トラックを `1fr` から `minmax(0, 1fr)` へ変える。`1fr` の暗黙の最小値は `auto`（＝内容幅）であり、中央の内容が広いとトラックが内容幅まで押し広げられてサイドパネルを潰しうるため、明示的に 0 を最小値にして「中央は与えられた幅に収まり、あふれる分は `.app-main` 自身がスクロールする」挙動へ揃える。

現在の幅は `.app-body` へインラインのカスタムプロパティ（`--side-panel-width: {width}px`）として与える。`index.css` の `:root` に残す `--side-panel-width: 280px` は、復元前・未保存時のフォールバック値として機能する。

### スプリッター

```html
<div
  class="app-splitter"
  role="separator"
  aria-orientation="vertical"
  aria-label="サイドパネルの幅"
  aria-valuenow="{現在の幅}"
  aria-valuemin="280"
  aria-valuemax="{現在のウィンドウ幅における実効上限}"
  tabindex="0"
></div>
```

`aria-valuemax` には固定の 420 ではなく**現在のウィンドウ幅で実際に到達できる上限**を入れる（下記「幅の決定規則」の実効上限）。支援技術に、その場で到達できない値を上限として伝えないため。

### キーボード操作

| キー | 動作 |
|---|---|
| `←` | サイドパネルを 16px 広げる（境界が左へ動く＝右のパネルが広がる） |
| `→` | サイドパネルを 16px 狭める |
| `Home` | 下限（280px）にする |
| `End` | 実効上限にする |

矢印キーの向きは「境界の移動方向」に対応させる。左矢印でサイドパネルが**広がる**（狭まるのではない）ことは、直感と逆になりやすいため受入基準とテストで固定する。

## 機能全体の設計

### アーキテクチャ決定

幅の決定を 3 層に分ける。DOM に依存する層を薄く保ち、規則は純粋関数側に置く。

1. `web/src/side-panel-width.ts` — 定数・クランプ計算・ポインタ座標からの幅算出・`localStorage` の読み書き（すべて DOM イベントに依存しない）
2. `web/src/use-side-panel-width.ts` — React state、初回マウント時の復元、`window` の `resize` 購読と再クランプ、変更時の保存
3. `web/src/AppLayout.tsx` — スプリッター要素のレンダリングとイベント配線（ポインタ・キーボード）

### 幅の決定規則

定数:

| 名前 | 値 | 意味 |
|---|---|---|
| `SIDE_PANEL_MIN_WIDTH` | 280 | サイドパネルの下限（現状幅。ここを下回らせない＝退行させない） |
| `SIDE_PANEL_MAX_WIDTH` | 420 | サイドパネルの上限（中央のチャットの圧迫を防ぐ） |
| `SIDE_PANEL_DEFAULT_WIDTH` | 280 | 未保存時・復元失敗時の既定 |
| `MAIN_MIN_WIDTH` | 480 | 中央ビューに確保する最小幅 |
| `NAV_WIDTH` | 200 | 左ナビ（固定） |
| `SPLITTER_WIDTH` | 6 | スプリッターのトラック幅 |

`SPLITTER_WIDTH`（TypeScript 側の定数）を**唯一の正本**とする。CSS の `--splitter-width` はこの定数から `.app-body` のインラインスタイルとして注入し、`index.css` に固定値を二重に置かない。実効上限の式が「スプリッターの実描画幅 = `SPLITTER_WIDTH`」に依存しているため、値の正本が 2 箇所にあると `aria-valuemax` と実レイアウトが食い違いうる。

現在のウィンドウ幅 `W` における**実効上限**:

```text
実効上限 = max(SIDE_PANEL_MIN_WIDTH,
               min(SIDE_PANEL_MAX_WIDTH, W - NAV_WIDTH - SPLITTER_WIDTH - MAIN_MIN_WIDTH))
```

クランプ結果 = `min(max(要求幅, SIDE_PANEL_MIN_WIDTH), 実効上限)`。要求幅が有限な数値でない場合は `SIDE_PANEL_DEFAULT_WIDTH` を要求幅として扱う。

**ポインタ座標から要求幅への換算**（絶対位置方式）:

```text
要求幅 = ウィンドウ幅 - ポインタの clientX
```

サイドパネルの右端はウィンドウ右端と一致するため、ポインタ位置からウィンドウ右端までの距離がそのまま要求幅になる。掴んだ位置のオフセット（スプリッター内のどこを掴んだか）や `SPLITTER_WIDTH` の補正は入れない——補正は最大でも 6px であり、クランプとキーボード操作のステップ（16px）より小さく、体験上の差が出ないため（KISS）。この結果をクランプ規則に通した値が新しい幅になる。

**下限と中央最小幅が両立しないウィンドウ幅での優先順位**: `W` が狭く `W - 200 - 6 - 480 < 280` になる場合、両方の制約は同時に満たせない。このとき**下限 280px を優先**し、中央が 480px を割ることを許す（外側の `max(SIDE_PANEL_MIN_WIDTH, ...)` がこれを表す）。理由は、サイドパネルを 280px より狭めることが現状からの退行になるのに対し、中央が一時的に狭くなるのは `.app-main` の既存のスクロールで受け止められるため。ウィンドウ幅 1024px では `200 + 6 + 480 + 280 = 966 ≤ 1024` で両立する。

数値（280 / 420 / 480 / 16px ステップ）は暫定値であり、実装後に `/demo` で目視確認して調整しうる。

### 保存

- キー: `ai-boss:side-panel-width`
- 値: 幅の px 値を 10 進数の文字列で保存する
- 読み取り時に次のいずれかなら**保存値を使わず既定 280px** を採る:
  - キーが存在しない
  - `localStorage` へのアクセス自体が例外を投げる（プライベートモード・ストレージ無効化環境）
  - 値が有限な数値として解釈できない（`"abc"` / `""` / `"NaN"` / `"Infinity"`）
- 値が数値として解釈できるが範囲外（例: 保存後にコードの上限が変わった、手で書き換えられた）の場合は、**捨てずにクランプして採用**する
- 書き込みが例外を投げた場合も UI は動き続ける（保存できないだけで幅の変更は成立する）

**保存値は「ユーザーが希望した幅」であり、表示中の幅ではない**。したがって:

- **ユーザー操作（ドラッグ・キーボード）による変更のみを保存する**
- **ウィンドウの `resize` に伴う再クランプは保存しない**（表示のみをクランプする）

ウィンドウを一時的に狭めると保存済みの希望幅が恒久的に失われる、という挙動を避けるための決定である。420px で使っていたユーザーがウィンドウを狭めて再び広げたとき、幅は 420px へ戻る（狭めた時点の再クランプ値に固定されない）。一時的なウィンドウ操作が設定を破壊しないほうが、ユーザーの意図に忠実である。

### テストで担保する範囲／しない範囲

**自動テストで固定する**:

| 対象 | 場所 |
|---|---|
| クランプ計算（下限ちょうど・上限ちょうど・下限未満・上限超過・ウィンドウ縮小時の実効上限・下限優先の破れ） | `side-panel-width.test.ts` |
| ポインタ X 座標から幅への換算（`ウィンドウ幅 - clientX` とクランプの合成） | `side-panel-width.test.ts` |
| `resize` 起因の再クランプが保存値を書き換えないこと | `AppLayout.test.tsx` |
| `localStorage` の読み取り（正常・キー無し・非数値・範囲外・例外送出） | `side-panel-width.test.ts` |
| `localStorage` への書き込み（値の形式・例外時に落ちないこと） | `side-panel-width.test.ts` |
| スプリッターの ARIA 属性（role / orientation / valuenow / valuemin / valuemax） | `AppLayout.test.tsx` |
| キーボード操作による増減・向き・境界での頭打ち | `AppLayout.test.tsx` |
| 保存値からの復元がグリッドへ反映されること | `AppLayout.test.tsx` |
| `resize` による再クランプ | `AppLayout.test.tsx` |

**自動テストで担保しない（`/demo` の目視に委ねる）**:

- 実ドラッグの追従（jsdom は PointerEvent・`setPointerCapture` を実装していない）
- カーソル形状（`col-resize`）・ホバー時の視認性・スプリッターの掴みやすさ
- ドラッグ中にテキスト選択が起きないこと
- 280〜420px という範囲、および 16px というキーボードのステップ幅が実際に使いやすいか

上記「担保しない」項目について、担保した体裁のアサーション（jsdom 上で人工的にイベントを合成して「ドラッグできた」と主張するテスト）を書かない。
