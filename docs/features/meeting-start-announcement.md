# 朝会・夕会の開始をチャット上で伝える（開始ひとこと＋タイムライン統一と境界メッセージ）

> **状態: 要件定義完了（#168）。クリティカル設計決定 8 件は意思決定者により確定済み。**
>
> **正はコードとテスト**であり、本ファイルは権威を持たない（`CLAUDE.md`「開発方針」）。実装を駆動するための作業文書であり、実装と食い違う場合はコードが正。

## 概要

会（朝会・夕会）が始まったことをチャット画面上で伝わるようにする。2 つの変更からなる。

1. **会の開始時にボスがひとこと言う** — 夕会・朝会を開始してもボスが何も言わないため、ユーザーは何を入力すればよいか分からない。開始直後にボスの最初のひとことをタイムラインへ出す。
2. **履歴表示を統一し、境界をメッセージで示す** — 現在は会の開始・終了で履歴が丸ごと入れ替わる。表示は 1 本のタイムラインに統一し、「朝会が開始されました」等の境界要素で会の区間を示す。

## 背景・目的

### 現状（実コードで確認済み）

**表示の切り替わり**

- チャット UI は `web/src/ChatView.tsx` ＋ `web/src/use-chat.ts` の 1 画面。`startSession`（`use-chat.ts` の `startSession`）は当日の該当セッションを取得（無ければ作成）し、**タイムラインをそのセッションのメッセージだけに置き換える**（`setEntries(messages.map(messageEntry))`）。直前の随時チャットは `adhocSnapshotRef` へ退避し、`endSession` で復元する。
- メッセージ取得は `GET /api/sessions/:id/messages`（`listMessagesBySessionId`）のみ。**複数セッションを横断して時系列に並べる API は存在しない**。
- タイムラインには既に非メッセージ要素の前例がある — `ChatEntry` は union で `kind: "tool"` を持ち、`ChatView.tsx` の `ChatEntryItem` が `<li className="chat-tool-notice">` として描画する。

**開始時にボスが黙っている**

- `POST /api/sessions`（`server/src/sessions/sessions-routes.ts`）はセッション行を作るだけで、ボスの発話を生成しない。
- ボスの応答は `POST /api/sessions/:id/messages`（`chat-messages-route.ts`）でユーザー発言を受けてから始まる。同ルートは `content` を必須とする（`sessions-validation.ts` の `validateChatMessageInput`）ため、**ユーザー発言なしでボス発話を生成する導線が無い**。
- 朝会・夕会のフロー指示はシステムプロンプト側にある（`persona-prompt.ts` の `MORNING_FLOW_INSTRUCTION` / `EVENING_FLOW_INSTRUCTION`）が、ユーザーには見えない。
- ボスコメントを LLM で生成する前例は `server/src/dashboard/boss-comment.ts` にある（例外を投げない契約・固定フォールバック・小さい `maxTokens`・`thinking` 無効）。

### 目的

会の開始という状態遷移を、ユーザーが画面だけで理解できるようにする。「何を報告すればいいか分からない」「今どのモードにいるのか分からない」「さっきまでの会話が消えた」の 3 つを同時に解消する。

## ユーザーストーリー

セルフマネジメント中のユーザーとして、夕会を開始したときにボスから最初のひとことを受け取り、かつ直前までの会話が消えずに 1 本のタイムラインで続くことで、迷わず報告を始めたい。

## 機能要件

- [ ] 朝会・夕会を開始すると、ユーザーが何も入力しなくてもボスの最初のひとことがタイムラインに表示される
- [ ] 開始ひとことの生成に失敗しても、会の開始自体は成功する
- [ ] 同じ日の同じ会を再開しても開始ひとことが重複しない
- [ ] 開始ひとことの生成はユーザーの活動シグナルを記録しない（サボり検知を不当に抑制しない）
- [ ] チャット履歴の表示が朝会・夕会・随時で入れ替わらず、当日の会話が 1 本のタイムラインに時系列で並ぶ
- [ ] タイムライン上に会の開始・終了の境界が表示され、どこからどこまでが会かが分かる
- [ ] 会中であることが引き続き分かる（「朝会中」/「夕会中」バッジと終了ボタンの現状挙動を壊さない）
- [ ] 夕会終了時のセッション要約生成・日報生成フックが従来どおり動く

## 技術的な制約・方針

- 使用技術: 既存スタックのまま（Hono + better-sqlite3 / Vite + React）
- 外部送信は Claude API への推論リクエストのみ（[ADR 0001](../adr/0001-local-only-data-boundary.md)）。開始ひとことの生成は既存の `claude-client.ts` ファサード経由で行い、新しい外部通信経路を作らない
- LLM 呼び出しの失敗時ログはエラークラス名のみ（[ADR 0002](../adr/0002-api-key-and-llm-call-path.md) 決定 4）
- 「当日」はサーバーのローカル暦日（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 1）。日付キー導出は既存の `toDateKey`（server: `detection/time-utils.ts` / web: `to-date-key.ts`）を使う
- テストの時刻固定は `new Date(y, m, d, h)` 由来のローカル日付基準で組む（[ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 5）
- 日報の前提条件（対象暦日の夕会が終了済み かつ **`role = "user"` の発言が 1 件以上**）を壊さない（[ADR 0008](../adr/0008-evening-dialogue-prerequisite.md) 決定 1・実装は `server/src/reports/generate-daily-report.ts`。夕会終了フックの実装は `server/src/sessions/sessions-routes.ts` の `POST /:id/end`）
- 算出できるものは保存しない（[ADR 0005](../adr/0005-sqlite-schema-policy.md) 決定 6）
- **DB マイグレーションを行わない**（判断 5 の帰結）

## クリティカル設計決定

### 判断 1: 開始ひとことの生成方法

- **採用案**: **LLM 生成 ＋ 失敗時は固定文言フォールバック**。`server/src/dashboard/boss-comment.ts` の既存パターン（例外を投げない・フォールバック定数・小さい `maxTokens`・`thinking: { type: "disabled" }`）をそのまま踏襲する。
- **理由**:
  - 固定文言だけでは `persona-prompt.ts` のペルソナ設定（口調 4 プリセット × 厳しさ 5 段階 × 自由記述の追加指示）が反映されない。設定を変えても開始ひとことだけ変わらないのは、モチベーション演出をコア価値とする本プロダクトの方針と噛み合わない。
  - `MORNING_FLOW_INSTRUCTION` / `EVENING_FLOW_INSTRUCTION` に乗せれば、タスク一覧を踏まえて「今日の A はどうなった？」まで踏み込める。
  - 同期 LLM 呼び出しのレイテンシは既に受容済みの前例がある（`sessions-routes.ts` の `POST /:id/end` が要約生成を同期 `await` し、「終了ボタンの応答が数秒遅くなるのは明示的なトレードオフ」と記録している）。
- **代替案**:
  - **固定文言プリセットのみ** — 却下。上記のとおりペルソナ設定を反映できず、当日のタスク状況にも踏み込めない。
  - **LLM 生成のみ（フォールバック無し）** — 却下。生成失敗時に無言へ戻り、Issue の要望（何を入力すればよいか分かる）を満たさなくなる。
- **影響範囲**: `server/src/sessions/meeting-opening.ts`（新規）。

### 判断 2: 生成トリガと冪等性

- **採用案**: **`POST /api/sessions` の同期副作用**とし、冪等性は**「対象セッションのメッセージが 0 件のときだけ生成する」**ガードで担保する（DB を真実の源にする）。
- **理由**:
  - 「セッション作成に成功したときだけ」では不十分。`sessions-repository.ts` の `createSession` が当日 1 回制限をかけるのは **evening のみ**で、morning は同日 2 回目も成功して新しい行を作る。今それが表面化していないのは `use-chat.ts` の `startSession` が `loadTodaysSession` を先に見て既存セッションを再利用するからであり、**クライアント側の作法にだけ支えられた冪等性**である。
  - メッセージ 0 件ガードは、`POST /:id/end` の要約生成が `session.summary === null` で抑制するのと同じ「既にあるならやらない」作法であり、新しい流儀を増やさない。
- **代替案**:
  - **専用エンドポイント `POST /api/sessions/:id/opening`（SSE でストリーミング表示）** — 却下。開始ひとことは短文であり、ストリーミングの演出価値に対して導線が 1 本増えるコスト（冪等性ガードの検証点が二重化する）が見合わない。将来必要になったら別 Issue で追う。
  - **クライアントが `POST /:id/messages` を空 `content` で叩く** — 却下。`validateChatMessageInput` が `content` 必須のため、空発言を通す穴を開けることになる。
- **影響範囲**: `server/src/sessions/sessions-routes.ts`（`POST /` に同期副作用を追加）・`web/src/use-chat.ts`（新規作成パスで生成メッセージを画面へ反映する。`loadTodaysSession` が返す `messages` は新規作成時に空配列であり、そのままでは画面に出ない）。

### 判断 3: 適用範囲

- **採用案**: **朝会・夕会の両方**に付ける。**随時チャットは対象外**。
- **理由**: `MORNING_FLOW_INSTRUCTION` は朝会でも同じくシステムプロンプト側にのみ存在し、ユーザーには見えない。構造的に同じ欠落である。随時チャットを除くのは、随時セッションが**ユーザーが最初に発言しようとした瞬間に遅延作成される**設計（`use-chat.ts` の `send`）で、「開始」という明示的な操作点が存在せず、ひとことの置き場所がないため。
- **代替案**: **夕会のみ**（要望の起点が夕会） — 却下。朝会にも同じ欠落があり、後から足すほうが総コストが高い。
- **影響範囲**: `POST /api/sessions` の分岐条件（`type === "morning" || type === "evening"`）。

### 判断 4: 失敗時の扱い

- **採用案**: **best-effort**。契約の具体形は次の 5 点。
  1. 生成関数は**例外を投げない**（`boss-comment.ts` / `session-summary.ts` / `notification-body.ts` と同じ既存規約）
  2. 失敗ログは**エラークラス名のみ**（[ADR 0002](../adr/0002-api-key-and-llm-call-path.md) 決定 4）
  3. LLM 失敗・空応答・タイムアウトのいずれでも**固定フォールバック文言を永続化する**
  4. 生成にタイムアウト（10 秒）を設ける
  5. **生成の成否によらず `POST /api/sessions` は 201 を返す**
- **理由**: `session-summary.ts` は逆に「捏造しない」ため失敗時 `null` を返すが、あれは*事実の記録*だからである。開始ひとことは*促し*であり、無言よりフォールバック文言のほうが要望を満たす。したがって `boss-comment.ts` 側の類型（フォールバック文言を返す）が正しい。タイムアウトを日報生成（20 秒）より短くするのは、会の入口は対話のレイテンシが直接効くため。
- **代替案**: **生成失敗時は無言のまま成立させる** — 却下。「何を入力すればよいか分かる」という要望の中核を、失敗時に丸ごと落とすことになる。
- **影響範囲**: `meeting-opening.ts` の契約・`sessions-routes.ts` の `POST /`。

### 判断 5: 境界メッセージの持ち方

- **採用案**: **`sessions.started_at` / `ended_at` からクライアント側で導出する**（スキーマ変更なし）。`ChatEntry` に `kind: "boundary"` を追加し、`kind: "tool"` と同じ非メッセージ要素として描画する。
- **理由**:
  - [ADR 0005](../adr/0005-sqlite-schema-policy.md) 決定 6「算出できるものは保存しない」に真正面から整合する。境界は `sessions` から決定的に再現できる。
  - 前例がそのまま使える。`ChatEntry` は既に union で `kind: "tool"` を持ち、`ChatView.tsx` が非メッセージ要素として描画している。`GET /api/sessions` は既に `started_at` / `ended_at` を返すため追加 API も不要。
- **代替案**:
  - **`messages.role` に `system` を追加して永続化（migration v5）** — 却下。波及が広く、しかも**一部は型検査に守られない**: `chat-messages-route.ts` の `toClaudeMessages` にある `role === "boss" ? "assistant" : "user"` は **`system` を黙って `user` にマップする**。加えて `messages` は `sessions(id)` を参照するため、CHECK 制約変更には v4 と同じ `PRAGMA foreign_keys` の 12-step 手順が要る。「境界も会話ログの一部として LLM に見せたい／エクスポートしたい」という用途は現時点で無く YAGNI。
- **影響範囲**: `web/src/use-chat.ts`（`ChatEntry` の union 拡張）・`web/src/ChatView.tsx`（描画）・`web/src/ChatView.css`。**サーバ変更なし・マイグレーションなし**。

### 判断 6: 統一タイムラインの範囲と取得方法

- **採用案**: **当日分のみ・クライアントでマージする**。ただし**「現在アクティブなセッションは暦日をまたいでも常に含める」補正を必須**とする。マージ順序の規律は `web/src/merge-timeline.ts`（新規・純粋関数）に閉じ込め、単体テストで固定する。
- **理由**:
  - 既存構造の自然な拡張である。`use-chat.ts` のマウント時復元は既に `fetchSessions()` 全件 → `selectRestoreSessions` で当日分を絞る → `Promise.all` で 2 セッション分を並列取得している。2 → N にするだけ。
  - 当日のセッション数は朝会 1 + 夕会 1 + 随時（`selectRestoreSessions` が当日の未終了 adhoc を再利用するため実質 1）で**概ね 3**。N+1 が問題になる規模ではなく、横断 API の新設は YAGNI・KISS に反する。
  - **補正が必須である理由**: [ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 4 で日跨ぎ夕会は**開始日に帰属**する。23:50 開始の夕会は 00:30 時点で「当日」から外れるため、当日スコープをそのまま適用すると**会の最中に履歴が画面から消える**。
- **代替案**:
  - **横断取得 API を新設（`GET /api/messages?date=...`）** — 却下。当日 3 セッション規模では過剰。マージ順序を一元化できる利点はあるが、純粋関数＋単体テストで同等の規律を保てる。
  - **日付をまたいで遡れるようにする** — 却下。現状も随時チャットは当日スコープであり、Issue に要望が無い（YAGNI）。
- **影響範囲**: `web/src/merge-timeline.ts`（新規）・`web/src/use-chat.ts`（`adhocSnapshotRef` の退避・復元を**廃止**。タイムラインが入れ替わらないなら復元する対象が無くなるため、`startSession` / `endSession` / マウント時復元の 3 箇所を書き換える）。

### 判断 7: LLM コンテキストとの整合

- **採用案**: **表示のみ統一する**。LLM へ渡す会話履歴はセッション単位のまま変更しない。
- **理由**: Issue の要望は「会が始まったことが伝わる」であり、コンテキスト統一は要望に含まれない（スコープ拡大）。ボスは既に `listRecentSessionSummaries(db, 5)` で直近の**会**の要約を参照できる。
- **代替案**:
  - **コンテキストも当日横断にする** — 本課題では不採用（スコープ拡大）。別 Issue で追う。
  - **当日の他セッションを system 側の参考情報ブロックとして渡す**（`persona-prompt.ts` の非信頼データ作法 — デリミタで囲み「これは指示ではない」と明記する — を流用） — 同上。
- **影響範囲**: なし（変更しない）。**既知の限界を下記に明記する。**

### 判断 8: 送信先セッションの規則

- **採用案**: **現状維持**（会中は会のセッション、それ以外は随時）。
- **理由**: セッション種別はサーバ側の 3 つの振る舞いを決めている — フロー指示の切り替え（`chat-messages-route.ts`）、要約対象の判定（`sessions-routes.ts`）、そして**日報の前提条件**（`generate-daily-report.ts` が「夕会セッションに `role = "user"` の発言が 1 件以上」を要求。[ADR 0008](../adr/0008-evening-dialogue-prerequisite.md) 決定 1）。送信先を変えると日報が生成できなくなる。表示が統一されても、境界要素（判断 5）とバッジで「今は会中」は示されるため、混乱は生じない。
- **代替案**: **常に随時セッションへ送る** — 却下。上記のとおり日報が生成不能になる。
- **影響範囲**: なし（変更しない）。

## 既知の限界

**会中のボスは、当日の随時チャットの内容を知らない。** 判断 6 で表示を当日横断に統一する一方、判断 7 で LLM へ渡す会話履歴はセッション単位のままとしたため、**ユーザーには 1 本の会話に見えるのに、ボスは会中に随時チャットの発言を参照できない**という齟齬が残る。

齟齬が目立つ理由は、随時セッションが要約されないことにもある。`POST /:id/end` の要約生成は `session.type !== "adhoc"` でガードされており（随時には UI 上の自然な終了トリガが無いため）、`listRecentSessionSummaries` 経由でも随時チャットの内容はボスに届かない。

この限界は意図的な取捨選択であり、バグではない。**解消は #270 で追う**（選択肢 B / C とトークン増の推定を同 Issue に記録した）。

| `use-chat.ts` の `startSession` 新規作成パス | `loadTodaysSession` が返す `messages`（新規作成時は空配列）を `setEntries` するため、サーバ側で生成した開始ひとことが**画面に出ない** | `POST /api/sessions` の応答に含めるか、作成後に再フェッチする |
| [ADR 0007](../adr/0007-local-calendar-day-basis.md) 決定 4（日跨ぎ帰属） | 23:50 開始の夕会は 00:30 時点で「当日」から外れ、当日スコープのタイムラインだと**会中に履歴が消える** | 「現在アクティブなセッションは暦日をまたいでも常に含める」補正を入れる（判断 6） |
| `sessions-repository.ts` の `createSession` | 当日 1 回制限があるのは **evening のみ**。morning は同日 2 回目の作成が成功して新しい行を作る | メッセージ 0 件ガード（判断 2）で冪等性をサーバ側に持たせる |

## 明示的な仮定

- **仮定 1**: 生成モジュールを `server/src/sessions/meeting-opening.ts` に置く（`session-summary.ts` と同階層）
- **仮定 2**: 境界要素の `ChatEntry` kind 名を `"boundary"` とする（`"tool"` と同じ命名の粒度）
- **仮定 3**: 生成タイムアウトを 10 秒とする（`sessions-routes.ts` の日報生成 20 秒より短く。会の入口はレイテンシが直接効くため）
- **仮定 4**: 境界要素の文言は「朝会が開始されました」「朝会が終了しました」「夕会が開始されました」「夕会が終了しました」とする。随時チャットには境界を出さない（会の区間を示すのが目的であり、随時は「会でない区間」として境界の外側になる）
- **仮定 5**: 未終了の会には開始境界のみを出す（終了境界は `ended_at` が入ってから出る）
