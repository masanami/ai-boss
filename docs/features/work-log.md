# 作業ログ（管理者共有向け・詳細時系列）と日報のスリム化

> 親 Issue: #144。運用フィードバック（日報の「決定事項」が当日の決定全件の逐次列挙となり冗長）を受け、日報（要約）と管理者共有向け作業ログ（詳細・時系列）を分離する。本仕様は作業ログの新設と、正本 `docs/features/daily-report.md` の改訂内容（日報側の変更）の両方を定める。改訂確定後は daily-report.md 本体も本仕様と同時に更新する。

## 概要

日報から「決定事項」セクションを廃止して要約に寄せ（最終的な結論の要点は「夕会サマリ」へ統合）、当日の決定ログ全件と activity_events を時系列に並べた管理者共有向けの「作業ログ」Markdown を新設する。作業ログは保存せず、任意の日付についていつでもオンデマンドで機械整形により生成でき、アプリ内で表示・クリップボードコピーできる。

## 背景・目的

- 日報の「決定事項」は当日の全セッション由来 `status = active` 決定の逐次列挙（daily-report.md の現行規定）であり、実運用で1日13件などになると要点（確定ノルマ・持ち越し判断）が経緯に埋もれ、日報というより時系列の作業ログになっていた（Issue #144）
- 一方でこの詳細な時系列情報自体には価値があり、捨てたいのではなく「管理者共有向けの作業ログ」として別の出力に分けるのが使い方に合う
- オーナー決定（2026-08-18）:
  1. 日報の「決定事項」セクションは廃止し、最終的な結論（確定ノルマ・持ち越し判断等の要点）は夕会サマリへ統合する
  2. 管理者共有向け「作業ログ」（当日の決定ログ全件＋activity_events を時系列で並べた出力。生成・表示・コピー可）を新設する
  3. 作業ログの生成条件は実装セッションが既存実装との整合を評価して決定し、明示的な仮定として本仕様に記載する（→「クリティカル設計決定 > 作業ログの生成条件」）

## ユーザーストーリー

自己管理が苦手な個人ワーカーとして、日報は要点だけが読み取れる要約として受け取り、管理者（実在の上司等）へ詳細を求められたときは当日の決定・活動を時系列で並べた作業ログをコピーして共有したい。

## 機能要件

### 日報側の変更（daily-report.md の改訂）

- [ ] 日報テンプレートから「決定事項」セクションを廃止する（決定ログの内容を日報に逐次列挙しない）
- [ ] 「夕会サマリ」の LLM 抽出値を3値から4値に拡張する: 「報告の要点」「ボスの講評」「決定の要点」「翌日への持ち越し」。「決定の要点」は当日の決定のうち最終状態として効いているもの（確定ノルマ・新規タスク登録・持ち越し判断等）の要約で、該当が無い日は「なし」とする
- [ ] 「決定の要点」の抽出材料として、LLM への入力に夕会の会話ログに加えて当日（ローカル日付）の `status = active` な決定の一覧（`content` のみ・作成日時昇順）を渡す
- [ ] 夕会サマリの表示順は「報告の要点」「ボスの講評」「決定の要点」「翌日への持ち越し」の4行とする。Markdown の構造はレンダラーが決め、LLM には値だけを出させる原則（daily-report.md のクリティカル設計決定）は維持する
- [ ] LLM 抽出の失敗・タイムアウト・形式不正時のフォールバックは現行仕様のまま維持する: 「夕会サマリ」は固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみとし、4項目は出力しない（決定の詳細はフォールバック時も作業ログで確認できるため情報は失われない）
- [ ] 上記以外の日報仕様（生成条件・テンプレートの他セクション・API・画面）は変更しない

### 作業ログ（新設）

- [ ] 指定したローカル日付の作業ログ Markdown を生成できる。生成はいつでも可能（夕会完了などの前提条件なし）
- [ ] 作業ログの内容は、当日（ローカル日付の 00:00:00.000〜23:59:59.999）の次の2系列を `created_at` 昇順で1本にマージした時系列の箇条書きとする
  - 決定ログ**全件**: `status` が `active` / `revised` / `withdrawn` のすべて。`content` のみを載せ（`rationale` は含めない）、`revised` は「決定（改訂済み）」・`withdrawn` は「決定（撤回）」のラベルで状態を明示する
  - activity_events のうち `task_start` / `task_update` / `break_start` / `break_end` / `checkin` の5種（`chat_message` は1メッセージごとに記録される機械イベントでありノイズになるため含めない — 会話の成果は決定ログとして現れる）
- [ ] 各行はタイムスタンプ（ローカル時刻 `HH:mm`）＋種別ラベル＋内容で構成する（→「作業ログテンプレート」）
- [ ] 作業ログビュー（画面）で日付を選んで作業ログを表示し、クリップボードへコピーできる（既定は当日）
- [ ] 作業ログは機械的な時系列整形のみで生成し、LLM を使わない（サボり検知ルールエンジンと同系の「純粋関数」原則。LLM 不使用のため失敗時フォールバックは不要で、生成は決定的）
- [ ] 作業ログは DB に保存しない。リクエストの都度、決定ログと activity_events から算出する（データ源から常に同じ出力を再現できるため保存は不要 — YAGNI）

### 作業ログテンプレート

生成する作業ログは次の固定構成とする。

```markdown
# 作業ログ 2026-08-18（火）

- 09:05 着手: タスクA（予定 60分）
- 09:30 決定: 本日のノルマは◯◯を完了させることとする
- 10:00 休憩開始（予定 15分）
- 10:12 休憩終了
- 11:30 決定（改訂済み）: △△を先に着手する
- 13:00 チェックイン — 順調に進行中
- 14:20 タスク更新: タスクB
```

- 表題は `# 作業ログ YYYY-MM-DD（曜）`（曜日は漢字1文字。日報の表題と同じ形式）とする
- タイムスタンプは各レコードの `created_at` のローカル時刻を `HH:mm`（24時間・0詰め）で表す
- 種別ごとの行フォーマット（`{}` は動的値）:
  - `task_start`: `- {HH:mm} 着手: {タスク名}`。`expected_minutes` があれば末尾に `（予定 {n}分）` を付す
  - `task_update`: `- {HH:mm} タスク更新: {タスク名}`
  - `break_start`: `- {HH:mm} 休憩開始`。`expected_minutes` があれば末尾に `（予定 {n}分）` を付す
  - `break_end`: `- {HH:mm} 休憩終了`
  - `checkin`: `- {HH:mm} チェックイン`
  - 決定（`active`）: `- {HH:mm} 決定: {content}`
  - 決定（`revised`）: `- {HH:mm} 決定（改訂済み）: {content}`
  - 決定（`withdrawn`）: `- {HH:mm} 決定（撤回）: {content}`
- `note` の付与規則（種別横断の共通規則）: activity_events の行（`task_start` / `task_update` / `break_start` / `break_end` / `checkin`）は `note` があれば行末（`expected_minutes` による `（予定 {n}分）` があればその後）に ` — {note}` を付す
- タスク名は `task_id` から `tasks.title` を解決する。`task_id` が `null`、または参照先タスクが存在しない（削除済み等）場合は、いずれも共通ラベル `（タスク未指定）` とする（原因別のラベル分けはしない — KISS。区別が必要になった時点で拡張する）
- 並び順は `created_at` 昇順。`created_at` が同一の場合は activity_events を決定より先に置き、同一テーブル内（activity_events 同士・決定同士）ではイベント種別・決定 `status` をまたいで `id` 昇順とする（順序が決定的になるようにする）
- 当日の決定・対象イベントが1件も無い場合、本文は固定文字列 `（記録なし）` の1行とする
- 動的値（タスク名・決定の `content`・`note`）は daily-report.md と同じエスケープ・正規化（`normalizeDynamicValue`: 改行の1行化・行頭 Markdown 記号のエスケープ）を適用する
- 日付範囲は対象ローカル暦日に固定する（日報の休憩対応付けのような夕会 `ended_at` までの拡張は行わない。作業ログは夕会に依存しない事実列挙であり、日跨ぎ夕会中に発生したイベントはその発生日の作業ログに載る）

## 非機能要件

- ローカルファースト（不変制約）: 作業ログの生成は SQLite の読み取りのみで完結し、外部送信は発生しない（LLM 呼び出し自体が無い）。共有（貼り付け）はユーザーの手動操作
- 日付の扱いはローカル日付キー（`toDateKey` と同じ基準）で統一し、テストはタイムゾーン非依存に書く（固定時刻は `new Date(y, m, d, h)` 由来で導出する）

## 技術的な制約・方針

- 使用技術: 既存スタックのまま（Hono + better-sqlite3 / React）。新規依存なし
- **DB スキーマ変更なし・マイグレーションなし**（作業ログは保存しない。日報側の変更もレンダリング・抽出のみで `daily_reports` テーブルは不変）
- 変更対象:
  - `server/src/reports/render-daily-report.ts`（「決定事項」セクション削除・夕会サマリ4値化）
  - `server/src/reports/evening-summary-tool.ts` / `extract-evening-summary.ts`（`key_decisions` の追加・決定一覧の入力注入）
  - `server/src/reports/generate-daily-report.ts` / `collect-daily-report-data.ts`（収集した決定を「レンダラーへ」ではなく「抽出のコンテキストへ」渡す配線変更）
  - `server/src/reports/`（新設: `collect-work-log-data.ts`〔収集〕・`render-work-log.ts`〔レンダラー〕・`work-logs-routes.ts`〔ルート〕。日報の同名パターンに対応させる）
  - `server/src/app.ts`（`/api/work-logs` のマウント）
  - `web/src/`（作業ログビュー・ナビ項目・API クライアント。コピー処理は日報ビューと共通化）
- 既存コードとの関係:
  - 作業ログの生成は日報と同じ「収集 → レンダリング」パターンに揃える（純粋関数レンダラー。ただし LLM 段・保存段は持たない2段構成）
  - データ源は `decisions` / `activity_events` / `tasks`（タスク名解決）を読み取り専用で参照する
  - Issue #141（ボス向けの作業ログ照会ツール・別課題）とはデータ源を共有するが、本仕様は人間（管理者）向けの Markdown 出力のみを扱い、#141 の実装には手を出さない

## 画面・API設計

### API

| メソッド/パス | 動作 |
|---|---|
| `GET /api/work-logs/:date` | 指定ローカル日付の作業ログ Markdown を都度生成して返す（保存しない）。データが1件も無い日も 200 で `（記録なし）` 本文を返す |

#### レスポンススキーマ

`date` はローカル日付キー（`YYYY-MM-DD`）。保存しないため作成・更新日時は持たない。

```jsonc
// GET /api/work-logs/2026-08-18 → 200
{
  "date": "2026-08-18",
  "content": "# 作業ログ 2026-08-18（火）\n\n- 09:05 着手: タスクA（予定 60分）\n..."
}
```

#### エラー形式

daily-report.md「エラー形式」で確立した `{ "error": "<メッセージ>", "code": "<安定コード>" }` 形式（基底の `{ error }` に UI 分岐用の安定 `code` を加えたもの）を踏襲する。

| 状況 | HTTP | `code` |
|---|---|---|
| `:date` が `YYYY-MM-DD` 形式でない、または実在しない暦日 | 400 | `invalid_date` |

- 404 は使わない（生成条件が無く、どの日付でも 200 で本文を返せるため）

### 画面

- ナビゲーションに「作業ログ」を追加する
- 作業ログビュー: 日付入力（`<input type="date">`・既定は当日）、選択日の作業ログ本文の表示、「コピー」ボタン
- コピー操作のフィードバックは日報ビューと同一仕様とする: 成功時は「コピーしました」を一時表示、失敗時はエラーメッセージ＋本文を全選択したテキスト領域での手動コピー退避、通知には `role="status"` / `role="alert"` を付す。実装はコピー処理を日報ビューと共通のフックへ抽出して共用する（DRY）
- 「再生成」ボタンは置かない（保存が無く、日付を選ぶたびに最新のデータから生成されるため）

## クリティカル設計決定

> 後続の実装チケットはこの決定に従い、独自判断で逸脱しない。

### 作業ログの生成条件（オーナーから委任された決定・明示的な仮定）

- **採用案**: **前提条件なし・いつでも生成可・保存なし（オンデマンド算出）**
- **理由**（既存実装との整合評価）:
  - 日報の「夕会完了＋ユーザー発言1件以上」という前提条件は、AI との振り返り対話を強制する**製品制約（壁打ち強制・toB 布石）**であり、LLM が生成する講評・要約を含む「日報」という成果物に紐づく。作業ログは LLM を使わない機械的な事実列挙であり、夕会由来のデータを一切含まないため、この前提を課す製品上・技術上の理由がない
  - 管理者への共有は日中の途中経過確認・早退時など夕会前にも起こりうるため、いつでも生成できる方が用途（管理者共有）に合う
  - 決定的な純粋関数で都度算出できるため、`daily_reports` のような保存テーブルは不要（YAGNI）。データ源（`decisions` / `activity_events`）が正本であり、同じ日付には常に同じ出力が再現される
- **代替案**:
  - 日報と同じ夕会完了前提 — 作業ログに夕会由来の内容が無いのに生成を人為的に遅らせることになり、管理者共有の用途を狭めるため却下
  - 生成結果を DB へ保存（`work_logs` テーブル新設）— 参照ユースケース（見返し）はデータ源からの再算出で満たせるため YAGNI で却下。スキーマ変更なしで完結する
- **影響範囲**: 新テーブルなし。`GET /api/work-logs/:date` は読み取り専用

### 日報「決定事項」の廃止と夕会サマリへの統合方式（オーナー決定の実現方法・明示的な仮定）

- **採用案**: 夕会サマリの LLM 抽出値を4値に拡張し、4行目相当として「決定の要点」を追加する。抽出ツール `submit_evening_summary` の `input_schema` に `key_decisions`（必須・空文字不可。該当なしの日は「なし」）を追加し、抽出プロンプトに当日の `status = active` 決定一覧をコンテキストとして注入する
- **理由**: 「最終状態に効いている決定」の絞り込みは決定ログに種別が無く機械的に定義できない（Issue #144 の論点）ため、要約は LLM の責務に置く。一方で Markdown 構造はレンダラー固定・LLM は値のみという既存のクリティカル設計決定を維持でき、構造の受入基準は引き続き純粋関数のユニットテストで検証できる
- **代替案**:
  - 決定事項セクションを機械的な絞り込みで残す — 絞り込み基準（種別）がデータに存在せず機械的に定義できないため却下
  - 3値のまま「報告の要点」に吸収させる — 確定ノルマ等が夕会の会話に現れない場合に脱落する。専用の値にして決定一覧を入力へ渡す方が確実で、出力位置も安定するため却下
- **影響範囲**: `evening-summary-tool.ts`（スキーマ・バリデータ）、`extract-evening-summary.ts`（プロンプト）、`render-daily-report.ts`（決定事項セクション削除・4行化）、`generate-daily-report.ts`（配線）。フォールバック契約（失敗時は注記1行）は不変

## 機能全体の設計

### アーキテクチャ決定

- 作業ログは「収集 → レンダリング」の2段とし、日報の生成サービスのパターンに揃える:
  1. 収集: 対象ローカル暦日の決定全件・対象 activity_events・タスク名を SQLite から読む（読み取り専用）
  2. レンダリング: 収集データを単一の純粋関数レンダラーへ渡し「作業ログテンプレート」の Markdown を組み立てる（DB・現在時刻・LLM に触れない。構造・順序はレンダラーが決定）
- ルートは `GET /api/work-logs/:date` を独立ルーターとして `server/src/app.ts` にマウントする（`/api/reports/:date` とのパス衝突を避けるため `/api/reports` 配下には置かない）
- 日報側は既存4段構成を維持し、変更は (a) レンダラー入力から `decisions` を外し「決定事項」出力を削除、(b) 抽出段の入力に決定一覧を追加し4値を返させる、の2点に限定する
- Web は `WorkLogView` を新設し、コピー処理（成功/失敗フィードバック・手動コピー退避）を `DailyReportView` から共通フックへ抽出して両ビューで共用する

### 実装計画（チケット分解の見通し）

1. server: 日報の「決定事項」廃止＋夕会サマリ4値化（レンダラー・抽出・配線・テスト改訂）
2. server: 作業ログの収集・レンダラー・`GET /api/work-logs/:date`
3. web: 作業ログビュー＋ナビ追加＋コピー処理の共通フック化（日報ビューへの適用含む）

最終的な分解は `/create-ticket` で行う。

## 受入基準

### 日報側の変更

- [ ] 当日に `status = active` の決定が存在する状態で日報を生成しても、日報に「決定事項」セクションが出力されない
- [ ] LLM 抽出が成功した場合、「夕会サマリ」に「報告の要点」「ボスの講評」「決定の要点」「翌日への持ち越し」の4行がこの順で出力される（LLM をモックし、レンダラーの構造をユニットテストで検証する。抽出内容の正確性は対象外）
- [ ] 当日の `status = active` 決定が0件の場合でも生成は成功し、LLM モックが「なし」を返すとき「決定の要点: なし」として出力される（レンダラーは渡された値をそのまま埋め込む）
- [ ] LLM 抽出への入力（ユーザーメッセージ）に、夕会の会話ログに加えて当日の `status = active` 決定の `content` 一覧が含まれる（LLM をモックし、渡された入力を検証する）
- [ ] `submit_evening_summary` の入力検証で `key_decisions` が欠落・空文字の場合は形式不正（フォールバック経路）になる
- [ ] LLM 抽出を失敗させた場合、「夕会サマリ」は固定文言「※ ボスの講評の生成に失敗したため、記録の機械整形で出力しています」の注記1行のみで構成され、4項目は含まれない（現行フォールバック契約の維持）
- [ ] `docs/features/daily-report.md` が本仕様の「日報側の変更」の5点（「決定事項」セクション廃止／夕会サマリ4値化／抽出入力への active 決定一覧の追加／4行の表示順／フォールバック契約の維持）をすべて反映した記述に改訂されており、旧規定（決定全件の逐次列挙）が残っていない
