# 催促を予約通知方式へ作り替える（ADR 0004 改訂）

> Issue #585。**草案（2026-09-27）**。論点 Q1〜Q8（Q7 はスライスの切り方）は未確定で、「推奨（未確定）」と書いた箇所は親・オーナーの回答で確定させる。★ はオーナー判断（製品方針）に当たる論点。

## 概要

モバイル（iOS / Android）では、「このまま何もしなければ◯時◯分に催促」を先に計算して OS の予約通知に登録し、活動があれば取り消して登録し直す（[ADR 0011](../adr/0011-productization-architecture.md) 決定 12〜14）。予約時刻は、検知エンジン（`evaluateRules`）を変えずに、**仮の発火を 1 つずつ履歴へ積みながら時刻を進めて評価する計画層**で求める。

## 背景・目的

- iOS はアプリを常駐させられず、「毎分判定して通知」（現行の `scheduler.ts`＝node-cron `* * * * *`）が成り立たない。モバイルはデスクトップと同等の全機能（ADR 0011 決定 20）で、催促はコア価値である。
- 未来の時刻を 1 回入れて評価するだけでは予約時刻は出ない。エスカレーション（`resolveEscalation`）・重複抑止・日次上限（`dailyNotificationCap`）が送信履歴（`DetectionInput.notifications`）に依存するためである。
- iOS の予約通知は 64 件が上限で、超えるとエラーを出さずに先に登録した分から切り詰められる（#576）。
- 予約通知では送信時に LLM で文面を生成できない（ADR 0011 決定 13）。

## ユーザーストーリー

- 製品版をスマホで使う利用者として、アプリを閉じていても、何もしなければ現行版と同じ時刻・同じ段階（L1 → L2 → L3）で催促が届いてほしい。
- 同じ利用者として、作業を報告したら、それ以降に予約されていた古い催促が届かないでほしい。

## 機能要件（機能全体。スライスごとの範囲は「スライス」節）

- [ ] 活動が無い前提で計算した予約の時刻・ルール・段階は、同じ入力で現行の毎分方式（`evaluateRules` を毎分呼ぶ方式）が出す発火と一致する（S1）
- [ ] 予約した時刻に、アプリが起動していなくても催促が届く（S3。シミュレータで確認。実機は製品化の後のフェーズ）
- [ ] 活動が記録されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] タスクが変更されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] 設定（勤務時間・会の時刻・日次上限・人格）が変更されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] アプリの起動・前面への復帰で、未配信の予約を取り消し、その時点の状態から予約し直す（S2）
- [ ] 予約の件数は OS の上限（iOS 64 件）を超えない（S1 で計画の件数を検証）
- [ ] 予約した時刻を過ぎた予約は、`sent_at` を予約時刻として送信履歴（`notifications`）に確定される（S1 で突き合わせの規則、S2 で DB への反映）
- [ ] 確定した送信履歴を入力にした次の計画で、エスカレーションの段階は毎分方式で書かれた履歴と同じになる（S2）
- [ ] 確定した送信履歴を入力にした次の計画で、重複抑止は毎分方式で書かれた履歴と同じに働く（S2）
- [ ] 確定した送信履歴を入力にした次の計画で、日次上限は毎分方式で書かれた履歴と同じに数えられる（S2）
- [ ] ダッシュボードの当日の段階表示は、確定した送信履歴だけを数え、未来の予約を数えない（S2）
- [ ] 予約した通知の文面は送信時に LLM を呼ばずに決まる（S2）
- [ ] 非 UTC の時間帯（例: JST）の端末で、指定した時刻どおりに予約される（S3）
- [ ] 予約の登録の失敗が呼び出し側に返る（S3）
- [ ] 予約の取り消しの失敗が呼び出し側に返る（S3）
- [ ] ADR 0004 を改訂する（S3。改訂案は「機能全体の設計」）

## 非機能要件

- パフォーマンス: 1 回の計画は、履歴の長さ（利用日数）に比例して遅くならない（入力の圧縮。クリティカル設計決定 1）。
- 信頼性: 予約の登録・取り消しの失敗を握りつぶさない（通知の実行系はクリティカル箇所）。

## クリティカル設計決定

### 1. 予約時刻を求める計画層（Q1・推奨（未確定））

- **採用案（推奨）**: 新しい純粋関数 `planNudges`（置き場所は `server/src` のコア。名前・ファイルは実装で決める）が、`now` から地平線の終わりまで **1 分刻みで `evaluateRules` を呼び、発火を仮の履歴へ積みながら進める**（`sweep` と同じ形）。活動は起きないものとして計算する（活動があれば計画し直す）。
  - **暦日ごとの入力**: 朝会・夕会の実効時刻と当日のセッション種別は、地平線に含まれる暦日ごとに呼び出し側が解決して渡す（暦日 → 値の対応）。計画層は刻みの暦日に応じて差し替える。地平線内の暦日が対応に欠けていれば呼び出し側の契約違反として例外を投げる（仮定 A4）。
  - **入力の圧縮**: 計画の前に、結果を変えない範囲で履歴を絞る純粋関数を通す（直近の一定期間＋種類ごとの最新の活動・`rule_key` ごとの最新の通知・日次上限の枠の分）。圧縮の前後で計画が一致することをテストで固定する。
  - **刻み**: 最初の刻みは `now`、以降は分の境界（現行 cron と同じ）。
  - **地平線（推奨）**: `now` から 24 時間、かつ予約件数の上限（Q3）に達したところまで。24 時間にするのは、夜に閉じたアプリを朝開かなくても翌朝の朝会の催促が予約済みであるため。
- **理由**: `evaluateRules` をそのまま使うため、現行の毎分方式との一致が作りから保証される（ルールの知識を計画層へ複製しない）。
- **代替案**: (a) 次に状態が変わる時刻（閾値・間隔・勤務時間の境界・会の時刻・締切・約束）を解析的に求めて飛ぶ — 速いが、ルールごとの時刻計算を計画層に複製することになり、ルール変更のたびに食い違う。(b) 圧縮せず 1 分刻み — 実測で履歴 5,000 件あたり 4.4 秒（Mac）で、スマホではさらに遅い。
- **影響範囲**: 新規の計画層のみ。検知エンジン無改変。

### 2. 予約と送信履歴の突き合わせ（Q2・推奨（未確定）・DB スキーマ＝クリティカル箇所）

- **採用案（推奨）**:
  - **`notifications` には確定した分だけを書く**。未来の仮の発火は書かない（ダッシュボードの段階表示が先取りして狂うため）。
  - 登録した予約の控えを別に持つ（新しいテーブル。列は予約 ID・予約時刻・`rule_key`・段階・ルール種別・タスク・文面・登録時刻の見込み。具体は S2）。
  - **計画し直すたびに、最初に突き合わせる**: 控えのうち「予約時刻が今以前で、それまでに取り消していない」ものを、`sent_at` = 予約時刻として `notifications` へ確定する。残り（未来の分）は取り消して控えから消す。登録に失敗した予約は控えに残さない（＝確定しない）。
  - 配信の成否は現行どおり区別しない（OS が表示したかはアプリが起きていないと分からない。現行も「送信を試みた」記録）。確定した行は `delivered` を「不明」とし、予約経由であることを `channel` で区別する。
  - 切り詰め: 上限（Q3）を守る設計のため起きない前提とし、登録後に OS の予約件数が控えと食い違えば記録して残す（確定の対象は控えのまま。S3）。
- **理由**: 現行の履歴の意味（送信を試みた記録）と同じ基準で、アプリが起きていない間の出来事を後から決定的に確定できる。
- **代替案**: (a) 控えを持たず OS の予約一覧（`pending`）だけを見る — 配信済みの予約は一覧から消えるため、何を予約していたか分からない。(b) 仮の発火を `notifications` に書いて取り消し時に消す — 読み手（ダッシュボード）が未来の段階を見る。
- **影響範囲**: DB スキーマ（新テーブル・`notifications` の書き方）。**クリティカル箇所（人間レビュー必須）**。

### 3. 予約件数の上限と、上限で予約しきれない分（Q3 ★・未確定）

- 実測では、朝会を放置した日は約 8 時間で 64 件に達する（内訳の大半は朝会・夕会の L3 の 10 分ごとの繰り返し）。アプリを開かない限り計画し直せないため、上限を使い切った後は、次にアプリを開くまで催促が止まる。
- 現状、OS の通知を出すのは検知の催促だけ（`sendNotification` の呼び出し元は `scheduler-tick.ts` のみ）で、催促以外に 64 件を分け合う予約は無い。
- **選択肢**:
  - A（推奨）: 催促に 63 件を使い、**最後の 1 件を「予約切れ」の固定通知**（例: 「しばらく報告が無い。アプリを開いて状況を報告しろ」）にする。検知の強度は現行のまま。上限を使い切ったことが利用者に分かる。
  - B: 64 件をすべて催促に使い、使い切ったら黙る。現行と同じ強度だが、止まったことが利用者に分からない。
  - C: 予約方式に限り繰り返しを間引く（例: L3 の繰り返しを `rule_key` ごとに N 回まで）。夜まで催促が続くが、**催促の強度がデスクトップ・開発者用の版と変わる**。
  - D: 重要な時刻（朝会・夕会・約束の L1）を優先して枠を確保し、残りを時刻順に割り当てる。
- 決定（未確定）: オーナー判断（催促の強度・体験の根幹）。

### 4. 文面（Q4 ★・未確定）

- 現行の文面は人格設定（口調 4 種・厳しさ 1〜5・カスタム指示・名前）とタスクから送信時に LLM で生成し、失敗時は人格を反映しない固定文（8 ルール × 3 段階）へ落ちる。予約方式では送信時に生成できない。
- **選択肢**:
  - A: 固定文（現行の `FALLBACK_TEMPLATES`）だけ — LLM 費用 0・常に動く。人格設定（口調・厳しさ・名前）が催促に出ない。
  - B: 予約ごとに事前生成 — 1 件ずつタスクに合った文面。計画し直すたび（活動・チャット発言のたび）に最大 63 件を再生成するため、費用と待ち時間が大きい（プラン込み枠の原価に直結）。オフライン時は A に落ちる。
  - C（推奨）: **人格設定ごとの文面セットを事前生成**して使う — 人格設定を保存したとき（と初回）に LLM で「ルール × 段階 × 数通り」の文面をまとめて生成して端末に保存し、タスク名・約束の時刻は差し込む。生成は人格設定の変更時だけ（1 回の呼び出し）で、生成前・失敗時は A に落ちる。タスクの中身は LLM へ送らない。
  - D: B と C の併用（直近の数件だけ事前生成、残りは C）。
- 決定（未確定）: オーナー判断（ボスの人格・トーン）。デスクトップが毎分方式のまま（Q5 の推奨）なら、デスクトップは現行どおり送信時に生成し、モバイルだけが C になる（端末で文面の質が変わる）。

### 5. デスクトップ（macOS）の方式（Q5・推奨（未確定））

- **採用案（推奨）**: デスクトップは #579 のクリティカル設計決定 2 のとおり**毎分方式を維持**し（メニューバー常駐・送信時の LLM 文面）、予約通知方式はモバイルだけに使う。
- **理由**: 通知プラグインのデスクトップ実装は予約に対応していない（実測）。統一するには macOS の予約通知を自前で実装する必要がある。毎分方式と計画層は同じ `evaluateRules` を呼ぶため、判定の食い違いは生じない。
- **代替案**: macOS も予約通知方式へ統一する — アプリを終了（Quit）しても催促が届く利点があるが、自前のネイティブ実装が要り、文面も送信時に生成できなくなる。

### 6. 通知プラグインの手当て（Q6・推奨（未確定））

- **仕様で決めること**: 予約・取り消し・予約一覧を担う**通知の予約ポート**を置き、製品版の実装は (1) 非 UTC の時間帯でも指定した時刻に予約される、(2) 登録の失敗が呼び出し側へ返る（`sendNotification` は使わない）、を満たす。
- **方式（推奨）**: プラグインを fork して iOS の日時の解釈を直し（`DateFormatter` に UTC を指定）、同じ修正を上流へ PR する。上流に取り込まれたら fork をやめる。JS 側の補正（`spike/ios-tauri` の `localWallClockAsUtc`）は採らない（上流が直った時点で黙って逆方向にずれる）。
- 実装の細部は S3 を実装対象にするときに決める。

### 7. 複数端末での催促（Q8 ★・未確定）

- 端末間同期（ADR 0011 決定 18）とモバイルの全機能（決定 20）により、Mac とスマホが同じデータから別々に催促を計画しうる。そのままでは (1) 両方の端末で同じ催促が鳴る、(2) Mac で作業を報告しても、スマホのアプリが起きるまでスマホに予約済みの古い催促が取り消されず鳴る（ADR 0004 が避けたい誤発火）。
- **選択肢**: A（推奨）本機能は単一端末を前提とし、複数端末の扱いは端末間同期の実装 Issue で決める（有力案は「催促を受ける端末を 1 台に指定する」）／B 本機能で「催促を受ける端末の指定」まで入れる／C 同期の中継からのサイレントプッシュでスマホに計画し直させる（iOS は届く時刻を保証しない・APNs が要る）。
- 決定（未確定）: どの端末が鳴るかは体験に関わるためオーナー判断。

## 機能全体の設計

### アーキテクチャ決定

- 計画層（`planNudges`）・入力の圧縮・突き合わせは、実行環境に依存しないコアの純粋関数とする（#579 のアーキテクチャ決定に従う）。DB・OS の予約は呼び出し側（S2・S3）が扱う。
- 計画し直す契機（推奨・S2）: アプリの起動・前面への復帰、状態を変える API 要求（`/api` の GET 以外）の後、アプリ起動中の暦日の変わり目、通知のタップ、時間帯の変更。

### IF / API

- `planNudges(入力) → 予約の列`。入力は `DetectionInput` から `now` と暦日ごとの値を除いたもの＋ `now`・地平線の終わり・件数の上限・暦日ごとの値。予約 1 件は `FiringNotification` ＋予約時刻。
- 突き合わせ（`reconcile`）: 入力は控えと今、出力は `toConfirm`（確定する履歴。`NotificationHistoryEntry` 相当の列）と `toCancel`（取り消す控えの列）の 2 つ（名前は実装で決めてよい）。

### ADR 0004 改訂案（草案・S3 で確定）

- 帰結「スケジューラは毎分チェック方式」を、「デスクトップと開発者用の版は毎分チェック方式、モバイルは予約通知方式。予約通知方式は検知エンジンを 1 分刻みで先へ評価する計画層で予約時刻を求め、予約時刻を過ぎた予約を送信履歴として確定する」へ改める。
- 決定 4（活動シグナルによるリセット）は「活動があれば未配信の予約を取り消して計画し直す」として表現される。決定 1〜3 は変えない。

### 実装計画（S1 のチケット分解の見通し）

1. 計画層（`planNudges`）と、`sweep` との一致のテスト
2. 入力の圧縮と、圧縮前後の一致のテスト
3. 突き合わせ（`reconcile`）

## やらないこと

- 実機での到達確認（アプリ終了中・ロック中・低電力モード・64 件の切り詰め順）（理由: オーナー判断で製品化の後のフェーズ）
- デスクトップ（macOS）の予約通知方式への統一（理由: クリティカル設計決定 5 の推奨。確定すれば範囲外のまま）
- 開発者用の版（Node サーバー・node-cron）の変更（理由: 毎分方式のまま残す）
- 検知ルール・閾値・エスカレーション間隔・日次上限の変更（理由: 本機能は実行方式の作り替えで、催促の強度は変えない。変える場合は Q3 の決定による）
- 複数端末での催促の重複の解消（理由: Q8。端末間同期〔ADR 0011 決定 18〕の実装とあわせて扱う推奨）
- LLM プロバイダの抽象化（#582）・スマホ向けレイアウト（#586）・Tauri の器（#579 S2）・製品版の DB（#580）
- バックグラウンド実行（iOS の BGAppRefreshTask 等）による計画し直し（理由: 時刻が保証されない。必要なら別 Issue）

## 受入基準（S1）

時刻はローカル日付で組み、`npm run test:tz` でも合格させる（ADR 0007）。

- [ ] 活動が無い入力について、`planNudges` が返す予約（時刻・ルール種別・`rule_key`・段階・タスク）は、同じ入力・同じ刻みで `evaluateRules` を 1 分ずつ呼んで発火を履歴へ積んだ結果と一致する。入力の例: 最優先の未着手タスク（L1 → L2 → L3 → L3 の繰り返し）、無音、朝会・夕会、勤務時間帯外の 1 回だけの発火、着手の約束、日次上限に達するルール
- [ ] 地平線が暦日をまたぐとき、翌日の朝会・夕会の予約は翌日の暦日に対応する値で計算される。入力の例: 当日の朝会を実施済みでも翌日の朝会は予約される／当日だけ朝会の時刻を上書きしていても翌日の朝会は翌日の値（恒常設定）の時刻に予約される（当日の上書きは当日しか受け付けない〔`meeting-schedule-routes.ts` の `not_today`〕ため、翌日の値は恒常設定になる）
- [ ] `planNudges` が返す予約は、地平線の終わり以降の時刻を含まない
- [ ] `planNudges` が返す予約の件数は引数で渡した件数の上限以下で、上限に達したときは時刻の早いものから上限の件数だけを返す（上限を使い切ったときの扱い〔Q3〕は `planNudges` の外の後段で行い、S1 の範囲外。Q3 がどの選択肢になっても `planNudges` のこの振る舞いは変わらない）
- [ ] 入力の圧縮を通した入力と通さない入力で、`planNudges` の結果が一致する。入力の例: 古い `task_start` だけが進行中タスクを指す、終わっていない古い休憩、同じ `rule_key` の古い通知、日次上限の枠に入る当日の通知
- [ ] 入力の圧縮後の活動・通知の件数は、履歴の長さ（例: 1 日分と 1 年分）によらず同じ上限以下になる
- [ ] 突き合わせは、予約時刻が今以前の控えを確定する履歴として返し、その送信時刻は予約時刻である
- [ ] 突き合わせは、予約時刻が今より後の控えを取り消す予約として返し、確定する履歴に含めない
- [ ] `server/src/detection/` のファイルは変更されない
- [ ] `npm run lint`・`npm run typecheck`・`npm test`・`npm run test:tz` が合格する

## 仮定（軽微・可逆）

- A1: 計画層のファイル名・置き場所（`server/src` のコア内）は実装で決める
- A2: 最初の刻みを `now`、以降を分の境界とする（現行 cron と同じ粒度）。`now` の刻みで発火する予約は「すぐ」に予約する（OS は過去時刻を拒否するため、登録時に数秒先へ寄せる。S3）
- A3: 活動の直後に最優先タスクが未着手のままなら L1 を再発火する現行の振る舞い（`resolveEscalation` の活動リセット）は変えない。予約方式では「計画し直した直後の L1 予約」になる
- A4: 暦日ごとの値の対応に地平線内の暦日が欠けていれば、`planNudges` は例外を投げる（呼び出し側の契約違反。受入基準は変えない）
