# 催促を予約通知方式へ作り替える（ADR 0004 改訂）

> Issue #585。2026-09-27 に論点 Q1〜Q8 を確定した。★（Q3・Q4・Q8）はオーナーの決定、それ以外は親（flywheel エージェント）の決定。

## 概要

モバイル（iOS / Android）では、「このまま何もしなければ◯時◯分に催促」を先に計算して OS の予約通知に登録し、活動があれば取り消して登録し直す（[ADR 0011](../adr/0011-productization-architecture.md) 決定 12〜14）。予約時刻は、検知エンジン（`evaluateRules`）を変えずに、**仮の発火を 1 つずつ履歴へ積みながら時刻を進めて評価する計画層**で求める。

## 背景・目的

- iOS はアプリを常駐させられず、「毎分判定して通知」（現行の `scheduler.ts`＝node-cron `* * * * *`）が成り立たない。モバイルはデスクトップと同等の全機能（ADR 0011 決定 20）で、催促はコア価値である。
- 未来の時刻を 1 回入れて評価するだけでは予約時刻は出ない。エスカレーション（`resolveEscalation`）・重複抑止・日次上限（`dailyNotificationCap`）が送信履歴（`DetectionInput.notifications`）に依存するためである。
- iOS の予約通知は 64 件が上限で、超えるとエラーを出さずに先に登録した分から切り詰められる（#576）。
- 予約通知では送信時に LLM で文面を生成できない（ADR 0011 決定 13）。

## ユーザーストーリー

- 製品版をスマホで使う利用者として、アプリを閉じていても、何もしなければ現行版と同じ時刻・同じ段階（L1 → L2 → L3）で催促が届いてほしい。
- 同じ利用者として、作業を報告したら、それ以降に予約されていた古い催促が届かないでほしい。

## 機能要件（機能全体。スライスごとの範囲は「スライス」節）

- [ ] 活動が無い前提で計算した予約の時刻・ルール・段階は、同じ入力で現行の毎分方式（`evaluateRules` を毎分呼ぶ方式）が出す発火と一致する（S1）
- [ ] 予約した時刻に、アプリが起動していなくても催促が届く（S3。シミュレータで確認。実機は製品化の後のフェーズ）
- [ ] 活動が記録されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] タスクが変更されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] 設定（勤務時間・会の時刻・日次上限・人格）が変更されると、未配信の予約を取り消し、変更後の状態から予約し直す（S2）
- [ ] アプリの起動・前面への復帰で、未配信の予約を取り消し、その時点の状態から予約し直す（S2 で計画し直しの入口、器〔#579 S2〕のライフサイクルの契機への接続は S3）
- [ ] 予約の件数は OS の上限（iOS 64 件）を超えない（S1 で計画の件数を検証）
- [ ] 予約した時刻を過ぎた予約は、`sent_at` を予約時刻として送信履歴（`notifications`）に確定される（S1 で突き合わせの規則、S2 で DB への反映）
- [ ] OS での予約の取り消しに失敗した控えの行は消えずに残る（S2）
- [ ] 取り消し待ちの控えの行は、次の計画し直しで取り消しが再試行される（S2）
- [ ] 取り消し待ちの予約と同じ予約（同じ予約 ID）を新しい計画が含むとき、その予約は二重に登録されない（S2）
- [ ] 新しく登録する予約の件数は、OS に残る取り消し待ちの予約と合わせて 64 件を超えない（S2）
- [ ] 取り消し待ちのまま予約時刻を過ぎた予約は、送信履歴に確定される（S1 で突き合わせの規則、S2 で DB への反映）
- [ ] 確定した送信履歴を入力にした次の計画で、エスカレーションの段階は毎分方式で書かれた履歴と同じになる（S2）
- [ ] 確定した送信履歴を入力にした次の計画で、重複抑止は毎分方式で書かれた履歴と同じに働く（S2）
- [ ] 確定した送信履歴を入力にした次の計画で、日次上限は毎分方式で書かれた履歴と同じに数えられる（S2）
- [ ] ダッシュボードの当日の段階表示は、確定した送信履歴だけを数え、未来の予約を数えない（S2）
- [ ] 予約した通知の文面は送信時に LLM を呼ばずに決まる（S2）
- [ ] 計画が件数の上限（63 件）で打ち切られたことを検出する（S1）
- [ ] 打ち切られたとき、打ち切りの時刻（上限で予約できなかった最初の発火の時刻）を求める（S1）
- [ ] 打ち切られたとき、最後の 1 件として「アプリを開いて報告しろ」という固定の通知を、打ち切りの時刻に予約する（S2）
- [ ] 打ち切られなかったとき、固定の通知を地平線の終わり（計画した時刻から 24 時間後）に予約する（S2）
- [ ] 文面は、個別の事前生成 → 人格設定ごとの文面セット → 固定文の順で決まる（S2。クリティカル設計決定 4）
- [ ] 個別生成の文面は、LLM への入力（人格設定・ルール・段階・タスクの状態・優先度・証跡・締切・約束の時刻・予約時刻）のどれかが変わると使い回さない（S2）
- [ ] 個別生成の文面への差し替えに失敗したとき、差し替え前の文面の予約が同じ予約時刻で有効に残る（S2）
- [ ] 非 UTC の時間帯（例: JST）の端末で、指定した時刻どおりに予約される（S3）
- [ ] 予約の登録の失敗が呼び出し側に返る（S3）
- [ ] 予約の取り消しの失敗が呼び出し側に返る（S3）
- [ ] ADR 0004 を改訂する（S3。改訂案は「機能全体の設計」）

## 非機能要件

- パフォーマンス: 1 回の計画は、履歴の長さ（利用日数）に比例して遅くならない（入力の圧縮。クリティカル設計決定 1）。
- 信頼性: 予約の登録・取り消しの失敗を握りつぶさない（通知の実行系はクリティカル箇所）。

## 技術的な制約・方針

- **前提: 催促を計画する端末は 1 台**（オーナーの決定 Q8）。複数端末の扱いは端末間同期（#595）で決める（クリティカル設計決定 7）
- 使用技術: TypeScript（計画層・突き合わせは `server/src` のコアに置く純粋関数）、Tauri 2 の通知プラグイン（S3）
- 前提（別 Issue）: #579 S2（Tauri の器）・#580 S2（製品版の DB）が S3 の前提。S1 は前提なしで `main` に入れられる
- 既存コードとの関係: **検知エンジン（`server/src/detection/`）は無改変**（ADR 0004 決定 2。帰結「検知エンジンに新しい入力経路を足さない」）。計画層は `scheduler-tick.ts` と同じ「エンジンを呼ぶ側」の層である
- 開発者用の版（Node サーバー・node-cron の毎分方式）は変えない

## クリティカル設計決定

### 1. 予約時刻を求める計画層（Q1・【決定】2026-09-27・親）

- **採用案**: 新しい純粋関数 `planNudges`（置き場所は `server/src` のコア。名前・ファイルは実装で決める）が、`now` から地平線の終わりまで **1 分刻みで `evaluateRules` を呼び、発火を仮の履歴へ積みながら進める**（`sweep` と同じ形）。活動は起きないものとして計算する（活動があれば計画し直す）。
  - **暦日ごとの入力**: 朝会・夕会の実効時刻と当日のセッション種別は、地平線に含まれる暦日ごとに呼び出し側が解決して渡す（暦日 → 値の対応）。計画層は刻みの暦日に応じて差し替える。地平線内の暦日が対応に欠けていれば呼び出し側の契約違反として例外を投げる（仮定 A4）。
  - **入力の圧縮**: 計画の前に、結果を変えない範囲で履歴を絞る純粋関数を通す。圧縮の前後で計画が一致することをテストで固定する。
    - 活動: 直近の一定期間（`now` の前日のローカル 0 時以降。仮定 A7）＋種類ごとの最新の 1 件。ただし `task_start` は、`task_id` が非 null の最新 1 件も別途残す（`silence.ts` の `getInProgressTask` は「非 null の `task_id` を持つ `task_start` の最新」を見るため、種類ごとの最新だけだと、その最新が `task_id: null` のケースで見落とす。S1 実装で判明・確認済み）。
    - 通知: 直近の一定期間（同上。日次上限の枠と、日付を含む `rule_key` の発火はすべてこの中に入る）＋**窓の外は、この計画で発火しうる日付を含まない `rule_key` ごとの最新の 1 件だけ**。対象は、タスクに紐付かない `break_overrun`・`silence` と、現在の未完了タスク（`todo`・`in_progress`・`paused`）の `unstarted`・`avoidance`・`deadline_overdue`・`commitment_missed`（現在の約束のキー）である。
    - 日付を含む `rule_key`（朝会・夕会の例 `morning_meeting:2026-09-27@09:00`、勤務時間帯外の例 `silence:2026-09-20`＝末尾が帯外区間の開始日）は、その日付の発火が必ず窓の中に入るため、窓の外の分を残さない。完了・中止したタスクや置き直す前の約束のキーも残さない。`rule_key` ごとの最新の 1 件を無条件に残すと、日付を含むキーが利用日数に比例して増える（実コード: `meeting.ts` の `buildMeetingRuleKey`・`rule-engine.ts` の帯外区間キー）。
  - **刻み**: 最初の刻みは `now`、以降は分の境界（現行 cron と同じ）。
  - **地平線**: `now` から 24 時間、かつ予約件数の上限（催促 63 件。決定 3）に達したところまで。24 時間にするのは、夜に閉じたアプリを朝開かなくても翌朝の朝会の催促が予約済みであるため（ただし件数の上限に先に達する日はこの効能が及ばず、決定 3 の固定の通知がアプリを開くよう促す。上限に達しない日も、地平線の終わりに固定の通知を置く）。
- **理由**: `evaluateRules` をそのまま使うため、現行の毎分方式との一致が作りから保証される（ルールの知識を計画層へ複製しない）。
- **代替案**: (a) 次に状態が変わる時刻（閾値・間隔・勤務時間の境界・会の時刻・締切・約束）を解析的に求めて飛ぶ — 速いが、ルールごとの時刻計算を計画層に複製することになり、ルール変更のたびに食い違う。(b) 圧縮せず 1 分刻み — 実測で履歴 5,000 件あたり 4.4 秒（Mac）で、スマホではさらに遅い。
- **影響範囲**: 新規の計画層のみ。検知エンジン無改変。

### 2. 予約と送信履歴の突き合わせ（Q2・【決定】2026-09-27・親・DB スキーマ＝クリティカル箇所）

- **採用案**:
  - **`notifications` には確定した分だけを書く**。未来の仮の発火は書かない（ダッシュボードの段階表示が先取りして狂うため）。
  - 登録した予約の控えを別に持つ（新しいテーブル。列は予約 ID・予約時刻・`rule_key`・段階・ルール種別・タスク・文面・登録時刻の見込み。具体は S2）。
  - **計画し直すたびに、最初に突き合わせる**: 控えのうち予約時刻が今以前のものを、`sent_at` = 予約時刻として `notifications` へ確定する。残り（未来の分）は OS で取り消す。登録に失敗した予約は控えに残さない（＝確定しない）。
  - **控えの行は、OS での取り消しが成功してから消す**。取り消しに失敗した行は消さずに「取り消し待ち」として残し、次の計画し直しで取り消しを再試行する（行を先に消すと、OS に残った古い催促を取り消す手がかりが無くなり、新しい計画と重なって重複・矛盾した催促が届く）。
    - 取り消し待ちの行と同じ予約（同じ予約 ID。仮定 A9）が新しい計画にあれば、登録し直さずにその行を有効に戻す（二重に登録しない）。
    - 取り消し待ちの行も OS の予約の枠を使うため、新しく登録する件数は、取り消し待ちの件数と合わせて 64 件を超えない（催促の件数の上限を取り消し待ちの件数だけ減らす。固定の通知の 1 件は残す）。
    - 取り消し待ちのまま予約時刻を過ぎた行は、OS が配信した可能性があるため、有効な行と同じく確定する（現行の「送信を試みた」記録と同じ意味）。
  - 配信の成否は現行どおり区別しない（OS が表示したかはアプリが起きていないと分からない。現行も「送信を試みた」記録）。確定した行は `delivered` を「不明」とし、予約経由であることを `channel` で区別する。
  - 固定の「アプリを開いて報告しろ」通知（決定 3）は検知の発火ではないため、送信履歴へ確定しない（`rule_key` を持たない）。
  - 切り詰め: 上限（決定 3）を守る設計のため起きない前提とし、登録後に OS の予約件数が控えと食い違えば記録して残す（確定の対象は控えのまま。S3）。
- **理由**: 現行の履歴の意味（送信を試みた記録）と同じ基準で、アプリが起きていない間の出来事を後から決定的に確定できる。
- **代替案**: (a) 控えを持たず OS の予約一覧（`pending`）だけを見る — 配信済みの予約は一覧から消えるため、何を予約していたか分からない。(b) 仮の発火を `notifications` に書いて取り消し時に消す — 読み手（ダッシュボード）が未来の段階を見る。
- **影響範囲**: DB スキーマ（新テーブル・`notifications` の書き方）。**クリティカル箇所: DB スキーマの変更を含むスライス（S2）の PR は人間レビュー必須**。

### 3. 予約件数の上限と、上限で予約しきれない分（Q3 ★・【決定】2026-09-27・オーナー）

- **決定**: **催促に 63 件を使い、最後の 1 件を「アプリを開いて報告しろ」という固定の通知にする**（選択肢 A）。検知の強度（閾値・間隔・日次上限・L3 の繰り返し）は変えない。
- **固定の通知は毎回の計画で必ず 1 件置く**（オーナーの補足決定 2026-09-27。予約した催促を使い切ったまま黙らないため。アプリを開かずに地平線〔24 時間〕を過ぎると、上限に達しない日でも催促が尽きるため）。
- **固定の通知の時刻**: 打ち切りの時刻（上限で予約しきれなかった最初の催促の予約時刻）と地平線の終わり（計画した時刻から 24 時間後）の早い方。打ち切りの時刻は必ず地平線の中にあるため、打ち切られたときは打ち切りの時刻、打ち切られなかったときは地平線の終わりになる。取り消し待ちがあって催促の枠が減った計画（決定 2）でも同じ規則で 1 件置く（枠の計算では固定の通知の 1 件を常に確保する）。
- **固定の通知の文面**: 人格設定によらない固定文（例: 「しばらく報告が無い。アプリを開いて状況を報告しろ」。文言は S2 で決める）。LLM で生成しない。
- **根拠（実測）**: 朝会を放置した日は約 8 時間で 64 件に達する（内訳の大半は朝会・夕会の L3 の 10 分ごとの繰り返し）。アプリを開かない限り計画し直せないため、使い切った後は次に開くまで催促が止まる。現状、OS の通知を出すのは検知の催促だけで、64 件を分け合う他の予約は無い。
- **検討した代替案**: B 64 件すべてを催促に使い使い切ったら黙る（止まったことが利用者に分からない）／C 予約方式に限り L3 の繰り返しを間引く（催促の強度がデスクトップと変わる）／D 朝会・夕会・約束の L1 を優先して枠を確保する。

### 4. 文面（Q4 ★・【決定】2026-09-27・オーナー。組み合わせ方の設計は親への推奨）

- **決定**: **予約 1 件ごとの事前生成（B）と、人格設定を保存したときのまとめ生成（C）を併用する**（選択肢 D）。
- **組み合わせ方**: **C を常に土台とし、計画の直近の数件だけに B を上乗せする**。予約はまず C（または固定文）の文面で登録し、B の文面が生成できたら同じ予約を差し替える。
- **C: 人格設定ごとの文面セット**
  - 内容: 8 ルール × 3 段階 × 3 通り ＝ 72 文。タスク名・約束の時刻は差し込み（プレースホルダ）にする。
  - 生成の契機: 初回（文面セットが無いとき）と、人格設定（名前・口調・厳しさ・カスタム指示）を保存したとき。
  - 上限（推奨値・仮定 A6）: 1 暦日あたり 3 回まで（失敗時の再試行を含む）。
  - LLM へ送るもの: 人格設定とルール・段階の名前だけ。**タスクの情報は送らない**。
- **B: 予約 1 件ごとの個別生成**
  - 対象: 計画し直すたびに、計画の**時刻の早いものから 3 件まで**のうち、同じ中身の文面をまだ持たず、予約時刻まで 60 秒以上あるもの。生成済みの文面は中身が同じ限り使い回し、計画し直しのたびには作り直さない。
  - **「同じ中身」の判定（使い回しのキー）**: LLM への入力全体（モデル名・システムプロンプト・依頼文・最大トークン数）のハッシュが一致すること。下の「LLM へ送るもの」の全項目（人格設定・ルール種別・段階・タスクの状態・優先度・証跡の要否と件数・締切・約束の時刻・予約時刻）がこれに含まれるため、どれか 1 つが変われば作り直す（`rule_key` とタスク名だけで判定すると、締切・優先度・証跡の変更後に古い文面が届く）。
  - 上限（推奨値・仮定 A6）: 1 時間あたり 12 回・1 暦日あたり 60 回。上限に達したら C を使う。
  - 差し替えの条件: 生成が終わった時点で、その予約が現在の計画に同じ中身のまま残っていて、予約時刻まで 30 秒以上あるときだけ差し替える。
  - **差し替えで代替の予約を失わない**: 差し替えは任意の上乗せであり、差し替えの失敗で催促を失ってはならない。B の文面の登録に失敗したときは、差し替える前の C（または固定文）の予約が同じ予約時刻で有効な状態に戻す。OS が同じ予約 ID での登録を置き換えとして扱えるならそれを使い（取り消してから登録しない）、使えなければ取り消し → B で登録 → 失敗したら元の文面で登録し直す。元の文面での登録し直しも失敗したら、その予約は「登録に失敗した予約」として扱い（控えに残さず確定しない。決定 2）、失敗を記録して次の計画し直しで登録し直す。控えの文面は登録が成功した文面に合わせる。どちらの方式を使うかは S3（通知の予約ポート）で決める。
  - LLM へ送るもの: **現行の送信時生成（`generateNotificationBody`）と同じ範囲に留める**。人格設定・ルール種別・段階・対象タスクの 1 行（タイトル・状態・優先度・証跡の要否と件数・締切。説明文は含まない）・約束の時刻（`commitment_missed` のみ）。「現在日時」には予約時刻を渡す。
- **上限の根拠**:
  - 3 件: 最も密な催促でも L1 → L2（15 分後）→ L3（25 分後）の 1 回分のエスカレーションに当たる。それより先の予約は、次の活動で取り消される見込みが高い。
  - 1 時間 12 回（5 分に 1 回）: 実測で最も密な 1 時間の発火は 17 件だが、B は中身の同じ催促を使い回すため、1 時間に要る新しい文面はこれより少ない。
  - 1 日 60 回: 現行のデスクトップは届けた催促 1 件ごとに LLM を 1 回呼ぶ。実測の最悪の日（活動なし・会を未実施）は 141 件、朝会を済ませた日は 52 件で、60 回はこれらを下回る＝**現行の送信時生成の最悪の日より費用が増えない**。
- **LLM 費用の見積もり（1 利用者・1 日。料金はモデル〔#583 で選定〕に依存するため、呼び出し回数とトークンで示す）**:

  | 生成 | 1 回あたり（入力 / 出力） | 上限の日 | 典型的な日（推定） |
  |---|---|---|---|
  | B | 約 1,000 / 最大 150（典型 60）トークン | 60 回 → 入力 約 6 万・出力 最大 約 9,000 | 約 20 回 → 入力 約 2 万・出力 約 1,200 |
  | C | 約 1,000 / 約 3,000〜4,000 トークン | 3 回 → 入力 約 3,000・出力 最大 約 1.2 万 | 0 回（人格設定を変えた日だけ 1 回） |
  | 合計 | — | 入力 約 6.3 万・出力 最大 約 2.1 万 | 入力 約 2 万・出力 約 1,200 |

  - 使い回しのキーに予約時刻が入るため、活動の後に同じ催促の時刻がずれると作り直しになる。典型的な日の回数はその分増えうるが、上限（1 時間 12 回・1 日 60 回）で頭打ちになり、上限の日の見積もりは変わらない。
  - 1 回あたりの入力は、既定の人格設定で `buildPersonaPrompt`（`purpose: "notification"`）が作るシステムプロンプトが約 700 文字、依頼文が約 150 文字の実測からの概算。典型的な日の回数は、1 日の催促のうち中身の異なるものが 20 件程度という推定で、実測していない。
- **文面が決まる順序（フォールバック）**: B の文面（中身が同じもの）→ C の文面セット（現在の人格設定のもの）→ 固定文（現行の `FALLBACK_TEMPLATES`）。B の生成が間に合わない・失敗した・上限に達したときは C、C がまだ無い・生成に失敗したときは固定文で予約する。どの段階でも予約自体は必ず行う（ADR 0004 帰結「文面生成が失敗しても催促自体は送る」）。B への差し替えに失敗したときも、差し替え前の文面の予約を残す（上記「差し替えで代替の予約を失わない」）。
- **デスクトップ**: 毎分方式のまま（決定 5）送信時に生成する。モバイルと文面の作り方が異なることは受け入れる。
- **影響範囲**: 通知文面の生成（**クリティカル箇所: Claude API 連携**。S2 の PR は人間レビュー必須）・文面セットと B の文面の保存先（S2 で決める）。

### 5. デスクトップ（macOS）の方式（Q5・【決定】2026-09-27・親）

- **採用案**: デスクトップは #579 のクリティカル設計決定 2 のとおり**毎分方式を維持**し（メニューバー常駐・送信時の LLM 文面）、予約通知方式はモバイルだけに使う。
- **理由**: 通知プラグインのデスクトップ実装は予約に対応していない（実測）。統一するには macOS の予約通知を自前で実装する必要がある。毎分方式と計画層は同じ `evaluateRules` を呼ぶため、判定の食い違いは生じない。
- **代替案**: macOS も予約通知方式へ統一する — アプリを終了（Quit）しても催促が届く利点があるが、自前のネイティブ実装が要り、文面も送信時に生成できなくなる。macOS でアプリの終了中に催促を届けることは本機能の範囲外とする（「やらないこと」）。

### 6. 通知プラグインの手当て（Q6・【決定】2026-09-27・親）

- **仕様で決めること**: 予約・取り消し・予約一覧を担う**通知の予約ポート**を置き、製品版の実装は (1) 非 UTC の時間帯でも指定した時刻に予約される、(2) 登録の失敗が呼び出し側へ返る（`sendNotification` は使わず `invoke("plugin:notification|notify")` の結果で受ける）、を満たす。
- **クリティカル箇所**: 通知の実行系。S3 の PR は人間レビュー必須。
- **方式**: プラグインを fork して iOS の日時の解釈を直し（`DateFormatter` に UTC を指定）、同じ修正を上流へ PR する。上流に取り込まれたら fork をやめる。JS 側の補正（`spike/ios-tauri` の `localWallClockAsUtc`）は採らない（上流が直った時点で黙って逆方向にずれる）。
- 実装の細部は S3 を実装対象にするときに決める。

### 7. 複数端末での催促（Q8 ★・【決定】2026-09-27・オーナー）

- **決定**: **本機能は催促を計画する端末を 1 台とする前提で作り、複数端末の扱いは端末間同期（#595）で決める**（選択肢 A）。
- **#595 への申し送り**: 端末間同期（ADR 0011 決定 18）とモバイルの全機能（決定 20）により、Mac とスマホが同じデータから別々に催促を計画しうる。そのままでは次の 2 つが起きる。
  1. **重複**: 両方の端末で同じ催促が鳴る。
  2. **取り消し漏れ**: Mac で作業を報告しても、スマホのアプリが起きて同期を受け取り計画し直すまで、スマホに予約済みの古い催促が取り消されず鳴る（ADR 0004 が避けたい誤発火）。
  - 有力案: 「催促を受ける端末を 1 台に指定する」。ほかに、同期の中継からのサイレントプッシュでスマホに計画し直させる案がある（iOS は届く時刻を保証しない・APNs が要る）。
- **検討した代替案**: B 本機能で「催促を受ける端末の指定」まで入れる／C 上記のサイレントプッシュ。

## 機能全体の設計

### アーキテクチャ決定

- 計画層（`planNudges`）・入力の圧縮・突き合わせは、実行環境に依存しないコアの純粋関数とする（#579 のアーキテクチャ決定に従う）。DB・OS の予約は呼び出し側（S2・S3）が扱う。
- 計画し直す契機（推奨・S2）: アプリの起動・前面への復帰、状態を変える API 要求（`/api` の GET 以外）の後、アプリ起動中の暦日の変わり目、通知のタップ、時間帯の変更。

### IF / API

- `planNudges(入力) → 予約の列と打ち切りの時刻`。入力は `DetectionInput` から `now` と暦日ごとの値を除いたもの＋ `now`・地平線の終わり・件数の上限・暦日ごとの値。予約 1 件は `FiringNotification` ＋予約時刻。打ち切りの時刻は、上限で返せなかった最初の発火の時刻（打ち切られなければ無し）で、固定の通知（決定 3）の時刻に使う。
- 突き合わせ（`reconcile`）: 入力は控え（各行は有効か取り消し待ちかの状態を持つ）と今、出力は `toConfirm`（確定する履歴。`NotificationHistoryEntry` 相当の列）と `toCancel`（取り消す控えの列）の 2 つ（名前は実装で決めてよい）。

### ADR 0004 改訂案（草案・S3 で確定）

- 帰結「スケジューラは毎分チェック方式」を、「デスクトップと開発者用の版は毎分チェック方式、モバイルは予約通知方式。予約通知方式は検知エンジンを 1 分刻みで先へ評価する計画層で予約時刻を求め、予約時刻を過ぎた予約を送信履歴として確定する」へ改める。
- 決定 4（活動シグナルによるリセット）は「活動があれば未配信の予約を取り消して計画し直す」として表現される。決定 1〜3 は変えない。

### 実装計画（S1 のチケット分解の見通し）

1. 計画層（`planNudges`）と、`sweep` との一致のテスト
2. 入力の圧縮と、圧縮前後の一致のテスト
3. 突き合わせ（`reconcile`）

## やらないこと

- 実機での到達確認（アプリ終了中・ロック中・低電力モード・64 件の切り詰め順）（理由: オーナー判断で製品化の後のフェーズ）
- デスクトップ（macOS）の予約通知方式への統一と、**macOS でアプリの終了中（Quit）に催促を届けること**（理由: 決定 5。デスクトップは毎分方式のまま）
- 開発者用の版（Node サーバー・node-cron）の変更（理由: 毎分方式のまま残す）
- 検知ルール・閾値・エスカレーション間隔・日次上限の変更（理由: 本機能は実行方式の作り替えで、催促の強度は変えない〔決定 3〕）
- 複数端末での催促の重複と取り消し漏れの解消（理由: オーナーの決定 Q8。端末間同期 #595 で決める。申し送りは決定 7）
- LLM プロバイダの抽象化（#582）・スマホ向けレイアウト（#586）・Tauri の器（#579 S2）・製品版の DB（#580）
- バックグラウンド実行（iOS の BGAppRefreshTask）による計画し直し（理由: 時刻が保証されない。必要なら別 Issue）
- LLM の通信の再試行（`runWithTimeoutAndRetry`・最大 2 回）を生成の上限の回数に数えること（理由: 現行の送信時生成と同じ有限回の再試行で、上限を定数倍〔最大 3 倍の要求〕より多く超える迂回にはならない。数えると 1 回の生成の失敗が枠を 3 回分使い、上限の値の意味が変わる）
- 生成中に C の文面セットができたとき、登録済みの予約の文面を C へ差し替えること（理由: 決定 4 の差し替えは B だけ。C は次の計画し直しから使う）
- S2 での器・OS への配線（起動・前面への復帰・暦日の変わり目・通知のタップ・時間帯の変更の契機を計画し直しの入口へつなぐこと、通知の予約ポートの実装）（理由: 器〔#579 S2〕と通知の予約ポートの実装は S3）

## 受入基準（S1）

時刻はローカル日付で組み、`npm run test:tz` でも合格させる（ADR 0007）。

- [ ] 活動が無い入力について、`planNudges` が返す予約（時刻・ルール種別・`rule_key`・段階・タスク）は、同じ入力・同じ刻みで `evaluateRules` を 1 分ずつ呼んで発火を履歴へ積んだ結果と一致する。入力の例: 最優先の未着手タスク（L1 → L2 → L3 → L3 の繰り返し）、無音、朝会・夕会、勤務時間帯外の 1 回だけの発火、着手の約束、日次上限に達するルール
- [ ] 地平線が暦日をまたぐとき、翌日の朝会・夕会の予約は翌日の暦日に対応する値で計算される。入力の例: 当日の朝会を実施済みでも翌日の朝会は予約される／当日だけ朝会の時刻を上書きしていても翌日の朝会は翌日の値（恒常設定）の時刻に予約される（当日の上書きは当日しか受け付けない〔`meeting-schedule-routes.ts` の `not_today`〕ため、翌日の値は恒常設定になる）
- [ ] `planNudges` が返す予約は、地平線の終わり以降の時刻を含まない
- [ ] `planNudges` が返す予約の件数は引数で渡した件数の上限以下になる
- [ ] 予約が上限に達して打ち切られたときは、地平線内の発火のうち時刻の早いものから上限の件数だけが返る
- [ ] 上限に達して打ち切ったとき、`planNudges` は上限で返せなかった最初の発火の予約時刻を打ち切りの時刻として返す
- [ ] 地平線の終わりまでの発火が上限以内に収まったとき、`planNudges` は打ち切りの時刻を返さない
- [ ] 入力の圧縮を通した入力と通さない入力で、`planNudges` の結果が一致する。入力の例: 古い `task_start` だけが進行中タスクを指す、終わっていない古い休憩、未完了タスクの `rule_key` の古い通知だけがある（活動がその後に無い）、`silence` の古い L3 だけがある、日次上限の枠に入る当日の通知、前日に始まった勤務時間帯外の区間の通知、1 年分の朝会・夕会と勤務時間帯外の日付つきの通知
- [ ] 入力の圧縮後の活動の件数は、履歴の長さ（例: 1 日分と 1 年分）によらず同じ上限以下になる

## S2 の設計（2026-09-28。確定済みの決定 1〜7・機能全体の設計から導いたもの）

S2 はどこからも本番の経路に配線しない（開発者用の版の振る舞いは変わらない。決定 5）。器（#579 S2）と通知の予約ポートの実装（S3）がまだ無いため、S2 は**ポートの型と、それを呼ぶ計画し直しの処理**までを作り、OS の予約は模擬のポートで確かめる（決定 2「DB・OS の予約は呼び出し側〔S2・S3〕が扱う」・決定 4「置き換えか取り消し→登録かは S3 で決める」から、S2 は両方の方式で正しく動く形にする）。

### 通知の予約ポート（型だけ・実装は S3）

- 予約の登録（控えの行の ID・予約時刻・題名・文面）と取り消し（控えの行の ID）の 2 つの操作。どちらも失敗を例外で呼び出し側へ返す（決定 6 の (2) を型の契約として先に置く）。
- 同じ ID での登録が既存の予約の置き換えになるかを、ポートが宣言する（決定 4 の「OS が置き換えとして扱えるならそれを使い…」。どちらで宣言しても S2 の処理は成り立つ）。
- OS へ渡す ID は控えの行の整数の ID（Tauri の通知プラグインの ID は 32 ビット整数）で、仮定 A9 の予約 ID（文字列の照合キー）とは別物である。同じ予約（A9 の予約 ID が同じ）の行を有効に戻すときは同じ行を使うため、OS へ渡す ID も同じになる。

### 予約の控え（新テーブル。決定 2「具体は S2」）

- 列: 予約 ID（仮定 A9。一意。固定の通知は「固定の通知であること＋予約時刻」から決める）・予約の種類（催促／固定の通知）・状態（有効／取り消し待ち）・予約時刻・ルール種別・`rule_key`・段階・タスク（催促のみ。固定の通知は空）・文面・文面の出どころ（個別生成／文面セット／固定文〔`FALLBACK_TEMPLATES`〕／固定の通知）・個別生成の使い回しのキー（催促のみ）・登録時刻。
- **固定の通知の表現（「S2 の着手時に決めること」の解消）**: 予約の種類を列で明示する。突き合わせ（`reconcileReservations`）は、種類が固定の通知の行を、予約時刻が今より後なら取り消す対象に含め、今以前なら確定の対象（`toConfirm`）に含めず「確定せずに消す」対象として返す。
- 文面セット（C）と個別生成（B）の文面は、それぞれ別のテーブルに使い回しのキーで保存する。生成の試行は回数の上限のために記録する（試行 1 件 ＝ 1 行・種類と試行時刻）。

### 計画し直しの手順（1 回）

1. 突き合わせ: 控えを読み、予約時刻が今以前の催促の行を `sent_at` ＝ 予約時刻で `notifications` へ確定し（既存の `insertNotification` は `sent_at` を現在時刻に固定し、`recordNotificationDelivery` は `delivered` を 0/1 でしか書かないため、`sent_at`・`delivered` ＝ NULL・`channel` を 1 回で書く関数を足す）、確定した行と今以前の固定の通知の行を消す（確定と行の削除は 1 つのトランザクション）。
2. 取り消し: 予約時刻が今より後の行（有効・取り消し待ちとも）を OS で取り消す。成功した行を消し、失敗した行を取り消し待ちにする。
3. 計画: 検知の入力を 1 つのトランザクションで読み（`buildTickInput` と同じ理由・#606）、入力の圧縮を通し、地平線（今から 24 時間）の暦日ごとの会の実効時刻・セッション種別を解決して `planNudges` を呼ぶ。件数の上限は 63 から取り消し待ちの件数を引いた数（0 未満にしない）。当日のセッション種別は実施済みのセッションから求め、翌日以降の暦日は（まだ始まっていないため）実施済みの種別を持たない。
4. 登録: 計画の各予約について、取り消し待ちの行に同じ予約 ID があればその行を有効に戻す（登録しない）。無ければ控えの行を先に書いてから OS へ登録し、登録に失敗したらその行を消す（控えに残さない）。最後に固定の通知を 1 件、打ち切りの時刻（無ければ地平線の終わり）に同じ手順で登録する。
5. 文面の上乗せ（計画し直しの完了を待たせない）: 文面セットが無ければ C を生成し、計画の先頭 3 件について B を生成して差し替える（決定 4）。

- 計画し直しは同時に 1 本だけ走らせる。走っている間に来た契機は 1 回にまとめ、終わった後にもう 1 回走らせる。
- 契機（機能全体の設計「計画し直す契機」）: S2 は**計画し直しの入口**と、**状態を変える API 要求（`/api` の GET 以外）の応答の後にその入口を呼ぶための `createCoreApp` の任意の引数**を作る。開発者用の版はこの引数を渡さない。起動・前面への復帰・暦日の変わり目・通知のタップ・時間帯の変更は器のイベントであり、入口への接続は S3 で行う。

### 文面（決定 4 の B と C の具体）

- 文面が決まる順序: B（使い回しのキーが一致する保存済みの文面）→ C（現在の人格設定の文面セット）→ 固定文（`FALLBACK_TEMPLATES`）。固定の通知の文面は固定文「しばらく報告が無い。アプリを開いて状況を報告しろ」（決定 3 の例文をそのまま採る）。
- **B**: LLM への入力は現行の送信時生成（`generateNotificationBody`）と同じ組み立て（人格プロンプト〔`purpose: "notification"`・現在日時あり〕・依頼文・最大トークン数 150）で、「現在日時」を予約時刻にしたもの。使い回しのキーはモデル名・システムプロンプト・依頼文・最大トークン数の SHA-256。
- **C**: LLM へ送るのは人格設定（名前・口調・厳しさ・カスタム指示）とルール・段階の名前だけ。人格プロンプト（`buildPersonaPrompt`）はタスク一覧・時間帯のヒントを含むため使わず、人格設定だけから組み立てる。応答は 8 ルール × 3 段階 × 3 通りの JSON で、形が合わなければ失敗として扱う（保存しない）。タスク名は `{task}`、約束の時刻は `{time}` の差し込みで、予約時に置き換える。3 通りのどれを使うかは予約 ID から決定的に選ぶ。使い回しのキーは人格設定の SHA-256（人格設定を変えずに保存しても作り直さない）。
- **1 回の数え方**: 生成の呼び出し 1 回（LLM の 1 回の要求。その内部の通信の再試行〔`runWithTimeoutAndRetry`・最大 2 回〕は同じ 1 回に含む）を 1 回とし、失敗も数える。

### 上限の迂回経路と塞ぎ方（決定 4 の上限）

| 経路 | 塞ぎ方 |

## 仮定（軽微・可逆）

- A1: 計画層のファイル名・置き場所（`server/src` のコア内）は実装で決める
- A2: 最初の刻みを `now`、以降を分の境界とする（現行 cron と同じ粒度）。`now` の刻みで発火する予約は「すぐ」に予約する（OS は過去時刻を拒否するため、登録時に数秒先へ寄せる。S3）
- A3: 活動の直後に最優先タスクが未着手のままなら L1 を再発火する現行の振る舞い（`resolveEscalation` の活動リセット）は変えない。予約方式では「計画し直した直後の L1 予約」になる
- A4: 暦日ごとの値の対応に地平線内の暦日が欠けていれば、`planNudges` は例外を投げる（呼び出し側の契約違反。受入基準は変えない）
- A5: 固定の「アプリを開いて報告しろ」通知は送信履歴へ確定しない（`rule_key` を持たず、エスカレーション・日次上限・ダッシュボードの段階に影響させない）
- A6: 決定 4 の上限の数値（B: 直近 3 件・1 時間 12 回・1 暦日 60 回・予約時刻まで 60 秒以上。C: 72 文・1 暦日 3 回）は推奨値であり、S2 の実装・実測で調整してよい（受入基準は S2 を実装対象にするときに書く）
- A7: 入力の圧縮で残す「直近の一定期間」は、`now` の前日のローカル 0 時以降とする（回避検知の窓 30 分・勤務時間帯外の区間の開始日〔前日になりうる〕の日次上限の枠を覆うため）。これに種類ごとの最新の活動と、決定 1 の対象の `rule_key` ごとの最新の通知を加える。圧縮前後の一致の受入基準で正しさを固定し、期間の長さは実装で調整してよい
- A8: 圧縮で残す対象の `rule_key` を現在のタスクから組み立てるか、通知の `rule_key` を読み解くかは実装で決める（キーの形式は検知エンジンの内部であり、`buildCommitmentMissedRuleKey` のように書き出された組み立て関数があればそれを使う）
- A9: 予約 ID は `rule_key`・段階・予約時刻から決まる（同じ予約は同じ ID になる）。取り消し待ちの行と新しい計画の予約が同じかどうかは、この ID で判定する
- A10: 固定の通知の時刻は S2 で `planNudges` の打ち切りの時刻（無ければ地平線の終わり）から決める。`planNudges` 自体は変えない（S1 の受入基準は変わらない）
- A11（S2）: 取り消し待ちの行を有効に戻すとき、OS に残っている予約の文面は古いまま（取り消しに失敗した時点の文面）でもよい。登録し直すと二重に登録するため（決定 2）
- A12（S2）: 件数の上限から引く取り消し待ちの件数は、計画の前の件数（有効に戻す行も含む）とする。有効に戻す行を二重に数えるため上限はわずかに小さくなりうるが、64 件を超えない側に倒す
- A13（S2）: 新しいテーブル・列の名前、`channel` の値（`scheduled`）、C の差し込みの書式（`{task}`・`{time}`）、C の 3 通りの選び方、C の最大トークン数、試行の記録・保存した文面の掃除の期間は実装で決める
- A14（S2）: 試行の記録は B・C とも 1 行 ＝ 1 回とし、LLM を呼ぶ前に書く。1 時間の枠は「今から 60 分前以降」、1 日の枠は「今のローカル暦日の 0 時以降」で、どちらも終わりを区切らない
- A15（S2）: C の生成は人格設定のハッシュが保存済みの文面セットと異なるときに起きる（「人格設定を保存したとき」を、保存の後の計画し直しでハッシュの変化として検出する形で満たす）。文面セットは最新の 1 件だけを残す。生成の間に人格設定が変わっていたら、その生成の結果は保存せずに捨てる（遅れて終わった古い設定の生成が新しい設定のセットを消さないように。設定の読みと保存は 1 つのトランザクションで行う）
- A16（S2）: B の差し替えで元の文面での登録し直しも失敗した予約は、決定 4 のとおり控えから消す。置き換えの失敗では元の予約が OS に残りうる（控えを消すと取り消す手がかりを失う）ため、消す前に取り消しを 1 回試す（取り消しも失敗したときは OS に残りうる。実機の挙動は S3 で確かめる）
- A17（S2）: 現行の送信時生成は対象タスクの証跡の件数を人格プロンプトへ渡しておらず（`generateNotificationBody` は `taskEvidenceCounts` を渡さない。タスクの行は常に「添付0件」）、B は「現行と同じ範囲に留める」（決定 4）ため件数も送らない。使い回しのキーは LLM への入力全体のハッシュなので、送らない件数はキーに入らず、件数の変更で古い文面が届くことも無い（件数を文面に反映しない点は現行の送信時生成と同じ）
- A18（S2）: 取り消し待ちだけで OS の枠（64 件）が埋まっているときは、固定の通知も置かない（64 件の上限を守る側に倒す。取り消しに成功した次の計画し直しで置かれる）
- A19（S2）: LLM のクライアントを作れない（バックエンドが未登録・API キーが無い）ときは、試行の枠を使わずに生成をやめる（製品版の送信先の解決は #582 S2 が呼び出し元ごとに置き換える。計画し直しの B・C もその対象に含める）
- A20（S2）: 計画し直しの契機は GET・HEAD・OPTIONS 以外の要求の後に呼ぶ。SSE で応答するチャットは、ボスのツールが応答を返した後のストリームの中で状態を変えるため、ルートのストリームの後始末（生成を止められたときの中断メッセージの保存と、止めた時点で実行中だったツールの完了を含む）が終わったときにもう 1 回呼ぶ。ストリームの側（`TransformStream` の `cancel`〔Node の拡張・WKWebView には無い〕）では観測しない
