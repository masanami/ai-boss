# ADR 0002: API キーはサーバーの `.env` にのみ保持し、LLM 呼び出しは必ずバックエンド経由にする

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/ai-boss-mvp.md`（クリティカル設計決定「APIキー・機密データの取り扱い」「外部システム連携（Claude API）」）。上位の制約は [ADR 0001](./0001-local-only-data-boundary.md)。バックエンド別の扱いは [ADR 0003](./0003-llm-backend-isolation.md)。

## 背景

ローカル Web アプリはサーバーとブラウザの両方を開発者が持つため、「どうせローカルなのだから」とフロントエンドから直接 LLM プロバイダを呼びたくなる誘因が常にある。そうすると API キーをフロントへ渡す必要が生じ、キーがブラウザのバンドル・DevTools・ローカルストレージに露出する。

ローカル前提のアプリではこの露出が軽視されやすいが、実際にはバンドルはビルド成果物として配布・コミットされうるし、ブラウザ拡張からも読める。またキーが複数箇所に散ると、後から「どこに何があるか」を追えなくなる。

## 決定

1. **`ANTHROPIC_API_KEY` の保持場所は `server/.env` ただ一箇所**とする。`.env` は gitignore 対象とし、リポジトリにコミットしない。
2. **フロントエンドへ API キーを渡さない。** `web/` のコード・ビルド成果物・レスポンスボディのいずれにも露出させない。
3. **LLM プロバイダへの呼び出しはすべてサーバー側から行う。** フロントエンドはローカルバックエンドとのみ通信し（REST + SSE）、プロバイダを直接呼ばない。ストリーミング応答はサーバーが SSE で中継する。
4. **API キーをログに出力しない。** 失敗時のログに残すのはエラークラス名までとする。
5. **永続状態の保持者はサーバーだけ**とする。**LLM 呼び出しと、DB への副作用を伴うビジネスロジック（タスク・決定・活動イベントの作成／更新、検知判定、日報生成）はサーバーに閉じる。** ボスによるタスク操作は tool use としてサーバー側で実行する。
   一方、**取得済みデータを画面表示のために導出するロジック（日付キーの整形・表示対象の絞り込み・進捗レベルや表情の決定など）はクライアントに置いてよい**。これらは永続状態を持たず、サーバーの応答から決定的に導けるものに限る。実例は保証台帳の「Web: API クライアントと純粋ロジック」節（G-170-96 / 102 / 104 / 105 / 107 / 108 / 111 / 112 等）。

## 検討した代替案

- **OS キーチェーンに保管する** — 却下。単一ユーザーのローカルツールに対して実装・運用コストが過剰で、`.env` との安全性の差が実利用上ほぼ無い。
- **フロントエンドから直接プロバイダを呼ぶ** — 却下。キー露出と CORS の 2 つの問題があり、tool use のサーバー側副作用（DB 書き込み）も実現できない。
- **応答完了後に一括返却する（SSE を使わない）** — 却下。ストリーミングの体感速度はモチベーション UI の要であり、長考時の体験が大きく劣化する。

## 帰結

- LLM 呼び出しを伴う機能は必ずサーバー側に実装箇所を持つ。web 側だけで完結する LLM 機能は作れない。
- キーの有無に依存する検査（`MissingApiKeyError`）はサーバーの設定読み込み層に閉じる。
- バックエンドとして Claude Code（サブスクリプション認証）を使う場合は API キーそのものが不要になるため、**キーを積極的に渡さない**扱いが必要になる（[ADR 0003](./0003-llm-backend-isolation.md)）。
- クリティカル箇所（API キーの取り扱い・LLM 連携）の変更は人間レビューを必須とする。
