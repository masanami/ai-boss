# ADR 0002: API キーはサーバーの `.env` にのみ保持し、LLM 呼び出しは必ずバックエンド経由にする

- **ステータス**: Amended
- **日付**: 2026-08-20（改訂 2026-09-26: 製品版の BYOK のキーを端末の OS が提供するセキュアストレージに保管すると決め、代替案「OS キーチェーン」の却下理由を更新した。末尾「改訂（2026-09-26）」）
- **関連**: 宣言元は退役した `docs/features/ai-boss-mvp.md`（クリティカル設計決定「APIキー・機密データの取り扱い」「外部システム連携（Claude API）」）。上位の制約は [ADR 0001](./0001-local-only-data-boundary.md)。バックエンド別の扱いは [ADR 0003](./0003-llm-backend-isolation.md)。

## 背景

ローカル Web アプリはサーバーとブラウザの両方を開発者が持つため、「どうせローカルなのだから」とフロントエンドから直接 LLM プロバイダを呼びたくなる誘因が常にある。そうすると API キーをフロントへ渡す必要が生じ、キーがブラウザのバンドル・DevTools・ローカルストレージに露出する。

ローカル前提のアプリではこの露出が軽視されやすいが、実際にはバンドルはビルド成果物として配布・コミットされうるし、ブラウザ拡張からも読める。またキーが複数箇所に散ると、後から「どこに何があるか」を追えなくなる。

## 決定

1. **`ANTHROPIC_API_KEY` の保持場所は `server/.env` ただ一箇所**とする。`.env` は gitignore 対象とし、リポジトリにコミットしない。
2. **フロントエンドへ API キーを渡さない。** `web/` のコード・ビルド成果物・レスポンスボディのいずれにも露出させない。
3. **LLM プロバイダへの呼び出しはすべてサーバー側から行う。** フロントエンドはローカルバックエンドとのみ通信し（REST + SSE）、プロバイダを直接呼ばない。ストリーミング応答はサーバーが SSE で中継する。
4. **API キーをログに出力しない。** 失敗時のログに残すのはエラークラス名までとする。
5. **永続状態の保持者はサーバーだけ**とする。**LLM 呼び出しと、DB への副作用を伴うビジネスロジック（タスク・決定・活動イベントの作成／更新、検知判定、日報生成）はサーバーに閉じる。** ボスによるタスク操作は tool use としてサーバー側で実行する。
   一方、**取得済みデータを画面表示のために導出するロジック（日付キーの整形・表示対象の絞り込み・進捗レベルや表情の決定など）はクライアントに置いてよい**。これらは永続状態を持たず、サーバーの応答から決定的に導けるものに限る。実例は `web/src/` の純粋ロジック群（`to-date-key.ts` / `today-tasks.ts` / `dashboard-progress-level.ts` / `boss-expression.ts` / `select-default-task.ts` / `select-restore-session.ts` 等）とその `*.test.ts`。

## 検討した代替案

- **OS キーチェーンに保管する** — 却下。単一ユーザーのローカルツールに対して実装・運用コストが過剰で、`.env` との安全性の差が実利用上ほぼ無い。**（2026-09-26 の改訂で前提が変わり、製品版では採用した。末尾「改訂（2026-09-26）」）**
- **フロントエンドから直接プロバイダを呼ぶ** — 却下。キー露出と CORS の 2 つの問題があり、tool use のサーバー側副作用（DB 書き込み）も実現できない。
- **応答完了後に一括返却する（SSE を使わない）** — 却下。ストリーミングの体感速度はモチベーション UI の要であり、長考時の体験が大きく劣化する。

## 帰結

- LLM 呼び出しを伴う機能は必ずサーバー側に実装箇所を持つ。web 側だけで完結する LLM 機能は作れない。
- キーの有無に依存する検査（`MissingApiKeyError`）はサーバーの設定読み込み層に閉じる。
- バックエンドとして Claude Code（サブスクリプション認証）を使う場合は API キーそのものが不要になるため、**キーを積極的に渡さない**扱いが必要になる（[ADR 0003](./0003-llm-backend-isolation.md)）。
- クリティカル箇所（API キーの取り扱い・LLM 連携）の変更は人間レビューを必須とする。

## 改訂（2026-09-26）

- **関連**: Issue #575・#576・[ADR 0011](./0011-productization-architecture.md)（製品化の構成）

### 経緯

オーナーは 2026-09-23、ai-boss を製品として販売するための構成を決めた（[ADR 0011](./0011-productization-architecture.md)）。製品版は利用者の端末で動く Tauri 2 アプリで、Node サーバーの常駐をやめる。LLM は既定で料金プラン込み（ai-boss の LLM 中継サーバー経由）とし、選択で利用者が自分の Claude または OpenAI の API キーを持ち込む（BYOK）。BYOK ではアプリからプロバイダを直接呼ぶ。

本 ADR の決定 1（キーは `server/.env` ただ一箇所）は、オーナー自身が `.env` を編集する単一ユーザーのローカルツールを前提にしていた。製品版には `server/.env` を編集する利用者も、キーを持つサーバーも無い。**BYOK のキーをどこに保管するか**を決め直す必要がある。保管先は 2026-09-26 にオーナーが確認した。

### 改訂後の決定

1. **製品版の BYOK のキーは、端末の OS が提供するセキュアストレージに保管する。**
   - macOS / iOS: キーチェーン
   - Windows: DPAPI
   - Android: Keystore
2. **キーを平文でファイルに書かない。**
3. **キーを WebView 側に返さない。** 保存したキーは画面（WebView）へ読み出さず、プロバイダの呼び出しに使う側だけが扱う（決定 2「フロントエンドへ API キーを渡さない」の考え方を製品版でも保つ）。
4. Tauri 2 にはキーチェーンの公式プラグインが無いため、**自前で実装する**（#576 では Rust の `security-framework` で約 30 行で保存・読み出しを確認した）。
5. **開発者用の版は従来どおり `server/.env`** とする（決定 1 のまま）。開発者用の版は `claude-code` バックエンドを含むオーナー用の版である（[ADR 0003](./0003-llm-backend-isolation.md) の改訂）。
6. **プラン込みの事業者のキーは配布物に埋め込まない。** ai-boss の LLM 中継サーバーだけが保持する（[ADR 0011](./0011-productization-architecture.md) 決定 9）。
7. 決定 4（キーをログに出力しない）は、製品版・開発者用の版・中継サーバーのいずれにも適用する。

決定 3（LLM 呼び出しはサーバー側から行う）と決定 5（永続状態の保持者はサーバーだけ）は、製品版では「サーバー」が無くなりアプリ内で TypeScript のコアを動かす形に変わる（[ADR 0011](./0011-productization-architecture.md) 決定 7）。アプリ内のどの層が LLM 呼び出しと永続状態を受け持つかは、実行の仕組みを作り替える移行 Issue で決め、そのときに本 ADR を改訂する。

### 検討した代替案（改訂）

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| 設定ファイル（`.env` 相当）に保管する | 製品版でも端末内のファイルにキーを書く | 一般の利用者の端末では、他のアプリ・バックアップ・同期ソフトからファイルが読まれうる。元の却下理由（「単一ユーザーのローカルツールに対して過剰」「`.env` との安全性の差が実利用上ほぼ無い」）は、利用者が自分でキーを管理するオーナー 1 人のツールという前提に立っていた。第三者に配布する製品ではこの前提が成り立たず、OS のセキュアストレージを使う理由が上回る |
| 事業者のサーバー側で暗号化して保管する | 利用者のキーを ai-boss のクラウドに預ける | SaaS 案（構成案 B）とともに撤回された。キーと推論が事業者のサーバーを通ることになり、BYOK は中継サーバーを通さない（[ADR 0011](./0011-productization-architecture.md) 決定 10）とした構成と両立しない。事業者が利用者のキーを預かる責任も生じる |

### 帰結（改訂）

- BYOK で Anthropic API をアプリから直接呼ぶ場合、WebView の Origin が転送されるため `anthropic-dangerous-direct-browser-access` ヘッダが必要になる（#576）。キーを WebView に返さないこと（決定 3）と両立する呼び出しの形は、移行 Issue で決める。
- キーの保管は OS ごとに実装が分かれる。Windows 対応の要否は未決（[ADR 0011](./0011-productization-architecture.md)「未決」）であり、DPAPI の実装が要るかはその判断に従う。
- キーチェーンの永続性（アプリの再インストール後・端末の再起動後）とバックアップの対象になるかは、実機での確認が製品化の後のフェーズに回されている（#576）。
- クリティカル箇所（API キーの取り扱い）の変更は人間レビューを必須とする点は変えない。
