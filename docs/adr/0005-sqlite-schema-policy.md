# ADR 0005: SQLite 単一ファイルを唯一の永続化先とし、セッションを第一級の概念として持つ

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/ai-boss-mvp.md`（クリティカル設計決定「DBスキーマ（新規）」）・`docs/features/daily-report.md`（`daily_reports` 追加時のマイグレーション規律）。上位の制約は [ADR 0001](./0001-local-only-data-boundary.md)。個々のテーブル定義の正本は `server/src/db/migrate.ts`。

## 背景

本アプリは「報告 → 決定 → 実行 → 検知 → 再報告」という日次サイクルを扱う。この構造をどうデータモデルへ落とすかで、後続機能の書きやすさが大きく変わる。

とくに会話の持ち方には分岐がある。チャットアプリとして素直に作ると「単一のメッセージスレッド」になるが、本アプリの価値は朝会・夕会という**区切られた報告の場**にある。区切りをデータとして持たないと、日次評価・日報生成・セッション種別ごとの催促がすべて「時刻でメッセージを切り出す」後付けロジックになる。

また、ローカル単一ユーザー・単一プロセスという実行前提は、一般的な Web アプリのスキーマ設計の常識（接続プール前提の排他制御・水平分割の余地）をそのまま持ち込む必要が無いことを意味する。

## 決定

1. **永続化先は SQLite の単一ファイルのみ**とする（[ADR 0001](./0001-local-only-data-boundary.md)）。better-sqlite3 による同期 API を使い、単一ライターを前提にする。
2. **`sessions` を第一級の概念として持つ。** 会話は単一スレッドではなく、種別（`morning` / `evening` / `adhoc`）を持つセッションに属する。`messages` は `session_id` に紐づく。決定・日報もセッションを参照する。
3. **`activity_events` を検知エンジンの単一入力テーブルとする**（[ADR 0004](./0004-deterministic-detection-engine.md)）。
4. **マイグレーションは単調増加する version 番号で管理する。** 各 version は冪等に適用でき、既存 version の内容は後から書き換えない。新しいスキーマ変更は新しい version として追加する。
5. **排他制御の作り込みを最小に保つ。** 単一プロセス・単一ライターの前提で、必要な原子性は書き込みトランザクション（`db.transaction`）で足りるものとして扱い、そのためだけの制約カラム・ロックテーブルを追加しない。
6. **算出できるものは保存しない。** データ源から決定的に再現できる出力（例: 作業ログ）は保存テーブルを持たず、都度算出する。保存するのは、生成に非決定性がある成果物（例: LLM の講評を含む日報）に限る。

## 検討した代替案

- **会話を単一スレッドで持つ** — 却下。朝会・夕会の区切りと日次評価が表現しにくく、日報生成が時刻ベースの後付け切り出しになる。
- **日報を保存せず都度生成する** — 却下。LLM の講評を含むため再生成しても同じ結果にならず、過去日報の見返しができない。
- **日報を世代管理する（append-only の versions テーブル）** — 却下。再生成履歴を参照するユースケースが無く YAGNI。日付 UNIQUE + 上書きで足りる。
- **作業ログを保存する（`work_logs` テーブル）** — 却下。決定的な純粋関数でデータ源から再算出できるため保存は不要。
- **セッションにローカル日付の一意制約カラムを足して「夕会は1日1回」を DB で保証する** — 却下。検査と INSERT をトランザクションで囲めば単一ライターの SQLite では十分で、スキーマの複雑化に見合わない。

## 帰結

- 「保存すべきか」を判断する基準が生成の決定性になる。新機能で出力を保存したくなったら、まず再算出可能かを問う。
- テストでは SQLite をモックせず、一時ファイルまたは `:memory:` の実 DB を使う。モックすると本 ADR の前提（実 DB の挙動）を検証できないため。
- 複数プロセス・複数端末からの同時書き込みは設計の前提外。これを必要とする機能は本 ADR の改訂を伴う。
