# ADR 0005: SQLite 単一ファイルを唯一の永続化先とし、セッションを第一級の概念として持つ

- **ステータス**: Accepted
- **日付**: 2026-08-20（改訂 2026-09-29: DB を非同期の DB ポート越しに使い、接続を 1 本に固定して TypeScript の直列化層で単一ライターを保つと決めた。決定 1・5 と帰結の「複数プロセス・複数端末からの同時書き込みは前提外」を置き換える。末尾「改訂（2026-09-29）」）
- **適用範囲**: 下の「決定」「帰結」は改訂前の記録として残している。**決定 1・5 と帰結の同時書き込みの項は、開発者用の版・製品版の両方で改訂（2026-09-29）に置き換わる**（開発者用の版も #580 S1 で非同期の DB ポート越しになったため）。
- **関連**: 宣言元は退役した `docs/features/ai-boss-mvp.md`（クリティカル設計決定「DBスキーマ（新規）」）・`docs/features/daily-report.md`（`daily_reports` 追加時のマイグレーション規律）。上位の制約は [ADR 0001](./0001-local-only-data-boundary.md)。個々のテーブル定義の正本は `server/src/db/migrate.ts`。

## 背景

本アプリは「報告 → 決定 → 実行 → 検知 → 再報告」という日次サイクルを扱う。この構造をどうデータモデルへ落とすかで、後続機能の書きやすさが大きく変わる。

とくに会話の持ち方には分岐がある。チャットアプリとして素直に作ると「単一のメッセージスレッド」になるが、本アプリの価値は朝会・夕会という**区切られた報告の場**にある。区切りをデータとして持たないと、日次評価・日報生成・セッション種別ごとの催促がすべて「時刻でメッセージを切り出す」後付けロジックになる。

また、ローカル単一ユーザー・単一プロセスという実行前提は、一般的な Web アプリのスキーマ設計の常識（接続プール前提の排他制御・水平分割の余地）をそのまま持ち込む必要が無いことを意味する。

## 決定

1. **永続化先は SQLite の単一ファイルのみ**とする（[ADR 0001](./0001-local-only-data-boundary.md)）。better-sqlite3 による同期 API を使い、単一ライターを前提にする。**（後半〔better-sqlite3 の同期 API・単一ライターの保ち方〕は改訂（2026-09-29）の決定 1〜3 で置き換え。SQLite の単一ファイルだけに保存する点は変えない）**
2. **`sessions` を第一級の概念として持つ。** 会話は単一スレッドではなく、種別（`morning` / `evening` / `adhoc`）を持つセッションに属する。`messages` は `session_id` に紐づく。決定・日報もセッションを参照する。
3. **`activity_events` を検知エンジンの「活動シグナル」の単一入力テーブルとする**（[ADR 0004](./0004-deterministic-detection-engine.md) 決定 1）。**検知エンジンが読む唯一のテーブルという意味ではない** — 発火判定には `tasks`（対象タスクと見積もり）・`notifications`（重複送信防止とエスカレーション履歴）・`settings`（閾値）・`sessions`（当日の朝会夕会の実施有無）も入力として渡る。一元化しているのは「ユーザーが動いたか」を表すシグナルであり、それ以外の判定材料は別テーブルから来る。
4. **マイグレーションは単調増加する version 番号で管理し、各 version の適用と `user_version` の更新を単一トランザクションで原子的に行う。** `server/src/db/migrate.ts` は version ごとに `db.transaction()` で移行 SQL の実行と `PRAGMA user_version` の更新を囲む（`PRAGMA user_version` はトランザクションに参加する）。適用が中断・失敗しても DB は直前の version 境界に戻るため、個々の移行 SQL が冪等でなくても `runMigrations` の呼び出しとしては冪等になる（#175・`server/src/db/migrate.test.ts` のロールバック／再実行／冪等性のテストが担保）。トランザクションはループ全体ではなく version 単位で張り、失敗した version より前は適用済みとして確定させる（復旧を単純にするため）。既存 version の内容は後から書き換えない。新しいスキーマ変更は新しい version として追加する。なお `PRAGMA foreign_keys` はトランザクション内では切り替えられない（黙って無視される）ため、外部キーを持つテーブルの再構築（12-step 手順）を要する将来の version はこの規約のままでは書けず、tx 外での FK 切り替えを含む手順の設計が別途要る（#179 の責務）。

5. **排他制御の作り込みを最小に保つ。** 単一プロセス・単一ライターの前提で、必要な原子性は書き込みトランザクション（`db.transaction`）で足りるものとして扱い、そのためだけの制約カラム・ロックテーブルを追加しない。**（「単一プロセス・単一ライターの前提」と「`db.transaction` で足りる」は改訂（2026-09-29）の決定 2・3 で置き換え。制約カラム・ロックテーブルを足さない方針は変えない）**
6. **算出できるものは保存しない。** データ源から決定的に再現できる出力（例: 作業ログ）は保存テーブルを持たず、都度算出する。保存するのは、生成に非決定性がある成果物（例: LLM の講評を含む日報）に限る。

## 検討した代替案

- **会話を単一スレッドで持つ** — 却下。朝会・夕会の区切りと日次評価が表現しにくく、日報生成が時刻ベースの後付け切り出しになる。
- **日報を保存せず都度生成する** — 却下。LLM の講評を含むため再生成しても同じ結果にならず、過去日報の見返しができない。
- **日報を世代管理する（append-only の versions テーブル）** — 却下。再生成履歴を参照するユースケースが無く YAGNI。日付 UNIQUE + 上書きで足りる。
- **作業ログを保存する（`work_logs` テーブル）** — 却下。決定的な純粋関数でデータ源から再算出できるため保存は不要。
- **セッションにローカル日付の一意制約カラムを足して「夕会は1日1回」を DB で保証する** — 却下。検査と INSERT をトランザクションで囲めば単一ライターの SQLite では十分で、スキーマの複雑化に見合わない。

## 帰結

- 「保存すべきか」を判断する基準が生成の決定性になる。新機能で出力を保存したくなったら、まず再算出可能かを問う。
- テストでは SQLite をモックせず、一時ファイルまたは `:memory:` の実 DB を使う。モックすると本 ADR の前提（実 DB の挙動）を検証できないため。
- 複数プロセス・複数端末からの同時書き込みは設計の前提外。これを必要とする機能は本 ADR の改訂を伴う。**（改訂（2026-09-29）の帰結で置き換え）**

## 改訂（2026-09-29）

- **関連**: Issue #580（S1: #597・PR #615／S2: 本改訂の PR）・[ADR 0011](./0011-productization-architecture.md) 決定 17・18・機能仕様 `docs/features/async-db-layer.md`（クリティカル設計決定 1・2・6）

### 経緯

製品版（Tauri 2 アプリ）では、ネイティブ Node モジュールの better-sqlite3 が WebView で動かないため、DB を非同期 API の `@tauri-apps/plugin-sql` へ移す（[ADR 0011](./0011-productization-architecture.md) 決定 17）。plugin-sql（2.4.1）は sqlx の接続プール（既定で最大 10 接続）越しに文を実行し、`execute`／`select` のたびに接続を取り直すため、別々の文で張ったトランザクションが同じ接続に乗る保証が無い。また非同期 API では、1 本の接続でも `BEGIN` の後の await の間に別の流れの文が混ざる（ローカルで実測）。決定 1 の「同期 API・単一ライター」と決定 5 の「`db.transaction` で原子性は足りる」は、同期 API で await を挟まずに走ることを暗黙の前提にしていた。

#580 の S1 でリポジトリ層を非同期の DB ポートに統一し（開発者用の版は better-sqlite3 実装）、S2 で製品版の plugin-sql 実装をそろえた。本改訂は、両版の実装がそろった時点で決定 1・5 と帰結を書き換える（[ADR 0011](./0011-productization-architecture.md) は ADR 0005 を「今回は改訂しない」とし、改訂を #580 の実装時に行うとしていた）。

### 改訂後の決定

1. **DB は非同期の DB ポート（`run`／`get`／`all`／`exec`／`transaction`。`server/src/db/db-port.ts`）越しに使い、ドライバは版ごとに替える。** 開発者用の版は better-sqlite3、製品版は plugin-sql（Rust 側はリポジトリ内の fork `native/tauri-plugin-sql/`。JS 側は上流の `@tauri-apps/plugin-sql`）。リポジトリ層・ルート・スケジューラ・マイグレーションは両版で同じ TypeScript のコードを使う。
2. **接続は 1 本とする。** 開発者用の版は better-sqlite3 の接続 1 本、製品版は fork でプールを最大接続数 1・接続の寿命なし・アイドルの期限なしにする（sqlx は寿命を過ぎた接続をプールへ返す時点で閉じて新しい接続に替えるため、最大接続数だけでなく寿命と期限も外す）。製品版の DB ファイルは Rust 側がアプリのデータディレクトリに開き、WebView には DB を開く権限（`load`）を与えず、接続には別の DB ファイルを付け足せない（ATTACH の上限 0）。
3. **単一ライターは、接続 1 本と TypeScript の直列化層（`server/src/db/serialized-db.ts`）で保つ。** 直列化層は DB 操作を 1 つずつ通し、`transaction(fn)` は `BEGIN IMMEDIATE`〜`COMMIT`（例外なら `ROLLBACK`）の間、他の流れの DB 操作を待たせる。入れ子は `SAVEPOINT` で合成する。直列化層はドライバに依存しないため、トランザクションの意味は両版で同じテストで固定する（両版で同じ契約スイート `server/src/db/test-support/db-port-contract.ts`）。
4. **判定に使う読み出しも、書き込みと同じトランザクションの中で行う。** 「トランザクションの外で読み、その結果を根拠に書く」流れと、複数の文で読んだ結果を 1 つの材料として組み合わせる流れは、非同期では間に別の流れが割り込めるため、トランザクションの中へ移す（#580 S1 の全数監査）。LLM の呼び出し・通知の送信・ファイル操作など DB 以外の長い await はトランザクションに入れない。
5. マイグレーションの規約（決定 4。`user_version`・版ごとのトランザクション）は両版で変えない。製品版も `migrate.ts` をポート越しに走らせ、plugin-sql のマイグレーション機能（`_sqlx_migrations`）は使わない。

### 帰結（改訂）

- 端末の中の DB は単一ライターのまま（上の決定 2・3）。複数プロセスから同じ DB ファイルへの同時書き込みは引き続き前提外で、開発者用の版と製品版は別の DB ファイルを使い、同じ DB で同時に動かさない。
- 端末間の変更は、同期の層（[ADR 0011](./0011-productization-architecture.md) 決定 18）が端末の中の単一ライターを通して取り込む。衝突解決の方式と同期向けのスキーマは Issue #595 で決める（2026-09-29 時点で未決）。決まった時点で、その結論に従って本 ADR を改訂する。
- 直列化層はトランザクションの間ほかの DB 操作を待たせるため、トランザクションの中で DB 以外の await をすると、その間アプリの DB 操作がすべて止まる。上の決定 4 の規則はこの帰結でもある。
- 製品版の plugin-sql は fork のため、上流の版に追従するときは `native/tauri-plugin-sql/FORK.md` の差分を当て直す。fork が成り立たなくなったときは、自前の Rust コマンド（接続 1 本を保持し execute／select だけを出す）へ切り替える（直列化層とポートの契約は変えない）。
- 製品版の DB は sqlx が作成時に WAL モードにする（開発者用の版の better-sqlite3 は既定のロールバックジャーナル）。接続 1 本のため振る舞いの差は無いが、DB ファイルを複製するときは `-wal`・`-shm` も対象になる。
