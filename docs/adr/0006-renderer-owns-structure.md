# ADR 0006: 生成物の構造はレンダラーが決め、LLM には値だけを出させる

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/daily-report.md`（機能要件・アーキテクチャ決定）。同じ原則を `docs/features/work-log.md` が継承していた。実際に守られている振る舞いは `server/src/reports/render-*.test.ts` が正本。

## 背景

本アプリは Markdown の成果物（日報・作業ログ）を生成する。日報は外部（記録リポジトリ・実在の上司）へ貼り付けて使うため、**構造が安定していること**が価値の一部である。見出しが日によって変わったり、チェックボックス記法が揺れたりすると、貼り付け先での再利用性が落ちる。

素直な実装は「テンプレートをプロンプトに書いて LLM に Markdown 全体を生成させる」だが、これは構造をプロンプトで保証しようとする設計であり、次の問題を持つ: 構造が確率的にしか守られない、構造に関する受入基準をユニットテストで固定できない、LLM 呼び出しが失敗したときに何も出せない、そしてユーザー由来の文字列（タスク名）が Markdown 記法として解釈されて構造を壊す経路が塞げない。

## 決定

1. **Markdown の構造は、成果物ごとに 1 つのサーバー側レンダラー（純粋関数）が決定する。** 表題・セクション見出し・順序・チェックボックス記法・固定文言はすべてレンダラーの責務とする。**「単一」とは成果物単位の話であり、リポジトリ全体で 1 関数という意味ではない**（現状は日報の `renderDailyReport` と作業ログの `renderWorkLog` の 2 つがあり、成果物が増えれば同じ形でレンダラーも増える。決定 3 の「同じレンダラーを共用する」は同一成果物の通常経路とフォールバック経路の話）。
2. **LLM の責務は「値」を返すことに限定する。** 構造化された応答（ツール入力）として、要約や講評といった個別の値のみを出させる。LLM に Markdown を組み立てさせない。
3. **通常経路とフォールバック経路は同じレンダラーを共用する。** LLM 呼び出しが失敗・タイムアウト・形式不正だった場合は、値なしの入力を同じレンダラーへ渡す。フォールバック専用の別テンプレートを持たない。
4. **動的値は埋め込み前に正規化・エスケープする。** 改行は空白へ畳んで 1 行に正規化し、行頭に来ると構造を壊す記号（`#` `-` `*` `+` `>` `|` および番号付きリスト形式）はエスケープする。この処理はタスク名・LLM が返した値・ユーザーのメモを問わず、すべての動的値に適用する。
5. **LLM が抽出した内容の正確性は自動テストの対象外とする。** テストで固定するのは構造（見出し・順序・記法・固定文言・正規化）のみ。

## 検討した代替案

- **プロンプトにテンプレートを書いて Markdown 全体を生成させる** — 却下。構造が確率的にしか守られず、受入基準をテストで固定できない。LLM 失敗時に代替出力が無い。
- **フォールバック専用のテンプレートを別に持つ** — 却下。2 つのテンプレートが並存すると片方だけ更新される。同じレンダラーに値なしで通すほうが、構造の一致が構造的に保証される。
- **動的値のエスケープを呼び出し側の責務にする** — 却下。埋め込み箇所が増えるたびに漏れる。レンダラーの入口で一律に処理する。

## 帰結

- 構造に関する受入基準は、LLM を介さない**純粋関数のユニットテスト**で検証できる。時刻・LLM をモックすれば決定的に再現する。
- LLM 呼び出しが失敗しても成果物は必ず出力される。日報のフォールバックは「講評の生成に失敗した」旨の注記 1 行を出し、値を要する項目は出さない。
- 新しい Markdown 生成機能を追加する場合も同じ 2 段（値の抽出 → レンダリング）または 1 段（レンダリングのみ）で構成する。作業ログは LLM を使わないため、レンダラーのみの構成になる。
- レンダラーは DB・現在時刻・LLM に触れない純粋関数として保つ。触れると決定性が失われ、本 ADR の利点が消える。
