# ADR 0007: 「当日」はサーバーのローカル暦日で統一し、テストはタイムゾーン非依存に書く

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/daily-report.md`（機能要件「日付基準の統一」・非機能要件）・`docs/features/work-log.md`（非機能要件）。実際に守られている振る舞いはコードと `*.test.ts` が正本。

## 背景

本アプリは「今日」という概念に強く依存する。今日のタスク、今日の活動、今日の日報、今日の夕会は 1 日 1 回、検知は勤務時間帯内のみ——ほぼすべての機能が日付境界を持つ。

日付の扱いは、決めておかないと実装ごとにばらつく典型的な領域である。`toISOString().slice(0,10)` は手軽だが UTC 基準になり、日本時間の朝 9 時が前日として集計される。片や `new Date()` のローカル基準と混在すると、同じ「今日」が機能によって違う日を指す。この種のずれは、日付をまたぐ操作（深夜の夕会）でしか露見しないため、通常のテストをすり抜けて本番で初めて気付く。

テスト側にも同じ問題がある。固定時刻を UTC 文字列（`"2026-08-14T00:00:00Z"`）で書くと、CI と開発機のタイムゾーンが違うだけでテストが落ちる、あるいは**落ちるべきときに通る**。

## 決定

1. **「当日」は常にサーバーのローカルタイムゾーンでの暦日**を指す。UTC 基準の日付キーを使わない。
2. **日付キーの導出は実行環境ごとに単一の関数へ集約する**（ローカル基準で `YYYY-MM-DD` を組み立てる）。各所で個別に `toISOString` を切り出さず、必ずその環境の共通関数を呼ぶ（server: `server/src/detection/time-utils.ts` の `toDateKey`、web: `web/src/to-date-key.ts` の `toDateKey`）。**server と web は実行環境が異なりモジュールを共有する仕組みが無いため、この 2 実装は意図的に別々**である（それぞれ `server/src/detection/time-utils.test.ts` と `web/src/to-date-key.test.ts` が別々に担保する）。共有パッケージを導入するまで「1 リポジトリに 1 実装」にはしない。
3. **集計範囲は半開区間 `[対象ローカル暦日の 00:00, 翌ローカル暦日の 00:00)`** とする。閉区間の上限（`23:59:59.999`）を使わない——保存形式がミリ秒より高精度になった場合に当日末尾のレコードを取りこぼすため。翌日の境界は**暦日を 1 日進めて求める**（固定秒数の加算をしない。DST のある地域で 24 時間 ≠ 1 暦日になるため）。
4. **日付をまたぐ操作の帰属は明示的に決める。** 夕会が 23:50 に始まり翌 00:30 に終わった場合、その夕会と日報は**開始日**に帰属する。判定の基準時刻をどれにするか（`started_at` か `ended_at` か `created_at` か）を機能ごとに曖昧にしない。
5. **暦日の区切りに関わるテストはタイムゾーン非依存に書く。** 日付キー導出・日跨ぎ判定・当日/前日の絞り込みを検証するテストでは、固定時刻を `new Date(y, m, d, h)` 形式のローカル日時から導出し、UTC 文字列リテラルで固定しない。
   **経過時間のみを扱うテストはこの限りでない**（無音・未着手・締切超過・エスカレーション間隔など、時刻の絶対値がローカル暦日に影響しないもの）。これらでは `new Date("2026-07-05T09:00:00.000Z")` のような UTC リテラルが既に広く使われており、TZ が変わっても結果は変わらないため問題にならない。
6. **日付境界のテストを必ず置く。** 日をまたぐケース（深夜の夕会・日付をまたぐ休憩・前日/翌日のレコードが混入しないこと）を、機能ごとに明示的に検証する。**ローカル暦日の契約は、UTC のみで実行するテストでは検証できない**——CI が UTC の場合、実装が誤って `toISOString().slice(0, 10)` を使っていても期待値と一致してしまい、契約違反を検出できない。境界テストは UTC 以外のタイムゾーンでも実行するか、日付キー導出関数へタイムゾーンを注入できる形にして両方を検証する。

> **既知の逸脱（決定 3 に未追従の箇所が残っている・#236）**: 日報・作業ログ・当日活動 API の 3 箇所は #172 で半開区間へ揃ったが、**`server/src/dashboard/today-escalation.ts` と `server/src/boss/activity-log-tool.ts` には未追従が残る**。
>
> どの点がどう未追従かは #236 の完了条件を正本とする（本項では対象ファイルの所在までを示し、内訳は #236 側だけに置く。両方に書くと片方が腐るため）。追跡は #236。

## 検討した代替案

- **UTC 基準で統一する** — 却下。ユーザーはローカル時間で生活しており、「今日の日報」が午前 9 時に切り替わるのは受け入れられない。単一ユーザー・単一マシンのローカルアプリでは、ローカル暦日が唯一自然な基準。
- **タイムゾーンを設定値として持つ** — 却下。シングルユーザーがサーバーと同じマシンで使う前提では、OS のタイムゾーンと乖離させる理由が無い。設定項目を増やすとテストの組み合わせも増える。
- **日付をまたぐ夕会を終了日に帰属させる** — 却下。「その日の振り返り」という意味論に反する。23:50 に始めた振り返りは前日分の振り返りである。
- **テストで実行環境のタイムゾーンを固定する（`TZ=Asia/Tokyo`）** — 不採用。テストランナーの設定に依存する形は、個別実行や IDE 経由の実行で崩れる。テストコード側でローカル基準に組むほうが壊れにくい。

## 帰結

- 日付を扱う新機能は既存の関数を使う。新たに日付整形ロジックを書かない。日付キー（`YYYY-MM-DD`）は決定 2 の `toDateKey`、**集計範囲の境界（対象暦日の 00:00 と翌暦日の 00:00）は `server/src/activity/local-day.ts` の `startOfLocalDayIso` / `startOfNextLocalDayIso`** を使う（後者は #172 で集約した。ファイルが `activity/` 配下にあるのは歴史的経緯で、ポリシーは activity 固有ではない）。
- 休憩の対応付けのように暦日をまたぎうる集計は、探索範囲の拡張規則を明示的に定義する（日報の休憩集計は `break_end` だけ `max(翌ローカル暦日 00:00, 夕会 ended_at)` を**排他上限**として探索する。上限が伸びるのは日跨ぎ夕会のときだけで、その場合 `ended_at` ちょうどの `break_end` はクエリから外れるが、対応する `break_start` が `ended_at` で打ち切られるため計上結果は等価になる）。一方、暦日に固定する集計（作業ログ）はその旨を明示する。
- 決定 6 の保護は**両方の手段を併用**して実現している（#177）。片方だけでは足りない: **日付キー導出には `toDateKey(date, timeZone?)` の任意第 2 引数**があり、実行環境に依存せず契約を固定できる。一方、`server/src/activity/local-day.ts` の半開区間境界のように **`Date` のローカルメソッドを直読みする層にはタイムゾーンの注入点が無い**ため、そちらは **`npm run test:tz`（非 UTC タイムゾーンでの追加実行）**が守る。日付境界に触る変更ではこの追加実行も通すこと。
  既定の `npm test` の TZ は**固定しない**（「検討した代替案」の `TZ=Asia/Tokyo` 固定を不採用にした判断は維持する）。非 UTC 実行が足しているのは、注入点の無い層の保護と、**DST を採用するタイムゾーンでしか露見しない退行**（暦日の 00:00 に固定 86400000ms を足す形など、23/25 時間の日で崩れる実装）の検出である。
- レビューでは「**暦日の区切りに関わるテストで** UTC 文字列に固定された時刻」を指摘対象とする。これは本プロジェクトで繰り返し発生している逸脱である。経過時間のみを扱うテストの UTC リテラルは指摘対象ではない（決定 5）。
