# ADR 0008: 日報の生成には夕会での対話完了を前提条件として課す

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/daily-report.md`（機能要件「夕会完了の前提条件（壁打ち強制）」・背景）。実際に守られている振る舞いは `docs/guarantees.md`。

## 背景

日報は「手で書く作業を無くす」機能に見えるため、**いつでも生成できるほうが便利**である。実際、実装上は当日のタスクと活動記録さえあれば夕会が無くても Markdown は組み立てられる。

しかしこの機能の位置づけはそこではない。日報は AI ボスとの振り返り対話の**成果物**であり、対話を経ずに出力される日報は、実態としては活動ログの整形にすぎない。加えてオーナーは、生成した日報を実在の上司へ共有する形での展開を見据えており、その際「AI との振り返りを経ないと日報が出せない」という制約こそが、利用者に振り返り対話を行わせる仕組みとして働く。

つまりこの前提条件は**技術的な制限ではなく製品設計上の意図**である。この区別が記録されていないと、後から「不便だから外す」という一見妥当な改善として削除されうる。

## 決定

1. **日報を生成できるのは、当日の夕会セッションが終了済みで、かつそのセッションにユーザーの発言が 1 件以上ある場合に限る。** 無言のままセッションを終了しても日報は生成されない。
2. 前提条件を満たさない場合、生成 API は **409 と安定した `code`** を返し、UI はその `code` で分岐して「夕会を完了すると日報を生成できます」という状態表示を行う。エラーメッセージの文言ではなく `code` で分岐する。
3. **前提条件チェックは生成サービスの入口で行い、自動生成（夕会終了フック）と手動再生成の両経路で共通化する。** 片方の経路だけ条件を緩めない。
4. **夕会は 1 日 1 回**とする。当日に夕会セッションが既に存在する場合、新たな夕会セッションは作成できない（409）。やり直したい場合は既存の当日夕会で会話を続け、日報を再生成する。
5. **フォールバック経路でも前提条件は維持する。** LLM の抽出が失敗しても日報自体は出力するが、夕会未完了なら出力しない。

## 検討した代替案

- **前提条件なしでいつでも生成できるようにする** — 却下。対話を経ない日報は本機能の目的を果たさず、製品としての差別化要素も失う。
- **夕会の存在のみを条件にし、発言の有無は問わない** — 却下。セッションを開いて即終了すれば条件を満たせてしまい、対話の強制にならない。
- **警告を出しつつ生成は許す** — 却下。警告は無視されるため制約として機能しない。
- **夕会を 1 日複数回許す** — 却下。「1 夕会 : 1 日報」の対応が崩れ、どの夕会の日報かが曖昧になる。やり直しは同じセッションでの会話継続と再生成で足りる。

## 帰結

- 作業ログ（管理者共有向けの機械的な事実列挙）には**この前提条件を課さない**。作業ログは LLM を使わず夕会由来のデータも含まないため、同じ制約を課す理由が無く、日中の途中経過共有という用途を狭めるだけになる。日報と作業ログで生成条件が違うのは意図的である。
- 「日報が生成できない」という状態は、バグではなく仕様として UI に説明を出す必要がある。
- この前提条件を緩める変更は、製品の意図を変える変更である。実装の都合や利便性を理由に単独で行わず、本 ADR の改訂を伴う。
