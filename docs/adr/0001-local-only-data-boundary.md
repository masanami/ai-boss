# ADR 0001: 全データをローカル SQLite に閉じ、外部送信を Anthropic への推論リクエストのみに限定する

- **ステータス**: Amended
- **日付**: 2026-08-20（改訂 2026-09-26: 製品化に伴い、決定 2 の外部送信先を「推論リクエスト（選択したプロバイダ、またはプラン込みでは ai-boss の LLM 中継サーバー）＋ライセンス確認」へ広げ、中継サーバーの境界を定義した。末尾「改訂（2026-09-26）」／同日再改訂: 端末間同期の中継を外部送信の許可範囲に加え、その境界を定義した。末尾「改訂（2026-09-26・端末間同期の中継）」）
- **適用範囲**: 表題と下の「決定」は改訂前の記録として残している。**製品版では決定 2 を改訂（2026-09-26）と改訂（2026-09-26・端末間同期の中継）で置き換える。開発者用の版（現行 `main`）には元の決定が有効**である（決定 1・3・4 は製品版でも維持）。
- **関連**: 宣言元は退役した `docs/features/ai-boss-mvp.md`（非機能要件・プライバシー）。適用の詳細は [ADR 0002](./0002-api-key-and-llm-call-path.md)（認証情報）・[ADR 0003](./0003-llm-backend-isolation.md)（Claude Code バックエンドの隔離）。実際に守られている振る舞いはコードと `*.test.ts` が正本。

## 背景

ai-boss は業務内容そのもの（タスク名・進捗・サボりの実態・上司への報告内容）を扱う。これは利用者にとって最も他人に見せたくない種類のデータであり、かつ macOS ローカル・シングルユーザーで完結する製品として設計されている。

この種のアプリは、機能追加のたびに「便利だから」という理由で外部通信経路が1本ずつ増えていきやすい（分析・クラッシュレポート・外部タスクツール連携・エージェントのテレメトリ）。1本ずつは小さな判断でも、累積すると「ローカル完結」という製品の前提が実質的に失われる。個々の PR のレビューでは、その1本が前提を壊していることに気付きにくい。

## 決定

**データ境界を製品の不変制約として固定する。**

1. **保存先はローカルの SQLite ファイルのみ**とする。他の永続化先（クラウド DB・外部ファイル同期・ログ収集サービス）を追加しない。
2. **プロセス外への送信は Anthropic への推論リクエストのみ**とする。これ以外の外部通信経路（テレメトリ・自動更新確認・分析・外部 API 連携）は、既定で無効化する対象として扱う。**（製品版では改訂（2026-09-26）の決定 2・3 で置き換え。開発者用の版〔現行 `main`〕には本決定が有効）**
3. この制約は**バックエンド実装の内部にも適用**する。LLM 実行系が独自に外部通信・ディスク書き出しを行う場合、それを無効化する責任は本アプリ側にある（[ADR 0003](./0003-llm-backend-isolation.md)）。
4. **この制約を破る拡張は、制約の再検討を伴う独立した意思決定として扱う。** 該当する既知の候補は「OS アクティビティ連携による自動サボり検知」「外部ツール（GitHub 等）連携によるタスク取り込み」「利用者同士のコミュニケーション機能」。これらは制約の範囲内に収まらないため、実装前に本 ADR の改訂を必要とする。

## 検討した代替案

- **クラウド同期を前提にする（複数端末対応）** — 却下。シングルユーザー・単一マシン利用が前提であり、同期の価値に対してプライバシー上の代償と実装コストが釣り合わない。
- **匿名化した利用統計だけ外部送信する** — 却下。「業務データは送らないが統計は送る」という線引きは実装のたびに再交渉が必要になり、境界としては機能しない。境界は「送らない」で固定するほうが守れる。
- **OS アクティビティ（アクティブアプリ・ブラウザ履歴）を検知シグナルに使う** — 見送り。検知精度は最も高いが、収集範囲・保存期間・LLM へ渡す粒度の設計が必要で、本制約の再設計とセットでなければ判断できない。

## 帰結

- サボり検知は OS シグナルを使えないため、明示チェックインとアプリ内操作を活動シグナルとする設計になる（[ADR 0004](./0004-deterministic-detection-engine.md)）。
- LLM 実行系として汎用のコーディングエージェント（Claude Code）を組み込む場合、そのファイル操作・シェル実行・Web 検索・セッション永続化・テレメトリを明示的に無効化しない限り本制約に違反する（[ADR 0003](./0003-llm-backend-isolation.md)）。
- 「外部へ共有する」機能（日報・作業ログ）は、アプリが送信するのではなく**利用者の手動コピー**として実装する。アプリ側に送信経路を持たせない。
- バックアップ・機材移行は利用者が SQLite ファイルを直接扱う形になる。アプリ内バックアップ機能は本制約の範囲内（ローカルファイル出力）でのみ設計できる。

## 改訂（2026-09-26）

- **関連**: Issue #575・[ADR 0011](./0011-productization-architecture.md)（製品化の構成）

### 経緯

オーナーは 2026-09-23、ai-boss を製品として販売するための構成を、**利用者の端末で動くアプリ＋最小限のクラウド**（#575 の構成案 C）に決めた（[ADR 0011](./0011-productization-architecture.md)）。LLM は API を前提とし、既定は料金プラン込み（アプリ → ai-boss の LLM 中継サーバー → 低価格モデル）、選択で利用者のキーの持ち込み（BYOK: Claude または OpenAI。アプリからプロバイダを直接呼ぶ）とする。クラウドはライセンス・課金・LLM 中継だけを担う。

これにより、決定 2 の「外部送信は Anthropic への推論リクエストのみ」は、送信先（OpenAI・ai-boss の中継サーバー）と送信内容（ライセンス確認）の両面で成り立たなくなる。一方、業務データを端末に閉じるという本 ADR の核は、構成案 C でも維持できる（同日にいったん決めた SaaS 案〔構成案 B〕はデータをサーバーに保存するため本 ADR の撤回を要したが、撤回されて構成案 C に置き換わった）。

### 改訂後の決定

1. **決定 1（保存先はローカルの SQLite ファイルのみ）は維持する。** 業務データは利用者の端末内のローカル SQLite に置く。クラウド側が持つのはアカウント・ライセンス・利用量だけであり、業務データを保存しない。
2. **決定 2 の外部送信を次の 2 つへ広げる。** これ以外の外部通信経路（テレメトリ・分析・外部 API 連携）を既定で無効化する対象として扱う点は変えない。
   - **推論リクエスト**: 送信先は、BYOK では**利用者が選択したプロバイダ**（Anthropic または OpenAI）、プラン込みでは **ai-boss の LLM 中継サーバー**とする。
   - **ライセンス確認**: ai-boss のクラウドへのライセンス（アカウント・課金状態）の確認。業務データを含めない。
3. **LLM 中継サーバーの境界**: 中継サーバーは**推論内容（プロンプト・応答）を保存もログ出力もしない**。中継サーバーが扱ってよいのは、推論をプロバイダへ転送することと、利用量の計測・制限に要る情報だけとする。
4. 決定 3（LLM 実行系の内部にも制約を適用する）と決定 4（制約を破る拡張は本 ADR の改訂を伴う）は変えない。

### 検討した代替案（改訂）

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| 業務データをサーバーに保存する（SaaS・構成案 B） | 事業者の DB にデータを置き、ブラウザで使う | 2026-09-23 にいったん採用したが同日に撤回された。本 ADR の核（業務データを端末に閉じる）を捨てることになる（[ADR 0011](./0011-productization-architecture.md) の代替案） |
| 事業者のキーを配布物に埋め込み、中継サーバーを置かない | プラン込みでもアプリから直接プロバイダを呼ぶ | 配布物からキーが抜き取られる。プラン込み枠を提供するには中継が必須 |

### 帰結（改訂）

- 外部送信先が「選択したプロバイダ」「ai-boss の中継サーバー」「ai-boss のライセンス確認」の 3 つになる。どれを使うかは利用者の選んだ LLM の利用方式で決まり、**BYOK の推論を中継サーバーへ流さない・プラン込みの推論をプロバイダへ直接流さない**（経路を黙って切り替えない。[ADR 0003](./0003-llm-backend-isolation.md) 決定 9 と同じ考え方）。
- 中継サーバーの「保存もログ出力もしない」は、中継サーバーの実装で担保する必要がある。担保の方法は中継サーバーの移行 Issue で決める。
- 端末間の同期方式は未決である（[ADR 0011](./0011-productization-architecture.md)「未決」）。クラウドへの保存を採る場合は本 ADR の再改訂を伴う。エンドツーエンド暗号化した同期を採る場合も、送信経路が 1 つ増えるため本 ADR の改訂を要する。**（同日に一時中継＋暗号化の同期に決まり、下の「改訂（2026-09-26・端末間同期の中継）」で許可範囲に加えた）**
- 「バックアップ・機材移行は利用者が SQLite ファイルを直接扱う」（帰結）は、一般の利用者向けにはアプリ内のエクスポート／インポート（本制約の範囲内のローカルファイル出力）が実質必須になる。

## 改訂（2026-09-26・端末間同期の中継）

- **関連**: Issue #590（製品化の未決 3 点）・[ADR 0011](./0011-productization-architecture.md) 決定 18

### 経緯

オーナーは 2026-09-26、[ADR 0011](./0011-productization-architecture.md) で未決だった端末間の同期方式を**一時中継＋暗号化**に決めた（同 ADR 決定 18）。端末は変更分を端末で暗号化して送り、クラウドは相手の端末が受け取るまで預かって削除する。正本は端末に置き、クラウドは配達だけを担う。モバイルもデスクトップと同等の全機能とする（同 ADR 決定 20）。

これにより外部送信の経路が 1 つ増える。上の改訂（2026-09-26）の帰結で見込んだとおり、本 ADR の改訂を要する。

### 改訂後の決定

1. **決定 1（保存先はローカルの SQLite ファイルのみ）は維持する。** 業務データの正本は端末内のローカル SQLite に置く。同期の中継が変更分を一時的に預かることは、業務データの永続化先を増やすことに当たらない（正本を持たず、受け取られたら削除し、事業者は復号できないため）。
2. **外部送信に「端末間同期の中継」を加える**（改訂（2026-09-26）の決定 2 の 2 つに加えて 3 つ目）。
   - **同期の中継**: 送信先は ai-boss の同期の中継サーバー、送るのは**端末で暗号化した変更分のみ**とする。
3. **同期の中継サーバーの境界**: 中継サーバーは**受け取った変更分を相手の端末が受け取るまで預かり、受け取られたら削除する**。預かりは**期限つき**とし、期限を過ぎた分も削除する。**変更分の中身をログに残さない**。暗号化と復号は端末で行い、**事業者は中身を復号できない**（復号に要る鍵は端末同士のペアリングで共有し、中継サーバーに渡さない）。中継サーバーが扱ってよいのは、暗号化された変更分の配達と、配達に要る情報（宛先の端末・期限）だけとする。
4. 改訂（2026-09-26）の決定 3（LLM 中継サーバーの境界）と、元の決定 3・4 は変えない。

### 検討した代替案（改訂）

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| 同期しない | 端末ごとに独立し、送信経路を増やさない | Mac とスマホを併用する人が二重管理になる（[ADR 0011](./0011-productization-architecture.md) の代替案） |
| サーバーに正本を暗号文で持つ E2E 暗号化同期 | クラウドに暗号文の正本を保存する | 事業者のクラウドに業務データ（暗号文）を保管し続けることになる。オーナーは正本を端末に置き、クラウドは配達だけの形を選んだ |
| クラウドに保存する（SaaS 寄り） | 業務データを事業者のクラウドに保存する | 本 ADR の核（業務データを端末に閉じる）を捨てることになる。業務データの保管責任と漏えい時の損失が大きい |

元の「検討した代替案」の「クラウド同期を前提にする（複数端末対応）— 却下」は、シングルユーザー・単一マシン利用を前提にした開発者用の版の判断として残す。製品版はモバイルにも出すため複数端末の同期を要し、クラウドに正本を置かない一時中継の形で本制約と両立させた。

### 帰結（改訂）

- 製品版の外部送信先は「選択したプロバイダ」「ai-boss の LLM 中継サーバー」「ai-boss のライセンス確認」「ai-boss の同期の中継サーバー」の 4 つになる。
- 同期の中継サーバーの「受け取られたら削除・期限つき・ログに残さない」は、中継サーバーの実装で担保する必要がある。担保の方法・期限の長さ・ペアリングの具体は移行 Issue で決める。
- バックアップの方式は未決である（[ADR 0011](./0011-productization-architecture.md)「未決」）。事業者が保存する形のバックアップを採る場合は本 ADR の再改訂を伴う。
