# ADR 0009: 朝会の終了には仕事の進め方のメンタリング完了を前提条件として課す

- **ステータス**: Accepted
- **日付**: 2026-09-08
- **関連**: 宣言元は `docs/features/work-approach-mentoring.md`（判断 2・判断 3）。Issue #276。実際に守られている振る舞いはコードと `*.test.ts`（`server/src/sessions/mentoring-gate.ts` ・`sessions-routes.ts`）が正本。[ADR 0008](0008-evening-dialogue-prerequisite.md) と同じ型の前提条件である。

## 背景

朝会のフロー指示（`MORNING_FLOW_INSTRUCTION`）は既に「優先順位とノルマを決定の形で提示し、タスクへ反映し、決定を記録する」まで含んでいる。つまり**優先度を「決める」ことは既にあった**。無いのは、**その進め方自体が妥当かを問い直す**視点である。優先順位を決めても、着手前に決めるべきことを決めていない・関係者に伝えるべきことを伝えていない・見積もりの前提が崩れている、といった不備は素通りする。

オーナーはこうした不備によって手戻りや時間のロスを繰り返しており、朝会で進め方を点検する時間を取りたい、という要望が出発点である。ただし**任意の機能にするとサボられる**——「自分の意志に頼らず必ず点検が入るようにしたい」というのが明示された要求だった。

**プロンプト指示だけでは「強制」にならない。** LLM の裁量で飛ばされうるため、サボらせない仕組みとして機能しない。機械的なゲートが要る。

つまりこの前提条件は**技術的な制限ではなく製品設計上の意図**である。ADR 0008 と同じく、**この区別が記録されていないと、後から「不便だから外す」という一見妥当な改善として削除されうる。**

## 決定

1. **朝会セッションを終了できるのは、メンタリングが完了している場合に限る。** 完了とは「そのセッションに `kind = 'mentoring'` の `decisions` 行が 1 件以上あり、**かつ**そのセッションに `role = 'user'` のメッセージが 1 件以上ある」の**両方**を満たすことをいう。

2. **ブロックする箇所は朝会の終了操作（`POST /api/sessions/:id/end`）1 箇所だけとする。** 日報生成・夕会・随時チャットはブロックしない。催促通知も追加しない。

   朝会で機械的に観測できる「前進」は会の終了しかない——「ノルマ確定」は LLM が `update_task` / `record_decision` を呼ぶことで進むもので、独立した確定操作が存在しない。したがってゲートを掛けられる点は終了操作である。ここを塞げば「メンタリングを終えずに朝会の成果へ進めない」が成立する。

3. **前提条件を満たさない場合、終了 API は 409 と安定した `code`（`mentoring_required`）を返し、UI はその `code` で分岐する。** エラーメッセージの文言ではなく `code` で分岐する（ADR 0008 決定 2 と同じ作法）。

4. **逃げ道は設定 `morning_mentoring_required` をオフにすることだけとする。** 既定はオン（キー未設定＝オン。不正な値も安全側でオンへフォールバックする）。**ブロック時の UI 表示には、設定でオフにできる旨を必ず併記する**——これを欠くと、ボスがメンタリングの記録を残さなかった場合にユーザーが朝会から抜ける手段を画面から見つけられなくなる。

5. **判定は `endSession` を呼ぶ前に、その前に読んだセッション行（`before`）に対して評価する。** `endSession` は冪等で再終了時も同じ行を返すため、**その戻り値では「初回の終了遷移か」を判別できない**。再終了（`ended_at` が既に非 NULL）では評価しない。

6. **完了判定は DB の状態だけで決まる決定的な判定とし、LLM の応答文の解釈に依存させない。** 判定本体は DB に触れない純粋関数（`isMentoringComplete`）に切り出し、件数の読み取りは呼び出し側の責務とする（ADR 0004 決定 2 と同じ作法）。

7. **固定するのは「点検の骨組み（手順）」だけで、「観点（何を見るか）」は固定しない。** 骨組みは「進め方の申告を受ける → 危ういと判断した点を具体的に指摘する（無ければ問題なしと明言する） → 結論を `record_mentoring` で記録する」の 3 ステップ。どの観点で見るかはその日の文脈からボスが選ぶ。**固定しているのは「点検したことの証跡の形」であって「点検の中身」ではない。**

## 検討した代替案

- **プロンプト指示のみでゲートを設けない** — 却下。上記のとおり LLM の裁量で飛ばされうるため「強制」にならない。
- **日報生成もブロックする** — 却下。日報は既に ADR 0008 で「夕会の対話完了」という前提条件を持っており、そこへ朝会のメンタリング未了という別条件を重ねると、**日報が出せない理由が 2 系統になって原因を追いにくくなる**。ローカル完結の単一ユーザーアプリとして、ブロックは 1 箇所で足りる。
- **ブロックせず macOS 通知で催促する** — 却下。催促は無視できるため、「自分の意志に頼らない」という要求を満たさない。
- **朝会の開始をブロックする（メンタリングを終えるまで他の話題に進めない）** — 却下。メンタリングは会話の中で行うため、開始をブロックすると会話そのものが始められず自己矛盾する。
- **`kind = 'mentoring'` の記録が 1 件以上あることだけを条件にする（発言数を問わない）** — 却下。ボスの開始ひとことや、ユーザーが一言も話さないうちのツール呼び出しで条件を満たせてしまい、**対話の強制にならない**（ADR 0008 が「夕会の存在のみを条件にする」案を却下したのと同じ理由）。
- **ユーザー発言が N 件（N ≥ 2）以上あることを条件にする** — 却下。会話の往復数は点検の質と相関せず、閾値の根拠が無い。
- **観点を固定し、すべて通過したかで判定する** — 却下。決定 7 のとおり観点を固定しない方針を採るため成立しない。また「観点をすべて通過したか」を LLM の文面から判定する形は非決定的で、テストで固定できない。
- **メンタリングを独立したセッション種別にする** — 却下。`sessions.type` の CHECK 制約の変更（テーブル再構築を伴うマイグレーション）に見合う利得が無く、`selectRestoreSessions` やタイムライン境界表示など種別を前提にした既存ロジックの改修が広範に発生する。

## 帰結

- **夕会・随時（`adhoc`）セッションの終了にはこの前提条件を課さない。** 夕会終了時の要約生成・日報生成フックは従来どおり動く。日報と朝会でブロック条件が違うのは意図的である（決定 2）。
- **「朝会を終了できない」という状態は、バグではなく仕様として UI に説明を出す必要がある。** その説明には逃げ道（設定オフ）を併記する（決定 4）。
- **メンタリングの記録は `decisions` テーブルに `kind = 'mentoring'` として入る**ため、`decisions` の読み出し側は用途に応じて `kind` を絞る必要がある。日報・作業ログ・チャット文脈は `'mentoring'` を除外し、決定ログ（参照面）は含める。**`kind` を絞らない読み出し経路を新たに足すと、メンタリングが「決定」として混入する。**
- **ボスが実際に何を指摘したか（観点の妥当性・網羅性）は自動テストの対象外とする。** テストが固定するのは、ゲートの発火条件・記録の形・プロンプトに指示が積まれる条件である。
- この前提条件を緩める変更は、製品の意図を変える変更である。実装の都合や利便性を理由に単独で行わず、本 ADR の改訂を伴う。
