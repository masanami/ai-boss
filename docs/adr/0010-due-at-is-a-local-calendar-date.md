# ADR 0010: `tasks.due_at` はローカル暦日（`YYYY-MM-DD`）で保存し、締切超過は翌ローカル暦日 00:00 で判定する

- **ステータス**: Accepted
- **日付**: 2026-09-10
- **関連**: 上位の原則は [ADR 0007](./0007-local-calendar-day-basis.md)（「当日」はローカル暦日・半開区間 `[D 00:00, D+1 00:00)`）。検知エンジンの純粋関数規律は [ADR 0004](./0004-deterministic-detection-engine.md)。宣言元は `docs/features/due-at-updated-at-semantics.md`（Issue #340）。実際に守られている振る舞いはコードと `*.test.ts` が正本。

## 背景

`tasks.due_at` は制約なしの TEXT で、入力検証（PR #338）は `YYYY-MM-DD`（暦日）と ISO 8601 日時（瞬時）の**両方**を受理する。保存形式が意味を決めないため、下流の解釈が割れていた。

- `web/src/TaskCard.tsx` は先頭 10 文字を切って `<input type="date">` に入れ、編集するとその暦日を書き戻す（＝暦日として扱う）
- `server/src/detection/deadline-overdue.ts` / `server/src/detection/priority.ts` は `new Date(due_at).getTime()` で瞬時として解釈する

同じ値が UI では暦日、検知では瞬時になるため、編集を経ると締切の意味が黙って変わりうる。さらに `new Date("2026-09-05")` は**UTC の 0 時**として解釈されるため、Asia/Tokyo では「9/5 締切」が 9/5 の午前 9 時に超過扱いになる（UTC-11 の地域では前日 9/4 13:00）。これは ADR 0007 決定 1（UTC 基準の日付キーを使わない）に正面から反する。

保存形式の決定は「締切超過をいつ検知するか＝催促がどれだけ強いか」というプロダクト体験に直結するため、実装の都合では決められない。オーナーが実 DB を実測したうえで判断した。

**実測（2026-09-10・`server/data/ai-boss.db`）**: 締切のあるタスクは 5 件で、**すべて時刻付き `T18:00:00+09:00`**。`YYYY-MM-DD` の値は 0 件だった。書き手は web ではなくボス（LLM）で、リポジトリ内に 18:00 を書くコードは無く、`server/src/boss/task-tools.ts` のツール定義が「ISO 8601 日時文字列」と書いているため LLM が就業終わりを自分で補っていた。

そしてこの 18:00 は、勤務時間帯 `[09:00, 18:00)` の**外**で超過する。`server/src/detection/rule-engine.ts` は勤務時間帯ゲートが開いているときだけ `deadline_overdue` を評価し、`server/src/detection/time-utils.ts` の `isWithinWorkingHours` は終端を排他的に扱う（18:00 ちょうどは時間帯外）。したがって**現状の実効挙動は「翌営業日の始業から催促」**である。

## 決定

1. **`tasks.due_at` の意味は「サーバーのローカル暦日」とし、保存形式を `YYYY-MM-DD` の 1 つに定める。** 「その日の何時まで」を表現する手段は持たない。
2. **締切超過は「締切の暦日 `D` の翌ローカル暦日 `D+1` の 00:00 を過ぎたとき」に成立する。** `D+1` 00:00 ちょうどはまだ超過ではない（ADR 0007 決定 3 の半開区間 `[D 00:00, D+1 00:00)` の上限に一致させる）。**暦日の始まりを締切とみなす解釈は採らない**——催促を丸 1 日前倒しして強くすることになり、上記の実効挙動を変えてしまうため。
3. **旧形式（時刻付き）の値は「不正値」ではなく「正規化対象」として扱う。** 破棄せず、**その瞬時のローカル暦日**へ写す。文字列の先頭 10 文字を切る方法は使わない（ローカル暦日をまたぐオフセットを持つ値で誤った日になり、ADR 0007 決定 2 が禁じる「各所での個別の日付切り出し」でもあるため）。
4. **正規化は「書き込み時に落とす」＋「読み出し時に旧形式を吸収する」の 2 段で行う。** 時刻付きの入力は**拒否せず受理して暦日へ落とす**——書き手がボス（LLM）であり説明文への追従は確率的で、拒否するとツール失敗が利用者の会話に出るため。読み出し時の吸収は、既存行を書き換えるマイグレーションが済むまでの過渡的な措置とする。
5. **`due_at` の解釈は `server/src/tasks/due-at.ts` の 1 モジュールに集約する。** 検知エンジンは `new Date(task.due_at)` を直接呼ばない。暦日の導出・暦日境界の算出は ADR 0007 の集約点（`detection/time-utils.ts` の `toDateKey` / `parseDateKey`、`activity/local-day.ts` の `startOfNextLocalDayIso`）を再利用し、日付演算を新規に書かない。
6. **暦として解釈できない値（`isValidIsoDateOrDateTime` を満たさない値）は「締切なし」として扱う。** この述語は本 ADR の決定で広げない——旧形式は実在する締切であり、不正値として落とすと利用者の締切が黙って消えるため（決定 3 と対になる規律）。

## 検討した代替案

- **瞬時（オフセット付き ISO 8601）へ一本化する** — 却下。時刻締切を表現できる利点はあるが、web に時刻入力または既定時刻の展開を足す変更が最大になり、「その日の 23:59 とする」といった恣意的な既定値の決定を 1 つ抱える。単一ユーザーのローカルアプリで時刻締切の需要は未確認であり、YAGNI に照らして表現力を先に足す理由が無い。
- **両形式を許したまま、下流の解釈だけを明示的に揃える** — 却下。移行が不要で変更量は最小だが、2 形式が残り続けるため将来の実装者が再び解釈を割る余地が残る（本 ADR が解こうとしている問題そのものが再発しうる）。UI にも日付と日時の 2 表現が出る。
- **暦日の「業務終了時刻」（設定済みの勤務時間帯の終わり）を締切とみなす** — 不採用。初版の機能仕様が「催促が今より遅くなる」リスクへの緩和案として併記していたが、そのリスクは date-only の値が実在する前提の話であり、実測で date-only は 0 件だった。勤務時間帯の設定値に締切の意味を結び付けると、設定変更が既存タスクの締切の意味を遡って変えることにもなる。
- **旧形式の値を不正値として `NULL` にする** — 却下。実在する 5 件の締切が黙って消える。

## 帰結

- **web は変更不要。** `web/src/TaskCard.tsx` / `web/src/TaskForm.tsx` は既に `<input type="date">` で `YYYY-MM-DD` を送り、表示も先頭 10 文字なので、本決定の保存形式と一致している。編集ラウンドトリップで締切の意味が変わる問題は、保存形式が 1 つになることで構造的に消える。
- **ボスに公開するツールの `due_at` の説明文を `YYYY-MM-DD` を求める文言へ変える。** 対象は `server/src/boss/task-tools.ts` の JSON Schema と `server/src/llm/backends/claude-code-backend.ts` の Zod shape の**両方**で、`server/src/llm/backends/claude-code-backend.test.ts` が両者の `description` 一致を検証しているため片方だけ変えると落ちる。
- **暦日で締切を持つタスクへの最初の催促は、翌暦日の始業（勤務時間帯の開始）になる。** 締切超過の条件成立は `D+1` 00:00 だが、その時刻は勤務時間帯外で `rule-engine.ts` のゲートが閉じているため。時刻付き `T18:00` の現状と同じ挙動である。
- **`due_at` を暦日として比較するテストは、固定時刻を `new Date(y, m, d, h)` 由来のローカル日時から導出する**（ADR 0007 決定 5）。UTC 文字列リテラルで固定しない。日付境界に触るため `npm run test:tz` も通す（ADR 0007 決定 6）。
- **既存行を暦日へ書き換える一度きりのマイグレーションは、本 ADR の決定に含まれない。** 読み出し時の吸収（決定 4）があるため振る舞いの正しさには不要であり、オーナーの実データを書き換える不可逆な操作でもあるため、独立した Issue で承認を取って行う。それが済むまで 2 形式が DB に共存する。
- 「その日の何時まで」を表現したくなったときは、本 ADR を改訂して保存形式を決め直す（`due_at` に時刻を戻すのか、別カラムを足すのか）。個別の機能で時刻付きの値をこっそり保存しない。
