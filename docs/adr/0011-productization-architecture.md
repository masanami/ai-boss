# ADR 0011: 製品版は端末で動く Tauri 2 アプリとし、クラウドはライセンス・課金・LLM 中継だけを担う

- **ステータス**: Accepted
- **日付**: 2026-09-26（決定は 2026-09-23。`claude-code` バックエンドの扱いと BYOK キーの保管先は 2026-09-26 にオーナーが確認）
- **関連**: Issue #575（製品化のシステム構成の検討と決定）・#576（iOS 技術検証: Tauri 2 と Flutter の比較。検証コードはブランチ `spike/ios-tauri` / `spike/ios-flutter`）。本 ADR に伴い [ADR 0001](./0001-local-only-data-boundary.md)・[ADR 0002](./0002-api-key-and-llm-call-path.md)・[ADR 0003](./0003-llm-backend-isolation.md) を改訂した。影響を受けるが今回は改訂しないものは [ADR 0004](./0004-deterministic-detection-engine.md)・[ADR 0005](./0005-sqlite-schema-policy.md)（「帰結」参照）。

## 背景

現在の ai-boss は、オーナー 1 人が自分の Mac で `npm run start` して使う前提で作られている。Hono サーバーが常駐して React の画面を `localhost` で配信し、SQLite（better-sqlite3・同期 API）に保存し、node-cron で毎分検知して macOS の通知センターへ催促を出す。LLM は既定で `claude-code` バックエンド（利用者自身の Claude サブスクリプション認証）を使う。

第三者に販売する製品にするには、この前提のうち次が崩れる。

- **LLM の課金経路**: サブスクリプション（Pro/Max の契約と Claude Code へのログイン）を必須にすると導入のハードルが高く、Claude 非利用者が離脱する。第三者向け製品で利用者のサブスクリプション認証を使うこと自体にも規約上の懸念がある。
- **配布とプラットフォーム**: 一般の利用者は Node.js と npm を用意しない。さらにオーナーは 2026-09-23、**デスクトップに加えてモバイル（iOS / Android）にも対応する**ことを要件に加えた。iOS / Android では Node サーバーを常駐させられない（Tauri のサイドカーはデスクトップ専用で、モバイル対応は未実装 — tauri#9774）。
- **催促の常駐**: iOS はアプリを常駐させられず、バックグラウンド実行の時刻も OS 任せで保証されない。「毎分判定して通知」はモバイルでは成り立たない。

一方で、業務内容という最も他人に見せたくないデータを端末に閉じていること（[ADR 0001](./0001-local-only-data-boundary.md)）は、製品の差別化要素にもなる。

## 決定

### 1. 構成: 端末で動くアプリ＋最小限のクラウド（#575 の構成案 C・ハイブリッド）

1. **アプリは利用者の端末で動く**（インストール型）。**業務データは端末内のローカル SQLite に置く**。
2. **クラウドが担うのはライセンス・課金・LLM 中継（プラン込み枠）だけ**とする。クラウドは業務データを保存しない。
3. **マルチテナント化はしない**。クラウド側が持つのはアカウント・ライセンス・利用量だけである。
4. **催促は OS ネイティブ通知**で行う（現行方式を維持する）。

### 2. 土台: Tauri 2

5. **製品版の土台は Tauri 2** とし、デスクトップ（macOS / Windows / Linux）と iOS / Android を 1 つの土台で出す（どの OS を対象にするかのうち、Windows 対応の要否は未決。「未決」参照）。
6. **OS ごとのネイティブ UI は採らない**。画面は既存の React を使う。**ネイティブで書くのは OS 連携の部品だけ**とする（iOS ウィジェット／Live Activity、Apple Watch への催促、macOS メニューバー／Windows タスクトレイ常駐、通知からの直接応答など。これらはどのフレームワークを選んでもネイティブ実装になる）。

### 3. 実行の仕組みを作り替える

7. **Node サーバーの常駐をやめ、TypeScript のコアをアプリ内で動かす**。モバイルで Node サーバーを動かせないためである。作り直すのは実行の仕組み（サーバー常駐 → アプリ内）であり、検知ロジック・ボスの人格・画面は流用する。コードを全部書き直すという意味の「一から作る」は採らない。

### 4. LLM の利用方式

8. **LLM は API を前提とする**。利用者の Claude サブスクリプション認証は製品版の前提にしない。
9. **既定は料金プラン込み**: アプリ → **ai-boss の LLM 中継サーバー** → 低価格モデル。中継サーバーが事業者の API キーを保持し、利用量を計測・制限する。**事業者のキーは配布物に埋め込まない**（抜き取られるため、中継は必須）。
10. **選択で BYOK（利用者のキーの持ち込み）**: 利用者が自分の Claude（Anthropic）または OpenAI の API キーを登録して使う。**BYOK ではアプリからプロバイダを直接呼び**、中継サーバーを通さない。キーの保管は [ADR 0002](./0002-api-key-and-llm-call-path.md) の改訂に従う（端末の OS が提供するセキュアストレージ）。
11. **`claude-code` バックエンドは製品版に含めず、開発者用（オーナー用の版）に残す**。モバイルでは動かせないため（[ADR 0003](./0003-llm-backend-isolation.md) の改訂）。

### 5. 催促の方式（モバイル）

12. iOS では**「このまま何もしなければ◯時◯分に通知」を先に計算して OS の予約通知に登録し、活動があれば取り消して登録し直す**方式にする。検知エンジンは純粋関数（[ADR 0004](./0004-deterministic-detection-engine.md) 決定 2）なので、未来の時刻を入れて評価すれば予約時刻を割り出せる。**iOS の予約通知は 64 件が上限**で、超えると**エラーを出さずに先に登録した分から切り詰められる**（#576 で確認）ため、予約の設計で上限を考慮する。
13. 予約通知では**通知文面を送信時に LLM で生成できない**。文面は事前生成かテンプレートにする（テンプレートによる代替は [ADR 0003](./0003-llm-backend-isolation.md) 決定 9 で既にある）。

### 6. Tauri 2 の採用に伴う既知の手当て（#576 で判明）

14. **通知プラグイン**（`@tauri-apps/plugin-notification` 2.4.0）は、iOS で予約時刻が UTC との時差の分ずれる不具合がある（JST では 9 時間早くなり、過去の時刻として拒否される）。プラグインを修正するか fork する。あわせて **`sendNotification` が失敗を握りつぶす**問題を手当てする。
15. **キーチェーン**には公式プラグインが無いため、自前で実装する（#576 では Rust の `security-framework` で約 30 行）。
16. **BYOK で Anthropic API をアプリから直接呼ぶ**場合、WebView の Origin が転送されるため `anthropic-dangerous-direct-browser-access` ヘッダが必要になる（無いと 401）。
17. **DB は better-sqlite3（同期 API）から非同期 API（`@tauri-apps/plugin-sql`）へ移す**。接続プール越しのトランザクションでは**同一接続が保証されない**ため、これをリスクとして設計で扱う（[ADR 0005](./0005-sqlite-schema-policy.md) への影響は「帰結」参照）。

## 未決（オーナー判断待ち）

次の 3 点は本 ADR では決めていない。決まった時点で本 ADR を改訂する（または新しい ADR を起こす）。

- **端末間の同期方式**: (1) 同期しない（端末ごとに独立）／(2) エンドツーエンド暗号化した同期（クラウドは暗号文の中継だけで、事業者も中身を読めない）／(3) クラウドに保存。工数（暗号化同期は +3〜6 週の見積もり）とプライバシー方針が大きく変わる。(3) を採る場合は [ADR 0001](./0001-local-only-data-boundary.md) の再改訂を伴う。
- **Windows 対応の要否**: Tauri なら追加費用は小さいが、署名・検証の手間は増える。
- **モバイルの位置づけ**: デスクトップと同等の全機能か、催促・チャット中心の補助か。

また、**実機での確認**（#576 の「実機で確認すべき点」: アプリ終了中・端末ロック中・低電力モードでの予約通知の到達、64 件の切り詰め順、キーチェーンの永続性、起動時間とメモリ、バックグラウンド移行時のストリーミング中断、時差の回避策が実機で効くか）は、オーナー判断で**製品化の後のフェーズ**に回した。#576 の結果はすべて iOS シミュレータとホスト Mac でのものである。

## 検討した代替案

| 案 | 内容 | 採らなかった理由 |
|---|---|---|
| **B: SaaS** | アプリを事業者サーバーで動かし、ブラウザでアクセスする。データは事業者の DB に置く | 2026-09-23 にいったん採用したが、同日に撤回して構成案 C に置き換えた。ADR 0001 のローカル保存を捨てることになり、マルチテナント化・マネージド DB への移行・運用とセキュリティと個人情報保護の責任が発生する。催促通知が Web Push 頼みになり到達性が落ちる |
| **Electron** | 既存の Node サーバーを内包してデスクトップアプリにする | デスクトップ専用でモバイルに対応しない。モバイルを別の仕組みで作ると土台が 2 つになり、Electron を持つ意味が薄い |
| **Flutter** | 画面とロジックを Dart で書き直し、全プラットフォームへ出す | #576 の iOS 検証 6 項目は Tauri 2 と同じく合格し、成立性はほぼ互角だった。プラグインが素直に動き、描画が 1 系統で運用が軽いという利点がある。しかし Tauri 2 は**既存の画面とロジックがそのまま動いた**（検知エンジンのテスト 216/216 件を変更なしで合格・画面は既存の React をコピーするだけで表示）ため、製品化までの工数と退行のリスクが小さい Tauri 2 を採った。**本格的なキャラクターアニメーションなどの重い演出は Flutter のほうが得意で、このトレードオフは受け入れる**（今の水準の UI は WebView で十分に作れる） |
| **OS ごとのネイティブ UI** | 画面を OS ごとにネイティブ言語で作り分ける | UI が 3〜4 本になり、UI の磨き込みが価値の中心で変更頻度が高い ai-boss では、機能のずれと検証（実機確認）の工数が 3〜4 倍になる。1 人運用ではここが律速になる。ネイティブは OS 連携の部品だけに限る（決定 6） |
| **React Native（Expo）** | ロジックを流用し、画面を React Native 用に書き直す | モバイルの完成度は高いが、画面の書き直しが要る。デスクトップ（macOS / Windows）対応は本家に遅れる非公式寄りで、デスクトップは別途 Tauri 等が要る可能性がある |
| **Capacitor（モバイル）＋ Tauri（デスクトップ）** | 画面は共通の Web のまま、モバイルだけ Capacitor で出す | 土台が 2 つになる。Tauri 2 でモバイル面が足りなかったときの退避先だったが、#576 で Tauri 2 がストリーミングとアプリ終了中の予約通知を実現できたため、切り替えは不要と判断した |
| **Node サーバーをサイドカーで同梱する** | 実行の仕組みを作り替えず、デスクトップ版だけ先に出す | Tauri のサイドカーはデスクトップ専用でモバイルでは動かない。モバイル対応の時点で作り直しになる |
| **利用者のサブスクリプション認証（`claude-code`）を製品版の前提にする** | 利用者が自分の Claude の契約で推論する | 導入のハードルが高く、Claude 非利用者が離脱する。第三者向け製品での利用に規約上の懸念がある。モバイルでは動かせない |
| **事業者のキーを配布物に埋め込む** | 中継サーバーを置かずにアプリから直接呼ぶ | 配布物からキーが抜き取られる |

## 帰結

- **ADR 0001〜0003 を本 ADR と同時に改訂した**（各 ADR 末尾の「改訂（2026-09-26）」）。
  - [ADR 0001](./0001-local-only-data-boundary.md): 業務データのローカル保存は維持し、外部送信を「推論リクエスト（送信先は選択したプロバイダ、またはプラン込みでは ai-boss の中継サーバー）＋ライセンス確認」へ広げる。中継サーバーは推論内容を保存もログ出力もしない。
  - [ADR 0002](./0002-api-key-and-llm-call-path.md): BYOK のキーは端末の OS が提供するセキュアストレージに保管する。
  - [ADR 0003](./0003-llm-backend-isolation.md): `claude-code` バックエンドは開発者用に限定し、製品版には含めない。
- **[ADR 0004](./0004-deterministic-detection-engine.md) への影響（今回は改訂しない）**: 帰結の「スケジューラは毎分チェック方式で、この純粋関数を呼ぶ薄い層として実装する」は、モバイルでは**予約通知方式**（決定 12）に置き換わる。検知エンジンを純粋関数として保つ決定 1〜3 はむしろ前提として効く（未来の時刻を入れて予約時刻を割り出すため）。エスカレーション（決定 4）の段階と活動シグナルによるリセットは、「予約の取り消しと再登録」として表現し直すことになり、予約 64 件の上限と通知文面を送信時に生成できない制約が加わる。
- **[ADR 0005](./0005-sqlite-schema-policy.md) への影響（今回は改訂しない）**: 決定 1 の「better-sqlite3 による同期 API を使い、単一ライターを前提にする」は、**非同期 API（`@tauri-apps/plugin-sql`）**へ変わる。決定 5 は「単一プロセス・単一ライターの前提で、必要な原子性は書き込みトランザクションで足りる」としているが、接続プール越しのトランザクションは同一接続が保証されないため、この前提を設計で保ち直す必要がある（#576 の見積もりで、DB を使う関数 163 個・テスト 56 ファイル・トランザクション 10 箇所・1〜1.5 週）。端末間同期（未決）の方式によっては、帰結の「複数端末からの同時書き込みは設計の前提外」にも触れる。
- **ADR 0004・0005 の改訂は、製品化の移行 Issue を実装するときに行う**。実装で決まる具体（予約の再登録の単位、トランザクションの保ち方）を先に ADR へ書かないためである。それまでは両 ADR の記述が現行コード（`main`）の正しい記述であり続ける。
- 移行作業は #575 から要件 Issue として切り出す（`/define-feature` → `/create-ticket`）。#575 で挙がった主な作業は、LLM 中継サーバー、ライセンス・課金、LLM プロバイダの抽象化（Anthropic / OpenAI の tool use・ストリーミング形式の差の吸収）、既定の低価格モデルの選定と推論原価の見積もり、BYOK で許可するモデルの範囲、予約通知方式への作り替え、DB 層の非同期化、スマホ向けの画面レイアウト、署名・公証・ストア申請・アプリ本体の自動更新、データのバックアップと端末移行（アプリ内エクスポート／インポート）、法務（利用規約・プライバシーポリシー・特商法表記）である。
- 工数の見積もり（#575・2026-09-23 更新）: Tauri 2 固有の差分 3〜6 週＋通知プラグインの修正 0.5 週、フレームワークと無関係な作業 8〜16 週、合計約 3〜5 か月（端末間の暗号化同期を入れる場合は +3〜6 週）。±50% の幅を見る。
- 開発者用の版（`claude-code` バックエンド・`server/.env`）は残るため、移行期間中と移行後の両方で、製品版と開発者用の版の差分を意識した実装が要る。除外の実装方式は移行 Issue で決める。
