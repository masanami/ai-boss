# ADR 0003: Claude Code を LLM バックエンドとして in-process で組み込み、その能力を明示的に剥奪して使う

- **ステータス**: Accepted
- **日付**: 2026-08-20
- **関連**: 宣言元は退役した `docs/features/claude-code-backend.md`（クリティカル設計決定・FR-06 / FR-09 / FR-12 / FR-15）。上位の制約は [ADR 0001](./0001-local-only-data-boundary.md)・[ADR 0002](./0002-api-key-and-llm-call-path.md)。実際に守られている振る舞いはコードと `*.test.ts` が正本。既知の逸脱だった Issue #166 は #213 で解消済み。

## 背景

本アプリの LLM 呼び出しは既定で Claude Code（Claude Agent SDK 経由）を使う。これはオーナーの Claude サブスクリプション枠を使い、API 従量課金への依存を減らすためである。

ここには構造的な緊張がある。**Claude Code は汎用のコーディングエージェントであり、既定でファイル読み書き・シェル実行・Web 検索・Web 取得の能力を持ち、会話履歴をディスクへ永続化し、テレメトリと自動更新確認の通信を行う。** 一方で本アプリは [ADR 0001](./0001-local-only-data-boundary.md) により「保存はローカル SQLite のみ・外部送信は Anthropic への推論リクエストのみ」を不変制約としている。

素朴に組み込むと、この不変制約は成立しない。ボスの文面を生成させるつもりの LLM が、原理的にはユーザーのファイルを読み、Web へ取得しに行き、会話を `~/.claude/projects/` へ書き出せてしまう。

つまり本 ADR が答えるべき問いは「Claude Code をどう使うか」ではなく、**「汎用エージェントから、本アプリに必要な能力だけを残して他を剥奪するには何をすればよいか」**である。

## 決定

### 組み込み方式

1. **Claude Agent SDK を in-process で組み込む。** カスタムツールは `createSdkMcpServer` / `tool()` で in-process MCP サーバとして定義し、`db` / `sessionId` をクロージャで束縛して既存のツール実行関数を再利用する。
2. **ツールの実行主体をバックエンド内部（ファサード配下）に一本化する。** 呼び出し元（HTTP ルート）はツールを実行しない。Agent SDK は in-process MCP ツールを自身のエージェントループ内で実行するため、外側にもツールループを併用すると**ツールの二重実行またはツールイベントの欠落**が起きる。ファサードは `onTextDelta` / `onToolEvent` のコールバック契約を提供し、ルートは SSE 送出のみを担う。
3. **ツールの入力スキーマは JSON Schema を単一ソースとして維持する。** Agent SDK が要求する Zod スキーマはバックエンド実装内に閉じて手書きし、両者の整合をユニットテストで担保する。JSON Schema → Zod の変換ライブラリは追加しない。
4. **会話状態はステートレスに保つ。** 毎回 DB から履歴を再構築して全文送信する。Agent SDK のセッション継続（resume）は「アプリのセッション ⇔ バックエンドのセッション」のマッピング状態を新設する必要があり、[ADR 0005](./0005-sqlite-schema-policy.md) の「算出できるものは保存しない」とも噛み合わないため使わない。

### 能力の剥奪（不変制約の維持）

5. **ビルトインツールを全面的に無効化する。** 許可するツールはアプリ定義のカスタムツールのみとする。単一の設定に頼らず、**複数の設定を併用する**: ビルトインツール集合を空に指定する / 設定ファイル（settings）の読み込みを無効化する / MCP 構成を厳格化する / 許可判定コールバックで未許可ツールを拒否する。**Agent SDK の `allowedTools` オプション（列挙したツールを許可判定コールバックの呼び出し前に自動承認する）は使わない**（Issue #213）。自動承認は許可判定コールバックを迂回するため、コールバック側に検証・監査ログ等を足しても効かなくなる罠になる（過去に実際にこの罠へ落ちた — #166）。
6. **`ANTHROPIC_API_KEY` を Agent SDK とその子プロセスへ渡さない。** 子プロセス環境は `process.env` のコピーから当該キーのみを除外して構築する（`PATH` / `HOME` 等の実行に必要な変数は保持する）。これによりサブスクリプション認証を強制し、意図しない従量課金経路への切替を防ぐ。
7. **セッション履歴の永続化を無効化する。** 会話データの保存先をアプリの SQLite に一本化する。
8. **テレメトリ・非必須通信を無効化する**環境変数（`DISABLE_TELEMETRY=1` / `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC=1`）を設定する。自動更新確認も併せて無効化されるが、実行系は npm 依存としてバージョン管理されるため意図した挙動である（セキュリティ更新は依存更新で取り込む）。
9. **失敗時に `api` バックエンドへ自動フォールバックしない。** オーナーの課金意図に反する無断の経路切替を禁止する。実行環境不備は専用のエラー型で表現し、チャット・再裁定は HTTP 500、ダッシュボードコメント・通知文面はテンプレートへフォールバックする。

## 検討した代替案

- **`claude -p` のサブプロセス spawn** — 却下。カスタムツールを stdio MCP サーバ（別プロセス）で橋渡しする新規アーキテクチャ層が必要で、実装・保守コストが不釣り合いに大きい。spawn オーバーヘッド（100–500ms）がツールループで複利的に効き、チャットの体感速度を損なう。プロセス分離が必須の要件が将来生じた場合の代替として温存する。
- **パーミッションモードによる制限のみで運用する** — 却下。将来ビルトインツールが追加されたときに穴が開きうる。明示的な許可リスト方式のほうが、既定で閉じている。
- **`api` バックエンドを既定のまま維持する** — 却下。サブスクリプション枠の活用という本機能の目的を果たせない。ただし `LLM_BACKEND=api` の明示による後方互換は維持する。
- **失敗時に `api` へ自動フォールバックする** — 却下。可用性は上がるが、オーナーが知らないうちに従量課金が発生する。課金経路の切替は明示的な操作であるべき。

## 帰結

- LLM バックエンドを追加・変更する場合、上記 5〜9 の能力剥奪を**新しいバックエンドでも独立に満たす**必要がある。「既存バックエンドで担保されているから」は理由にならない。
- ツールを追加する場合、実行主体はファサード配下に置く。ルート側でツールを実行する実装を書かない（二重実行が再発する）。
- Agent SDK にはリクエスト単位の `tool_choice` / `max_tokens` に完全一致する機能が無い。ツール使用の強制はプロンプト指示で代替し、応答長に契約があるもの（ダッシュボードコメント）は**生成後に検証してテンプレートへフォールバック**する。プロンプト指示だけで上限を保証しない。
- 1回のバックエンド呼び出しのタイムアウトとリトライは、`claude-code`・`api` **両経路ともファサード層（`runWithTimeoutAndRetry`）の統一ポリシー**に従う。**リトライは、その1回のバックエンド呼び出し（`dispatchStream`/`dispatchCreate` の1回の呼び出し）内でツール実行（DB 副作用）やテキスト配信が起きていない失敗に限定**する。副作用が発生した後の失敗は再試行せずエラー契約へ流す。`api` 経路は SDK 自身の `maxRetries` を 0 にし、ファサード側のリトライと二重にかからないようにする。
  - **エラー種別判定と `Retry-After` の尊重は `api` 経路のみ**、ファサードの任意フック（`RetryTimeoutOptions.classifyError`。実体は `backends/api-backend.ts` の `classifyApiError`）で有効にする。401/400 等の非一時的エラーは再試行せず、429 の `Retry-After` はその時間だけ待つ（残り予算に収まらない場合は待たずに元エラーで即失敗する。共有期限は必ず守る）。**`claude-code` 経路にはフックを渡さず一律リトライのまま**であり、両経路の非対称は意図的に残す（`claude-code` 側で Agent SDK 自身がリトライを行うかは本アプリのコードからは制御・検証できないため、この非対称の実質的な影響は未確認——別途調査が必要な場合は Issue を切る）。
  - 経緯: `api` 経路をファサードの統一ポリシーへ寄せたのは Issue #176。その時点では SDK 側のエラー種別判定・`Retry-After` 尊重が失われるトレードオフを受け入れていたが、Issue #223/#224 で上記フックにより二重リトライを再導入せずに回復した。
  - `claude-code` は Agent SDK 内部の複数ラウンドが単一ディスパッチに収まるため、タイムアウト予算は会話全体で1つを共有する。`api` のツール使用ループ（`streamBossMessage`）は1ラウンド＝1バックエンド呼び出しのため、予算はラウンドごとにリセットされる。LLM 呼び出し部分の合計は `MAX_TOOL_ROUNDS` × 予算（既定 600 秒）で頭打ちになるが、ラウンド間のツール実行・`onToolEvent` 通知はこの予算に含まれないため、呼び出し全体（ツール実行時間を含む壁時計時間）としての単一の共有予算ではない。詳細は `claude-client.ts` の `streamBossMessage` doc comment。
- クリティカル箇所（LLM 連携）の変更は人間レビューを必須とする。
